# 08｜项目面试手册：先讲清全局，再选择核心链深挖

> 本章用于开场、选题和追问；五条链的机制学习集中在 [09](09-core-business-chain-review.md)。源码核对对象是 2026-09-07 的 `research/iron-ore-rag` 当前工作树，HEAD 锚点为 `05b9137d841e139cd0457af95369a14d16736404`；检索评测相关源码/资料和本文件含未提交 WIP，因此不能把全部现状说成该提交已经包含。本轮没有重跑实验。个人贡献边界不明确，口述统一使用“项目中采用了”“这条链路的设计是”。

## 1. 项目定位与价值

这个项目不是一个“把文件丢给大模型”的聊天 Demo，而是一条工业知识处理链：

- 把 XLSX、PDF、Markdown 等资料解析为保留来源坐标的证据块；
- 把用户问题结合会话历史改写、拆分，并在知识作用域内召回与重排；
- 以 SSE 输出回答、来源和 Trace，并用 Redis 信号把停止请求送到持有模型连接的实例；
- 把回答证据约束为可审核的任务草案和确定性的版本差异；
- 用冻结数据、原始输出和负结果区分“代码能跑”与“效果得到验证”。

目标用户可以理解为需要查询工艺、设备、制度或标准资料的业务人员和审核人员。核心价值不是替代专家决策，而是缩短资料定位路径，并让答案和后续业务对象尽量保留来源、版本与人工门禁。

当前事实边界：默认聊天是 workflow 编排与 PGVector 向量检索；关键词、图、Web、Agent/Profile/MCP、ROS 等能力只能按各自接入状态介绍，不能合成一条“全功能默认链”。

## 2. 30～60 秒项目概括版

> 这是一个面向工业文档的 RAG 应用，后端使用 Java 17 和 Spring Boot，整体是模块化单体。离线侧把 XLSX、PDF 等资料经过结构解析、分块、Embedding 后写入 PostgreSQL 和 PGVector；在线侧先结合会话做问题改写和拆分，再经过作用域控制、向量召回、去重、融合、重排和上下文选择，把带来源的证据组织进 Prompt，并通过 SSE 流式返回。
>
> 它比较有价值的地方有三点：第一，针对表格保留 sheet、单元格范围和展示文本/检索文本两种表示，而不是粗暴转纯文本；第二，回答后的任务草案必须引用本次检索允许的证据 ID，再经过确定性校验和人工状态门禁，模型不能直接控制设备；第三，项目把解析、检索、回答分层评测，保留失败和负结果。当前默认仍是向量检索，混合检索和新的上下文选择器只在隔离评测链验证过，不能说已经成为生产默认。

## 3. 2～3 分钟完整介绍

> 项目解决的是工业资料“能查到、能解释来源、能受控落地”的问题。输入不只是普通文本，还包括表格和 PDF；输出除了聊天回答，还有来源列表、grounding 证据、Trace，以及基于证据生成的任务草案和版本差异。
>
> 在知识接入侧，上传先完成文件存储和文档元数据登记，摄取再通过 RocketMQ 事务消息异步调度。消费者根据 MIME 和解析 profile 选择解析器，XLSX 会保留标题、表格、合并单元格和单元格范围；随后按展示内容和 embedding 文本的双预算切块，批量生成向量，并替换关系块与索引。这样做是因为表格直接拼成长文本会复制合并单元格、形成超长块，还会丢失可追溯位置。事务消息保证的是“本地状态允许执行后消息才可见”这一段最终一致性，不等于消费者只执行一次，也不覆盖外部模型、对象存储和所有索引。
>
> 在线问答侧，会话历史先参与问题改写和子问题拆分，意图只负责收窄知识集合，真正召回由通道完成。当前默认用 Qwen3-Embedding-8B 请求 1536 维向量，在 PGVector 中召回，再用 `qwen3-rerank` 精排；框架也有 Elasticsearch BM25、LightRAG 和 Web 适配器，但默认未开。通道结果依次去重、按 RRF 等方式融合、限制候选池、补充用于重排的元数据，再做 Cross-Encoder 重排，最后按请求总预算选上下文。Prompt 把系统规则、历史、证据和当前问题分层组织，LLM 的 token 通过 SSE 返回。来源和 grounding 来自程序侧选中块，但回答里的引用仍主要靠提示词，不等于逐句蕴含校验。
>
> 流式链路还处理了停止竞态：任务 ID 对应 Redis 取消标记和 Pub/Sub，本实例保存模型取消句柄，用户停止、客户端断开、模型错误都可能竞争结束状态，因此数据库用条件更新让第一个终态收敛，清理步骤彼此隔离。这个机制不能替代授权或持久工作流：停止服务当前没有校验 task owner，Redis Pub/Sub 也不是持久队列，项目没有流式 Trace 的后台修复扫描，所以不能宣称所有崩溃都可自动恢复。
>
> 业务闭环里，模型生成的任务 JSON 只能引用本次 grounding 白名单；Java 校验器检查结构、步骤顺序、证据 ID 和文档版本，草案经人工批准后才允许模拟执行。工作簿版本差异由程序逐单元格计算，不让模型承担确定性 diff。这里仍有边界：证据 ID 合法不代表每句话都被语义蕴含，所有者可以自审，ROS 也只到 dry-run。
>
> 效果方面，项目没有把单元测试或接口成功当成答案质量。历史 3 类文档、24 题小型评测把解析锚点、检索和 48 条人工盲评回答分开；后续公开 Hotpot/SciFact 诊断又把召回损失、选择损失和服务超时拆开。公开集上混合检索并非在所有数据都优于向量重排，新覆盖选择器也没有超过简单基线，所以默认配置没有因为“新算法”而改动。这些结果只属于对应提交、数据和协议，不外推生产性能。

## 4. 系统地图：角色、模块与数据

本节是**项目实际实现**。图只表达职责和时间边界，不代表每个可选通道都默认开启。

```text
                         ┌──────────── 离线 / 异步 ────────────┐
文档管理员 -> HTTP API -> 文件存储 + 文档元数据 -> RocketMQ -> 摄取内核
                                                        │
                          解析块 -> 检索块 -> Embedding ─┼─> PGVector
                                                        ├─> ES（可选）
                                                        └─> LightRAG（可选）
                         └───────────────────────────────────┘

                         ┌──────────── 在线请求 ──────────────┐
普通用户 -> 登录上下文 -> 会话/改写/意图 -> 多通道检索 -> 选择 -> Prompt
                                                              │
                                      SSE <--- LLM 流式生成 <--┘
                                       │
                          来源、grounding、消息、Trace
                         └───────────────────────────────────┘

审核/操作人员 -> 从回答选文档 -> 证据任务草案 -> 批准 -> 模拟执行
                                └-> 同稳定文档键版本 diff
```

### 4.1 主要角色

| 角色 | 主要动作 | 当前权限事实 |
| --- | --- | --- |
| 普通登录用户 | 对话、停止、反馈、查看自己的会话和任务 | 会话/任务读取有用户约束；停止入口当前只校验登录、未校验 task owner；登录也不等于知识对象隔离 |
| 知识维护者 | 建库、上传、触发切分、配置意图 | 多个知识 Controller 没有对象所有权或角色校验；当前更接近登录后共享管理面 |
| 任务审核者 | 查看证据草案、批准、模拟 | 当前所有者可批准自己的草案，没有职责分离角色 |
| 管理员 | 用户和部分管理/诊断动作 | pooled 评测入口显式要求管理员；普通 `/rag/eval` 没有同级的显式管理员检查 |
| 外部依赖 | 对象存储、PostgreSQL/PGVector、Redis、RocketMQ、模型服务、可选 ES/LightRAG/MinerU | 每个依赖有不同的一致性和失败语义，不能用一个“事务”概括 |

### 4.2 模块化单体

| Maven 模块 | 主要职责 | 面试说明 |
| --- | --- | --- |
| `bootstrap` | Spring Boot 启动、Controller、RAG 编排、摄取、铁矿业务、评测入口 | 大部分主链入口和用例实现位于这里 |
| `framework` | 通用 Web、异常、上下文等基础能力 | 不是独立微服务 |
| `infra-ai` | 模型、Embedding、重排等基础设施适配 | 通过接口隔离供应商差异和故障 |
| `mcp-server` | MCP 服务端/工具能力 | 是扩展边界，不代表默认聊天一定调用工具 |

模块化单体的收益是调用、事务和本地调试直接；代价是边界主要靠包和接口维持，热点隔离、独立扩缩容与故障域需要额外部署设计。面试中不要因为有四个 Maven 模块就称为微服务。

### 4.3 数据与状态归属

| 组件 | 保存/承载 | 不应误解为 |
| --- | --- | --- |
| PostgreSQL | 用户、知识库/文档/块、向量、会话、消息、Trace、任务与版本元数据 | 跨所有外部系统的全局事务 |
| PGVector | 1536 维向量与 HNSW 近邻检索 | 自带业务 ACL 或保证每次近似召回相同 |
| Redis | 登录/上下文相关缓存、取消键、Pub/Sub 等短期协调 | 持久化工作流或可靠事件总线 |
| RocketMQ | 文档摄取异步调度与重试 | exactly-once 业务执行 |
| 对象存储 | 原文件和衍生资源 | 数据库提交的一部分 |
| Elasticsearch | 可选 BM25 倒排索引 | 当前默认检索后端 |
| LightRAG | 可选图检索服务 | 已验证的租户级图隔离 |

## 6. 五个核心模块的一句话亮点

- [结构化文档摄取与知识更新](09-core-business-chain-review.md#core-ingestion)：用统一结构块和双文本表示保留表格语义与来源，再把消息调度、状态和索引替换的边界讲清。
- [查询理解、混合检索与上下文选择](09-core-business-chain-review.md#core-retrieval)：把“召回更多”和“最终证据更好”拆成候选、融合、重排、请求级选择四个可评测阶段。
- [Prompt、SSE、引用与取消](09-core-business-chain-review.md#core-streaming)：回答传输与任务状态同时收敛，且明确来源列表不等于逐句事实校验。
- [证据约束任务与版本比较](09-core-business-chain-review.md#core-evidence-task)：模型只产候选，证据白名单、Java 校验、人工批准和 dry-run 逐层收紧权限。
- [评测与证据闭环](09-core-business-chain-review.md#core-evaluation)：冻结输入、保留原始输出与失败，用分层指标和停止门槛避免把偶然数字写成成果。

## 7. 重要补充模块与简单模块

### 7.1 身份上下文、认证与授权边界

本节前半是**项目实际实现**，后半是**结合项目的设计分析**。

请求经 Sa-Token 登录拦截后，`UserContextInterceptor` 把当前用户放入线程上下文，并在请求结束清理。会话和铁矿任务服务会用用户 ID 约束对象；但知识库、文档管理和检索数据模型没有完整租户/所有者边界，`created_by` 也不等于可执行的 ACL。当前密码校验还是直接字符串比较。

流式停止还有一个更窄但明确的对象级授权缺口：`stop(taskId)` 会发布取消信号，却没有先证明这个 task 属于当前用户。生产修复应在信号发布前以 `(taskId, userId)` 查询或条件更新；不可把随机 ID 难猜当成授权。类似校验应位于 Service/策略层，让 Controller、内部调用和后续持久取消入口共用。

面试中可以这样说：

> 项目已经有“谁登录了”的认证链和部分用户对象隔离，但离多租户知识系统还差“谁能对哪个知识对象做什么”。生产化需要把 tenant/owner/ACL 建模到知识库、文档、块和索引过滤字段；写 API 做对象级授权，读链让向量、关键词、图检索使用同一 scope，数据库再用 Row-Level Security 或等价机制做纵深防御。密码要改为带盐的自适应哈希，诊断端点要默认关闭并只给运维角色。

关键追问：为什么只在 Controller 校验不够？因为后台任务、评测入口、内部服务和直接 SQL 可能绕开；反过来只靠 RLS 也不够，因为 ES/图服务和对象存储不受 PostgreSQL 策略控制。

### 7.2 多模型路由、首包探测与熔断

本节是**项目实际实现**，并补充通用可靠性原理。

项目把模型按档位和候选配置组织，选择器会处理默认档、preferred、思考能力与不健康候选；`RoutingLLMService` 负责流式调用、首包探测、失败切换和熔断恢复，相关测试覆盖 half-open 恢复等行为。

需要讲清三种不同机制：

- **路由**决定本次从哪些候选开始尝试，依据能力、档位和健康状态；
- **超时/首包探测**界定一次调用是否可用，避免“连接建立但长期无 token”；
- **熔断**跨请求记住连续失败，在 open 期快速失败，half-open 用少量探针判断恢复。

它们不能保证无感切换：流式回答一旦向用户发送内容，再换模型可能造成重复或语义断裂；不同供应商的 tokenizer、上下文、思考协议和安全策略也不完全等价。应记录每次尝试、首包延迟、失败类型和最终模型，同时限制总尝试预算。

### 7.3 固定工作流、工具调用、Agent 与 MCP

本节是**项目实际实现 + 相关技术原理**。

默认 `ragent.engine.type=workflow` 表示程序预先规定检索、拒答和生成步骤。一次工具调用只是让模型或程序在某个受控步骤构造函数参数；Agent 还要根据工具观察反复规划下一步并在预算/停止条件下循环。MCP 解决 Host、Client、Server 之间如何发现和调用 resources/tools/prompts，不负责替 Agent 规划，也不自动提供业务授权。

项目有 MCP 服务端/客户端适配和 Agent Profile，workflow 链也能把 MCP 意图作为有限分支；但 Profile 更接近提示词、工具和运行参数的配置单元，不能因此宣称系统已有开放式 ReAct 自主规划。完整对比与接入数据结构见 [09 的边界专题](09-core-business-chain-review.md#67-rag长上下文微调与工具执行边界)。

MCP 的面试重点是协议边界：Host 管理 Client，Server 暴露 resources/tools/prompts，双方通过能力协商确定可用特性。协议统一“怎么发现和调用工具”，不替业务决定“这个用户能否调用、参数是否安全、结果是否可信”。本项目的证据任务展示了正确的收口方式：即使模型或工具返回结构化参数，仍用确定性白名单和状态门禁校验。

若扩展为 Agent，应新增：工具级权限与确认、最大步数/费用/时间预算、幂等键、结果 schema 校验、不可逆动作的人审、完整轨迹与注入测试。先在只读工具和模拟环境验证，不直接把 ROS real execution 打开。

### 7.4 远程刷新与两套摄取抽象

本节是**项目实际实现**。

远程文档可以用 ETag、Last-Modified，缺失时用内容哈希判断是否变化；调度处理还包含租约/心跳、未变化跳过、失败清理等测试。这解决“定时轮询不等于每次重建索引”。

仓库同时有：

1. 知识文档默认使用的固定摄取内核：解析 → 切分 → Embedding → 写索引；
2. 独立的可配置摄取任务/节点引擎：节点、条件和中间输出可编排。

两者不能混称为默认能力。知识文档服务的 pipeline 执行分支当前明确报“重构中”，所以面试中应说“项目保留了通用管线模型，但当前知识上传主链固定走内核”。若要统一，应先定义稳定的块/向量/索引输出契约、节点幂等和失败恢复，再做等价性回归。

### 7.5 会话、记忆、反馈与可观测性

本节是**项目实际实现**。

会话历史会在问题改写前加载；达到阈值后可形成摘要，避免每轮无限携带全部消息。回答结束保存消息、来源和 Trace，系统还有反馈、推荐问题、管理看板等辅助能力。

这些模块面试中一段即可：

> 会话提供连续语义，Trace 提供阶段耗时和错误现场，反馈提供用户侧信号。三者不是同一个东西：历史摘要可能丢信息，Trace 成功不代表答案正确，点赞也不是无偏 gold。要形成生产闭环，需要把匿名化反馈转成可复查样本，按 prompt/index/model 版本分桶，并防止把线上反馈直接当训练真值。

### 7.6 本地基础设施与复现

本节是**项目实际实现**。

项目提供 PostgreSQL/PGVector、Redis、RocketMQ、对象存储等本地依赖和数据库初始化脚本。复现需要区分：

- **依赖健康**：端口、容器和外部模型可达；
- **构建/单测**：代码可编译、确定性机制符合断言；
- **业务冒烟**：真实文档能摄取，问题能返回来源与终态；
- **质量评测**：固定数据集、原始输出、评分和人工复核完整。

空库初始化与已有库升级也不是一回事；直接重放初始化 SQL 可能破坏已有数据。密钥由环境注入，报告只保存模型/配置标识和哈希，不保存值。

### 7.7 ROS1 dry-run 与物理执行边界

本节是**项目实际实现 + 设计边界**。

项目能把已批准任务编译成结构化白名单计划，并通过可选网关做 dry-run；测试还明确拒绝 real execution 和未知 mission type。它证明的是“AI 输出没有直接变成任意控制字符串”，不是机器人已经可靠执行。

若进入真实设备，至少还需独立安全控制器、运动/区域/速度约束、急停、双人审批、设备身份认证、指令签名、防重放、超时与回滚、仿真/硬件在环测试。LLM 应位于任务建议层，不进入毫秒级闭环控制。

## 8. 项目级高价值追问

本节同时覆盖**事实回答**和**可扩展设计**。先给结论，再按项目证据收口。

### Q1：为什么选择模块化单体，而不是微服务？

当前领域对象和核心事务集中，单体降低本地复现、调用和事务复杂度；模块已经按 Web、AI 基础设施、MCP 划分。若摄取和在线问答出现独立扩缩容、资源争抢或故障隔离需求，可先用队列和部署单元拆摄取 worker，而不是为了名词一次拆散所有事务。

### Q2：项目最难的不是“调用大模型”吗？

难点在概率组件和确定性业务之间的契约：解析是否保留结构，召回是否拿到证据，Prompt 是否正确使用，流式请求如何终止，模型 JSON 如何受证据和状态约束，最后怎样用可复核评测证明。模型 API 只是其中一个依赖。

### Q3：为什么有向量检索还要 BM25？

向量擅长语义近邻，BM25 对产品编号、标准号、专有词和精确 token 往往更直接；两者错误可能互补。项目已有 BM25/RRF 配对评测，但 Hotpot 上混合重排没有优于向量重排，SciFact 上有小幅聚合提升，所以合理结论是“按领域验证后选择”，不是混合检索天然更优。

### Q4：怎样保证回答不幻觉？

不能绝对保证。项目通过无证据短路、证据 Prompt、来源、grounding 和业务对象校验降低风险；但引用主要由生成模型给出，合法证据 ID 也不证明每句话被蕴含。进一步要做 claim 切分、引用对齐/NLI 验证、低置信拒答和人工抽检，并单独评测忠实度与可回答性。

### Q5：事务消息是否保证文档只摄取一次？

不保证。它协调本地状态和消息可见性，消费者仍可能重复投递；Embedding、对象存储和外部索引也不在同一数据库事务里。需要条件状态、稳定文档/块键、替换写、幂等消费、重试上限、死信/补偿和对账共同收敛。

### Q6：用户点击停止，为什么不能只关闭 SSE？

关闭连接只影响输出，模型调用、Trace 和资源可能继续。项目通过任务 ID 绑定 Redis 取消信号、本地 provider handle 和条件终态；正常完成发 `finish + done`，取消通常发 `cancel + done`。仍需承认 task owner 未校验、进程崩溃、Pub/Sub 丢失和供应商不支持取消时的边界。全局队列限制模型资源，而当前幂等注解既被评测开关绕过，也不覆盖整个 SSE 生命周期。

### Q7：你如何评价一个 RAG 改动？

先冻结语料、问题、配置、模型和提交；分别看解析可用性、候选召回、最终选择、回答忠实/正确、延迟与费用。保存失败请求和原始输出，用配对对比和预注册门槛决定是否继续。项目中的 D2 和 CS-DEV 都保留了负结果并没有开默认开关。

### Q8：项目现在能做多租户吗？

不能据源码这样承诺。当前有登录和部分用户对象约束，但知识库/文档没有完整 owner/tenant ACL，向量、ES 和图通道也没有统一多租户策略。生产接入方案见 [09 的权限隔离专题](09-core-business-chain-review.md#61-权限隔离从登录到检索级-acl)。

### Q9：长上下文模型能否替代检索？

不能一概替代。长上下文适合把一份或少数完整资料临时交给模型，减少切分边界；RAG 更适合不断更新、需要权限过滤和逐条来源的多文档知识。微调主要改变稳定行为、风格或格式，也不适合替代有版本的事实库。三者可以组合，但“放进窗口”不等于模型会稳定使用，应在同一数据上比较答案、忠实度、延迟和费用。

### Q10：为什么不用知识图谱解决所有多跳问题？

图能显式连接实体和关系，但构图有抽取错误、消歧、版本、ACL 和高成本；很多精确事实仍需回到原文。合理做法是把图当候选发现/路径解释层，与文本证据融合，并在多跳数据上验证，不把图路径直接当事实。

### Q11：项目里的“已验证”应怎么分级？

建议用五级语言：源码存在、单测断言、隔离链跑通、固定数据集指标、生产 SLO/业务效果。当前大量结论停在前四级，没有第五级证据。这样可以避免把 HTTP 200、测试通过或公开集结果升级为生产成果。

### Q12：如果只有五分钟，最值得展示什么？

画两条时间线，深讲“表格结构 → 证据块 → 检索”和“回答证据 → 任务草案 → 人审/dry-run”，再给出一次负结果。它们能同时体现后端可靠性、AI 质量意识和业务安全边界。

### Q13：有 MCP 和 Agent Profile，为什么仍说默认是 workflow？

因为 MCP 是能力接入协议，Profile 是提示词/工具/运行参数配置，二者都不自动产生开放式规划循环。当前主配置由程序决定步骤，MCP 意图也是有限分支；真正 Agent 还需 plan-act-observe 循环、工具权限、每步 schema、总步数/时间/费用预算、人审与轨迹评测。源码里“可配置工具”不能直接等同“自主 Agent 已落地”。

### Q14：Embedding 模型同为 1536 维，为什么不能自动切换？

维度只是数组长度，不同模型、权重、instruction 或归一化会形成不同坐标空间。当前摄取按知识库指定模型生成文档向量，PGVector 查询侧却走全局默认/候选路由；若切到不兼容候选，SQL 仍能计算余弦但结果没有可靠语义。应记录 `vectorSpaceId`，按索引空间选择 query 模型；不兼容空间各自召回后只能做名次融合，并重建旧向量后再切版本。

## 10. 表达红线与收尾模板

### 10.1 容易说错的话

| 不准确表达 | 更准确的说法 |
| --- | --- |
| “我设计并实现了整套系统” | “项目中采用了……；我能从源码和评测解释这条设计” |
| “支持混合检索，所以效果更好” | “适配器和隔离评测已存在；不同公开集结论不同，默认仍是向量” |
| “有事务消息，所以 exactly once” | “本地状态与消息最终一致；消费端仍需幂等和补偿” |
| “有引用就没有幻觉” | “来源可追溯，但引用—claim 蕴含尚未机械验证” |
| “TopK 填满提升召回” | “填满和有效证据是两回事；D2 填满却损害多项质量指标” |
| “测试都通过了” | “仓库有这些测试；只有在本轮实际执行后才报告结果” |
| “Redis + CAS 保证安全停止” | “它们传递取消并收敛终态；owner 授权、底层取消、资源清理和崩溃修复仍是独立责任” |
| “有 MCP 就是 Agent” | “MCP 标准化能力接入；是否形成 Agent 取决于规划循环、权限、预算和停止机制” |
| “Embedding 维度一样就能故障切换” | “同维度不等于同向量空间；query/document 必须绑定同一模型版本、instruction 与归一化契约” |
| “公开 benchmark 证明工业场景有效” | “只证明固定公开集与配置上的检索行为，中文业务仍需 gold” |
| “ROS 已接入生产控制” | “有白名单编译与 dry-run，可选网关不等于真实控制闭环” |

### 10.2 收尾模板

> 我会把这个项目概括成“证据先行、确定性收口”。离线侧尽量保留文档结构和版本，在线侧把召回、选择、生成分开观测，业务侧不让模型输出直接获得执行权限。当前最值得继续做的不是再堆一个算法名，而是补齐知识对象 ACL、引用蕴含验证和中文业务回归集，再用相同协议判断混合检索或图检索是否值得成为默认。
