## 3. 产出 B：复习笔记

**目标**：用户以后不打开代码，只读这套笔记就能复习并口述整个项目。宁可漏掉次要细节，也不要写成源码走读。

### 3.1 写作规范（原样放进每个写作 Agent 的提示词）

1. **按流程叙述**。每个流程开头用一段话交代：谁发起、带来什么、想得到什么、这次请求或这一步到哪里为止。之后按发生顺序往下讲，讲清每一步的判断条件、并发下会怎样、失败怎么处理、哪几步不在同一个事务里。形式不限：能用连贯段落讲清的就写段落；步骤多、分支多时再分点。分点不要切得太碎——一个点应当是一个完整的步骤或一个完整的意思，不要一句话一个点，层级最多两级。
2. **先问题后做法再取舍**。每个大节开头一两句说清“不这么做会出什么事”；方案处写明为什么不选另一个常见方案（例如为什么用数据库当队列而不用消息队列）。
3. **少用私有名字**。类名、方法名、表名、字段名、配置键、脚本文件名原则上不出现，用功能性称呼代替（“任务表”“领取语句”“模型调用包装器”“调用台账”）。每篇最多保留 5 个确实绕不开的私有名字，首次出现时用括号注明作用。通用技术名词照常使用：`FOR UPDATE SKIP LOCKED`、epoch / fencing token、租约、心跳、SSE `Last-Event-ID`、幂等键、指数退避与抖动、熔断、bootstrap 置信区间、Wilson 区间。
4. **只写关键路径**。入选标准：简历三条里提到的、面试官大概率追问的、RAG / Agent 的通用关键环节、理解后续步骤必需的。参数校验、DTO 转换、日志、前端、配置装配一律略去。关键默认值（租约 30 s、心跳 10 s、轮询 5 s、每实例 2 个槽位、接管 3 次上限等）要写，因为会被问。
5. **如实写边界**。每篇末尾一节“边界与不足”，3—6 条：非原子的地方、没覆盖的故障、基于模拟上游的数字、已知未查明的现象。
6. **数字**只取自状态文件“结果摘要”与对应改动说明，连同条件一起写；不新增、不换算、不四舍五入成更好看的值。
7. **每篇结尾加“口述版”**：一段连贯的口语，模拟面试时 1—2 分钟的讲法。
8. **篇幅不设字数限制**，以“讲清楚且记得住”为准：关键机制该展开就展开，次要细节按第 4 条直接不写，不要为了全面而堆砌。语言平实，不用比喻，不写“核心亮点”“优雅地”之类的评价词。
9. 事实以**当前代码**为准；代码与改动说明或计划不一致时按代码写，并在交付说明里列出不一致之处（不写进笔记正文）。

## 4. 产出 C：面试问答

单个文件 `面试问答.md`，约 60—80 题。每题格式：

```markdown
### Q12 为什么用数据库当任务队列，而不用项目里已有的 RocketMQ？
**答**：（口语化，150—300 字，先结论后理由，能直接念出来）
**要点**：3—5 个短语，供快速回忆
**可能的追问**：1—3 个，指向本文件其他题号或简短作答
```

分组（括号内为大致题数；每组可交给一个 Agent）：

1. **简历逐句深挖**（25）：对简历三条的每个短语至少 2 问——是什么、为什么、怎么验证、坏了会怎样、数字怎么来的。必含：恢复要多久（约一个租约周期，默认 30 s；实验用 6 s）；加机器有没有用；心跳线程自己卡住怎么办；时钟不同步怎么办；续跑会不会重复扣预算或重复写产物；命中率为什么能从不足 10% 到 80%（基线是坏的）；成本降了质量变没变；换供应商怎么办；重试会不会放大故障；57.5% 和 98.5% 是怎么测出来的。
2. **方案取舍**（10）：数据库队列对 MQ / Redis 分布式锁 / Temporal；至少一次对恰好一次；阈值压缩对滑动裁剪对摘要；显式对隐式缓存；召回前过滤对召回后过滤；内容哈希复用对文档级差异比对。
3. **RAG 与 Agent 通用题**（20）：先用 WebSearch 查近一年“RAG / Agent / 大模型应用开发 面经”，挑高频题（分块策略、混合检索与融合、重排、幻觉与引用、评测指标、查询改写、多轮记忆、工具调用协议、ReAct 与原生工具调用、多 Agent 的代价、上下文管理、流式输出、成本控制等）。作答时**优先用本项目的做法回答**；项目没做的如实说“项目里没做，我的理解是……”，不编造经历。
4. **测试与可信度**（8）：没有线上流量怎么证明；模拟上游的数字能不能信；为什么用配对差与置信区间；噪声基线是什么；不变量检查是什么；“这是 demo 吗”。
5. **后端基础的项目化提问**（8）：`SKIP LOCKED` 与行锁、事务隔离与先删后插的可见性、线程池互等死锁、SSE 对 WebSocket、优雅停机、幂等的几种做法；与秒杀项目的租约 / 锁 / 限流互相呼应的题。
6. **反问与弱点**（5）：项目最大的不足；如果上线还差什么；再给两周会做什么；哪部分是开源项目自带的；你一个人做的吗。

规则：答案中的事实与数字只能来自 B 的成稿和状态文件；私有名字同样少用；写完不提交。主会话合并后按“被问到的概率”在文件开头列一个 Top 15 题号清单。

验收：每组题数达标；抽 10 题核对答案与笔记一致；第 1 组覆盖简历三条的每个短语。

## 6. 附录：已定稿的简历条目（三份产出的主线）

- **长任务可靠性**：针对分钟级任务在发版、宕机时丢失的问题，以 PostgreSQL 实现任务队列，通过心跳租约、epoch 写保护与事件回放实现跨实例接管和断点续跑，并通过 `kill -9`、进程暂停等故障注入验证任务不丢失、产物不重复。
- **模型调用成本**：通过调用台账发现多轮调用的提示缓存几乎全部失效（命中率不足 10%），定位到每轮改写首条系统消息破坏了缓存前缀；分离静态前缀与动态提醒并配置显式缓存断点后，同负载对照命中率恢复至约 80%，单任务输入成本下降约 70%。
- **上游容错**：针对第三方模型与 Embedding 接口超时、限流的问题，实现分层超时、带抖动的有限重试，区分调用失败与检索无命中；模拟上游 30% 请求无响应时，任务成功率由 57.5% 提升至 98.5%。

概述句：本人负责研究任务模块及其可靠性与成本优化；项目为预研原型，未上线。
