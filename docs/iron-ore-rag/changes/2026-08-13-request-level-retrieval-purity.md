## 改动目的

在不扩大最终上下文、不重建冻结索引的前提下，把 `TopK=10` 恢复为整个用户请求的上限，并让文档名、工作表和表格行语义真正参与 rerank。目标是减少“答案证据已经召回，但同时混入大量低相关块”的情况，并让预算、路由和排序问题可以由评测接口定位。

本次不改变阶段 2/3 的产品边界，不把意图关闭时的全局检索本身判定为 bug，也不依据一次在线运行宣称生成准确率提升。

## 对照版本与术语

- **检索改动前当前版（C-final）**：基于后端提交 `b375a7e`，是本轮优化前从已有实验臂中选出的当前项目配置；`intent=off`、`ocr=off`，索引冻结为 `123 + 14 + 4 = 141` 个块。
- **冻结索引检索对照（D0）**：完全复用 C-final 的文档块、向量和题集，只把检索代码替换为提交 `fd538a8`，用于尽量隔离本次代码的影响。
- **重新入库组合验证（D1）**：同时应用新检索代码和 XLSX 分块提交 `ed2590e`，再从 seed 导入三份文档。PDF 需要重新调用 MinerU，因此它不是检索代码的单变量实验。
- **公平回填固定回放（D2）**：复用 D1 数据库并固定每题的改写结果，只比较请求级公平回填开关；该后续机制最终保持默认关闭。

本文把 `fd538a8` 之前的调用链称为“检索改动前实现”。它同时包含从上游继承的通用检索结构和本 fork 更早的改动，不能简单等同于“原作者 1.1.0 版本”。以下“原设计考虑”仅在能由代码结构解释时给出；无法从源码证明的作者意图会明确写成实现行为，而不是替作者推断。

检索链路里有三种容易混淆的数量限制：

| 名称 | 约束对象 | 目的 |
| --- | --- | --- |
| `recallBudget` | 每个向量、关键词或图谱通道初次取回的候选 | 保留足够召回面，尚未决定最终给 LLM 什么 |
| `candidateLimit` | 融合后继续回表、rerank 的候选池 | 控制数据库读取和模型重排成本 |
| `contextTopK` | 请求入口的最终证据总额，以及分配后的子问题额度 | 控制 Prompt 长度、噪声和产品返回上限；本实验入口配置为 10 |

本次固定配置对应 `recallBudget=20`、`candidateLimit=40`、入口 `contextTopK=10`。`defaultTopK=10` 在请求入口先解释为请求总额；分配后，各子问题自己的 `RetrievalBudget.contextTopK` 保存 `5 / 5` 或 `4 / 3 / 3` 等子配额。因此，“请求级 TopK=10”是指：无论一个用户问题是否被改写成多个子问题，最终送入 LLM 的**去重证据块总数最多为 10**。它不是“每个子问题分别最多返回 10 块”，也不是向量库最初只能召回 10 个候选。

## 问题如何发现

C-final 的 Context Precision 只有 `17.1%`。评测先对每题计算“包含任一固定锚点的返回块数 / 该题全部返回块数”，再对 21 道可回答/近领域题取算术平均；数值低说明正确证据旁边混入了较多无关上下文，不等同于回答准确率只有 17.1%。

逐题检查发现，21 道可回答/近领域题中有 17 道被改写为 2～3 个子问题。检索改动前实现只构造了一份数值为 10 的 `RetrievalBudget`，但每个子问题都独立执行这份预算，最后再把各自上下文拼接。预算对象只是不可变参数，不会在某个子问题取走 10 块后自动扣减。换句话说，一个请求拆成三个子问题后，执行的是“三次各自最多 10 块”，而不是“三个子问题共享 10 块”。因为部分子问题候选不足或结果重合，实测没有简单达到 20～30 块，但按 chunk ID 去重后的请求级唯一块仍为平均 `13.05`、最大 `19`，17/21 道题超过配置值 10。生产 Prompt 当时按子问题分段组装，同一块命中多个子问题时还可能重复出现，所以这个唯一块统计已经是较保守的噪声度量。

继续增加 TopK 会把**每个子问题**的额度一起调大。这样增加的不只是可能的相关证据，还包括重复块和低相关块；rerank 需要保留的输出、Prompt token 以及生成时需要辨别的噪声也会随拆分数增长。候选输入量由独立的 `candidateLimit` 控制，并不会因最终 TopK 必然同步增长；但这也说明增加最终 TopK 不能修复预算作用域。所以这里首先要修作用域，而不是用更大的数值掩盖问题。

随后沿调用链核对了三个数据契约：`RetrievalEngine` 的最终 TopK 在子问题层被重复使用；改写 JSON 虽包含 `should_split`，解析器却只看 `sub_questions`；入库已有 `embedding_text` 和结构元数据，rerank 输入却只有展示正文。C-final 的 Hit@5 又已经较高，说明多数题的正确块其实已经进入前排候选，主要矛盾是“正确块存在，但同一请求还带回太多无关块”，不是简单的召回池不足。由此把低纯度拆成可独立测试的代码问题，而不是先调大 TopK 或更换模型碰运气。

## 根因

### 1. 单查询预算被当成请求总预算

从代码结构看，检索改动前实现把每个子问题视为一次完整检索，并让多个子问题并行复用同一套参数。这种结构实现简单，也让每个子问题拥有完整的最终输出空间；但“复用同一个数值”不等于“共享同一份总额度”。每条子链都执行完整的 `contextTopK=10`，合并后没有请求层的统一上限，最终块数自然随拆分数量变化。

Rerank 的 `top_n` 曾承担后处理结果列表的主要截断。虽然 `DefaultContextFormatter` 在渲染 Prompt 时还会按每个子问题的 TopK 截断，但 rerank 关闭、跳过或失败后，检索结果列表、`intentChunks`、来源归因和评测可能继续保留更大的融合候选池。也就是说，不同消费者看到的块集合并不一致；一个可选模型步骤不应顺带承担统一结果上限。

### 2. 改写协议声明了开关，解析器没有执行

最初引入多问题改写时，模型协议只有 `rewrite` 和 `sub_questions`，没有 `should_split`；解析器直接读取非空数组在当时符合契约。后来 Prompt 增加了 `should_split`，用来把“是否需要拆分”和“拆成哪些问题”分离，但 Java 消费端仍沿用旧协议，只看数组是否非空，相同子问题也不去重。

这属于生产端与消费端演进不同步，而不是有意忽略开关。模型若返回内部不一致的 JSON，例如 `should_split=false` 但数组偶然含两项，旧解析器仍执行两次检索；重复数组项也会重复检索并占用上下文额度。本问题不是 Prompt 少写一句话，而是后端没有落实已经声明的布尔契约。

### 3. 召回表示与重排表示不一致

入库时本来就保存了两种文本：

- `content` 是面向用户和 LLM 的展示正文，例如段落或 Markdown 表格；
- `embedding_text` 是面向检索的结构化表示，会带章节路径，表格按“列名: 值”组织。

检索改动前实现让向量召回使用 `embedding_text`，但 rerank 只接收展示正文；文档名、sheet、cell range 等元数据又在 rerank 之后才回表补全。从工程结构看，后置补元数据可以减少关系库读取量，并且足以支持最终来源展示和按文档聚合；问题是它来得太晚，无法参与排序。

这会造成“召回阶段利用结构找到正确块，重排阶段又丢掉结构”的不一致。国标 PDF 的标准名是区分相似试验方法的重要信号；XLSX 的 sheet、章节路径和“列名: 值”往往比 Markdown 中的列位置更容易表达一行的业务语义。正确块虽然被召回，仍可能因 rerank 看不到这些信息而被低估。

### 4. 三段预算只在单条子查询内闭合

检索改动前的数据结构已经区分了召回、候选和最终上下文三种预算，但这些语义只在一条 `retrieve → fuse → rerank → render` 子查询链内闭合。多个子问题汇合时没有再执行一次请求级扣减，导致单查询正确、聚合后超额。C-final 已有较高 Hit@5、却只有 `17.1%` Context Precision，正说明此时应在汇合点收口最终上下文并改善排序，而不是缩小前端召回池或继续增加最终块数。

## 方案取舍

- 不增加最终 TopK：这会掩盖请求级预算失效，并继续增加 Prompt 噪声和成本。
- 不直接压小每个子问题的召回池：候选召回和最终展示是两个预算，过早截断可能损害召回。
- 不只修改 Prompt：`should_split`、额度分配和排序输入都是后端契约，必须由代码和测试约束。
- 选择“每题保留候选、请求级统一分配最终额度、结构化文本只用于排序”的方案：既守住 10 块产品上限，又不把内部 ranking text 暴露为引用正文。

## 具体改动与调用链

### 1. 把最终额度分配到请求层

`RetrievalEngine` 先保留请求级 `contextTopK=10`，再按子问题数分配最终额度。例如三个子问题按 `4 / 3 / 3` 分配，而不是每个子问题各取 10。`recallBudget` 和 `candidateLimit` 仍可在每条子查询上保留足够候选，收紧的是最终送入 LLM 的预算，不是用过早截断换取表面纯度。

提交 `fd538a8` 的第一版修复为每个子问题增加始终启用的 `FinalTopKPostProcessor`：即使 rerank 未启用、失败或跳过，也会按已分配额度截断。这样各子问题额度相加不超过 10，但跨子问题去重后留下的空位不会自动补回；D1 的 `xlsx-hard-06` 正是由此暴露出后续的回填问题。

D2 为了单独验证回填，把实现演进为“各子问题先返回受控候选池，再由请求级选择器统一去重和选择”。公平回填机制虽然能够填满空位，但固定回放未通过质量门槛，因此开关保持默认关闭。该演进不撤销请求级 10 的上限，只改变候选如何进入最终 10 块。

### 2. 让 `should_split` 成为真正的后端契约

`MultiQuestionRewriteService` 现在按以下顺序处理模型 JSON：

1. `should_split=false` 时只采用 `rewrite`，不因为数组残留内容而拆分；
2. `should_split=true` 时读取 `sub_questions`，裁剪空白并按原顺序去重；
3. 旧响应缺少布尔字段时，才根据有效子问题数量推断，保留兼容性；
4. 规则降级路径同样执行去重。

这样既落实显式协议，也没有要求在线模型一次性完美迁移到新格式。

### 3. 分离展示文本与排序文本

元数据补全从 rerank 之后移动到之前，回表得到文档名、sheet、cell range 和已落库的 `embedding_text`。随后构造独立的 `rankingText`：使用“去扩展名的文档名 + embedding text”供 rerank 判断；`content` 仍用于最终 Prompt、引用和前端展示。

这一选择复用了入库时已经生成的结构信息，不需要重新解析文档，也避免把为机器检索组织的 key-value 文本冒充用户看到的原文。它会增加进入 rerank 前的元数据读取，因此先用 `candidateLimit` 控制候选池，避免无限扩大回表和模型输入。

### 4. 为评测暴露排序与作用域证据

隔离评测接口增加 collection、最终分数、Excel sheet 和 cell range 等逐块诊断字段。它们用于判断“是否跨知识库混入”“正确块在哪一步掉出”“来源范围是否正确”，不改变产品回答 API，也不把内部 ranking text 返回给用户。

用中文表示，当前调用链是：

```text
多路召回
  → 去除同一文档块的重复结果
  → 融合向量、关键词和图谱通道分数
  → 限制候选池，控制后续回表和模型成本
  → 回表补文档名、sheet、cell range 和 embedding_text
  → 使用结构化 ranking text 重排
  → 在整个用户请求范围内去重、分配并截断到 TopK
  → 确定同一选中块集合，再分别构造 Prompt 分组和去重后的统一结果
```

D1 检查点对应的处理器顺序是 `Deduplication(1) → Fusion(5) → MetadataEnrichment(8) → Rerank(10) → FinalTopK(15)`。当前 D2 代码已经演进为 `Deduplication → Fusion → CandidatePoolLimit → MetadataEnrichment → Rerank → 请求级选择`；这里列出两条链路，是为了区分“D0/D1 指标对应的第一版实现”和“当前保留的实现”，不是两套组件同时运行。

当前请求级选择先确定同一选中块集合。Prompt 仍按子问题分组渲染，来源、grounding 和评测则读取按首次出现顺序去重的统一列表；默认关闭公平回填时，同一块仍可能在多个子问题 Prompt 段落中重复出现，但不会在来源和评测列表中重复计数。因此这里保证的是消费者基于同一选中集合，不把它夸大为列表顺序和出现次数完全相同。

## 验证

### Java 回归

针对新增行为的 11 个测试先通过，随后运行检索相关的 78 个测试，全部通过。覆盖内容包括：

- 两/三个子问题的请求级额度分配；
- rerank 关闭或失败后的最终上限；
- 元数据在 rerank 前可用，展示正文与 ranking text 隔离；
- `should_split=false`、重复子问题与异常 JSON 的解析；
- Vector、Keyword、Graph 通道、作用域、融合和已有排序行为的回归。

### D0：冻结索引，只替换检索代码

D0 直接复用 C-final 的 `123 + 14 + 4 = 141` 个冻结块，不重新解析或生成向量，因此它用于隔离检索代码的影响。意图和 OCR 均关闭，题集仍为固定 24 题，其中 21 题参与可回答指标。

| 指标 | C-final | D0 | 变化 |
| --- | ---: | ---: | ---: |
| 平均返回块数 | 13.05 | 6.52 | -50.0% |
| 最大返回块数 | 19 | 10 | -9 |
| 超过请求级 TopK=10 的题数 | 17/21 | 0/21 | -17 |
| Context Precision | 17.1% | 29.2% | +12.2 个百分点 |
| 路由纯度 | 73.6% | 84.8% | +11.3 个百分点 |
| 文档召回 | 97.6% | 97.6% | 不变 |
| Anchor Recall | 86.5% | 84.1% | -2.4 个百分点 |
| 锚点 Hit@5（至少一个） | 95.2% | 90.5% | -4.8 个百分点 |

分族 Context Precision 均高于 C-final：XLSX `27.9% → 50.7%`、原生 PDF `7.0% → 14.0%`、扫描 PDF `11.7% → 20.7%`、跨领域 `26.2% → 33.8%`。这说明收益不是单一文档族偶然抬高总体均值。

自动 Hit@5 的下降只发生在 `cross-scope-01`。D0 返回的第 3 块已经是 YS/T 360.3 的标准标题“钛铁矿精矿化学分析方法第3部分：氧化亚铁量的测定重铬酸钾滴定法”，文档召回仍为 100%，但固定锚点使用“钛铁矿精矿中氧化亚铁量的测定方法”，严格字符串规则判为未命中。为保持冻结协议，没有事后修改题集或回填自动分数；记录时同时保留原始指标与这条人工判读。

D0 的检索 P95 从 `8.5 s` 变为 `16.8 s`。两次运行时间不同且重写、向量和 rerank 都依赖在线模型服务，因此不能把单次延迟变化归因于本次本地代码。

### D1：从 seed 干净重建，组合验证

D1 使用同一 OCR 关闭配置重新导入三份文档。XLSX 在线结果与离线结果一致：79 块、最大 1,019 字符、0 块超过 1,024、0 个多余精确重复块、解析锚点 5/5。两份 PDF 本次生成 16 和 6 块，而冻结索引是 14 和 4 块，说明 MinerU 远端结果存在时间漂移；D1 总体 PDF 指标不能单独归因于本次代码。

XLSX 六题的可比结果如下：

| --- | ---: | ---: | ---: |
| 锚点 Hit@5（至少一个） | 100.0% | 100.0% | 100.0% |
| 锚点 Hit@5（全部） | 83.3% | 83.3% | 83.3% |

| Context Precision | 27.9% | 50.7% | 39.3% |

D1 唯一丢失的是 `xlsx-hard-06` 的一个目标锚点。该内容仍存在于正确工作表的对应块中，但问题拆为三个子问题后，该块未进入最终请求上下文。这在当时暴露出一项明确限制：子问题分别截断后再去重，会留下未使用的请求额度，却不会从各子问题候选中回填。因此 D2 固定改写输出并验证请求级公平补位，而不是简单增大最终 TopK。真实锚点文本和单元格范围只保留在 Git 忽略的本地评测数据中。

完整 D1 总体指标低于 D0，主要下降发生在本次重新解析后发生块形状变化的两类 PDF；因此不作为检索代码失败或成功的单因果证据。D1 的数据库和结果哈希已保存到 `local-data/eval/snapshots/current-D1-chunk-purity/`，该目录受 Git 忽略并只在本机保留。

## 改动效果与限制

D0 是隔离程度最高的检索代码对照：它冻结了 141 个块及其向量，仅替换检索代码后，平均上下文减半、Context Precision 和路由纯度提高、文档召回不变；但在线改写和 rerank 仍存在运行波动，因此不是完全确定性的因果实验。自动 Anchor Recall 与 Hit@5 也有小幅下降。D0 没有重新运行完整回答和人工盲评，所以效果只能表述为“预算收口与检索纯度改善”，不能据此声明回答准确率提升。

D1 同时包含 XLSX 新分块和 PDF 在线重新解析，只能用于组合兼容验证；XLSX 分块指标稳定，两类 PDF 的块数发生远端漂移，所以 D1 总体指标不能作为本地检索改动的单因果证据。完整分块效果见 [XLSX 结构感知分块](2026-08-13-xlsx-structure-aware-chunking.md)。

### D2 后续结论与停止决定

D1 提出的请求级公平补位已在 D2 以默认关闭的开关实现，并用固定 24 题改写做 off/on 各三次回放。机制能够补满空位，但 Hit@5、Context Precision 和路由纯度未通过非退化门槛；D1 单次丢失的目标题在 D2 off 三次中已全部命中，也没有形成配对恢复证据。详细协议、实现和负结果见[请求级公平回填固定回放评测](2026-08-14-request-level-fair-refill.md)。

因此 D1 的请求级上限和结构化重排继续保留，公平回填保持 `false`；本阶段不继续增加重复次数或调参。
