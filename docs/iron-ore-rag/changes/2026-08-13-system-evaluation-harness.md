## 改动目的

为基线版本和当前版本建立一套小而完整的系统评测：同一组工业文档、问题和判定规则能够分别测量解析、检索、意图、OCR、回答与拒答，并留下可复核的输入哈希、运行配置和人工标签。它既为简历中的数字提供出处，也用于定位后续应修代码还是保持现状。

## 问题如何发现与边界

阶段 1 只用一个规整工作表区域和 8 道题证明 XLSX/Markdown 最小样本可用，不能回答以下问题：完整工作簿与两类 PDF 是否都能摄取；正确文档是否进入前五；返回上下文是否纯净；意图或 OCR 是否真的带来收益；不可回答问题是否会被错误作答；当前版是否优于冻结基线。

原有手工测试也没有同时锁定题集、原文、索引、模型配置和数据库状态。若直接在同一环境中反复切换 OCR、意图或代码版本，即使数字变化，也无法区分代码影响、重新入库影响和在线模型波动。

本改动只建立 `3` 份文档、`24` 道固定题的小型评测，不把结果外推为行业基准。不改冻结基线源码，不建设通用 Excel 转换器，不测试已废弃的 `ChunkerSettings.strategy`，不接入真实机器人，也不把 OCR、检索和回答指标合并成一个含义不清的“准确率”。

## 根因

1. 缺少统一的数据契约，题目、标准文档、文本锚点和可回答性标签不能在运行前整体校验。
2. 缺少环境隔离和状态快照；重新解析、意图切换、缓存和对象存储变化可能污染下一实验臂。
3. 检索依赖在线 Query Embedding、改写与 rerank，一次运行不能区分稳定差异和服务波动。
4. 自动锚点只能判断证据是否进入上下文，不能完整判断答案事实、来源、禁止断言和拒答是否正确；直接比较未匿名回答也容易引入版本先验。

## 候选方案与选择理由

- 没有扩成大规模通用 benchmark，而是选择 `XLSX + 原生 PDF + 扫描 PDF` 三类代表文档和 24 题。现有企业材料有限，小样本更容易逐题审计，也能诚实保留适用边界。
- 没有侵入冻结基线代码，而是通过两版共有的 `/rag/eval` 和 `/rag/v3/chat` 做外部评测，保证比较对象仍是实际 checkout。
- 基线和当前版使用不同 PostgreSQL、Redis DB、MQ 后缀和对象存储桶；OCR 臂从 seed 重新入库，意图臂只切换专用意图。这样把需要重建索引的变量和只改变路由的变量分开。
- 每个冻结点生成不可覆盖的 manifest，记录 checkout、数据集、语料、配置、结果和数据库 dump 的 SHA-256。工具发现已有 manifest 时拒绝覆盖，避免后来一次有利运行替换原始证据。
- 预先定义 B0/B1/B2/C0/C1/C2/C-final 实验臂和放行门槛；分别报告解析锚点、检索指标、意图 Top-1、延迟和人工回答质量，不用单一综合分掩盖退化。
- B0/C-final 回答先随机匿名化，再由用户按统一字段盲评，最后用独立 key 解盲。人工判断因此不知道答案来自基线还是当前版。

## 实施内容

- 新增 [`eval/iron-ore/README.md`](../../../eval/iron-ore/README.md) 和 [`RUNBOOK.md`](../../../eval/iron-ore/RUNBOOK.md)，定义数据契约、实验臂、执行顺序、指标、门槛和恢复方式。
- 外部工具覆盖数据集校验、知识库导入、chunk 审计、检索、完整 SSE 回答、意图切换、匿名盲评、固定门槛选型、归档和数据库恢复。
- 真实数据留在 `local-data/eval/`：24 道题由 18 道单文档题、3 道近领域混淆题和 3 道不可回答题组成；每份文档另有 5 个解析锚点。仓库只保留 Schema、示例和工具。
- 固定单一 Chat、Embedding、Rerank 候选并禁止静默降级；运行报告记录 checkout 和配置，避免把模型切换误认为代码收益。
- 专用意图 SQL 只创建两个 KB 意图，同时兼容 `bcfba62` 和当前 Schema；切换工具只操作评测 ID 和对应 Redis 逻辑库。
- 快照、恢复和意图切换工具在项目 Compose 容器内调用 PostgreSQL/Redis 客户端，不要求宿主机安装 `psql`，也不把密码拼进命令。

## 改动效果

### 冻结基线运行结果

基线 checkout 为 `bcfba6201fc5a7b73bf6b2ae743ed1fef6c2afb6`，运行期间保持干净。B0 的三份文档生成 `123 + 14 + 4 = 141` 个块和向量；24 个完整回答对应的 24 条 trace 均为 `SUCCESS`，没有 `RUNNING` 或 `FAILED`。

| 指标 | B0 意图关/OCR 关 | B1 意图开 | B2 OCR 开 |
| --- | ---: | ---: | ---: |
| 评测题数 | 24 | 24 | 12 道 PDF 题 |
| 锚点 Hit@5（至少一个） | 95.2% | 95.2% | 100.0% |
| 锚点 Hit@5（全部） | 71.4% | 66.7% | 83.3% |
| Anchor Recall | 86.5% | 88.9% | 93.1% |
| Context Precision | 16.7% | 17.7% | 11.4% |
| 路由纯度 | 73.8% | 64.7% | 59.0% |
| 检索 P95 | 17.5 s | 20.2 s | 8.1 s |
| Top-1 意图准确率 | 不适用 | 94.4% | 不适用 |

B2 只包含两类 PDF，不能把其总体列与 B0/B1 的 21 道可回答/近领域题总体直接比较。可比的分族结果为：原生 PDF Hit@5 `83.3% → 100%`、Anchor Recall `69.4% → 94.4%`；扫描 PDF Hit@5 保持 `100%`、Anchor Recall 保持 `91.7%`。解析锚点同时为原生 PDF `3/5 → 4/5`、扫描 PDF `5/5 → 5/5`。

B0 的 24 个完整回答已采集，回答 P95 为 `24.1 s`、最大 `31.7 s`。一次在线运行还不足以把 B2 的变化归因于 OCR，因此这些结果只作为诊断证据，不单独支持开启 OCR。

### 当前版运行与固定选型结果

当前 checkout 为 `b375a7e5493a09d35af498b6c241536440ecdd1c`。C0/C2 分别从同一个 current seed 干净入库，均生成 `123 + 14 + 4 = 141` 个块和向量；C1 只在 C0 状态上开启两条评测意图。固定选择器最终输出 `intent=off, ocr=off`。

| 指标 | C0 意图关/OCR 关 | C1 意图开 | C2 OCR 开 | C-final 关闭配置复跑 |
| --- | ---: | ---: | ---: | ---: |
| 评测题数 | 24 | 24 | 12 道 PDF 题 | 24 |
| 锚点 Hit@5（至少一个） | 85.7% | 90.5% | 100.0% | 95.2% |
| 锚点 Hit@5（全部） | 61.9% | 66.7% | 83.3% | 66.7% |
| Anchor Recall | 77.0% | 86.5% | 93.1% | 86.5% |
| Context Precision | 17.5% | 18.7% | 11.6% | 17.1% |
| 路由纯度 | 66.8% | 65.3% | 60.2% | 73.6% |
| 检索 P95 | 18.2 s | 20.0 s | 8.7 s | 8.5 s |
| Top-1 意图准确率 | 不适用 | 100.0% | 不适用 | 不适用 |

C1 满足 Top-1 至少 `90%`，且 XLSX、原生 PDF、扫描 PDF 三族 Hit@5 均不下降；但路由纯度由 `66.8%` 降至 `65.3%`，因此意图门槛失败。C2 的原生 PDF 解析锚点由 `3/5` 增至 `4/5` 且无损失，但扫描 PDF 为 `5/5 → 5/5`，未达到至少新增一个扫描件锚点的门槛，因此 OCR 门槛失败。规则在运行前已固定，没有因为 C1/C2 的部分有利指标而放宽。

C-final 从冻结的 C0 入库快照恢复后，重新执行同一关闭配置。它与 B0 的锚点 Hit@5 均为 `95.2%`、Anchor Recall 均为 `86.5%`；全部锚点 Hit@5 为 `66.7%`，低于 B0 的 `71.4%`；Context Precision 为 `17.1%`，较 B0 的 `16.7%` 高约 `0.4` 个百分点。检索 P95 为 `8.5 s`，但该延迟同时受在线模型服务影响，不能单独归因于代码版本。

C-final 24 个完整回答全部完成，数据库对应 24 个会话、48 条消息和 24 条 trace run；回答 P95 为 `22.6 s`、最大 `23.5 s`。B0/C-final 共 48 条回答随机匿名化后由用户完成严格判定，再通过独立 key 解盲。

人工结果中，B0 与 C-final 的总体严格通过率均为 `79.2%`（19/24），21 道可回答/近领域题均为 `76.2%`（16/21），3 道不可回答题均为 `100%` 正确拒答。分族严格通过率也完全相同：XLSX `83.3%`、原生 PDF `66.7%`、扫描 PDF `83.3%`、近领域混淆 `66.7%`、不可回答 `100%`。24 道配对题没有任何人工标签差异，因此本轮只能表述为当前版维持基线回答质量，不能表述为回答准确率提升。

同一关闭配置、同一冻结索引下，C0 与 C-final 的锚点 Hit@5 分别为 `85.7%` 和 `95.2%`，其余指标也有波动。这是当前小样本最重要的重复性限制：可把冻结数据、门槛和失败案例用于定位问题，但不能把一次有利复跑写成稳定提升。

### 已暴露问题及处置

- XLSX 的 123 个块平均 1,573 字符，70 块超过 1,024 字符目标，16 块超过 3 倍容差，最大 12,489 字符；精确重复块比例约 13.8%。该证据随后形成了独立的[XLSX 结构感知分块与去重](2026-08-13-xlsx-structure-aware-chunking.md)改动。
- B0 原生 PDF 只恢复 `3/5` 个解析锚点，并对应最低的分族 Hit@5（83.3%）和 Context Precision（7.3%）。OCR 对部分指标有利但未通过固定门槛，因此仍保持关闭。
- B1/C1 的意图 Top-1 分别达到 `94.4%` 和 `100%`，却没有带来稳定的路由纯度收益，说明分类准确不等于检索收益；本阶段不继续增加意图数量。
- B0/C-final 的 Context Precision 只有 `16.7%/17.1%`，且多问题请求返回块数失控。逐题和 chunk 审计随后推动了[请求级检索预算与结构化重排](2026-08-13-request-level-retrieval-purity.md)，而不是继续增大 TopK。
- C0/C-final 在同一关闭配置和冻结索引上仍有明显波动。D2 后续通过固定 `subIntents` 和 off/on 各三次回放隔离在线改写，但公平回填未通过质量门槛并保持默认关闭，详见[D2 记录](2026-08-14-request-level-fair-refill.md)。

## 限制与停止状态

- 评测只覆盖 3 份文档和 24 道题，适合证明本项目的工程改动，不是通用工业 RAG 基准。
- B2/C2 只运行 12 道 PDF 题，其总体指标不能与包含 XLSX 和跨领域题的 B0/B1/C0/C1 直接比较。
- Query Embedding、改写和 rerank 依赖在线服务；同配置复跑已经观察到波动，因此单次延迟和小幅指标变化不作为稳定因果结论。
- B0 与 C-final 的 48 条盲评回答没有任何配对标签差异，最终结论是回答质量维持基线，而不是准确率提升。
- 自动实验、人工解盲及后续 D0/D1/D2 定位均已结束。失败门槛和负结果继续保留，不再为改善数字修改题集、放宽门槛或重复调参。

## 数据与兼容性

- 无产品数据库迁移、无公共 API 变化、无基线源码变化。
- 真实问题、标准事实、原始响应和 PostgreSQL dump 不进入 Git。
- 原始报告、人工得分、不可覆盖 manifest 和数据库 dump 位于 Git 忽略的 `local-data/eval/`；精确执行与恢复命令只在 [`RUNBOOK.md`](../../../eval/iron-ore/RUNBOOK.md) 维护，不在改动说明中重复。
- OCR 或分块参数变化需要恢复各自 seed 并重新入库；意图开关只改两条意图、清对应 Redis 后重启。
- `restore_eval_database.py` 仅允许两个 `ragent_eval_*` 名称，且要求 `--yes-replace` 和完整数据库名双重确认。
