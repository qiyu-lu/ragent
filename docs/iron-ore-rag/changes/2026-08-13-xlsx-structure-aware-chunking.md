## 改动目的

把规则型 XLSX 转换为长度受控、无处理链额外制造的重复项、仍保留表头语义和单元格范围的检索块。目标不是追求更大的召回数量，而是先修复输入表示，使 embedding 和 rerank 面对的是可区分、可引用的业务单元。

## 对照版本与处理层次

本文中的 C-final、C0 和 D1 是评测运行标签，不是发布版本或分支名：

- **分块修复前的冻结当前版（C-final）**：后端提交 `b375a7e` 在 `intent=off`、`ocr=off` 配置下完成复测后保存的当前索引，XLSX 共 123 块；它对应提交 `ed2590e` 之前的分块行为。
- **分块修复前的同配置运行（C0）**：同一关闭配置下较早执行的一次当前版运行，本文只用它记录一次摄取耗时，不把单次时间差写成性能提升。
- **使用新分块重新入库的组合验证（D1）**：应用提交 `ed2590e` 和检索提交 `fd538a8` 后，从 seed 重新导入三份文档；其中 XLSX 的离线与在线分块结果可以直接核对，整体检索变化则不是 XLSX 单变量结果。

本次处理链如下：

```text
XLSX 原始字节
  → ExcelDocumentParser：Apache POI 打开工作簿并遍历可见 Sheet
  → ExcelTableNormalizer：读取单元格、公式、超链接和合并区域，规范化为 headers + rows
  → 每个 Sheet 形成 H1 标题块和一个 TableBlock
  → TableChunker：按表格结构生成 Markdown 展示正文和 key-value 向量正文
  → ChunkPacker：与其他块类型共用的后处理打包，处理前导语、小尾块和 piece 边界
  → ChunkAssembler：分配 chunk ID，把 Sheet/章节路径补入 embedding_text
  → 生成向量并入库
```

`ed2590e` 没有更换 Apache POI，也没有修改 `ExcelDocumentParser` 打开工作簿和遍历 Sheet 的流程、`ExcelTableNormalizer` 已有的公式/超链接读取，或 `ChunkAssembler` 的最终装配。它修改的是中间三层：`ExcelTableNormalizer` 的**表格语义归一化**、`TableChunker` 的**结构分块预算**、`ChunkPacker` 的**通用后处理打包**。

因此，这不是单一的“文档解析问题”。合并值复制和纵向重复续行发生在 POI 已经读出单元格之后，属于解析后的表格表示问题；预算估算和已切 piece 被再次合并属于分块与打包问题。它也不是 OCR 问题，更不是 POI 无法读取 XLSX。

## 问题如何发现与边界

评测工具先通过文档 API 读取分块修复前的冻结当前索引，再按最终 `content` 统计平均值、最大长度、超过 1,024/3,072 字符的数量，并对规范化后完全相同的正文分组。这里的“17 个多余精确重复块”按每组 `数量 - 1` 计算，表示 123 块中有 17 个可以从重复组里移除的额外块，不是有 17 个重复组。修复前没有保存 P95，因此效果表中保持“未记录”，不从现有汇总反推该数值。

审计结果是：同一 XLSX 生成 123 个块，其中 70 个正文超过目标 `1,024` 字符，最大 12,489 字符，多余精确重复块占约 13.8%。利用已经保存的 Sheet 和 cell range 回溯后，最长块和最大重复组都落在合并单元格区域。这个过程先证明“入库块的形状异常”，再沿来源定位代码，而不是先看到回答不理想就假定 TopK 太小。

本次只修复已有规则型 XLSX 的表格归一化、结构分块与通用打包中的可证实问题。不建设任意复杂工作簿转换平台，不修改冻结题集，也不把离线块形状改善提前写成回答准确率或 Context Precision 提升。

## 根因

### 1. 合并单元格展开没有区分表头与数据区

XLSX 的合并区域通常只在左上角单元格保存真实值，其余坐标为空。之前的 `ExcelTableNormalizer` 会把左上角值复制到合并区域内的每个坐标。这个设计有合理用途：一个数据行脱离原表后仍能携带纵向合并的分类字段，多行表头的每个子列也能继承父表头。

例如表头 `B1:C1` 合并为“检测条件”，第二行分别是“温度”和“湿度”。表头展开后可以得到“检测条件|温度”和“检测条件|湿度”；如果完全不展开，第二列会丢失父级语义。因此不能把所有合并值复制一律删除。

问题是旧规则没有区分表头、横向合并说明和纵向共享分类：

```text
数据区 B5:D5 横向合并，Excel 只在 B5 保存“较长说明”

POI 读到：     [较长说明, 空, 空]
旧归一化结果： [较长说明, 较长说明, 较长说明]
旧 KV 文本：   阶段: 较长说明; 参数: 较长说明; 备注: 较长说明
```

同一句长说明会同时出现在 Markdown 的多个单元格和 key-value 文本的多个字段中。这是 `ExcelTableNormalizer` 对**解析后表格语义**的处理造成的文本膨胀，不是 `TableChunker` 复制了正文。

纵向合并还要区分两种情况：

- `B7:B8` 是共享分类，但 C7、C8 分别有不同条件时，两行都需要携带分类值，不能去重；
- `B10:D12` 整个区域完全合并，只有 B10 有真实值且第 11、12 行原本全空时，旧展开会生成三条相同行，后续可能形成完全重复块。

此前只看展开后的内容，无法区分“用户确实录入了两条相同记录”和“空续行被合并值填出来”。这是重复块的直接来源。

### 2. 长度预算只测量了一种中间文本

一个表格块实际有两份用途不同的文本：

| 文本 | 形态与用途 |
| --- | --- |
| `content` | 带完整表头、分隔线和行的 Markdown，进入 LLM 上下文、引用和前端预览 |
| `embedding_text` | “Sheet/章节路径 + 列名: 值”的结构化文本，用于 embedding 和检索 |

旧 `TableChunker` 主要累计 key-value 数据行的字符数，没有同时渲染并测量 Markdown 表头、分隔符、转义和换行，也没有计入之后由 `ChunkAssembler` 补入的 Sheet/章节路径。因此某个中间长度判断通过，不代表最终入库的两份文本都满足预算。

旧设计不计算较深的章节前缀，是为了避免相同前缀反复挤占每块空间、把表格退化成一行一个块；对行数不多且 key-value 文本不超过容忍上限的表格保留整表，则有利于跨行比较并减少重复表头。这些考虑适合普通小表，但默认 `maxChars=1024`、`toleranceFactor=3` 时，旧路径可能把 `3,072` 当成整表的实际目标，而不是偶发原子内容的容忍上限。

还有一个边界：旧算法通常在“当前分组已经有行、再加入下一行将超限”时才落块。一条数据行如果自身已经非常长，空分组没有可提前落下的内容，为保持一行的键值语义，它仍会作为原子行进入单块。合并值重复又会进一步放大这条行，最终形成配置目标 1,024、实际正文最大 12,489 的结果。

宽而稀疏的表也会放大误差：整张表可能有很多列，但某行只填写少数长字段；Markdown 仍重复整套宽表表头和空单元格骨架。按固定字符截断会把列名和值拆开，旧实现又把整行视为不可分，因此无法安全降到预算内。

### 3. 通用 `ChunkPacker` 撤销了表格切分决定

`TableChunker` 会把同一张表拆成多个 `ChunkDraft`，并用 `piece` 表示“这些草稿来自一个 Block 的结构切分”。随后运行的 `ChunkPacker` 是所有文档类型共用的二次打包器；它原本会把“单位说明”“以下规则适用于本表”等短前导语带到正文旁边，也会把不足 `maxChars / 4` 的小尾块并入相邻块，避免几十字碎片单独占用一个 TopK 名额。

问题不在于需要通用打包，而在于旧实现只有当整节已经超过 `toleranceChars` 时，才进入尊重 `piece` 的节内打包路径。例如 `TableChunker` 已切出两个约 600 字符的 piece，在 `maxChars=1024`、`toleranceChars=3072` 下，标题加两个 piece 仍小于 3,072；旧 `ChunkPacker` 会把整节当作可合并单元，重新组成超过 1,200 字符的块。上游已经做出的结构切分因此被后处理撤销。

小尾块合并同样使用容忍上限，且没有检查顶级章节。Excel 中每个 Sheet 会映射为一个 H1 顶级路径；若为凑最小长度跨 Sheet 合并，块正文会同时包含两个工作表内容，最终却只能给出一组 outline/cell range，来源边界也随之失真。

`ChunkAssembler` 不是本次回并的来源。它在 `ChunkPacker` 之后分配 ID，并把正文里尚未包含的 Sheet/章节路径补到 `embedding_text`；本次没有修改它。但正因为前缀最后才加入，旧 `TableChunker` 只测量 key-value 正文会低估最终向量文本长度。

## 候选方案与选择理由

- **增大 TopK**：只能返回更多已经膨胀或重复的块，不能修正块内结构，还会增加上下文噪声和 rerank 成本，因此排除。
- **超过上限直接截断**：可能截掉业务字段、步骤或来源范围，使回答看到不完整事实，且无法处理重复块，因此排除。
- **按固定字符数切分**：会把表头与数据行、键与值、Sheet 与单元格范围拆开，虽然长度变短，但检索文本和引用语义会失真，因此排除。
- **结构感知归一化与分块**：在表格语义仍可见时处理合并区域、稀疏宽行、双文本预算和上游 piece 边界，能够同时修正根因并保留来源信息，因此采用该方案。

## 实施内容

### 1. 在归一化层按区域语义处理合并值

`ExcelTableNormalizer` 在展开合并值之前先记录源工作表哪些行原本有真实内容，然后采用分区规则：

- 表头区域继续横向展开，使每个子列保留完整父子表头；
- 数据区域在每一行只让合并区域的第一列携带一次值，消除横向重复；
- 纵向共享分类遇到其他列存在真实数据时仍逐行携带，不丢掉行语义；
- 只折叠“源行原本全空、由合并展开后又与上一行完全相同”的续行，用户主动录入的相同记录仍保留；
- 被折叠行覆盖的来源范围并入保留块，使 cell range 仍覆盖完整合并区域。

这种做法没有使用“正文相同就去重”的危险规则，而是同时检查原始单元格状态和合并关系。

### 2. 在表格分块层同时约束两份表格草稿文本

`TableChunker` 不再用三倍容忍值作为普通表格目标。每次尝试加入一行时，实际渲染候选表格 Markdown，并同时估算带 Sheet/章节路径的 embedding 文本；两份表格草稿都不超过 `maxChars=1024`，且行数不超过 `rowsPerChunk`，才继续合并。后续 `ChunkPacker` 仍可能为草稿附带标题或前导语，所以这里描述的是表格分块层的双预算，不把 1,024 写成整个通用装配链对所有原子内容的无条件硬保证。

如果单行仍然超限，则先跳过空列，再把非空的“列名 + 值”按预算贪心组合成多个窄表片段。每个片段仍是合法的小表，键和值不被截断，并保留同一个原始行 cell range。在这条行拆分路径中，只有单个键值对自身已经超过 1,024 时才保留原子超限例外，避免为满足字符数字面指标而截断业务事实。

### 3. 在通用打包层把结构边界变成硬约束

`ChunkPacker` 做了三项收口：

- 只要一节中存在上游 `piece`，就进入 piece-aware 打包，不再把表格片段重新合回；
- 前导语和小尾块只有在合并后仍不超过 `maxChars` 时才并入，不再使用三倍容忍值；
- 顶级 outline 不同就先落块，对 XLSX 即禁止跨 Sheet 合并。

这样保留了通用打包“减少低信息碎片、保留说明上下文”的价值，同时不覆盖表格 chunker 已经做出的结构决定。

| XLSX 块数 | 123 | 79 |

D1 的 XLSX 摄取总耗时由 C0 的 `11.3 s` 变为 `7.0 s`，其中 embedding 由 `10.3 s` 变为 `6.3 s`；这只是同机各一次运行，只记录现象，不作为稳定性能结论。

### 检索观察，不作单因果归因

D1 继续使用冻结 24 题。XLSX 六题的锚点 Hit@5（至少一个）保持 `100%`，Context Precision 相对 C-final 从 `27.9%` 变为 `39.3%`，Anchor Recall 从 `100%` 变为 `94.4%`。缺失锚点对应的正确块仍在索引中，但在三子问题请求的最终配额中没有入选；详细归因见[请求级检索预算与结构化重排](2026-08-13-request-level-retrieval-purity.md)。因此这里可以认定块形状和重复问题已消除，但不把单次 D1 写成稳定检索提升。

## 限制与停止状态

- 真实验证只覆盖一个企业工作簿；规则能够处理本文件中的多行表头、合并区域和稀疏宽行，但不能据此外推为任意复杂 Excel 支持。
- 在 `TableChunker` 的行拆分路径中，单个不可再拆的键值对若自身超过预算，仍保留为原子超限；通用打包也继续保留不可分非 piece 原子节的容忍语义。因此 1,024 是本规则型工作簿验证通过的目标预算，不是任意输入的绝对上限；新的工作簿形态必须先增加对应回归样本。
- D1 的检索变化同时包含请求级预算与结构化 rerank 改动，不能全部归因于 XLSX 分块。
- D1 暴露的请求级空位后来在 D2 中用固定改写和公平回填单独验证；机制能够填满 TopK，但质量 gate fail，开关保持默认关闭并停止本轮调参。该负结果不改变本次分块形状修复已经通过的结论。
