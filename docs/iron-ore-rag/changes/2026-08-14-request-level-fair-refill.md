## 改动目的

D1 已把最终上下文限制为请求级 TopK，但多子问题分别按配额截断后再全局去重时，重复块会留下空位；正确证据即使仍在候选池后部，也没有机会补入。本改动验证一个受开关保护的请求级选择器：在不提高 TopK、不改变知识库的前提下，利用现有候选填补空位，并用固定改写的配对回放决定是否默认启用。

## 问题如何发现

D1 中 `xlsx-hard-06` 的一个目标锚点未进入最终上下文，但人工追踪确认该内容仍在正确工作表的候选块中。源码追踪进一步发现：每个子问题先取固定配额前缀，随后才在请求层合并去重；跨题重复造成的空位既不会归还请求预算，也无法从已被截掉的候选尾部补位。这是“候选存在但额度没有用满”的选择问题，不是召回池不足。

该单次缺失只用于形成待验证假设。D2 后续固定回放显示，默认路径的三次 off 都已命中目标题，因此没有把这次 D1 现象追认成稳定收益。

## 根因

1. 最终配额在子问题层过早截断，候选尾部在请求级去重前已经丢失。
2. 跨子问题重复只会减少最终唯一块数，旧链路没有请求级回填阶段。
3. 不同 query 的 rerank 分数不保证可横向比较，不能安全地把全部候选按一个全局分数排序。
4. 在线改写会改变 `subIntents`，若直接重复问答，无法判断差异来自选择器还是改写漂移。

## 方案取舍

- 不增大 TopK：目标是正确使用既有 10 块额度，而不是扩大 Prompt。
- 不把不同子问题的 rerank 分数做全局排序：选择按子问题轮询，保持每题内部排序并避免假设跨 query 分数同尺度。
- 不在生产问答中直接做随机 A/B：增加固定回放接口，六轮复用完全相同的 24 组 `subIntents`，隔离在线改写。
- 先以默认关闭的特性开关交付：机制正确和质量改善是两个门槛，只有固定评测非退化才允许切换默认值。

## 具体改动与调用链

1. `MultiChannelRetrievalEngine` 返回受 `CandidatePoolLimitPostProcessor` 约束的候选池；候选池守卫位于元数据补全和 rerank 之前，控制回表及模型成本。
2. rerank 保留模型排序头部，并按统一 chunk 身份键追加未入选的融合尾部，使请求级选择仍有可回填候选。
3. `RequestLevelChunkSelector` 先轮询满足各子问题初始配额，再轮询剩余候选，直到请求级 TopK 填满或候选耗尽；默认 off 路径继续按旧版固定前缀选择。
4. `RetrievalContext.kbChunks` 成为 Prompt、来源、grounding 和评测共同读取的最终唯一块列表，避免“评测顺序”和“模型看到的顺序”不一致。
5. `RetrievalSelectionDiagnostics` 记录候选数、旧版固定前缀唯一数、相对旧版新增数、最终唯一数和空位数。`refillAdded` 是相对旧版固定前缀的总增量，包含配额内跳过重复后向后扫描所得，不等同于只统计第二轮回填。
6. `POST /rag/eval/replay`、回放脚本和重复比较器严格校验数据集、语料、setup、固定 `subIntents`、运行模式和诊断字段，防止只改报告标签而未切换后端。

## 工程结论

公平回填解决了 D1 已知的“候选充足但请求额度未用完”问题，但没有通过质量门槛。三次固定回放中，off 每次得到 `167` 个最终唯一块、`73` 个空位；on 每次得到 `240` 个、`0` 个空位，涉及的 `19/24` 题全部补满。on 各轮自身的旧版前缀唯一数为 `166～167`，因此相对增量为 `73～74`；同时 Hit@5、Context Precision 和路由纯度的中位数均下降。因此 `rag.search.request-level-refill-enabled` 保持 `false`，不把“填满 TopK”写成检索质量提升。

## 固定回放协议

D2 只比较公平回填开关，不重新改写、不重新入库：

1. 复用 `current-D1-chunk-purity` 的同一数据库和 `D1-chunk-and-purity/setup.json`；off/on 之间只重启后端并切换开关，不调用 `prepare_kb.py`。
2. 从 D1 检索报告读取 24 题已经产生的 `subIntents`，经 `POST /rag/eval/replay` 绕过在线改写模型。六份报告必须逐题精确一致。
3. 固定意图路由关闭、OCR 关闭、TopK=10、相同模型与检索配置，`concurrency=1`；回放接口绕过在线改写，但 embedding 和 rerank 服务仍在线。
4. off 和 on 各顺序运行三次，共 `6 × 24 = 144` 次检索；比较器要求重复编号恰为 1、2、3，并拒绝不兼容或有失败项的报告。

## 预先定义的质量门槛与配对校验修正

比较器先要求六份 24 题报告完整、固定 `subIntents` 精确一致、最终唯一数不超过 TopK，并要求 on 在候选足够时填满 TopK。质量门槛为：

- 目标题 `xlsx-hard-06` 在锁定数据集中的目标锚点（`reference_anchors[1]`）须由 off 缺失变为 on 命中，配对恢复至少 `2/3`，且该题 Anchor Recall 不下降；锚点原文不进入 Git；
- 总体 Anchor Recall 中位数至少增加 `0.01`，文档召回和 Hit@5（至少一个）不下降；
- Context Precision、路由纯度的中位数降幅分别不得超过 `0.02`；
- P95 延迟只记录，不参与放行。

D1 单次缺失形成了“off 缺失、on 恢复”的验证假设。六轮完成后，`d2f0b1f` 将恢复条件严格落实为同一次重复中的 off-miss/on-hit 配对，而不是看到 on 命中就算恢复；这是收紧校验，没有放宽任何质量阈值。实际 off 三次均命中，所以该条件明确失败，最终决策仍为 fail。

## 结果

下表均为三次重复中位数，质量指标只统计 21 道可回答/近领域题：

| 指标 | off | on | 结论 |
| --- | ---: | ---: | --- |
| 锚点 Hit@5（至少一个） | `0.905` | `0.762` | 下降 `0.143`，失败 |
| Anchor Recall | `0.841` | `0.865` | 增加 `0.024`，通过 |
| Context Precision | `0.254` | `0.200` | 下降 `0.054`，失败 |
| 文档召回 | `1.000` | `1.000` | 不下降，通过 |
| 路由纯度 | `0.915` | `0.811` | 下降 `0.104`，失败 |
| 检索 P95 | `6542 ms` | `9584 ms` | 仅记录 |

逐题中位数也不支持默认开启：Hit@5 为 `0/21` 改善、`3/21` 退化；Context Precision 为 `2/21` 改善、`15/21` 退化。机制诊断则稳定通过：off 三次均为 `167` 个最终唯一块和 `73` 个空位；on 三次均为 `240` 个最终唯一块和 `0` 个空位，`refillAdded` 中位数为 `73`（范围 `73～74`），每次均补满原先有候选却留空的 19 题，且无 TopK 越界。这个范围按 on 各轮自身的“旧版固定前缀唯一数”计算，不是 off 空位数发生矛盾，也不是纯第二轮操作计数。

修正后的目标题门槛同样失败：off 三次已经全部命中，on 的命中不能算作从 off 到 on 的配对恢复，恢复次数为 `0/3`。这也说明不能用一次 D1 的缺失锚点为后续机制预设收益。

最终 gate 为 `fail`，失败项是目标题配对恢复、总体 Hit@5 不回退、Context Precision 容差和路由纯度容差。填入更多低位候选扩大了上下文，但本轮证据没有证明这些新增块提高了前部命中或纯度。

## 改动效果、限制与停止决定

- 工程效果：候选池保留、请求级唯一选择、统一上下文和可核验诊断均按设计工作，19 道有空位的问题在每次 on 回放中都被补满。
- 质量效果：Anchor Recall 中位数提高，但 Hit@5、Context Precision 和路由纯度均超过允许退化，P95 也变差；不能上线，也不能写成质量提升。
- 评测限制：只有同一冻结数据库的 24 题、各三次重复；在线 embedding/rerank 仍可能波动，中位数不是通用结论。
- 停止决定：保持 `rag.search.request-level-refill-enabled=false`，不放宽门槛、不继续调参；D1 的请求级上限、去重、结构化 rerank 和 `should_split` 修复不受影响。
