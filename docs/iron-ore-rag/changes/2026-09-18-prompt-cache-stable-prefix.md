## 改动目的与发现过程

研究 Agent 每一轮都把整段历史重发给模型。供应商对命中缓存的输入按折扣计费，所以命中率直接决定输入成本。P7 回归的调用台账显示：B 模式 3,486 次调用、输入 3,803 万 token、命中 197 万（5.2%）；C 模式输入 4,427 万、命中 8,448（0.02%）。

排查分三步：读百炼上下文缓存文档；用协议测试夹具捕获 AgentScope 实际发出的请求字节；每次只改一处，重放到真实端点（`qwen3.7-flash`，共 34 次调用，逐次数字见 `eval/agentic-research/manifests/career-cache-probe-2026-09-18.json`）。

| 与上一请求的差别 | 命中 |
| --- | --- |
| 逐字节相同 | 4/4 命中（128 token 对齐，约不含最后一条消息） |
| 系统消息末尾加一行；工具不变，前 1,944 token 相同 | 0 |
| 工具换序；或把提醒移出系统消息 | 0 |
| 旧布局的下一步：只改提醒里的数字并追加历史 | 0 |
| 系统消息稳定、历史只追加（隐式缓存） | 逐步 4 次中 1 次 |
| 显式标记打在最新一条历史消息上 | 3/3 命中整段旧前缀（1949→2272→2394），写入只计增量 |
| AgentScope `cacheControl(true)` 生成的消息级标记 | 被忽略：0 写入、0 命中 |

## 根因

1. 每次调用把剩余次数、可引用证据 ID、阅读覆盖等易变提醒拼进第一条系统消息。实测系统消息（含工具定义）内任何改动都会让整个请求不命中，所以 C 为 0。
2. B 的 5.2% 是每次恰好 1280 token 的固定命中，等于 B 的工具 714 + 静态提示 632 + 模板 17 token 按 128 取整，是供应商对共享前缀的未公开行为；探针复现不了，C（926 + 1018）在 3,000 多次调用中从未出现，不能依赖。
3. 超过输入上限时每轮从最早的往返滑动裁剪，前缀每轮都变。
4. 首条用户消息用 `Map.of` 序列化，键序随 JVM 变化，跨进程重建（续跑、接管）得不到同一前缀。
5. 隐式缓存即使前缀稳定也不保证命中（文档明写，实测逐步 4 次中 1 次），只做稳定前缀不够。

## 方案取舍与选择理由

- **提醒放哪**：兼容端点对第二条 system 不可靠；拼进最后一条工具结果的副本也能保持前缀，但会篡改工具输出。选择每次调用在末尾临时追加一条 user 消息，不写入 Agent 记忆。
- **隐式还是显式**：隐式免费但不保证；显式写入按 125%、命中按 10% 计费，5 分钟有效且命中即续期。研究任务相邻调用间隔远小于 5 分钟，所以选显式，由 `research.explicit-prompt-cache` 控制，关闭后退回隐式，稳定前缀仍在。
- **标记位置**：系统消息（含工具）与提醒之前的最新一条历史。SDK 默认标最后一条，而最后一条是易变提醒，标在那里每次都要把整段历史按 125% 重写。每请求最多 4 个标记，这里用 2 个；系统消息上的标记让不同任务的首次调用共享静态前缀。
- **线路格式**：百炼只认内容块内的标记。不改 SDK，在 `HttpTransport` 装饰器里改写，并从流式 usage 读回 SDK 不解析的 `cache_creation_input_tokens`，否则台账会漏记写入成本。
- **裁剪**：参考“到阈值才整体压缩”的做法，把滑动裁剪改为阈值压缩：越线时一次压到上限的 60%，先把最早的工具结果换成保留 tool_call ID 与证据 ID 的存根（可用 `read_source` 重读），不够再整轮移除；水位只增不减，两次越线之间前缀不变。

## 实现与调用链

```text
ReActAgent 记忆：静态 sysPrompt + 只追加的历史
  -> BoundedResearchModel.stream
       compact(messages)：越线才压缩，水位存在实例里
       追加末尾临时 user 提醒（不写回记忆）
       研究调用设置 cacheControl(true)；最终生成不设
  -> OpenAIChatModel + PromptCacheFormatter：标记系统消息与倒数第二条
  -> PromptCacheTransport：消息级标记改写为内容块标记；读取流式 usage 的缓存写入量
  -> 百炼 /compatible-mode/v1/chat/completions
  -> ResearchBudget 台账：cachedTokens、cacheCreationTokens、cacheType、durationMs、firstTokenMs
```

主要代码：`bootstrap/src/main/java/com/nageoffer/ai/ragent/research/runtime/` 下的 `BoundedResearchModel`、`PromptCacheFormatter`、`PromptCacheTransport`、`ResearchModelFactory`、`ResearchAgentFactory`（首条消息按键排序）、`ResearchBudget`；报告 `eval/agentic-research/cache_report.py`（按调用序号给出命中率与延迟 P50/P95，折扣率为参数，用 P7 复算得 B 5.19%、C 0.02%，与台账一致）。

## 验证与效果

- 协议回归 Python 36/36、Java 220/220（基线 33/217）。新增用例：系统消息与工具逐字节稳定、每次只有末尾一条提醒（旧提醒不进记忆）、压缩后前缀稳定、压缩保持 tool_call 配对且最新一轮完整、上下文仍超限时抛 `MODEL_CONTEXT_BUDGET`、显式标记为内容块且写入量入账、失败调用也记耗时。
- 新代码实际生成的请求原样重放：Flash 逐步命中整段旧前缀 2272→2394（写入 122、144），Max 命中 2272（写入 122）。
- X1：同一 40 题（QASPER、MuSiQue 回归集各前 20 题），模式 B、C，全部角色 `qwen3.7-flash`，预算与 P7 相同；真实百炼与 SiliconFlow，按 before B → after B → after C → before C 顺序各跑一次；before 为 `65c99c7`、after 为 `73deab5`。汇总见 `eval/agentic-research/manifests/career-x1-2026-09-18.json`。

## 限制与停止状态

- 每臂只跑一次；每模式 40 题，答案 F1 护栏样本小。两组 embedding 失败率 4.6%—10.1%，条件相近但不相同。
- X1 没有触发压缩（输入都低于 2.8 万的估算上限），压缩只由协议测试覆盖。压缩改写早期消息后，若最新标记与系统消息之间超过 20 个内容块，需要重写一次整段前缀。
- C 模式几乎不委派（before 1/40、after 0/40），worker 的缓存行为没有被 X1 覆盖，只有协议测试。
- 计费是按文档折扣折算的输入 token 当量，不是账单，未核对发票。首 token 时延只有新台账有，无法做前后对比。
- 显式缓存依赖百炼的内容块语法；换供应商需要新的适配器或关闭开关。
- 提醒移到末尾后单任务调用数下降，是否影响作答质量要用更大样本复核。
