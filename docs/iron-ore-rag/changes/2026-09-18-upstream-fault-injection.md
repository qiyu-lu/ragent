## 改动目的与发现过程

第三方模型与 embedding 接口会超时、限流、无响应。历史事故：1200 个任务中 72 个超时，全部卡在检索工具 30.01 s——HTTP、检索通道、工具三层超时同为 30 s，失败被吞成“空结果”。此前的 R2 / S2（`6353eb7`、`0b39d31`、`8bbff9a`、`65c99c7`）已做分层截止时间、失败与无命中分离、可重试错误重试一次、取消传到 HTTP、连续失败停止补查。

缺的是两样东西：一个“在多大故障率下系统表现如何”的数字；一个不花接口费、可反复跑的上游替身（W2 的接管测试同样需要）。补数字时顺带复查了重试与熔断，发现两处缺口。

## 根因（两处补缺）

1. **重试同步**：embedding 重试固定等 300 ms，语料导入是固定的指数梯度。一次上游抖动里同时失败的调用会在同一时刻一起重试，形成二次冲击。
2. **研究路径不进熔断**：研究检索绑定了 `RequestOperation`，`ModelRoutingExecutor` 对这类失败在 `markFailure` 之前直接重抛，所以研究路径的 embedding 超时从不计入候选熔断；半开状态的探测名额在取消时也不归还。

## 方案取舍与选择理由

- **替身形态**：独立 Python 进程、OpenAI 兼容，而不是 Java 内的 mock。这样被测的是整条 HTTP 链路（连接、流式解析、超时、取消），并且旧提交也能接入——旧版本通过宽松绑定的环境变量 `AI_PROVIDERS_*_URL` 指向替身，不需要改旧代码。
- **确定性**：chat 端点按场景脚本吐出原生 tool_call 序列（检索、阅读、再检索、结束）；embedding 把文本哈希成确定性的 1536 维单位向量，查询与文档标题相同即必然命中第一。故障旋钮：无响应比例、429 / 5xx 比例、延迟、流中途断开；随机种子固定。
- **退避**：采用 AWS Builders' Library 的 equal jitter：上限的一半固定（重试不会立刻发出），一半随机（同批失败者错开）。重试预算不变：embedding 只重试一次，且剩余时间不足 1.5 s 时不重试；实际延迟写入重试事件。研究模型调用本来就用 Reactor 的抖动退避，不动。
- **熔断**：截止时间内的失败计入熔断；取消不是上游故障，只归还可能持有的半开名额。所有候选都被熔断跳过时快速失败为不可重试的 `CIRCUIT_OPEN`。embedding 不做跨模型降级——不同模型的向量不可比。
- **不再扩大范围**：没有做对冲请求、重试预算令牌桶、舱壁；X3 只注入 embedding 无响应这一种最贵的故障。

## 实现

- 模拟上游 `eval/agentic-research/stub_upstream.py`，一条命令启动 `scripts/stub-upstream.sh`；Spring profile `stub`（`application-stub.yaml`）只声明 `stub` 供应商与候选模型，不动主配置；固定小语料 `stub_corpus.py` 导入库 `research_corpus_stub`。
- 退避：`RequestOperation.jitteredDelay(retry, base, cap, random)`，embedding 客户端与 `ResearchCorpusCommand` 使用。
- 熔断：`ModelRoutingExecutor` 的失败计数与半开名额归还。
- 基准：`x3_upstream.py` 每格（版本 × 故障率）起独立的模拟上游与随机隔离库，用该版本编译产物里的 `ResearchRunCommand` 跑同一批脚本化任务；`scripts/career-x3.sh` 建临时工作树、编译、跑完全部格，中断后重跑只补缺失的格。

## 验证与效果

回归：Python 41/41、Java 225/225（W1 后 36/220），`zh_CN` 区域下同样全绿。

X3：50 个脚本化研究任务，B 模式，embedding 无响应率 0 / 10% / 30% / 50%，无响应的请求被替身挂住 90 s。治理前 `3381fa9`（P7：三层同为 30 s、不重试），治理后 `97edcc1`。**全部数字基于模拟上游，不是真实供应商。** 汇总见 `eval/agentic-research/manifests/career-x3-2026-09-18.json`。

| 无响应率 | 成功率 前 → 后 | 终态 完成/部分/失败 前 → 后 | P50 s 前 → 后 | P95 s 前 → 后 | 浪费的模型调用 前 → 后 |
| ---: | --- | --- | --- | --- | --- |
| 0% | 100% → 100% | 50/0/0 → 50/0/0 | 0.9 → 0.9 | 1.0 → 1.1 | 0 → 0 |
| 10% | 88% → 100% | 44/0/6 → 50/0/0 | 0.9 → 1.0 | 30.1 → 13.4 | 6 → 0 |
| 30% | 54% → 100% | 27/6/17 → 50/0/0 | 1.1 → 12.9 | 30.7 → 37.3 | 41 → 0 |
| 50% | 40% → 82% | 20/7/23 → 41/4/5 | 30.1 → 13.3 | 30.6 → 49.9 | 51 → 42 |

成功 = COMPLETED、有产物、且读到了每个被要求文档的证据；错误完成 = COMPLETED 但缺这些证据。两版在所有故障率下错误完成都是 0：旧版的失败形态是 30 s 处整体 `RESEARCH_TIMEOUT`（10% 时 6 个、30% 时 23 个、50% 时 30 个），不是“零证据却答完”。新版 50% 时的 9 个失败为 `RESEARCH_FAILED_WITHOUT_EVIDENCE` 4 个、无错误码的 PARTIAL 4 个、`NATIVE_FINISH_REQUIRED` 1 个，都是如实失败。

解读：

- 收益来自“单次 12 s 截止 + 一次抖动重试”：一次无响应只花 12 s 加退避，而不是把整个任务拖到 30 s 超时。代价是成功任务变慢——30% 时 P50 从 1.1 s 升到 12.9 s、P95 升到 37.3 s，因为旧版在这一档把慢任务直接判了失败，它的 P50 只统计了幸存者。
- 50% 时两次尝试都无响应的概率约 25%，重试救不回来，成功率 82%，浪费调用 42 次。
- 新版 embedding 请求数随故障率上升（75 → 83 → 117 → 156）：重试带来的额外上游负载，是用负载换成功率。

## 限制与停止状态

- 只注入了 embedding 无响应；429 / 5xx、延迟分布、流中断和 chat 端点故障有旋钮但没跑基准。
- 每格一次运行、固定种子；没有做多种子的方差。
- 评测命令直连 `SiliconFlowEmbeddingClient`，不经 `ModelRoutingExecutor`，熔断补缺 `77ca3ae` 不在 X3 数字里，只由单测覆盖。
- 替身的请求日志在请求结束时才写，格子结束时仍被挂住的请求不会出现，所以无响应次数以 Java 侧 embedding 台账为准。
- 旧版在 30 s 处整体超时，是 P7 的配置决定的；这里比较的是“治理前的实际行为”，不是同一超时下的纯重试收益。

## 数据兼容与回滚
