## 改动目的、发现与根因

标准 PDF 入库时丢数值参数，数值类问题因此答不出来。评测库里《铁矿石 硅含量的测定 重量法》（GB/T 6730.10—2014）的切片是"温度控制在 ,放置 。"，原文是"温度控制在 400 ℃±20 ℃，放置 1min"；同一份文档里条款号也丢了点（"7411"）。

阶段 1 先建了 141 条数值事实清单（取自原文，扫描件人工读图），在基线 `S1-base`（`59b858c`，默认解析参数 `pipeline`、`is_ocr=false`、公式识别开）的入库切片上逐条查找：原文匹配 98/141（69.5%）；硅含量 2/24、取样 3/21，其余 5 份 14/15～22/22。严格空槽（"温度控制在 ,"一类，去掉"加热，"这种动词误报）0.91 处/千字。

根因由阶段 1 的解析定位实验确定（直接调 MinerU v4 API，同参数复跑两次 `full.md` 哈希一致）：

- **公式识别吃数字（H1）不成立**：硅含量关掉公式识别，事实 5/24、空槽 84 处，和开着差不多；取样 3/21。
- **换 `vlm` 模型不成立**：硅含量 5/24、空槽 51。
- **自己的解包或分块丢内容（H3）排除**：硅含量 `full.md` 546 个数字、入库切片 513；全铁 1393 / 1349。丢失发生在 MinerU 的输出里。
- **全角数字不是问题**：全铁（全角数字）22/24。
- **成立的是 H4**：2014 版两份 GB/T 的文字层完好（`pdftotext` 抽得出 1,252 / 7,991 个数字），MinerU 的文本抽取丢掉"数字 + 单位"这类字形。强开 `is_ocr=true` 后，硅含量事实 2→17/24（LaTeX 去壳后 21）、数字 546→1149、空槽 82→13；取样 3→17/21、空槽 83→8。
- **扫描件不能一刀切地强开 OCR**：硫铁矿（8 页扫描件）默认参数时 MinerU 已自动 OCR，14/15；强开 OCR 反而 11/15。

所以问题出在少数文档上，修法是"对这些文档换解析参数"。另外两类噪声顺带处理：切片里混有出版社水印、购买方印章行和页眉页脚（基线噪声行 52 行）；入库没有任何 NFKC 或全角半角归一化，全靠 MinerU 代劳。

## 方案取舍与选择理由

- **按文档判定，只对不合格的文档换参数**：借鉴 RAGFlow 的逐框质检（框内乱码 ≥ 50% 时只对该框 OCR，`parser_ocr.go:624-636`），粒度放大到文档。没有对所有文档强开 OCR：扫描件强开反而变差，OCR 也更慢。
- **预判 + 审计 + 回退一次**：PDFBox 抽文字层，按每页字符数和乱码比例分成扫描件 / 坏字体 / 文字层可用。坏字体首次就开 OCR，其余用默认参数；解析结果对文字层比两个信号，不合格就把 OCR 开关取反重解析一次，保留得分高的那次。两次都不合格只标"需人工复核"，不拒收，也不再重试。
- **审计信号与阈值**：严格空槽密度和数字保留率。保留率的分母是去掉多数页面重复行和页码行的文字层（不去掉，76 页的取样标准页眉会多出约 1,600 个数字），分子剥掉 HTML 标签（表格的 `colspan` 数字不算）。在 6 份 PDF 的探针结果上标定：坏解析的严格空槽 1.3～9.2 处/千字（原写 0.86～7.2，审查时按探针复算更正）、好解析 0～0.10，阈值取 0.3；保留率坏 0.40～0.70、好 ≥ 0.98，取中点 0.85。扫描件没有可用的文字层分母，只看空槽。
- **公式开关不动**：H1 不成立，改它没有依据。`model_version` 做成可配置、默认不发；阶段 2 评测实例固定为 `pipeline`，免得服务端默认值变化让结果漂移。
- **归一化放在一个函数里**（审查后分成比对形态与入库形态两种，见文末）：解析之后、分块之前对每个 Block 做一次：数值型行内公式去壳（`$400 \pm 20 ^ { \circ } \mathrm { C }$` → `400±20°C`）、度数符号、NFKC、破折号、零宽字符、国标小数分组空格（`0.000 1`）、行内空白。带上下标、分式的公式保留原样，去壳会丢结构。与评测侧 `evalkit.normalize` 共用 `eval/kq/normalization_cases.json` 的 15 条用例；阶段 3 的全文索引和查询也用它。
- **去页面家具用频次规则**：家具行由 PDF 文字层定义（出现在多数页面的整行），解析结果里出现满 3 次才删。标准号形态的页眉保留第一次出现（封面上的标准号是正文）。不按"水印""东北大学"这类字面写规则，换一批文档就失效。
- **条款号丢点不修**（计划 §5.2）：OCR 解析后它随参数恢复了一部分，剩下的不写猜测性规则。

## 实现与调用链

- 摄取内核 `DefaultIngestionKernel` 第 ② 步调用 `ParseQualityStage.run`：PDF 只抽一次文字层（`PdfTextLayerAnalyzer`，PDFBox），闸门、清洗和元数据抽取共用。
- `ParseQualityAuditor`：预判 → 经 `MinerUDocumentParser` 解析（解析参数可按次覆盖，`MinerUClient` 补发 `model_version`）→ `ParseTextMetrics` 算严格空槽与保留率 → 不合格时 OCR 取反重解析一次。审计结论（每次尝试的参数、空槽、保留率、失败原因、选中哪次）写进 `t_knowledge_document.doc_metadata.parseAudit`，来源面板对 `RECOVERED` / `NEEDS_REVIEW` 显示"解析复核"。
- `ParsedDocumentNormalizer`：先 `RepeatedLineFilter` 去家具，再 `IngestionTextNormalizer.normalize` 逐 Block 归一化；代码块原样保留，图片只动说明文字。
- 配置：`rag.ingestion.parse-quality.*`（阈值见上）、`rag.ingestion.normalize.*`、`mineru.model-version`（默认留空）。两个 `enabled` 的 Java 字段默认是 false，`application.yaml` 自收尾起写成 true。
- 测试：`ParseQualityAuditorTest`、`KqLocalCorpusCalibrationTest`（本机有 `local-data` 时复现 8 组判定，没有时跳过）、`IngestionTextNormalizerTest` 与 `ParsedDocumentNormalizerTest`（读共享用例）、`MinerUClientRequestTest`。

## 限制与停止状态

- **三项在同一臂里一起打开**，检索层的提升分不到闸门、归一化、去家具各自头上。解析层可以按文档拆：覆盖率的提升几乎都来自两份被 OCR 救回的 GB/T，归一化只贡献了全铁的 1 条。
- **调参集混淆题变差（只报告）**：`con-07`、`con-11` 的锚点块在 S2 里内容没变，却掉出了向量召回的前 20（S1 时它们的余弦只比池底高一点）。归一化改了调研表几千处全角标点（79 块 → 77 块），调研表的块在池里变多。测试集的混淆题反而变好；两边各 7～8 题，说明不了方向。
- **阈值在同一批文档上标定**：6 份 PDF 都在调参集里，阈值没有在集外文档上验证过。坏字体分支（首次就开 OCR）在这 7 份里没有被触发，只有单元测试覆盖。
- **残留噪声**：全铁的页眉在 PDFBox 文字层里是乱码"犌犅/犜"，对不上，删不掉（多留 2 行）；硫铁矿的水印在解析结果里只剩 1～2 次，不够 3 次，保留。NFKC 会把上标 ² 变成 2（MinerU 多用 LaTeX 表示上标，影响小）。审查发现这句对不经过 MinerU 的调研表不成立：S2 库里 `Fe²⁺` 成了 `Fe2+`，全角标点全部消失；已改，见文末。
- **还差 10 条事实**（原文匹配）：取样 3 条、硅含量 5 条（其中 2 条去掉 LaTeX 外壳后能匹配）、全铁 1 条、硫铁矿 1 条。条款号丢点没有处理。
- **MinerU 结果会漂移**：阶段 1 同参数两次 `full.md` 哈希一致，但服务端模型更新后不保证。阶段 2 没有重复入库。
- **收尾时改为默认开启**（2026-10-10，用户确认）：`application.yaml` 里 `rag.ingestion.parse-quality.enabled` 与 `rag.ingestion.normalize.enabled` 改为 true。代价是每份 PDF 多一次 PDFBox 文字层审计，不合格的文档多解析一次（本语料 6 份里 2 份）；已入库的文档在重新分块前不变。评测用的 S1 配置样例显式写 false，保留基线条件。

## 审查后的修正（2026-10-10 晚）

收尾后对整个分支做了一次只读审查（入库、检索、治理、评测四块）。闸门与归一化默认开启的路径上有三类问题，这次都改了，阈值没动。

**发现**

- **重解析失败会让整篇文档入库失败**：重解析本身抛异常（MinerU 排队超时、OCR 超时）时，异常一路上抛，首次已经成功的解析结果也丢了，文档直接标为失败。闸门关闭时这份文档本来能入库，与上文"两次都不合格只标需人工复核，不拒收"相反。
- **审计信号有误报**，只是这 7 份资料碰巧没触发：
  - 空槽正则 `约\s*[,，。.]` 会命中"修约。"，硅含量 OCR 那次唯一的一处空槽（0.104 处/千字）就是它；`在\s*[,，。.]` 也会命中"存在，""所在。"。
  - 阈值只看密度。两三千字的短标准（YS/T 两份、硫铁矿）一处误报就超过 0.3 处/千字，扫描件会因此被强开 OCR，而阶段 1 的实验显示扫描件强开 OCR 更差。
  - 两次都不合格时，`better()` 先比空槽密度，保留率只在密度完全相等时才看。
  - 剥 HTML 标签的 `<[^>]+>` 会把表格里"< 15000"这类正文一直吞到下一个右尖括号。取样那份 OCR 结果被吞 11 段、320 个数字，保留率记成 0.981，实际是 1.03。
  - 生产默认开着图片描述，视觉模型的转写混进了审计文本，而标定与评测时这一项都关着。回退那次解析还会再上传全部图片、再调一遍视觉模型，落选那次的图片成了没有任何地方引用的对象。
- **归一化改写的是入库正文，而且对所有解析器都生效**：
  - S2 库里的调研表（POI 解析的 XLSX，不经过 MinerU）原有 16 块带上标、79 块带中文标点，全部被拍平，例如"二价铁（Fe²+）……，占干矿总重量的百分比"变成"二价铁(Fe2+)……,占干矿总重量的百分比"。
  - "10⁻³"变成"10-3"，"①"变成"1"，意思已经变了。
  - 同一段里任意两个 `$` 会被当成公式：货币符号被删掉；两个 `$` 跨行时，连换行也一起吞掉。

**改法**

- **解析分两步**：`MinerUDocumentParser` 实现新的 `StagedDocumentParser`，拆成取结果（`fetch`，持有 MinerU 许可）和展开两步。展开分 `preview`（只展开正文）和 `complete`（上传图片并图生文）。
  - 闸门用 `preview` 审计候选结果，只对选中的那次调 `complete`；图生文的描述也不再计入审计文本。
  - 普通解析照旧是一次 `fetch` 加一次 `complete`，许可现在只覆盖 MinerU 侧的工作。
- **重解析失败不拒收**：重解析失败（线程未被中断时）保留首次结果，在尝试记录里写 `parseError`，判"需人工复核"。首次解析失败照旧抛出，与闸门关闭时一样。
- **审计**：
  - 空槽正则排除"修约""存在""所在"一类复合词。
  - 空槽要同时满足密度超过 0.3 处/千字、且至少 3 处（新配置 `min-strict-slots`）才算不合格。
  - HTML 标签只认 MinerU 用到的标签名。
  - 择优顺序改为：解析成功 → 合格 → 不合格项少 → 有一方保留率不达标时比保留率 → 空槽密度，打平留首次。
  - 评测侧的指标（`evalkit`，metric v2）不改，已发表的数字可以复现。
- **归一化分成两种形态**：
  - 入库形态（`normalizeForStorage`）只做不改意思的换写：全角数字、字母与 ％＋－．／＜＝＞ 转半角；㎎ 一类单位字符、微符号、拉丁连字、康熙部首与兼容汉字展开；减号统一；删零宽字符；拼回小数分组；压缩空白。中文标点、上下标、带圈数字、中文破折号与标准号里的"—"原样保留。
  - 公式去壳只对 MinerU 的 markdown 做。跨行、夹着汉字、HTML 标签或英文单词、超过 120 个字符的，都不当公式处理。
  - 比对形态（`normalize`）仍做整体 NFKC，全文索引与查询、元数据抽取、页面家具比对、评测契约用它。
  - `doc_metadata.normalization.version` 记为 2；1 是此前评测用的整体 NFKC。

**已验证**

- **单元测试**：闸门 17 个，覆盖重解析失败保留首次、线程中断不吞、短文档单处空槽不判不合格、复合词、正文里的"<"、描述不计入、择优顺序；解包器 2 个（预览不上传、不描述）；归一化 21 + 7 个。
- **回归**：p7（Python 53/53、Java 13 + 212）与 p2 通过，`eval/kq/tests` 70 个通过。
- **标定复核**：`KqLocalCorpusCalibrationTest` 在本机 6 份 PDF 的 8 组探针上判定不变。坏解析空槽 1.6～9.2 处/千字、保留率 0.40～0.67；好解析空槽 0（硅含量 OCR 那次的"修约。"不再计入），保留率 1.01～1.03。
