### 3.1 为什么选择 HotpotQA

官方数据提供问题、答案、候选段落以及句级 `supporting_facts`，适合判断“必要证据是否被选择保留”。采用 distractor 模式中给定的候选段落，保留标题与句子序号映射，候选整段作为第一版选择单位。

这属于固定候选下的选择与回答实验：支持文档本来就在提供的上下文中，不能称为全库召回提升或 HotpotQA 官方全量成绩。多跳推理也不等同于显式多要点问题，因此结果要按 bridge/comparison 分组，中文集另行验证业务问题覆盖。

实施规则：

1. 从官方 train 中选 200 题作开发、官方 dev 中选 400 题作本地冻结测试；使用种子 `20260905`，记录源版本、SHA-256、ID、题型和筛选理由。先验证实际字段、许可和文件来源。
2. 按原有 bridge/comparison 构成分层随机抽样；不按算法是否失败挑选测试题。公开 dev 只能称本地留出测试，不能称秘密测试或消除了模型预训练污染。
3. 对完全重复问题及支持文档重叠作检查。优先移除跨开发/测试支持文档重叠的开发题并按既定随机顺序补齐；若做不到足额，报告实际规模和重叠率，不静默改为逐题随机切分。
4. 保留原英文，不先翻译成中文，不向候选加入答案、gold 支持标记或标准推理链。
5. 主 token 预算预设 1024，敏感性预算 512/2048，块数上限 10；统计各预算下全部候选能否放下。预算不构成瓶颈的题也保留，按全部候选是否可容纳分层报告，不为了制造提升删除它们。
6. 原始顺序不能直接作为唯一排序基线，须基于问题重排。同一输入、顺序和评分快照用于所有选择器。
7. 第一版不人为增加重复段落或删除证据。以后如做此类压力测试，必须单列 constructed 标签，不并入自然数据主结果。

### 3.2 中文业务集如何扩充

目标新增 12–20 份独立来源文档，涵盖 SOP、设备手册、技术规范、记录说明及表格材料，另加 3–5 份近领域或其他业务干扰文档。可使用企业 IT/运维类公开手册增加通用性，报告中与工业材料分组，不能统称真实企业私有数据。

旧工作簿的多 Sheet 不算多份独立材料。旧文档及人工构造版本留在回归/开发侧；真实版本对作为同一来源组划分。测试材料可以入检索库，但测试问题、答案和 gold 不进入索引、提示词或运行时选择特征。

120 题的目标构成：

- 单要点直接问答 24；
- 同文档多要点、跨段落问答 36；
- 跨文档或跨表格综合问答 24；
- 同名概念、单位、适用范围或真实版本混淆 18；
- 资料缺失、不可回答 18。

按文档来源组划分 40/80，再在组内编题，类型数量允许为来源隔离作少量调整，提前记录。问题草稿可由模型辅助生成，但事实、证据位置和不可回答判断要经人工复核；未复核题只用于冒烟。执行代理不能代签人工完成。

每题保存：`id/source/split/group_id/language/question/answerable/task_type/expected_facts/forbidden_claims/evidence_requirements`。证据位置至少包含文档 ID、版本和句号或页/Sheet/单元格定位。

证据需求表达为：所有必需要点均须满足，每个要点可以有多组等价支持方案，每组方案可以需要多个片段。这样不会把重复表述强制当成多条必需证据。所有匹配均绑定来源及定位，不能跨版本靠短语碰巧相同判定命中。

从官方机构、文档所有者或项目官方文档取得材料，保存许可、获取日期、版本和哈希；公开可下载不自动等于可再分发。原文和答案保留在忽略目录，仅提交下载脚本、来源清单、schema 和合规示例。

### 3.3 其他公开数据集的定位

- MultiHop-RAG：具有知识库、跨文档问题和证据，可作为第二轮真实全库检索扩展；第一轮不与 HotpotQA 同时引入，避免扩大适配范围。
- RAGBench：更适合后续回答忠实性/证据评估扩展；其已有回答上的标注不能直接作为我们重新生成回答的标签。
- LongBench：可用于后续中文或长上下文补充；不是所有子任务都带本方案需要的证据定位，不作为第一轮覆盖率主集。

## 6. 阶段 P2：实现简单基线，再实现覆盖选择

### 6.1 对照矩阵

| 标签 | 策略 | 比较目的 |
| --- | --- | --- |
| CS-L | 当前真实 legacy 配置和路径 | 整体产品行为基线，保留原本预算与成本 |
| CS-P | 同候选池中的旧分配/前缀策略，加统一预算守卫 | 隔离候选池变化后的旧选择机制 |
| CS-R | 全部候选相对原问题统一重排，再按预算选择 | 检查简单全局重排是否足够 |
| CS-M | 原问题相关性 + MMR 去重复 | 强简单基线 |
| CS-C | 原问题相关性 + 要点新增覆盖 + 冗余控制 | 本轮候选策略 |
| CS-C-no-cover / no-diversity | 分别移除覆盖或冗余项 | 归因消融 |

CS-P/R/M/C 使用相同冻结候选池、块上限和 token 上限；CS-L 是真实旧配置，必须另列，不能将池规模/预算变化产生的收益全归给选择算法。CS-M 与 no-cover 尽量共用实现；等价时只运行一次并说明映射。

### 6.2 第一版机制

1. 优先复用现有问题拆分。仅能从原问题提取显式信息需求，禁止利用 gold 推理链；最多 4 个要点，无法可靠拆分则以原问题作为一个要点。首轮不增加生成式规划器。
2. 对同一候选池计算原问题统一重排分数。对每个要点分别获得完整候选评分矩阵；不可直接混用不同子问题的旧 raw score。评分接口的次数及输入量计入成本。
3. 将每个要点行内分数转成固定的排名权重或开发集确定的归一化权重，作为覆盖代理，不称为支持概率。其与人工支持标签的差异另做诊断。
4. 用固定模型的候选文本向量余弦计算冗余（必要时截断负相似度），CS-M/C 共用同一矩阵；额外 embedding 及缓存构建成本单列。
5. 候选集合 S 的目标使用 `F(S)=相关性累计 + λ×各要点最大支持代理之和 − μ×冗余惩罚`。要点首次得到强支持时收益大，重复覆盖同一要点的收益递减。
6. 贪心按 `新增 F / 新增渲染 token` 选择。块超预算则跳过并继续检查可容纳项；没有正向增益或预算耗尽则停止，不强制填满。明确并列按稳定块 ID 决定。
7. 第一版保持选择单位为完整块，不生成摘要、不拼造证据。数字、单位、版本差异不能只因语义相似被当成完全重复；这种错误列入专门检查集。

λ/μ 在开发集的至多 12 组预先列出的组合中选择，MMR 给相同量级调参机会。所有臂共享评分和候选缓存，但报告各自部署所需的真实调用数。若覆盖收益只来自额外评分，须明确成本；不得把离线缓存时间当作在线延迟。

主业务 token 预算 2048，敏感性 1024/4096，块上限 10。公共预算见 3.1。token 指实际序列化的证据正文、标题、来源标记及包装文本开销；完整 prompt 还须预留系统指令、问题和输出空间。选定可复现 tokenizer；若与服务端不一致，注明本地估算与服务 usage 的差异，不能把字符数叫 token。

机制主比较的最终证据统一按原问题重排顺序渲染，让选择顺序不混入位置效应；多要点归因留在元数据中。真实 legacy 保持原渲染方式，单列整体差异。

### 6.3 Java 接入

新增可替换选择接口，输入原问题/预测要点/候选/特征/预算，输出有序唯一块、要点归因、选择理由与诊断。优先在 `RetrievalEngine` 的候选汇合后、格式化前接入。

新模式默认 legacy；禁止借旧 `request-level-refill-enabled` 的开关语义开启覆盖策略。既有来源、引用、权限/知识库 scope 和 SSE 行为保持正确。超时/无效评分可回落旧策略，但必须标记；正式实验不能把降级请求冒充新策略成功。

必要测试：互补证据与重复挤占、单要点、零候选、预算装不下、重叠来源去重、单块多要点归因、确定性并列、缺失评分、版本与数字差异、来源顺序与实际 prompt 一致、legacy 默认行为。运行相关既有检索与重排测试。

## 7. 阶段 P3：开发实验与冻结测试

### 指标定义

- 主指标：完整证据覆盖率。可回答题中，最终集合满足全部必需证据需求的比例；HotpotQA 为保留全部标注支持句。匹配必须绑定文档/句 ID，不只检查答案短语。
- 候选完整覆盖率：完整证据是否已在候选池中，显示召回天花板。
- 条件完整覆盖率：在候选完整且预算可容纳的题中，选择后完整覆盖的比例。它是诊断指标，不能替代包含所有题的主指标。
- 证据召回率、冗余、上下文 token、最终块数、选择耗时、总检索 P50/P95、额外调用数和费用。
- 业务回答：严格通过率、可回答题误拒答率、不可回答题正确拒答率、无依据断言率、来源定位正确率。
- 公共回答：答案 EM/F1，并报告“答案正确且支持证据完整”的联合通过率；仅短答案答对不证明使用了证据。

不可回答题不进入正例覆盖率分母，单独计分；空 gold 不自动记作覆盖成功。请求失败保留在总体结果中，另外报告成功请求指标，不能静默删掉。

开发阶段先完成 CS-P/R/M/C 回放与消融，选出最强简单基线；参数、预算、样本 ID、评分提示和判定协议全部锁定后才运行冻结测试。测试题可由脚本处理，但调参阶段不得根据测试逐题输出修改策略。

建议推进门槛（工程决策门槛，不是论文通用标准）：

- 开发集 CS-C 相比最强简单基线，完整证据覆盖率至少提高 5 个百分点；同时在固定预算下没有明显单要点退化，才进入完整端到端评估。
- 冻结测试分别报告公共/中文效果，配对改进与退化数，按来源组进行配对 bootstrap 区间估计；HotpotQA 对共享支持文档聚类，报告有效组数。置信区间跨 0 时称趋势或不确定，不能称显著提升。
- 业务端到端严格通过率需要有正向证据；仅公共集提升只支持公共机制结论。单要点或不可回答题退化超过 5 个百分点即保留默认关闭并分析。
- 真实请求 P95 目标不超过最强简单基线 1.25 倍；比较同硬件、同并发、同模型、同时间段和同缓存状态。超过时如实报告质量/延迟取舍，不自动放宽。

中文 80 道测试不足以精确验证小幅收益，分组更小。报告题数、原始计数和区间；若证据不足，结论就是尚不确定。后续增加未见材料和样本须作为新一轮，不追加到已看结果的测试里再反复挑优。

## 8. 阶段 P4：端到端与调用预算

先用开发侧固定小批次验证模型兼容与费用，再冻结执行规模。无需为下载公开数据、离线程序、普通代码修改或本地测试单独等待批准。

完整测试参考规模：公共 400 + 中文 80，共 480 题；真实 legacy、最强简单基线、CS-C 三臂各生成一次，共 1440 条回答。另预先固定 60 题分层稳定性子集，每臂追加两次，共增加 360 条；总计 1800 条回答，不含开发调试、重排、embedding 和评分调用。若三个标签实际同实现，不重复计费。

先复用现有模型，但执行时核查准确模型 ID/服务端可用性，不保证历史在线版本仍相同。统一生成提示、解码参数和输出额度；新旧臂交错执行并记录时间，不能拿旧日期回答比较新策略。

执行前产出 `run-budget.md`：列出配置中实际服务商、发送的数据类别、预计调用数、预计 token、按当时价格估算的费用、硬上限、重试上限和缓存策略。已有授权范围可复用；未知付费额度或新的非公开材料上传不能靠本计划推定授权。此时只就具体缺口向用户确认，其他离线工作继续。不要打印密钥。

若 CS-C 未通过开发门槛，不运行全量三臂生成；完成基线和负结果报告。预算有限时在冻结测试前缩减规模并记录，不能根据已看到的测试成绩选择只跑有利子集。

中文测试回答按匿名打乱臂进行人工复核；模型评分可辅助定位，但不替代未完成的人工验收。公共 EM/F1 自动计分，人工抽查支持句映射和至少 30 条有争议/不一致样本，说明抽查性质。

## 9. 最终交付与结束条件

交付：独立选择模块及必要测试；数据适配/验证/回放/报告脚本；来源与划分清单；真实可运行 RUNBOOK；开发冻结记录；正负结果和成本表；至少 3 个成功案例及 3 个失败案例（若不足则报实际数）；可由新会话恢复的状态文件。

建议文件：

- `eval/context-selection/README.md`、`RUNBOOK.md`、新 schema 与测试；
- `docs/iron-ore-rag/changes/<日期>-context-selection.md`；
- `docs/iron-ore-rag/context-selection-status.md`：当前阶段、完成项、最近命令/结果、产物位置、待人工事项和下一步；
- `local-data/eval/context-selection/`：原始数据、候选/评分快照、模型响应和人工表。

检查 Markdown 链接、数据忽略规则与 `git diff --check`。计划阶段不运行旧数据入库、恢复数据库或任何修改历史证据的工具。

结束条件包括：完整验证支持开启；验证无收益而保留关闭；或已完成自动化工作但明确缺少人工标签/实际模型预算等外部输入。工具写完不等于评测完成，未运行不记 PASS。

简历按结果分层：机制覆盖提升、端到端回答提升、成本降低分别陈述。公共子集成绩和中文业务成绩分开；没有端到端收益时只写实际验证的覆盖/成本结果，不包装为准确率提升，也不声称首次提出算法。

## 10. 公开来源（2026-09-05 核查）

- [HotpotQA 官方主页](https://hotpotqa.github.io/) 与 [官方代码及数据说明](https://github.com/hotpotqa/hotpot)：问题、候选与支持事实协议；官方仓库说明数据采用 CC BY-SA 4.0。

- [Sufficient Context](https://arxiv.org/abs/2411.06037)：区分证据不足和模型未利用已有证据，为诊断提供参考；本轮不开发其充分性模型。
