# 面试流程笔记：工业知识问答与计划编制

> 阅读口径：文档处理、普通问答、版本比较和统一研究工作流均按当前实现讲解。深度研究与计划生成已经共用原生工具、独立 worker 和最终产物生成；送检、审批模拟与 ROS 已退役。机制测试、真实 API 结果和历史检索实验分别说明，不能互相替代。

## 项目介绍：自我介绍时可以这样讲

我基于开源 Ragent 做了一个工业知识问答与计划草案项目，面向需要查阅设备台账、操作规程和检测要求的业务人员。用户既可以查询某个具体要求，也可以围绕一项工作，把分散在资料中的准备条件、操作步骤和注意事项整理成一份可以人工核对的计划。

这里主要有两类问题。第一类是资料到答案：资料在 Excel、PDF 等文件里，表格中的设备、指标和要求存在对应关系，查到一个数值还要知道它属于哪个对象、来自哪个版本。第二类是资料到计划：回答一个问题时找到的片段，未必足以覆盖一份计划需要的条件、步骤和设备；用户也可能没有说清检测项目，或者在看到草稿后改变要求，需要继续补查和修订。

文档侧，我改进了工业表格的解析、分块和检索结果组织，保留表头与数据的对应关系，以及工作表、单元格位置和版本信息，让回答可以回到原文核对。研究侧，用户选择深度研究或计划生成后，系统保存目标和范围，Agent 按实际证据决定检索、补读、追问或结束；能独立处理的比较维度可以委派给 worker，最后由同一个生成阶段形成报告或计划草稿。

例如用户要求按两份资料整理实验准备计划，第一次检索只找到方法介绍，Agent 可以继续查实验条件；必要用户条件缺失时暂停并追问，资料没有披露的设备或参数保留缺口。用户回复后沿原范围继续，最终草稿可以回查实际阅读过的来源。这条路径已经实现，具体模型是否补齐内容要看逐例结果；当前仍是本地原型，产物交给人核对。

## 如果被追问：为什么需要这个 Agent

计划编制需要把多个方面的信息凑齐，而下一次查询有时取决于刚找到的内容。例如先查到某个检测方法，才能继续查它的设备要求；发现资料适用的实验室不同，需要先向用户确认对象；用户改变目标后，原先的一部分依据可能不再适用。Agent 的职责是根据这些观察决定继续检索、追问还是形成草稿，让计划可以在多轮交互中逐步完善。

RAG 负责找到有来源的资料，Agent 负责组织补查过程，程序负责工具范围、结构校验、状态保存和取消规则。一次检索已经足够时就直接生成草稿，不要求所有任务都多轮调用。输入固定、分支明确的业务仍可使用固定流程；这里选择 Agent，针对的是计划形成过程中资料缺口和用户要求会变化的部分。

P7 在固定语料、问题、模型和检索设置下比较一次检索、单研究者和主 Agent 按需委派，并单独核对比较报告与计划的原文。额外调用是否减少遗漏、引用是否支持结论以及成本是否值得，都要由结果判断。不能把流程完成或引用编号合法写成计划质量提升，也不能把英文公开集指标改名为工业准确率。

### 高频追问 01：什么时候用 RAG，什么时候直接给完整文档，什么时候考虑微调？

资料少、长度可控且查询范围明确时，我会先把完整文档交给模型作为简单基线；资料较多、版本经常变化，并且需要定位出处时，再用 RAG 缩小证据范围。微调更适合有足够样例时调整任务行为、表达风格或输出习惯，不能代替资料更新和来源管理。Agent 则放在需要根据查询结果继续补查、追问和修订的任务中。

当前项目做的是文档入库、RAG 问答和任务原型，没有训练或微调模型，也没有完成与长上下文方案的系统对照。因此我的选型依据是当前资料形态和可追溯要求；如果要进一步证明选型收益，我会用同一批问题比较完整文档输入、普通 RAG 和按需补查，分别看正确性、遗漏、耗时与成本。

## 后面的流程笔记怎么读

阅读时先记住两条主线：一条是“文档上传后变成可检索资料，用户提问后得到带来源的回答”；另一条是“用户在对话中提出计划目标，Agent 按缺口补查和追问，形成带依据的计划草稿”。普通问答提供查询入口，计划任务负责持续保存目标和进度，两者共用检索能力。用户可以直接提出计划目标，也可以在已有问答之后继续要求生成计划。

第一至七节说明现有文档与普通问答流程，第八至十节说明已经实现的研究、委派和最终产物路径。登录、基础问答和模型适配等沿用上游能力；本分支的改动包括工业表格处理、来源与版本记录、检索组织和统一研究工作流。下文把输入、判断、状态变化和后续处理放在同一条流程中理解。

各节后的 22 个高频追问用于口述复习。回答中的“当前实现”和“已有改动”对应代码或记录；“我会”表示建议处理方案。遇到故障类问题，按“观察什么现象 → 用什么证据定位 → 怎样处理 → 为什么这样选”的顺序回答，指标同时说明统计对象和边界。

## 一、用户登录，再带凭证访问业务

用户先提交账号和密码。登录接口不要求已有登录状态，服务检查输入是否为空，再按账号查询用户；账号不存在或者密码不匹配，都返回账号或密码错误，不建立会话。匹配成功后，交给 Sa-Token 建立登录状态，返回 token 和基本用户信息，本次登录请求结束。

前端保存 token，后续请求把它放进请求头。业务请求先经过登录检查，凭证有效才继续；接着根据服务端登录状态取得用户编号，从数据库重新读取用户信息，放到当前请求的用户上下文中，业务代码再从这里取得操作者。普通同步请求结束后清理上下文，避免线程复用时残留上一个用户的信息。

登录成功不等于可以访问所有人的数据。会话读取和已有任务流程还会检查对象归属；当前知识库并没有完整的用户级文档权限隔离，不能把检索范围当成权限控制。另外，当前账号密码仍是直接字符串比较，这部分不是已经完善的生产级认证方案。

## 二、上传文档，并另行启动后台处理

用户先选择知识库，再上传文件。服务检查知识库、文件来源和处理参数，校验通过后把原文件放到对象存储，再在数据库登记文件位置、文件名、文档版本和处理方式，将文档记为“待处理”。文件版本按文件名中的版本标记提取，不是让模型判断。到这里上传请求就结束了，还没有进行解析、分块和向量化，因此上传成功不代表已经能检索这份资料。

用户接着点击“开始分块”，这是另一条请求。服务向 RocketMQ 发送事务消息，先让消息暂时不对消费者可见，再在本地数据库事务中尝试把文档改成“处理中”。更新条件要求文档不能已经处于处理中，因此并发重复点击时，只有拿到处理资格的请求可以提交这次事务消息；没有拿到资格的请求回滚自己的消息。接口响应本身不能代替任务结果，前端还需要查看文档状态。

消息提交后，消费者取得文档编号和操作者，重新查询文档及知识库配置，从对象存储读取文件，再交给处理链执行。处理链先根据实际文件类型和解析配置选择解析器，把文件变成段落、标题、表格等结构，再切分为较小的资料块。Excel 的特殊处理放在下一节，普通文档则尽量保留段落、列表项等边界。

分块完成后，把每块用于检索的文本交给 Embedding 模型，也就是把文本转换成数值向量。返回后检查向量数量是否和资料块一一对应、是否为空、维度是否符合配置；通过后才开始替换数据库中的旧资料。当前默认使用 PostgreSQL 和 PGVector，关系数据中的资料块与向量记录在同一个本地事务中更新，避免只换了正文却没换向量。

索引写入完成后，外层再把文档记为“处理成功”，保存块数、各阶段耗时和处理日志。如果解析或向量化等步骤失败，通常会记录失败状态和原因，等待用户重新触发；这类异常可能已经被业务层处理，不一定让消息队列自动重试。原文件存储、数据库、模型调用并不是一个共同事务；索引提交后的状态更新也可能失败，所以不能只凭一次接口成功判断所有环节都完成，更不能说事务消息保证任务只执行一次。

### 高频追问 02：上传成功却搜不到，或者一直显示处理中，你怎么排查？

我先查文档状态和本次处理日志。`PENDING` 通常先确认是否触发分块；`RUNNING` 要查消息有没有被消费、执行停在哪一阶段；`FAILED` 看原始异常；`SUCCESS` 后仍搜不到，再核对实际资料块、同编号向量、启用状态和查询范围。观察的量包括消息积压、消费延迟、任务停留时间、块与向量数量，以及解析、分块、Embedding、写库的耗时。当前已有处理日志和阶段耗时，但失败时部分耗时可能还没回填，必须结合异常日志判断。

现有摄取主体会捕获很多异常、记录失败后返回，因此不能期待 MQ 自动重试所有业务失败。我的处理方式是先修复文件、配置或外部依赖，再重新触发；长期 `RUNNING` 则先确认旧任务是否还在执行。如果补自动恢复，我会增加执行批次、超时对账和重试上限，避免直接改状态、重发消息后产生两个并行执行者。

### 高频追问 03：用了事务消息，是否就不会丢任务、不会重复执行？

事务消息把“文档取得处理资格”和“消息可以交给消费者”联系起来；当前通过条件更新防止两个启动请求同时把同一文档置为处理中。它不能证明消费只发生一次。当前消费者没有按消息或处理批次建立完整的幂等执行登记，而且索引已提交、最终状态更新失败时，页面状态与实际索引也可能不一致。

如果补齐，我会用文档编号加处理批次作为执行身份，领取、完成和失败更新都校验批次；块与向量按同一批次准备完成后再切换可读版本，失败由对账任务处理。重试前先核对已有产物，成功批次直接返回结果。这样保护的是实际数据状态，不能只靠消息是否收到过来判断整个流程是否完成。

## 三、Excel 先保留表格关系，再做分块

处理 Excel 时，程序先逐个读取可见工作表，把单元格转换为显示文本，数字、日期和公式结果尽量按表格中的显示方式处理。同时记录每一行原来是否有真实内容，这个记录要在展开合并单元格之前完成，否则后面无法区分真实数据和程序补出来的内容。

遇到合并单元格时，表头和数据区分开处理。表头中的合并值会补到对应列，保留列的含义；数据区只沿合并区域的第一列向下携带内容，避免把一大段说明横向复制到每一列。展开后，如果某行原来完全为空，而且现在的内容只是重复上一行，就把它并入上一行的来源范围，不再生成一条重复记录。原文件中本来就有的两条相同记录仍然保留，不做无差别去重。

清理全空行列后，程序取得表头、数据行和每行对应的原始单元格范围，再按完整数据行分组。每组同时准备两份文本：一份保留表格形式，方便给人阅读和作为回答依据；另一份写成“列名：值”，并补上工作表等上下文，交给向量模型。例如“设备：C1；传感器：S7”，比只留下两个孤立值更容易表达它们的关系。这里不是把每个单元格单独做向量。

分组时同时检查展示文本和检索文本的长度，还要限制行数。再加一行会超过预算，就先结束当前块；如果单行本身太宽，就按完整的“列名和值”组合拆成几个较窄片段，不从一个字段中间直接截断。后续合并小块时保留已经切好的边界，也不把不同工作表重新拼到一起。默认的 1024 是字符目标，不是 token 上限；一个字段本身过长时，当前实现会保留完整字段，因此不是所有输入都一定小于这个值。

最后，每块资料带着文件、工作表和单元格范围一起保存，正文、检索文本和向量使用同一个块编号关联。以后检索命中它，就能继续找到对应的原始位置。当前主流程按一行表头处理，不能据此说已经解决任意复杂、多层表头 Excel 的理解问题。

### 高频追问 04：为什么这样分块，1024 怎么选的，怎么知道改动有效？

1024 是已有配置中的字符目标，我没有证明它是所有文档的最优值。我的实际改动先解决可定位的问题：合并单元格展开制造重复内容、宽行预算失效，以及后续打包把已经切开的片段重新拼大。固定字符截断容易拆开列名和值，所以保留字段对应关系，并同时检查展示正文与检索文本。

判断时先看原文件的关键事实是否进入块，再看长度分布、超目标块数和处理链制造的重复数。历史同一份 XLSX 的块数从 123 变为 79，超过 1024 字符的正文块从 70 变为 0，多余精确重复块从 17 变为 0，抽查的 5 个解析锚点仍全部保留。这证明该工作簿的块结构改善，不等于答案准确率提升。若进一步调大小，我会固定资料与问题，比较关键事实覆盖、检索效果和模型输入量，不能只追求块更少。[分块改动记录](../changes/2026-08-13-xlsx-structure-aware-chunking.md)

## 四、用户提问，先整理问题并确定查询方向

用户提交问题，可以带上已有会话编号继续追问。服务先建立 SSE 连接，也就是保持一条连接持续把回答片段发给前端，并先返回本轮任务编号。请求经过全局排队取得执行机会后，先加载该用户会话的旧摘要和最近对话，再保存本轮原问题；这样后面组装提示词时，不会把当前问题重复放进历史。新会话也在这个阶段创建并生成标题。

接下来先按维护好的术语映射统一简称、别名，再把当前问题和截取后的对话历史交给模型改写。例如前面一直在讨论设备 C1，这次问“它异常时先检查什么”，改写希望补回这个对象。一次请求包含多个明确问题时，可以拆成几个子问题分别检索；程序会处理是否拆分的标志，并对返回结果去空、去重，而不是模型给出几条就直接照单全收。改写调用或结果解析失败时，退回术语归一化后的原问题。

然后根据配置和已有业务类别判断查询方向。模型只能从系统已有类别中选择，程序再过滤无效编号和低分结果。单个问题存在多个接近的业务方向时，系统会按规则判断是否需要先让用户澄清；需要澄清就直接返回选项，本轮不继续检索。纯闲聊可以直接进入对话生成，其余问题才进入查资料的流程。

对于知识问题，分类结果用于确定优先查哪些知识库。置信度足够时，主要查询绑定的知识库；没有可靠分类时，基础配置回退到全部有效知识库，而工业演示配置可以选择不做全库兜底，避免混入无关领域。这个范围选择解决的是“去哪里找资料”，不是“用户是否有权读这些资料”。如果启用了已有工具接口，也可以按配置提取参数、执行工具，再把结果交给后续回答。本节是现有问答链路；在对话中识别计划目标并建立持续任务的分支，放在第八节按设计说明。

### 高频追问 05：问题被改写错了，或者意图识别把资料范围选错了，怎么办？

我会把原问题、术语归一化结果、改写结果、子问题和最终知识库范围放在一起检查，尤其看设备编号、检测对象、否定条件有没有变化。正确资料被范围过滤掉时，后面调重排没有作用；改写把一个条件拆没了时，增加 TopK 也不能补回用户原意。明确的多个问题才拆分，指代和条件尽量补全到每个子问题中。

当前改写调用或解析失败会回退到归一化后的原问题；已有改动落实了 `should_split` 标志并对子问题去重，低置信或相近意图也有澄清、回退分支。模型返回格式正确但意思改错，目前没有完整自动校验。如果补齐，我会用标注样本比较改写前后的关键证据命中和路由正确率，单列误改写、错误缩小范围与不必要澄清；发现某类问题稳定退化时，让该类问题保留原问或先追问。

## 五、检索候选，重排后组织回答依据

拿到子问题和查询范围后，先确定最终回答可以使用多少资料。当前请求级目标是最多选择 10 个不同资料块；有多个子问题时，先分配每题的份额，例如两题各分 5 个。这个额度限制的是最终资料块数量，不是模型整次调用的 token 或费用；每题前面的候选召回仍可以取更多，以便后面筛选。

当前默认只启用向量检索。服务先把子问题转换为查询向量，再到 PGVector 中按知识库范围查找相近的资料块。文档向量已经在入库时生成，所以提问时不需要重新给所有文档编码。需要注意，查询和文档应使用兼容的向量模型；当前入库按知识库指定模型，查询走全局模型配置，这个一致性没有被代码完全强制保证，维度一样也不代表两个模型的向量可以直接比较。

候选返回后，先去重并控制候选池大小，再根据块编号回数据库补齐文档名、版本和表格位置。随后把“问题和每个候选的检索文本”成对交给重排模型，让它进一步判断相关性。表格重排时会带上文档名和“列名：值”等结构信息，但最后提供给回答模型的仍是用于展示的资料正文，不把拼装出来的排序文本冒充原文。重排失败时，可以退回原来的候选顺序。

多个子问题检索结束后，再合并各题选中的资料，并按块编号形成去重后的来源集合。当前默认先取每题的前几条，再做请求级去重；重复项占掉的空位不会自动补满，所以最后可能不到 10 块。同一个块也可能仍出现在两个子问题的提示词段落里，因此不能把“来源集合去重”直接说成整个提示词绝对没有重复。关键词、图谱和联网检索不是当前默认主链；默认只有一路时，也没有真实发生多路融合。

最后把选中的资料按文档整理，文档内部尽量恢复原有块顺序，交给回答模型。同时准备文档级来源和块级证据快照：前者供前端展示来源和引用编号，后者随回答保存，供后续任务使用。两者来自这次检索真正选中的资料，不是让模型临时编造。普通知识问答如果没有检索上下文，就直接提示未找到相关资料，不继续调用最终回答模型；即使有合法引用编号，也仍需核对引用内容是否真的支持回答。

### 高频追问 06：RAG 没找到正确依据，你先改哪里，为什么不直接调大 TopK？

我按证据经过的位置排查：原文事实没有进入块，修解析和分块；块存在但候选没有，查改写、范围、Embedding 模型兼容性和召回；候选有而最终上下文没有，查重排与选择；上下文有而答案错，才查生成。比较候选阶段与最终阶段的证据覆盖，才能知道证据在哪一步丢失。标注了相关块时可算 Recall@K，即前 K 块覆盖了多少应找出的相关块；本项目工业评测实际还使用关键短语的 Anchor Recall，口径见第十一节。

已有改动包括把元数据补全放到重排前，让文档名和表格键值参与排序，以及让多个子问题共享请求级最终额度。先保留较充分的候选，再控制最后给模型的资料；直接调大最终 TopK 会一起增加重复和低相关内容。确实发现正确证据不在候选池时，才考虑扩大召回或增加检索通道，并观察新增证据是否值得额外开销。

### 高频追问 07：向量检索、BM25 和重排分别什么时候用？为什么没有默认混合检索？

向量检索用于发现语义接近、表达不同的资料；型号、标准编号等精确词漏召回时，我会测试 BM25 补充。两路候选合并可用 RRF 按名次融合，避免直接相加不同量纲的分数。重排则把问题和候选内容一起比较，更细地判断相关性，但增加一次模型调用，所以要限制候选池。

当前默认是向量检索加重排。已有公开集对照中，混合重排在 Hotpot 子集没有超过向量重排，在 SciFact 上略有收益，因此保留可选配置，没有宣称混合检索一定更好，也没有据此改变默认链路。这些是检索对照，不是中文工业回答准确率。是否启用，要看目标问题上的新增证据覆盖、排序效果以及耗时成本。[混合检索记录](../changes/2026-09-05-hybrid-retrieval-comparison.md)

### 高频追问 08：用了 RAG 仍然出现幻觉，你怎么处理？

我先把回答拆成可以核对的事实，逐条看对象、数字、单位和条件是否被本次原文支持。没有把必要证据交给模型，就回到检索链；证据已经给到却被张冠李戴或补出新结论，就处理生成约束。主题相近的片段不一定能支持答案，模型自信也不能替代证据。

当前已有无上下文时直接提示未找到资料、保存真实来源，以及计划草稿的引用编号校验；还没有覆盖所有回答的自动语义核查。如果补齐，我会要求事实对应证据，资料缺失时明确留空，对关键参数和适用条件增加核对，失败后定向补查或重新生成。指标看有依据的事实占比、答案要点覆盖，并同时记录不可回答题的正确拒答与可回答题的误拒答；第二个模型的评分只能辅助检查，不能当作保证正确的裁判。

## 六、流式返回回答，用户也可以中途停止

资料准备好以后，服务把回答规则、旧对话、检索资料和当前问题按角色组织成消息，交给大模型生成。模型陆续返回的正文通过 SSE 发给前端，前端不断追加显示；服务端也累计完整文本，不依赖浏览器再把最终答案传回来。

模型正常结束时，服务尝试把回答、来源、证据快照和所回复的用户消息关联保存，再向前端发送完成信息和结束标记，关闭连接并更新本轮运行记录。后续达到会话轮次条件时，后台会把较早的对话压缩成摘要，供以后的提问使用；摘要不会删除原消息，也不决定本轮回答是否完成。回答保存失败时，当前实现仍可能结束连接，所以“前端看到了回答结束”和“数据库一定保存成功”要分开理解。

用户点击停止时，会拿本轮任务编号另发一个停止请求，它与正在生成的回答并发执行。服务先在 Redis 写一个带有效期的取消标记，再通过发布订阅通知各个在线实例。这样停止请求即使到了另一台实例，也能让持有模型连接的实例收到通知；如果通知先到、任务后登记，后登记的任务还可以读到取消标记。

真正持有任务的实例只让一个线程执行取消，已经取得模型调用句柄就取消连接；句柄还没回来，就保留取消状态，等后来绑定句柄时补取消。已经生成正文时，尝试保存这部分回答并标记为中断，再通知前端停止显示。正常完成、报错和取消更新运行记录时，都只修改仍在运行的记录，避免迟到回调把已经确定的终态反复覆盖。

停止接口返回只表示提交了取消信号，不代表供应商已经停止推理或计费。当前普通聊天也没有断线后从某个字继续播放的能力；重新打开只能读取已保存的消息。后文计划任务保存目标、证据和草稿后继续推进，属于业务状态恢复，与流式文字续播是两件事。

### 高频追问 09：用户觉得回答很慢，你看什么指标，先优化哪里？

我会拆开排队、问题改写、检索、重排、模型首包和后续生成，先定位主要等待发生在哪里。面向用户的首字时间从提交问题算到第一段正文，不能把提前返回的任务编号当作答案首包；还要看总耗时、超时率和 P95，也就是约 95% 请求不超过的耗时。模型已经开始输出但很慢，则另看输出长度和生成速度。SSE 改善逐步展示体验，不会让前面的检索自动变快。

项目已有 Trace 和阶段日志，历史评测也记录过耗时，但没有据此证明稳定的线上性能提升。我的处理会跟随瓶颈：改写慢就减少不必要的模型改写，重排慢就控制候选池并检查服务延迟，首包慢就检查输入长度和模型候选，排队慢则检查并发限制和依赖承载。缺少客户端或排队时间戳时先补采集，再用同批请求比较；不能把各阶段 P95 直接相加当成端到端 P95。

### 高频追问 10：停止请求到了另一台实例，或者停止后模型回调又到了，怎么办？

现有链路先在 Redis 写带有效期的取消标记，再发布通知；持有模型调用的实例收到后执行取消。通知先到、句柄后绑定时，任务登记和句柄绑定处还会检查取消状态，补上取消。进程内通过原子判断只允许一次终止处理，数据库终态更新只影响仍在运行的记录，迟到回调不能把取消覆盖成成功。

我会区分“停止接口已接收”“持有实例已处理”“底层调用已取消”三件事，用任务编号关联日志。补监控时关注取消信号到本地处理的延迟、重复终态处理和停止后仍收到的数据；客户端显示停止不代表供应商已经停止计费。对话计划 Agent 的取消也要使用自己的任务状态，不能仅关闭 SSE 连接就认为计划已经取消。

## 七、模型怎样选型，调用失败时怎样处理

模型调用前，服务会根据任务需要选择模型候选，例如问题改写使用快速档，普通生成使用标准档，需要深度思考时选择支持相应能力的候选。同步调用要等到完整文本返回；一个候选调用失败后，才尝试下一个。业务层拿到文本后还要自己解析和校验，所以“模型接口返回成功”不等于返回的 JSON 或业务结论一定正确。

流式回答的切换边界是首个有效内容。系统先暂存候选模型的回调，收到正文或思考片段后才正式把这条流交给上层；首包前报错、没有内容就结束，或者等到超时，都可以取消当前候选并尝试下一家。一旦已经把内容交给用户，后面再出错就不会接着拼另一个模型的回答，避免两份生成结果混在一起。

服务还在当前进程内记录模型的连续调用失败。达到阈值后暂时跳过，冷却结束只放一个请求试探，试探成功再恢复使用。它处理的是接口可用性，不是答案质量，而且多实例之间不共享这份状态。向量模型也不能像生成模型一样随意更换，必须同时考虑已有文档向量是否仍然兼容。

### 高频追问 11：为什么选择这些模型，RAG 和 Agent 用的是同一个模型吗？

可以这样回答：“我按任务选择模型。问题改写是短任务，优先考虑延迟；问答和计划编制需要理解中文规程、综合证据并遵守输出要求；检索则分别用向量模型做召回、用重排模型判断问题与候选片段的相关性。选型主要看业务质量、响应时间、调用成本和部署条件，模型名称通过配置管理。”按[仓库主配置](../../../bootstrap/src/main/resources/application.yaml)，目前的分工如下；部署覆盖、候选健康状态和调用回退都会影响某次请求实际使用的模型。

| 环节 | 当前模型或路由 | 选型时主要考虑什么 |
| --- | --- | --- |
| 问题改写与拆分 | `FAST` 档，优先 `qwen-flash` | 保留原问题的对象、参数和限制，尽快生成可检索的问题；要测改写错误率和延迟 |
| 普通问答、意图判断 | `STANDARD` 档，优先 `qwen3-max` | 读懂中文规程、依据资料回答，实际候选还受健康状态和部署覆盖影响 |
| 研究主 Agent、worker、最终报告或计划 | 独立研究配置 `qwen3.7-flash-2026-07-15` | 使用原生工具协议、遵守范围与引用契约；P7 比较时固定同一模型，不沿普通问答候选回退 |
| 文档与查询向量化 | 默认 `Qwen/Qwen3-Embedding-8B`，通过 SiliconFlow 调用，请求 1536 维 | 找到同义表达下的相关证据；关注召回、向量存储与检索成本，以及文档和查询是否使用同一向量空间 |
| 候选重排 | 默认百炼 `qwen3-rerank` | 进一步判断问题和候选内容是否匹配，让有限的上下文优先保留有效证据；它不负责生成最终答案 |
| 图片内容提取 | 配置 `qwen-vl-max`，有图片解析需求时调用 | 将图片中的文字和说明转成可检索内容；可直接读取的 Excel 单元格继续用表格解析 |

普通问答和研究工作流使用两套模型接线。意图判断走默认标准档，普通问答开启深度思考时走 `DEEP` 档。研究使用 AgentScope SDK 的百炼兼容端点，按 `research.model-id` 配置固定模型，关闭思考，不通过普通 `LLMService` 候选回退。聊天中的“深度研究”是研究入口名称，不能等同于普通回答的 `DEEP` 模型档位。

如果追问“为什么选 8B、为什么是 1536 维”，我会说明：Qwen3 Embedding 的多语言检索和可调整输出维度能力，使它适合作为候选；当前 1536 维是项目请求和向量库的配置，不是该模型唯一支持的维度。[Qwen 官方说明](https://qwenlm.github.io/blog/qwen3-embedding/)描述了这些能力。维度减少可以降低向量存储和相似度计算开销，但是否损失本项目的关键证据召回，需要固定数据对照；现有材料没有证明 8B 比所有小模型更适合，也没有证明 1536 是最优值。

如果追问“为什么不用更便宜的模型，怎么证明选得对”，我会固定同一批问题、证据、提示词和输出要求进行比较。检索模型看 Recall@K 和 nDCG@K，后者还考察相关资料的排序位置；回答模型看事实要点、引用支持率和资料不足时能否合理拒答；Agent 看工具选择、参数合法率、该追问时是否追问，以及整项任务完成情况。再比较首个正文延迟、完整任务 P95 耗时、失败率和每个有效完成任务的成本，包含失败、重试和回退。小模型满足质量要求时就可以替换相应环节；多轮任务还要检查累计错误，不能只看单轮 JSON 成功率。这是建议补做的模型对照，现有 RAG 检索实验不能当成模型选型横评。

研究当前设置 `temperature=0`、`thinking=false`、单次输出上限 4096 token；每运行最多 16 次模型、24 次工具，并预留 2 次最终生成。低温度不保证事实正确或每次完全一致，单次 token 上限也不能代替全局额度。实际工具结果来自服务端；结构与引用校验失败最多修复一次，修复请求同样记录 usage。

### 高频追问 12：模型限流、超时或输出到一半断了，是否都能重试或换模型？

当前流式路由把首个有效内容作为切换边界：首包前失败可以尝试下一候选；正文或思考片段已经交给上层后，就不能无缝拼接另一家生成结果。同步调用可以在候选失败后回退，但返回了格式错误的业务 JSON，要由业务层处理，不能等同于供应商不可用。当前已有候选回退和进程内熔断。

如果补重试策略，我会先分类：限流和短暂网络错误做有总次数、总时间上限的退避；参数不合法直接修正请求；中途断流保留中断状态，由用户重新生成或重试任务。按模型分别统计首包超时、调用失败、回退和熔断探测结果，避免无限重试把故障放大。更换 Embedding 模型还需要重建或隔离原有向量，不能只改配置后继续混查。

## 八、在对话中建立研究任务，保存目标和范围

用户选深度研究或计划生成后，目标、输出类型、约束和资料范围成为 `ResearchBrief`。服务校验会话 owner 和资料状态，再创建持久运行；普通问答继续使用原来的请求链。运行绑定明确编号，追问、取消、刷新恢复都使用这个编号，不用“最近一条消息”猜归属。

`clientRequestId` 用于同一创建请求幂等。相同编号但内容不同会被拒绝，重新生成用新的编号。资料仍按原项目共享知识库规则访问；运行、事件、证据和产物按 owner 隔离，不能把检索范围当成完整文档权限模型。

### 高频追问 13：Agent 状态机怎么设计，为什么不能只用“处理中、成功、失败”？

等待用户、后台研究和产物形成是不同状态。程序根据真实工具与数据库事件转换，模型不能直接宣告完成。

| 状态 | 含义 |
| --- | --- |
| `QUEUED` | 已保存，等待后台执行资格 |
| `RUNNING` | 正在检索、阅读或生成产物 |
| `WAITING_INPUT` | 问题已保存，等待 owner 携带 revision 回复 |
| `COMPLETED` | 合法产物与终态已经原子保存，仍需核对语义 |
| `PARTIAL` | 已形成产物，同时明确研究超时、额度或子任务缺口 |
| `FAILED` | 本次没有形成合法产物，错误单独保存 |
| `CANCELLED` | 用户取消，迟到结果不能覆盖 |
| `INTERRUPTED` | 重启后原执行者已经丢失，可另建请求重新研究 |

人工等待不计活动时长，恢复保留已用额度和成功 worker 结果。终态重新生成创建新的运行，旧结果保持可回查。

### 高频追问 14：Agent 一轮究竟做什么，算不算 Function Calling，为什么按需委派？

模型通过原生 `tool_calls` 提出工具和参数，SDK 执行服务端 Java 工具，把真实结果交回模型。下一次查询可以消费刚读到的观察，因此不同于事先并发拆好所有问题。纯文本答案或一段工具 JSON 都不能完成研究；必须通过真实 `ask_user` 或 `finish_research`。

依赖链由同一个研究者顺序推进。比较两份独立资料、整理相互独立的计划维度时，主 Agent 可以一批委派两个 worker；每个 worker 有独立上下文，只回传带阅读依据的压缩结果。多一个 Agent 会增加费用、排队与整合风险，是否发生委派及其结果在 P7 中单独记录。

### 高频追问 15：Agent 具体调用哪些工具，什么时候调用？

工具由 [ResearchTools](../../../bootstrap/src/main/java/com/nageoffer/ai/ragent/research/runtime/ResearchTools.java) 和 [ResearchWorkerCoordinator](../../../bootstrap/src/main/java/com/nageoffer/ai/ragent/research/runtime/ResearchWorkerCoordinator.java) 注册，不通过普通问答的 MCP 意图分支调用。

| 工具 | 用途与服务端约束 |
| --- | --- |
| `search_knowledge` | 在 brief 的允许范围内查候选；模型可以缩小范围，不能扩大 |
| `read_source` | 阅读当前研究者取得的候选或邻块，返回可引用的正文与来源，检查变更、停用和 hash |
| `conduct_research` | 仅主 Agent 可用；创建独立子目标，继承或缩小父范围，不允许二层委派 |
| `ask_user` | 仅主 Agent 可用；保存必要用户问题并暂停，资料未披露的事实直接列缺口 |
| `finish_research` | 提交实际已读依据支持的发现、缺口与冲突，交给最终生成阶段 |

worker 只有搜索、阅读、结束三个工具。源文档、最终引用正文和工具结果由后端读取；工具不提供任意 URL、SQL 写入或设备控制。

## 九、按证据缺口补查，并保存用户输入

计划从研究开始就关注准备条件、步骤、资源和参数，报告关注结论、比较、条件与限制。搜索候选不是阅读证明，主 Agent 与 worker 都需要真正读到允许的正文才能引用。主 Agent 可以重读 worker 的依据；收到压缩发现不等于收到 worker 全部工具历史。

例如文件说明一种实验方法但未给设备功率，系统应把功率列为缺口；用户尚未说明准备时间且这会影响计划时，可以追问。回复保存为 `user_input`，优先于旧目标中的未知条件；文档事实保持其独立证据身份。后端保存已完成子任务和读取证明，回复后不能无理由重复所有委派。

### 高频追问 16：工具名称错了、参数错了、外部接口超时，分别怎么处理？

SDK 和服务端校验工具名称、必填字段、范围和证据身份；错误作为真实工具结果或失败事件记录。工具超时、模型超时、原生结束缺失分别保存，不能把它们都写成“没有证据”。一个 worker 超时会保留其他 worker 的成功发现和自身缺口；是否能形成 PARTIAL 还取决于最终生成阶段。

模型返回了文字但没有原生结束时记录 `NATIVE_FINISH_REQUIRED`。有正文或调用成功都不能冒充完成。最终结构或引用失败最多修复一次，仍失败则保留错误，不保存伪造产物。

### 高频追问 17：Agent 一直检索、上下文越来越长，怎么防止死循环和失控成本？

所有角色共用 16 次模型、24 次工具、300 秒活动时长，其中 2 次模型额度保留给最终生成。每运行最多 4 个 worker、同时 2 个；每 worker 最多 6 次模型与 180 秒。单 JVM 模型请求共用并发额度 2，抢最后额度使用原子计数，不是各自读一次剩余额度后再扣。

研究输入上限 28000 token 采用保守估算，按完整 assistant/tool 往返裁掉早期历史；不能把估算叫精确 tokenizer 硬门禁。实际供应商 token 与请求状态逐次记录，失败、取消或超时没有 usage 时标 unknown。预算耗尽仍保留已读依据与成功发现，使用预留额度尝试形成带缺口的产物。

### 高频追问 18：Agent 会不会编造工具结果，或者被资料里的指令带偏？

文档正文是不可信证据，不能改变系统规则、工具清单或允许范围。实际工具结果来自服务端；owner、范围和引用身份在模型之外校验。提示词不能保证模型完全不受注入影响，合法证据 ID 也不能证明文字真正支持结论，因此仍要原文核对。当前工具范围仅用于研究，不赋予业务办理或设备执行权限。

## 十、统一生成报告或计划草稿，持久保存结果

研究结果交给 [ResearchArtifactGenerator](../../../bootstrap/src/main/java/com/nageoffer/ai/ragent/research/service/ResearchArtifactGenerator.java)。它使用同一份 brief、发现和实际证据，根据 `outputType` 生成报告章节或计划结构。步骤顺序、参数与引用身份经校验后，服务器补全引用正文和位置，再把产物与终态原子保存。

未知参数保留 null 和缺口，用户条件单独标注来源。最终产物可以展示、回查和下载；它是供人核对的研究结果或计划草稿，不包含预约、审批和设备执行链。资料范围变化或终态重新生成时建立新运行，原结果保留。

版本比较继续由独立接口读取两个 XLSX 原文件，按工作表和单元格地址计算增删改。它不是研究 Agent 的自动动作，也不识别整行移动、Sheet 改名或公式业务等价性；详细口径见[版本比较](08-evidence-task-and-version.md#3-版本比较是另一条独立请求)。

### 高频追问 19：进程重启、两个请求同时推进、旧模型结果迟到，怎么恢复？

后台以短事务领取带 epoch 的执行资格，模型和工具调用发生在事务外。取消和完成都按当前 epoch 条件落库；迟到执行者失去资格就不能写回，终态与产物在同一事务提交。取消关闭父子调用订阅，但远端推理是否停止保持 unknown。

当前采用单 JVM。启动时将失去执行者的 QUEUED/RUNNING 标记为 INTERRUPTED，不恢复流式 token。GET 与 SSE 只读取已保存状态和事件，页面重连不会重新执行；用户可用新请求编号重新生成。

### 高频追问 20：用户重复提交、重复回复或取消时，怎么保证结果一致？

创建按 owner、会话和 clientRequestId 幂等，内容冲突显式拒绝。输入必须属于该 owner 的 WAITING_INPUT 运行并带当前 revision；旧回复不能推进新状态。取消幂等，取消与完成竞态由数据库条件更新决定赢家，失败执行者不能另写产物。重新生成使用新请求编号并保留旧运行，不把终态直接改回处理中。

## 十一、怎样判断问答与计划生成是否有效

先固定文档、问题和期望找到的证据，再检查原文件中的关键内容有没有正确进入资料块。没有进入块，先查解析和分块；已经入库但召回候选里没有，查问题改写、查询范围和向量检索；候选里有但最终上下文没有，查重排和筛选；证据已经给模型却仍答错，再查提示词和生成。这样能把问题落到具体一层，而不是回答不好就一直调大检索数量。

对比检索改动时，尽量保持索引、问题和配置一致，再比较召回的证据、最终上下文、答案和引用。上下文变少不自动等于质量提升，引用编号合法也不等于原文支持结论。已有小样本结果可以说明表格块结构和部分检索行为改善，不能外推成工业领域通用准确率提升。

研究 Agent 使用固定公开题和比较、计划应用任务验证。应用任务覆盖资料齐全、缺少用户条件、缺少文档依据、适用条件与参数缺失；资料没有真正矛盾时不能硬称冲突。先比较一次检索生成与按需补查：是否少漏了用户要求的内容，是否把无依据内容明确留空，引用是否支持计划，以及额外调用带来多少时间和成本。资料齐全时应尽快形成草稿，资料不足时应停止并说明原因，不能把调用轮数多当成更智能。

程序机制与模型行为分开验证。程序侧检查任务归属、资料范围、重复创建、并发额度、取消与迟到结果、只读 SSE 和迁移保留数据；模型侧检查能否发现缺口、选对查询方向、合理追问和形成有依据的产物。受控 HTTP 桩与浏览器测试证明接线，真实 API 任务和原文核对检验模型行为，两类结果分别报告。

### 高频追问 21：你用什么指标判断 RAG 改动有效，实际取得了什么结果？

我把解析、检索和回答分开判断。解析看关键内容是否进入块、长度和重复情况；检索看应找的证据有没有被召回、是否进入最终上下文；回答再检查事实要点和引用支持。不能用某一个中间指标代替整条链的效果。已有 D0 对照固定 3 份文档、141 个块及向量，使用 24 道问题，其中 21 道参与可回答检索指标，主要结果如下：

| 指标 | 具体判断对象 | 改动前 → D0 |
| --- | --- | --- |
| 平均返回块数 | 每道题最终得到多少不同资料块 | 13.05 → 6.52 |
| Context Precision | 每题含任一参考锚点的块数 ÷ 返回块数，再对题平均 | 17.1% → 29.2% |
| 文档召回 | 找到的参考文档数 ÷ 应找到的参考文档数，再对题平均 | 97.6% → 97.6% |
| Anchor Recall | 命中的参考关键短语数 ÷ 应命中的短语数，再对题平均 | 86.5% → 84.1% |
| 锚点 Hit@5 | 前 5 块至少命中一个参考短语的题目比例 | 95.2% → 90.5% |

这里的锚点是事先标注的原文关键短语，Context Precision 也是本项目的锚点代理指标，不能直接当成语义正确率。实际结论是上下文数量减少、这项纯度指标上升，但部分证据覆盖指标下降，因此保留取舍，不说所有效果都变好了。后续公平回填虽能补满空位，却没有通过质量门槛，所以仍默认关闭；这说明我会根据对照结果决定是否启用，而不只看功能是否跑通。D0 没有完成回答层的重新盲评，不能据此声称回答准确率提高。[检索对照记录](../changes/2026-08-13-request-level-retrieval-purity.md)

### 高频追问 22：怎么证明计划 Agent 有用，而不只是多调用了几次模型？

统一研究已实现，P7 固定 QASPER validation、MuSiQue Full dev 的问题、语料、模型与范围，对照 A 一次检索、B 单研究者、C 按需委派。A 复用项目检索与共享生成器，是控制变量比较，不等于生产普通聊天全链路。另有固定 12 个比较和 12 个计划任务按实际引用原文核对。成功标准包括必需内容有依据、未知项被明确列出、没有把不适用条款混入，不能只看是否返回 JSON 或进入完成状态。

| 指标 | 我会怎样统计 |
| --- | --- |
| 计划任务通过率 | 满足预设核对标准的任务数 ÷ 全部测试任务数，失败和超时保留在分母中 |
| 必需内容覆盖率 | 已正确表达且有依据的必需项数 ÷ 该任务应覆盖的必需项数 |
| 无依据事实比例 | 不能被来源支持的可核查事实数 ÷ 输出的可核查事实数；没有事实时另记缺答 |
| 追问是否合理 | 缺必要信息时有没有追问、信息充分时有没有多问，按场景分别记录 |
| 时间与成本 | 记录每任务耗时、模型及工具次数、输入输出 token；人工等待时间单列 |

工具成功率、JSON 合法率和平均轮数只解释过程。真正的取舍是：额外补查是否减少遗漏和无依据内容，是否值得增加的延迟与成本；资料齐全的简单任务不应无谓绕圈。程序测试的通过率只说明对应机制。真实质量结果、失败样例和资源记录见[验证报告](../agentic-research-validation-report.md)与[执行记录](../agentic-research-execution-log.md)，不能只挑 C 获胜的样例。
