# 表头判定改用 Jev：计划

> 状态：**2026-10-12 写定，在任何代码之前提交**。结果与结论写在本文件末尾和改动说明里。
> 目标：Excel 版面切分里"这一行是不是表头"现在靠硬编码阈值（超过 40 字、一半以上是数字就不算表头），换一份表格就可能不成立。评估 Jev 是否适合做这个判断，适合就接进去。
> 与旧工作的关系：table-structure 计划 §0.3 定过"不让大模型标注"，理由是结果不稳定、要钱、要另做评测。Jev 不是生成模型（§1），这次只把一个是/否判断交给它，版面切分的其余规则不动；评测沿用冻结的调研表标准答案。

## 0. 已定事项

1. 用户要求（2026-10-12）：评估 Jev 找表头是否合适，合适就改；只用现有表格；过程用 Git 记录；接入方式参考 AgentScope-java。
2. 只改一个判断：区域第一段的第一行是不是表头（原 `ExcelLayoutAnalyzer#headerLike`）。区域、分段、标题、续段、重复表头、表头行数都还按规则。
3. 规则判定保留，作为默认实现和兜底。新开关 `rag.ingestion.excel-layout.header-judge: rule | jev`，先默认 `rule`，过 §4 门槛再改默认。
4. 客户端照 AgentScope-java 的 `agentscope-extensions-jev` 自写。该模块 2026-09-23 才进 main，没有发版；本项目用 2.0.1，不能直接依赖。照搬的做法有四点：
   - 独立客户端，不注册成聊天模型；
   - 三种题型，按题核对应答；
   - 429、529、5xx 和超时按退避重试；
   - 没把握或调用失败时退回原路径（AgentScope 叫 failOpen）。
   放在 infra-ai，用 OkHttp + Gson，与现有模型客户端一致。
5. 模型钉在 `jev-1.13.0`，不用 `jev-latest`。别名会随发版换模型，写定的阈值就不再成立。

## 1. 为什么 Jev 适合这个判断，以及不适合什么

- Jev（TypeSafe System One）不是聊天模型。它接收一段状态和若干问题，返回是/否概率（noul）、选项分布（choice）或等级分（score），不生成文本。"第一行是表头吗"正好是一个是/否判断，代码按结果分支。
- 成本：只按输入 token 计费，$0.042 / 百万 token，输出不计费（官方文档，2026-10）。一张表的判定输入几百到两千 token，一份 12 个 sheet 的调研表约 25 次调用，费用可以忽略。
- 返回的是概率，可以设阈值：有把握才采用，没把握或调用失败就按规则。外部服务出问题不会让入库失败。
- 不适合交给它的：区域、合并、坐标这些几何判断，规则是精确的，Jev 又只收文本。整张 sheet 塞进状态既贵又不准，官方说状态越长准确率越飘。
- 风险：
  - 官方说中文等 CJK 能处理，但不如英文，要实测。
  - 调用会把表头和前几行数据发给 TypeSafe（境外服务）。现在已经把全文发给百炼、MinerU，数据类别相同，但企业资料出境要另行确认。开关默认关。

## 2. 改动

- **客户端**：infra-ai `infra/jev/` 放 `JevClient`、题型与应答、`JevProperties`（`ai.jev.*`）。密钥读 `TYPESAFE_API_KEY`，没有再读 `JEV_API_KEY`。
- **判定**：`core/parser/excel/` 放 `HeaderJudge` 接口、`RuleHeaderJudge`（原 `headerLike` 原样搬过去）和 `JevHeaderJudge`。
- **判定输入**：
  - 本区域从候选行起的逻辑行，续行不算。按列对齐，合并块只出现一次，别的区域的格子不算。
  - 附 sheet 名，以及区域开头最后一个不超过 30 字的单格行（表题候选）。
  - Jev 只看前 6 行。单格超过 80 字截断，末尾加"…"。这几行里全空的列去掉。
- **问题**：noul 题，英文提示，问 `first_row` 是不是给 `rows_below` 各列命名的表头。提示里不放调研表里出现的词，免得拿测试内容教模型。
- **决策**：P(表头) ≥ 0.8 判有表头，≤ 0.2 判无表头。介于两者之间或调用失败，按规则。
- **没有密钥**：`jev` 模式退回规则并告警一次，不影响入库。

## 3. 评测：只用现有两版调研表与冻结的标准答案

- **原表组 G**：
  - 收集两版调研表上版面分析实际交给判定的每一行，即各区域第一段的第一行。
  - 按标准答案打标签：是某张表的表头行，标"有表头"；是无表头表的首个数据行，标"无表头"；对不上的单列出来，不计分。
  - 两版的判定输入相同的只算一次。最多 25 个，其中只有 1 个无表头（现场人员排版"矿样解释"）。
- **去表头组 R**：
  - G 里每个有表头的候选去掉第一行，原来的首个数据行成为待判定行，标"无表头"。
  - 这组模拟表头不在区域里、或表本来就没有表头的情况。用的都是真实数据行，不新编表格。
- **三种判定**：
  - 规则。
  - Jev 单独：P ≥ 0.5 即表头，只报告。
  - 混合：§2 的决策，准备上线的就是这种。
- **运行**：
  - Jev 跑 3 次，看稳定性。
  - 每次还用混合判定把两版调研表完整过一遍版面分析，按 `TableStructureOfflineReport` 的口径与标准答案对照。
- **报告**：写 `local-data/kq-eval/runs/jev-header-*.json`，内容包括：
  - 各组准确率；
  - Jev 采用、没把握、失败各多少次；
  - 每个候选三次的概率，三次判定是否一致；
  - token 用量与耗时。

## 4. 门槛：写代码前定，之后不改

1. **不退化**：3 次都满足，两版调研表 25/25 张表、52/52 个文字格，表内格子当段落 0 处（混合判定，完整版面分析）。
2. **有提升**：混合判定在 G∪R 上的准确率，3 次都不低于规则，且 3 次平均严格高于规则。
3. 两条都过：`application.yaml` 改为 `header-judge: jev`，没有密钥时自动退回规则。任一条不过：保持 `rule`，结果照写。
4. Jev 单独判定、稳定性、费用、耗时只报告。
5. 提示词、阈值、截断参数按 §2 写定。如果看完结果再改，改动单独提交，写明是看过结果后改的，并重跑全部 3 次。

## 5. 限制（运行前写下）

- G 只有 1 个无表头样本。R 由同一批表派生，两组都不是集外表格。结论只说明在这份调研表的真实行上规则和 Jev 谁判得准，不代表集外 Excel。
- 规则是对着这份调研表写的，G 上规则全对在预期之内，Jev 在 G 上最多打平。

## 6. 命令

在有 `TYPESAFE_API_KEY` 的终端里运行，约 3 分钟，调用约 220 次：

```bash
./mvnw -o -q -pl bootstrap -am test -Dtest=JevHeaderJudgeReport -Dsurefire.failIfNoSpecifiedTests=false
```

- 也可以在 IDEA 里直接运行 `JevHeaderJudgeReport`，JUnit 运行配置里要有这个环境变量。
- 结果写 `local-data/kq-eval/runs/jev-header-*.json`，控制台打印三次的汇总和门槛判定。
- 缺密钥就跳过；密钥无效时第一次调用就失败，不写报告。
- 报告代码先用本地桩自测过（桩的概率是假的，报告没有保留）：G 25 个、R 24 个，没有对不上标准答案的候选；每次运行调用 74 次（两版完整版面分析 50 次 + R 24 次）。
