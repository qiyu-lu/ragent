# 01 普通问答链路

## 这条链路是什么

发起方是前端用户：在某个会话里提一个自然语言问题，可选地打开"深度思考"开关。请求带来的只有三样东西——问题文本、会话 ID（为空表示新会话）、深度思考开关；身份从登录态里取。用户想得到的是一段基于企业检测资料生成的、带来源列表的流式回答。

这次请求的终点是一条 SSE 长连接的结束：服务端在同一条连接上先回元信息（会话 ID、任务 ID），再逐段推送思考与正文，最后推送一个完成事件（带消息 ID、来源列表、消息状态）和一个 `[DONE]`，然后关闭连接。回答同时落到消息表里，下一轮作为历史被读回来。连接关不上、或用户中途点"停止"，都在这条链路里收尾，不留后台任务。

整条链路的骨架是上游自带的：SSE 控制器、排队限流、会话记忆、改写、多通道检索与融合、重排、提示词组装、流式回调、链路追踪。我在这条链路上自己加的是四处：**检索范围与权限求交**、**请求级的上下文额度与公平回填**、**融合关闭时的候选池成本兜底**、**停止接口的任务归属校验**（以及取消路径上几个竞态窗口的收口）。另外我把上游的意图树、关键词通道、图谱通道、MCP 工具整块删掉了，现在只剩一条向量通道加一条默认关闭的联网通道——所以下面讲的"范围解析"已经不是上游那套意图分类，而是"当前用户可读的全部有效知识库"。

按发生顺序往下讲。

## 一、进门：单请求幂等与并发闸门

不这么做会出什么事：模型调用是长连接、贵、占线程。前端一次误触或网络重试就能让同一个用户同时挂几条流；并发量上来后，所有请求一起卡在上游模型上，谁也拿不到首字，整站表现为"都很慢"而不是"少数被拒"。

这一段整段是上游自带的。

- **同一用户只允许一条在途对话**。控制器上挂了幂等提交注解，键取当前用户 ID，重复提交直接返回"当前会话处理中"。这是按用户维度的互斥，不是按请求内容去重。要注意的是：上游留了一个"测评模式"开关，打开时这道防重锁整个被跳过，而随程序发布的配置里它默认是打开的——所以当前默认配置下真正挡住并发的是下面那道全局闸门，不是这道锁。
- **全局并发闸门 + 排队**。拿到请求后不直接执行，而是进一次基于 Redis 的分布式公平排队：默认最多 10 路并发，排队最长等 15 s，令牌带 30 s 租约、200 ms 轮询。拿到令牌才把后续逻辑丢进入口线程池执行。
- **等不到就走拒绝分支，而不是报错**。超时后服务端仍然把用户的问题和一条"系统繁忙，请稍后再试"的助手消息落库（消息状态标为被拒），再在同一条 SSE 上发元信息、拒绝事件、完成事件、`[DONE]`。这样前端不需要为"被限流"单开一条错误路径，会话历史里也能看见这一轮发生过什么。
- 排队期间如果连接自己断了（完成、超时、出错），会回调取消排队，不至于给一个已经没人听的连接发令牌。

任务 ID 在这里就生成了，并且**先把"任务属于谁"写进 Redis，再把任务 ID 随元信息发给前端**（这一步是我加的，理由在最后一节取消里讲）。

## 二、会话记忆：读历史、写用户消息

这一步要的是"让模型看见上下文"，同时把用户这句话立刻记下来。

- 历史和摘要**并行**从库里读：一边读最近若干轮原始消息（默认保留 8 轮），一边读该会话最新的一条摘要（超过 9 轮开始压缩，摘要限 400 字）。两边都有兜底——摘要读失败就不带摘要，历史读失败就当空历史，都不让一次问答挂掉。摘要以一条系统消息的形式插在历史最前面。
- 然后把用户这句话追加进消息表，拿到的消息 ID 回传给回调，供后面生成的助手消息记"回复的是哪一条"。追加动作内部会顺带触发会话创建与标题生成，以及达到阈值时的历史压缩。
- **落库和后面的检索、生成不在同一个事务里**，也不可能在：后面要跑几秒到几十秒的模型流。所以中途失败时用户消息已经存在、助手消息缺失，这是有意的——前端刷新后仍能看见自己问了什么。

## 三、问题改写与拆分

不这么做会出什么事：用户的原话里有指代（"它的上限是多少"）、口语缩写、行业别名，直接拿去做向量检索召回会很差；而一句话里塞了两三个问题时，只检索一次必然漏掉其中一部分。

流程是：先做**规则归一化**（把配置好的业务术语别名统一替换成标准词），再把归一化后的问题连同最近 4 条对话消息（最多两轮，且只留用户与助手消息、把系统摘要过滤掉省 token）一起，调一次**快速档模型**，要求它返回一个 JSON：改写后的问题、是否需要拆分、子问题数组。

- 判断条件上有一处是我改的：**以模型返回的"是否拆分"布尔位为准**，而不是看数组里有几条。上游实现忽略这个字段，模型明明判定不拆、数组里偶发多条内容，也会触发多次检索，白白瓜分后面的上下文额度。现在判定不拆就只用改写结果一条，判定要拆才用数组并去重。
- 失败处理很简单且是单层的：模型调用异常、返回不是合法 JSON、或者改写结果为空，一律**回退成"归一化后的问题"单条**，不做跨档位升级重试。改写只是检索质量的优化，不值得为它把整次问答拖住。
- 改写开关关掉时，走纯规则：归一化后按标点切句。

## 四、检索范围：权限在召回之前求交（自己加的）

不这么做会出什么事：知识库有公开库、私有库、按用户/角色授权的库。如果先全库召回、再在结果里过滤掉不可读的块，那么私有库里那条最匹配的块会**先占掉 TopK 的名额再被删掉**，用户拿到的是一个变短甚至为空的上下文——越权没发生，但答案质量被别人的私有数据悄悄拖垮了；更糟的是块数、耗时这些旁路信息也会泄露"存在一条更匹配的内容"。

所以范围解析放在召回之前，产物是一个字符串列表（本次能看的知识库物理集合名）：

1. 取**所有未删除的知识库**的集合名（唯一的"全库范围"来源；不使用按名字通配的做法，通配会命中已删除库的残留索引、测试库、旧结构）；
2. 取**当前用户可读的知识库**——一条 SQL 走完所有者、公开、按用户或角色授权三条路径；
3. 两者求交，得到本次的检索范围。

这个范围由引擎**按子问题各算一次**，挂在检索上下文里，各通道只读不判。这样同一个子问题下多条通道看到的范围一定一致，不会出现一条通道按新权限、另一条按旧权限的情况。

权限隔离的完整内容（越权矩阵、授权模型）在权限那一篇。这里只记一个跟检索直接相关的结论：在真实 PostgreSQL/pgvector 上的集成测试里，把最佳匹配放进私有库后，其他用户即使把最终条数压到 1，拿到的仍然是公开库的块——证明过滤发生在召回之前，而不是召回之后。

## 五、多通道召回

现在启用的只有向量一条通道（联网通道默认关闭），但引擎仍然是多通道结构，因为融合、归因、超时降级这几件事都建立在"通道是可插拔的一路证据"之上。这部分是上游自带的。

- **通道并行执行**，各自跑在检索线程池上。每条通道有**通道级超时（默认 15 s）**：超时只放弃这一路的结果、按空结果降级，不中断已经发出去的查询，其余通道照常参与融合。这是为了不让最慢的一路钳制整个子问题。
- **通道内异常也降级为空结果**，不向上抛。附带的代价是"通道挂了"和"通道没搜到"在上层看起来一样，只能靠日志区分（这是下面"边界"里的一条）。
- 一个例外的判断：**如果一条通道都没启用**，不静默返回空，而是打警告——那意味着全站退化成裸模型问答，属于配置事故而非正常降级。

向量通道自己做的事：把子问题实时调一次 embedding 模型拿到查询向量并归一化，然后在范围内的所有集合上**一条 SQL** 查完（共享表，集合名 `IN`，`LIMIT` 是整个范围的总条数），取数深度只受"每通道召回额度"管，默认 20 条。两个容易被追问的细节：

- 查询前会话级地放宽索引参数（`hnsw.ef_search`、迭代扫描），为的是带过滤条件时仍能填满 `LIMIT`，避免过滤式向量检索的召回悬崖；
- 拿回来的结果**先按分数排序再截断**，不信任数据库返回序——迭代扫描的宽松序模式允许轻微乱序，而规划器不会补排序节点。
- 查询向量**不走 embedding 复用缓存**，那套内容寻址的复用只覆盖入库侧（见 embedding 复用那一篇）。

## 六、后处理链：去重 → 融合 → 成本兜底 → 富化 → 重排

后处理器是一条按序号排的链，逐个执行；**某个处理器抛异常就跳过它，链继续往下走**，不让一次重排失败毁掉整次召回。

1. **去重**：按块身份合并多路命中，保留首次出现的实例，不比较跨通道的原始分数——余弦分和 BM25 分量纲不同，直接比是错的。
2. **融合（RRF）**：只看各通道各自的原始名次，按 `权重 / (k + 名次)` 累加打分，默认 k 取 20（候选池通常只有几十条，常见的 60 会把名次抹平），通道权重让新接入或可信度低的通道话语权小一些。名次取自各通道不可变的结果列表，所以上一步已经合并过也不丢"多路命中"的信息。单通道时跳过融合，保持原召回顺序。融合后按**候选池上限（默认 40）**截断，只把头部送进下游——这就是"粗排 + 精排"的两阶段分工。
3. **候选池成本兜底**（自己加的）：融合被关掉或融合失败时，上面那道截断就不存在了，回表和重排会先按全量做完再截断。加一个独立的守卫处理器放在富化和重排之前，保证无论融合是否生效，候选池规模都有同一个上限。
4. **元数据富化**：按块 ID 回表补文档归属、块序号、文档名，并为重排单独拼一段"文档名 + 结构化检索文本"。重排看这段文本，最终进模型的上下文仍用原始正文——这样 PDF 的标准文件名、表格的表名键值能参与精排，又不会污染引用和前端预览。只富化、不重排，顺序不变；回表规模被候选池上限兜住。
5. **重排**：把候选池交给重排模型，要头部若干条。上游原本到此就截断，我改成：**模型返回的头部在前，没进头部的融合候选按原顺序追加在后**，整池继续往下传。原因见下一节——最终取几条不能在子问题内部决定。

## 七、请求级额度：多子问题怎么分 TopK（自己加的）

不这么做会出什么事：上游给**每个子问题各发一份最终条数**。配置写 10，问题被拆成 3 个，实际进模型的就是 30 条——拆得越多、上下文越长、精度越低、token 成本越高，而这三者都不在配置里写着。更隐蔽的是跨子问题重复：两个子问题召回同一块，去重后名额就凭空少一个，没人补。

所以我把检索漏斗的预算显式拆成三段，一次算好，各阶段只读属于自己的那段：

- **每通道召回额度**（想大，保召回，默认 20）；
- **候选池上限**（重排的成本天花板，默认 40）；
- **最终进模型条数**（产品语义上的 TopK，默认 10）。

前两段是每个子问题各一份的质量预算，第三段是**整次请求**的总额度，必须在子问题之间分摊。启动时校验漏斗单调收窄（召回额度 ≥ 最终条数、候选池上限 ≥ 最终条数）。

分摊规则：总额度除以子问题数，余数按顺序前几题各多一条。极端情况下子问题数超过总额度，靠后的子问题分到 0 条，显式打警告并跳过它的检索——保证"最终 10 条"这个产品契约不被突破。

各子问题**并行**跑各自的检索链（独立线程池），单个子问题整条链失败时降级为空上下文，不影响其他子问题。

最后是请求级选择。这里有两套行为，由开关切换，**当前默认走的是旧行为**：

- **旧行为（默认）**：每题只取自己配额长度的前缀，跨题重复留下的空位不回填。
- **公平回填（默认关闭）**：第一阶段按题轮询，每题在自己配额内一次取一个全局唯一的候选，跳过重复继续往后扫；第二阶段继续轮询，用各题剩下的唯一候选把总额度填满。关键取舍是：**不同子问题的重排分数不可横向比较**（不同 query 下的分数不同分布），所以空位不按"全局最高分"竞争，而是轮流各补一个。

不管走哪一套，最后都做一次全局去重，产出一份**唯一的、有序的**块列表。这个顺序很重要：提示词按子问题分组渲染，来源编号、落库的证据片段、离线评测里的命中率都必须与模型实际看到的顺序对应，否则评测数字和线上行为对不上。

如果整次请求一条块都没选出来，链路在这里**短路**：直接推一句"未检索到与问题相关的文档内容。"，走完成事件收尾，不调生成模型。

## 八、提示词组装与来源编号

顺序上有个容易记错的地方：**先装来源列表，再组装提示词**。因为行内角标用的编号必须和前端来源面板、落库的来源是同一份。

1. **装来源**：把最终块列表按文档归并（同一文档取最高分的块作为摘录和排序依据），按分数降序从 1 开始编号，回表补来源类型和外链，产出文档级来源列表。这份列表随完成事件下发、随助手消息落库，并且是行内角标的唯一编号源。
2. **注入引用编号**：上下文格式化阶段只写内部文档 ID 作为锚点；这一步按上面的编号把锚点替换成模型可见的编号。引用开关关闭时**仍然要过这一道**，只是不注入编号、只把内部 ID 抹掉——否则内部 ID 会漏进模型可见文本。
3. **装证据片段**：另外装一份块级片段随消息落库，只供答完之后生成推荐追问用，不进提示词。
4. **组装消息序列**，固定三段：系统提示词（按智能体配置取模板，开了引用再拼一段引用规则）→ 对话历史（摘要作为历史第一条系统消息，自然紧跟系统提示词）→ **证据与问题合并成的一条用户消息**（多子问题时编号列出）。

上下文本身的渲染规则有两条值得记：块**按文档聚合**，文档之间按"该文档最佳块的名次"排序，文档内部按块序号升序还原原文顺序；**刻意不把文档标题写进上下文**——标题一进去，模型就会写"出自《XX》"这类归因表述，提示词层面的禁令压不住，文档名只在前端来源面板里出现。

生成请求用温度 0、top_p 1；深度思考开关决定走不走思考档模型。

> 提示缓存那套（稳定前缀、阈值压缩、显式缓存断点）是研究任务链路上的改造，**不在这条普通问答链路里**，见提示缓存那一篇。

## 九、流式输出与落库

- 模型开始吐字前，连接上已经发过元信息事件（会话 ID + 任务 ID）；同时本地把这个任务注册进任务管理器，登记 SSE 发送器和"被取消时怎么收尾"的回调。
- 思考片段和正文片段分别以两种类型推送，按码点切成小块发（默认每 1 个码点一条事件，按码点切是为了不把代理对劈开）。思考开始到正文第一个字之间的时长被记成"思考耗时"，随消息落库。
- 正文在内存里累积。**完成时**才一次性把助手消息落库（正文、思考、来源、证据片段、回复的消息 ID、正常状态），然后发完成事件（带消息 ID、会话标题、来源列表）、发 `[DONE]`、注销任务、关闭连接。
- 落库失败只记日志，**仍然发完成事件**——前端已经看完整段回答了，此时报错只会让用户以为答案没生成。代价是这条回答不会进历史。
- 出错时注销任务并以异常关闭连接；SSE 发送器内部用 CAS 保证连接只关一次，且关闭后再发事件是静默丢弃，不抛给全局异常处理器（响应体已经开始写了，再走异常处理器会把响应写坏）。
- SSE 连接有 5 分钟全局超时。
- 整条链路外面还套着一层链路追踪（上游自带）：记一次 run 和各阶段节点，失败或取消时收尾成对应终态。它是**旁路观测**，本身失败不能影响主链路。

## 十、用户取消

不这么做会出什么事：用户点了"停止"，但生成还在继续——上游 token 继续烧、连接不释放、已经吐出的半截回答丢失不落库；多实例部署时，停止请求还很可能落到一个根本没跑这个任务的实例上。

停止是一个**独立的 HTTP 请求**（带任务 ID），不走 SSE 连接。流程：

1. **归属校验（自己加的）**：取当前登录用户，检查这个任务 ID 是不是他的；管理员可以停任意任务。不属于自己和任务不存在返回**同一句提示**，不泄露任务是否存在。上游原本谁都能凭任务 ID 停别人的流。归属关系写在 Redis 里（不是本地内存），因为停止请求可能落到任一实例；跟取消标记同样 30 分钟过期，**任务正常结束时不删除**——否则用户在结束那一瞬间点停止会被误判成越权。这也是为什么归属要在生成任务 ID 之后、把任务 ID 发给前端之前就写进去：前端拿到 ID 时，归属一定已经落地。
2. **先打标记，再广播**。往 Redis 写一个取消标记（同样 30 分钟过期），再通过 Redis 的发布订阅把任务 ID 广播给所有实例（包括自己——本机也通过监听器统一处理，避免两条路径重复执行）。两步的顺序不能反：标记是给"还没注册上来的任务"看的。
3. **各实例本地处理**：查本地任务表，命中才继续；用 CAS 把"已取消"置位，保证只执行一次。然后按顺序做三件事——先把追踪状态收尾成已取消（旁路观测必须先于后面两步，后面抛异常也不能留下一个永远 RUNNING 的记录，且数据库更新只允许"运行中 → 已取消"，所以重复调用安全、也不会把正常终态改写成取消）；再调模型流的取消句柄；最后构造取消收尾载荷、发取消事件和 `[DONE]`、关闭连接。
4. **收尾时把半截回答落库**，消息状态标成"被中断"。如果一个字都没吐出来就不落库。
5. **两个竞态窗口**（这部分是我后来收口的）：取消可能早于任务在本地注册——注册时会回查 Redis 标记，发现已取消就立刻走收尾；取消也可能早于模型流句柄绑定上来——绑定时发现已取消就立刻取消句柄。发送取消收尾同样用一个 CAS 位保证只发一次。
6. 取消置位之后，所有流式回调（正文、思考、来源、完成、错误）都先检查取消位并直接返回，不再往已关闭的连接上写。

## 边界与不足

- **取消不是原子的**。"写 Redis 标记 / 广播 / 本机置位 / 取消模型流 / 落中断消息 / 发 SSE 事件 / 收尾追踪状态"是若干独立动作，任何一处失败只记日志。最坏情况是用户看到连接已关，而上游模型还在跑完剩下的 token；这一段没有做补偿或对账。
- **通道失败和"没搜到"在上层不可分**。通道级超时与异常都降级成空结果，后处理器异常只是跳过；对调用方和前端而言都是"结果变少了"，只有日志区分。没有做按通道的失败率统计或熔断，这条链路上的上游容错（退避、熔断）只覆盖了研究任务那边的模型调用。
- **请求级公平回填默认是关闭的**，线上默认仍是"每题取配额前缀、重复留下的空位不回填"。公平回填只由单元测试覆盖，没有在这条问答链路上做过前后对照的效果实验。
- **问答链路的 SSE 不支持断线续传**。没有事件 ID、不认 `Last-Event-ID`，连接一断这一轮就只能重问；带断点的 SSE 只做在研究任务那条链路上。另外任务的本地注册表是进程内的，实例重启后在途任务无法恢复，只能靠 5 分钟超时兜底。
- **上下文是模型看到的全部**，链路里没有"检索到的内容是否足以回答"的判定，也没有生成后的忠实度校验。空检索会短路回一句固定话术，但"检索到了但都不相关"会照样送进模型。
- **这条链路上没有量化实验数字**。本篇引用的唯一实验结论是权限求交那条（真实 PostgreSQL/pgvector 上的集成测试），其余关于额度、融合参数、上下文布局的取舍都只有单元测试和日志归因支撑，没有做过端到端的答案质量对照。

## 口述版

普通问答这条链路，从用户在会话里提一个问题开始，到一条 SSE 连接正常结束为止。请求进来先过两道闸：同一个用户只允许一条在途对话，然后进一次基于 Redis 的公平排队，默认十路并发、最多等十五秒，等不到不是报错，而是把一条"系统繁忙"的消息落库再从同一条连接上正常收尾，前端不用为限流单写一条错误路径。

拿到执行机会后，先并行读会话历史和摘要、把用户这句话落库，再调一次快速档模型做改写和拆分——改写失败就回退成归一化后的原问题，它只是检索质量的优化，不值得把整次问答拖住。接着解析检索范围，这一步是我自己加的：把所有未删除的知识库和当前用户可读的知识库求交，结果挂在检索上下文里，各通道只读不判。关键是这个交集必须发生在召回之前——如果先全库召回再过滤结果，私有库里那条最匹配的内容会先占掉名额再被删掉，用户拿到的是一个被别人的私有数据拖短的上下文。集成测试里把最佳匹配放进私有库，其他用户哪怕把最终条数压到一条，拿到的仍然是公开库的块。

然后是召回和后处理：通道并行跑，每条通道十五秒超时，超时只丢自己这一路、其余照常融合；结果先去重，再用 RRF 按名次融合——余弦分和 BM25 分量纲不同没法直接比，RRF 只看名次，天然跨模态可比；融合后按候选池上限截到四十条送重排，回表富化只在这四十条上做，成本有上界。

我在这一段改的第二件事是把检索预算拆成三段：每通道召回额度、候选池上限、最终进模型条数。上游把最终条数发给每个子问题各一份，配置写十条、问题拆成三个，实际进模型就是三十条，上下文精度和 token 成本都随拆分次数恶化。现在最终条数是整次请求的总额度，在子问题之间分摊，最后做一次全局去重产出唯一有序的列表——这个顺序同时被提示词、来源编号和离线评测复用，保证评测数字对应的就是模型真正看到的顺序。相应地重排也改成不在子问题内部截断，而是头部在前、剩余候选在后整池往上传。需要说清楚的是，配套的公平回填开关目前默认是关的，线上还是旧的前缀行为。

再往后是装来源、注入引用编号、组装提示词，然后流式推送，完成时一次性落库、发完成事件和 DONE。取消是一条独立的 HTTP 请求：先校验任务归属——这也是我加的，上游原本谁都能凭任务 ID 停别人的流，归属写在 Redis 里、随取消标记一起过期、任务结束时不删，避免用户在结束瞬间点停止被误判成越权；然后写取消标记、广播给所有实例，各实例本地 CAS 置位，先收尾追踪状态，再取消模型流，最后把半截回答按"被中断"落库并发取消事件。取消早于任务注册、早于模型句柄绑定这两个窗口都单独收口了。诚实地说，这一串动作不是原子的，最坏情况是连接关了而上游还在跑完剩下的 token，这块没做补偿。
