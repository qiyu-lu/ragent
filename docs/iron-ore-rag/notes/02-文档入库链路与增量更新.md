# 02 文档入库链路与增量更新

这一篇讲一份文件从上传到可以被检索出来，中间经过哪些步骤，每步的判断条件和失败后果是什么；以及文档改版重新入库时，怎么做到只为改动的那一小部分重新付向量化的钱。

## 一、上传：只登记，不干活

发起方是管理员在后台上传一份检测资料（或者填一个可下载的 URL），带来的是一个文件和一份摄取配置（解析档位、分块预算），想得到的是"这份文档以后能被问答检索到"。但**上传这个请求到登记为止就结束了**，不会等解析和向量化。

不这么做会出什么事：解析一份带版面的 Excel 要调外部版面服务和视觉模型，向量化要按块批量调嵌入接口，几十秒到几分钟很正常，挂在 HTTP 请求上必然超时，而且重试就是重复付费。

上传这一步按顺序做三件事，顺序本身是有讲究的：

1. **纯校验前置到第一个副作用之前**。先校验来源类型、定时刷新配置、摄取配置，再去存文件。反过来的话，存了对象却抛异常，存储里就留下一个没有文档记录指向它的孤儿文件。
2. **先按字节探测真实类型（只读流的前几 KB），再存文件，然后查解析器路由表**。路由表里没有认领这个类型的解析器，就立即删掉刚存的文件并拒绝。这一步用的是和后面分块阶段**同一套路由**，所以不会出现"上传成功、分块必失败"的情况。
3. **从文件名解析出文档键与版本号，插一行文档记录，状态为待处理**。文件名里形如 `V1.2` 的片段被识别成版本，去掉版本后的部分作为文档键。同一份资料的两个版本是**两份独立的文档记录**，各有各的块，不是一份文档的两个历史版本（这点下面第五节展开）。

然后由管理员（或定时刷新）触发分块。触发这一步做的是：把文档状态从"非运行中"改成"运行中"并发一条分块消息，两件事放在一个事务消息里（本地事务改状态、成功才投递，加一个回查器兜住半消息）。状态更新带 `!= RUNNING` 条件，更新行数为 0 就说明已经有人在跑，直接报"正在进行中"——这是防重复触发的唯一闸门，靠的是数据库的条件更新而不是应用层判断。

## 二、摄取内核：五步骨架

消费者收到消息后执行真正的摄取。全系统只有这一条摄取执行序列，不管是手工触发、定时刷新还是离线导入，走的都是它；内核本身不碰任务状态、不写日志，只负责"字节进、块和向量落库出"。

- **① 类型识别**：摄取执行序列里唯一一次按字节探测 MIME。识别不出直接失败。识别结果事后会回填到文档记录上，覆盖上传登记时探测的那一个；前端展示用的类型标签仍由扩展名决定，两者互不导出。
- **② 解析**：用 (MIME × 解析档位) 两个维度去查解析器。档位有快速档和保真档两级，是"愿意花多少外部成本换多少版面还原度"这一个维度，和格式正交：同样是 Excel，快速档本地解析，保真档走外部版面解析服务。查找顺序是"精确 MIME + 请求档位 → 通配 + 请求档位 → 精确 + 快速档 → 通配 + 快速档"，**全不命中就显式报错**，不会静默兜底到某个通用解析器上——静默兜底的后果是用户以为自己选了保真档、实际拿到的是纯文本。启动时还有一次自检：对外声明支持的每个扩展名，探测出的 MIME 必须被某个解析器精确认领，否则进程起不来。
  解析的产出不是一大坨文本，而是一串带类型的结构块：标题、段落、列表、代码、表格、图片。后面分块就靠这个类型分发。
- **③ 分块**：见第三节。
- **④ 向量化**：见第四节。模型标识和维度都来自"向量落点"这个入参，它由知识库配置和部署配置合成，不允许为空、不允许回落到系统默认模型——嵌入模型选错，整个库的向量就和检索时的查询向量不在同一个空间里，是静默的错误。返回的每条向量都逐条校验维度，对不上立即报错，不然要等写向量库做类型转换时才炸。
- **⑤ 落库**：见第五节。

每一步的耗时单独计时，和块数、缓存命中数一起写进分块日志。整段摄取包在一个 try 里，任何一步抛异常就把文档状态改为失败、日志记下错误信息，不重试；失败的文档由人看到状态后手动重跑。

另外有一个兜底：定时任务每分钟扫一遍，把停在"运行中"超过 30 分钟的文档重置为失败。这覆盖的是进程崩溃这类"消息已消费、状态没人收尾"的情况——没有它，那份文档会永远卡在运行中，连重试的入口都点不动。

## 三、分块：切法由文档结构决定

不这么做会出什么事：按固定字符数硬切，表格会被从中间劈开（后半截没有表头，检索出来是一堆没有列名的数字），标题会和它管辖的正文分家。

这里的取舍是：**切法由文档结构唯一决定，用户只能调体量**。用户可配的只有分块预算——目标块大小（默认 1024 字符）、相邻块重叠（默认取块大小的八分之一）、表格每块行数上限（默认 50）、为保完整性允许超出目标的倍数（默认 3 倍）。块大小硬上限 8192 字符，在构造预算时就拦住，因为真正的硬约束是嵌入模型的输入长度，不拦的话超长块要到向量化那一步才报错。

几个值得记住的点：

- **块大小取 1024 而不是常见的 512**：防语义稀释靠的是按章节边界打包，不是把块压小；而问答链路最终进模型的默认只有 10 块，块太小会让这些名额被同一章节的碎片占满。
- **目标大小是目标不是硬上限**：切开一个完整语义单元的代价高于超出目标，所以允许撑到目标的若干倍来保完整性。
- **重叠不只是为了冗余**：它同时是切分时向后回退去找句末标点的最大距离。取小了，切口会落在句子中间；中文长句配 1024/64 经常回退不到句号，所以重叠按块大小等比给。
- **表格分块**（这里只带一句，它在第四节还会回来）：按行贪心累加，同时按展示文本和向量文本两种渲染的实际长度算预算，超出行数上限或加下一行会超预算就先落一块，每块都带完整表头；展示文本是完整的 markdown 表格，向量文本改成"列名: 值"的形式，因为 markdown 表格靠位置对齐列名和值，嵌入模型读不懂位置。

**每个块有两份文本，这是后面很多事情的前提**：

- **展示文本**是文档原貌，标题按原文位置留在正文里，用于回填给大模型和前端预览。
- **向量文本**是真正送去向量化的那份，等于"正文里还没出现的那几级章节路径 + 正文"。同一节被切成多块时，只有首块的正文自带标题，续块光看正文不知道自己属于哪一章，所以要补章节路径；但首块已经自带的那几级就不再重复拼，否则只是把章节名连写两遍、白占向量里的位置。

向量文本会和展示文本一起落库。这不是为了展示——它让换嵌入模型时可以直接重新向量化而不必重新解析（省掉版面解析和视觉模型的重复成本），也让人工编辑过的单个块能正确重算向量。入库时的结构信息（章节路径、表格的"列名: 值"渲染、图片去掉 URL 后的描述）只存在于这一列里，重走一遍装配拿到的只是裸正文。

## 四、按内容哈希复用向量（W5）

不这么做会出什么事：一份几十页的调研表改了一行数字，重新入库时整份文档的每一个块都会被重新送去向量化。更新慢，而且按 token 重复付费——实测一份 79 块的调研表，全量重嵌入是四万多个计费 token。

只读核对时发现三件事，正好构成做法的基础：块表里早就存了内容哈希但没人用；重新入库走的是"整份删掉再插入"；摄取侧只有一个向量化入口，普通入库、管道节点、单块重嵌入全都经过它。所以只要在这一个入口上加缓存就够了。（顺带一提：另一套"管道模式"的摄取路径当前被显式禁用、直接抛错，所以现在真正可达的只有上面那条执行序列。）

### 4.1 缓存键为什么是这三段

键是 **（模型、维度、向量文本的 SHA-256）**，和块 ID、文档、知识库都无关。

- **按内容寻址，不按文档寻址**。这是和另一个常见做法的分岔：如果按"文档 ID + 块序号"做增量，那么上传新版本成了另一份文档就完全命不中，回退旧版本也命不中。按内容寻址的话，同一份文档重新入库、新版本里没变的段落、回退到旧版本，三种情况都能命中。参考的是 LangChain 的 `CacheBackedEmbeddings` 和 LlamaIndex 摄取管道的去重思路。
- **模型这一段用解析后的"供应商:模型名"，不用候选别名**。别名是配置里的一层间接，今天指向 A 模型，明天可以改指向 B 模型；如果键里存别名，改指向之后旧向量还会被当成有效命中返回，而不同模型的向量根本不在同一个空间里——这是"embedding 不能跨模型降级"的同一条规则。候选清单里查不到这个别名时，这一批既不查缓存也不写缓存，由上游调用去报模型不可用。
- **维度也在键里**。同一个模型截成不同维度的向量互不通用。键里已经含维度，取回来之后还会再核一遍向量长度，不对就当没命中——错维的向量写进向量库要到类型转换时才报错。
- **哈希的对象是向量文本，不是展示文本**。真正送给模型的是向量文本，展示文本相同而章节路径不同的两个块，向量应该不同。

### 4.2 一次向量化的执行顺序

1. 对每个块的向量文本算 SHA-256，解析出真实模型标识。
2. **批量查缓存**：一条语句按（模型、维度、哈希集合）更新最近使用时间并返回命中的向量。查和"刷新 LRU 时间戳"是同一条语句做的，不用先查后写两次往返。
3. **未命中的按首次出现顺序去重**再送上游：同一份文档里重复出现的表头、页眉只送一次，返回后按哈希分发回各个块。
4. **回写缓存**：主键冲突时保留先写入的向量、只刷新最近使用时间。并发下两个入库任务同时算出同一段文本的向量是可能的，保留先写的那条就够了——同模型同文本的向量本来就该一样。
5. 按原始顺序组装出"块 + 向量"的列表，块的顺序和入参完全一致。同时返回三个计数：块数、命中数、上送文本条数，写进分块日志。

### 4.3 两个关键取舍

**缓存写入不和块写入同事务**。原本计划写的是"同库同事务"，实施时改了。理由：缓存只省钱，不参与正确性——同一段文本在同一个模型下的向量不依赖它属于哪份文档。如果放进块写入的事务里，块写入失败就会把已经付过费的向量一起回滚掉，重试时再付一次钱，正好和这件事的目的相反。

**缓存故障一律降级**。查表或写表抛异常只记一条 warn，这一批全部改走上游，入库不失败。整个开关也可以配置关掉，关掉后每次入库都全量调上游。

**存成 `REAL[]` 而不是 pgvector 的向量类型**。缓存是按主键精确取，不需要相似度索引；`REAL[]` 按 float4 二进制原样往返，维度不固定在列上，所以不同维度的模型可以共用一张表，建表时加一个"数组长度 = 维度"的检查约束兜住。淘汰：写入之后数一次总行数，超过上限（默认 10 万条，1536 维一条约 6 KB）就按最近使用时间删掉最旧的若干条；命中也会刷新这个时间。读路径不做计数。

### 4.4 表格中插一行为什么会让该表后续所有块失效

这是复用率的天花板，也是最容易被追问的一点。

表格分块是**按行顺序贪心累加**的：从第一行开始往组里加，加到超出行数上限或者再加一行会超预算就落一块，然后重新起一组。所以块的边界完全由"从表头数下来第几行"决定。在一张表的中间插入一行之后，插入点之后的每一组都会整体后移一行，于是**这张表后面所有块的文本都变了**，哈希全变，一个都命不中。改之前的那些块不受影响。

修复方向是改用内容定义的分块边界（按内容滚动哈希决定切点，插入一行只影响局部），但没有做。W5 的实测也没有覆盖这种情况——手上只有一对真实版本，改动正好落在段落里。

### 4.5 实测数字

一份调研表的两个版本（V1.2 / V1.3），各 79 块。

**真实上游**（SiliconFlow `Qwen/Qwen3-Embedding-8B`，1536 维，2026-09-19 单次运行，新建的空库、缓存从空表开始，关闭了图片解析）：

| 步骤 | 块数 | 命中 | 上送文本 | 上游调用 | 计费 token | 向量化耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| V1.3 关闭缓存（对照） | 79 | 0 | 79 | 3 | 45,722 | 34.7 s |
| V1.2 首次入库 | 79 | 0 | 79 | 3 | 45,645 | 9.2 s |
| V1.2 原样重新入库 | 79 | 79 | 0 | **0** | 0 | 0.07 s |
| 升级到 V1.3 | 79 | 77 | **2** | 1 | **1,368** | 0.29 s |
| 回退到 V1.2 | 79 | 79 | 0 | **0** | 0 | 0.03 s |

token 是供应商响应里返回的 `usage.total_tokens`，5 步里上游失败 0 次。V1.2→V1.3 需要重嵌入的是 2/79 块，计费 token 从全量的 45,722 降到 1,368，占 2.99%。每一步之后，块表和向量表里这份文档的行数都等于块数。

同样的流程在模拟上游下跑过一遍，块数和命中数完全一致——说明**复用率只由文本决定**，换上游不影响。

耗时只能看量级，不报加速倍数：两次全量向量化分别是 34.7 s 和 9.2 s，同样 79 块、3 次调用差了近 4 倍，那是供应商延迟的波动，而且只跑了一次。能下的结论只有一条：命中时不调用上游，向量化耗时从"秒到几十秒、随供应商波动"降到查一次表的亚秒级。

## 五、落库：先删后插与事务可见性

不这么做会出什么事：重新入库时如果是"边删边插"或者分两个事务，中间有一段时间检索会读到半新半旧的块——一半是旧版本的数字，一半是新版本的，而且看不出哪块是哪版。这种结果对"检测数据问答"这种场景是直接的事实错误。

落库这一步的形状是：内核把"整体替换这份文档的块"交给一个写入器，写入器**开一个事务**，然后扇出给所有注册的落点。落点现在有两个：关系库的块表（最先执行）和向量库（最后执行）；未来加一个索引后端就是加一个落点实现，内核和写入器一行不改。

每个落点内部都是**先删这份文档的全部块，再插新块**。先删后插的顺序留在落点实现内部、不暴露给调用方，因为向量那条链上还挂着图谱同步的装饰器，它正是靠这个顺序构成 upsert 语义的。

关键在于**这两个落点确实在同一个事务里**：应用只有一个数据源，关系库落点走 MyBatis、向量落点走 JdbcTemplate，两者都加入外层开启的那个事务。这件事是用集成测试验证的，而不是靠读代码推断——测试让第三个落点在两张表都已经删旧插新、尚未提交时停住，另一个连接这时读到的仍然是旧版本的 3 个块；放行提交后读到新版本的 2 个块；如果第三个落点抛异常，两张表一起回滚到旧版本。**所以版本切换对检索方是原子的：要么全旧，要么全新。**

两个必须说清的边界：

- **事务只覆盖 PostgreSQL**。启用 ES 关键词索引、图谱或 Milvus 时，那些后端的先删后插在事务之外，失败时可能半新半旧。这是上游原有的行为，没有改。
- **块写入本身没有省**。这次省的只是向量化的上游调用；块表和向量表仍然是整份删掉重插，块 ID 每次重新生成。块表还是逻辑删除，每次重新入库都会留下一批标记为已删的旧行。

## 六、文档版本

版本是从文件名里认出来的：文件名中形如 `V1.2` 的片段作为版本号，去掉它之后的部分作为文档键，认不出版本的普通文档就以去扩展名的文件名作为文档键。

**同一文档键的不同版本是两份独立的文档记录**，各自有自己的块和向量，互不覆盖。取舍在这里：做成"一份文档 + 版本历史"的话，上传新版本要么覆盖旧块（旧版本就查不到了），要么要在检索时额外维护"哪个是当前版本"的过滤；做成两份独立文档则两版都可检索、对比两版差异只是查两条记录，代价是默认检索会同时召回两个版本的块，靠引用里的版本字段让人区分。

版本这个字段一路带到了检索结果和研究任务的证据里：每条引用都带文档名和版本号；研究任务复读一条证据时，会比对证据上记的版本和当前文档的版本，不一致就判定这条证据已经过期。另外还有一个按文档键 + 两个版本号做表格差异对比的接口，走的是同一套版本字段。

## 边界与不足

- **表格插行会让该表后续所有块失效**：分块边界按行顺序累加，插入点之后的分组整体后移。没有改成内容定义的边界；W5 只有一对真实版本，没有覆盖插行的情况。
- **事务边界只覆盖关系库和向量库这两张表**：缓存写入不在块写入的事务里（有意为之）；上传登记、发分块消息、执行摄取、回写状态和日志分属不同事务；启用 ES、图谱或 Milvus 时它们的先删后插也不在事务内，失败可能半新半旧，是既有行为。
- **写入量没有减少、淘汰也很粗**：块表与向量表仍整份删插，块 ID 每次重新生成，逻辑删除会不断累积已删旧行；缓存淘汰只在写入后整表数一次行数删最旧的，条目远超上限时应该换成定时任务或按时间分区。
- **图片块基本命不中缓存**：Excel 内嵌图片的描述来自视觉模型，每次生成的文字可能不同，向量文本就不同。W5 的实测关闭了图片解析。
- **耗时数字不可用于报加速比**：真实上游只跑了一次，两次全量向量化的耗时相差近 4 倍，是供应商延迟波动。
- **卡死恢复只认超时**：停在运行中超过 30 分钟的文档被重置为失败，恢复的是状态、不是执行；真正卡住 29 分钟的任务也无从发现。

## 口述版

文档入库是一条五步的链路：上传只做登记：先校验，再按字节探测类型、存文件、查解析器路由，然后插一行待处理的文档记录就返回，真正的解析和向量化异步做——因为解析一份带版面的表格要调外部服务和视觉模型，挂在 HTTP 请求上必然超时。触发分块时用一条带"状态不等于运行中"条件的更新来防重复触发，更新行数为 0 就说明已经有人在跑。异步那边是五步：探测类型、按 MIME 乘解析档位查解析器（档位是"花多少外部成本换多少版面还原度"这一个维度，查不到显式报错不兜底）、按结构分块、向量化、落库。分块的原则是切法由文档结构决定、用户只调体量，每个块会产出两份文本：展示文本是文档原貌，向量文本是"正文里还没出现的章节路径加正文"，送去向量化的是后者，而且它会落库，这样换模型时可以直接重嵌入而不用重新解析。

我做的增量更新是这样：原来改一行字，整份文档 79 个块全部重新向量化，按 token 重复付费。我在唯一那个向量化入口上加了一层内容寻址的缓存，键是"模型、维度、向量文本的 SHA-256"，和文档、知识库都无关——按文档做增量的话，上传新版本成了另一份文档就完全命不中；按内容做，原样重入、新版本里没变的段落、回退旧版本都能命中。键里模型用的是解析后的"供应商:模型名"而不是配置里的别名，因为别名改指向之后旧向量就不能用了，这跟 embedding 不能跨模型是同一条规则；维度也在键里。实测一份 79 块的调研表，真实上游下 V1.2 升到 V1.3 只有 2 块需要重嵌入，计费 token 从 45,722 降到 1,368，原样重入和回退旧版本是 0 次上游调用。有两个取舍我会主动讲：缓存写入故意不和块写入同事务，因为缓存只省钱不参与正确性，放进去的话块写入失败会把已经付过费的向量一起回滚；缓存读写出错一律降级走上游，入库不失败。落库那边是先删后插，关系库块表和向量表在同一个事务里扇出，我用集成测试证明过——未提交时另一个连接读到的仍是旧版本的全部块，提交后才整体切到新版本，不会出现半新半旧。已知的限制是表格分块按行顺序累加，在表中间插一行会让这张表后面所有块的边界都移动、全部失效，修复要换成内容定义的边界，我没做。
