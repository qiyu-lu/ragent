# 03 研究 Agent 的一次运行

这一篇讲的是：一个研究任务被执行器领到之后，在这台机器上到底发生了什么——主 Agent 怎么一步步检索、阅读、必要时拆给子 Agent、最后怎么结束并生成报告或计划。

起点是执行器已经拿到任务并持有租约（怎么领、怎么续租、失联后谁接管，见第 05 篇）。它交给运行时的东西是：一份研究简报（目标、产出类型是报告还是计划、用户约束、允许的知识库与文档范围）、这次运行的持久化状态（之前跑过的部分结果、已用掉的额度）、一个取消句柄。想得到的东西是一个结论对象：要么是一条向用户的追问，要么是一组"每条断言都挂着证据 ID"的发现。这一步到"结论落库、产物落库"为止；任务状态怎么变、事件怎么推给前端，是第 04 篇的事。

## 一、为什么需要一个受控的工具循环

不加约束地让模型自己跑工具循环，会出三类事故：一是不收敛，模型换着措辞反复检索同一个问题，把额度耗光也不结束；二是引用造假，它看了检索返回的摘要就直接写结论并编一个证据编号，报告看起来有出处、实际对不上原文；三是不可预算，一次任务花多少模型调用、多少钱、多久，事前不知道、事中停不下来。

所以这里的做法是：模型只负责"下一步做什么"，其余全部由服务端把关——工具的参数校验、调用次数、并发、可引用的证据集合、什么时候必须结束，都在服务端的包装层里，不依赖提示词的自觉。提示词只是用来说明意图，所有硬约束都有代码兜底。

## 二、一次运行的主线

**准备。** 执行器为这次运行建一个会话对象，它同时持有：租约凭证、共享预算、取消控制、以及这个 Agent 自己的"已读证据表"和"已接受的子任务结果"。然后按角色建模型调用包装器和工具集：主 Agent 注册四个工具（检索、阅读、追问用户、结束）加一个委派工具；子 Agent 只注册三个（检索、阅读、结束）——追问和再委派在工具契约层就不存在，模型看不见，也就不可能调用。

首条用户消息是简报加已保存的研究状态，序列化时按键排序，目的是同一个任务在任何进程里重建出来的前缀逐字节一致，供应商的前缀缓存才能命中（缓存怎么布局见第 06 篇）。这条原始请求随"研究已开始"事件一起落库，接管方据此重建同样的前缀。

**循环。** 之后就是标准的 ReAct 往返：模型输出一次工具调用 → 服务端执行 → 结果回灌 → 再次调用模型。每一轮有两个卡点。

- 模型调用之前，检查取消、检查总时长、检查租约是否还是自己的；如果服务正在停机，主 Agent 在这里停下并把任务交还队列（进行中的模型调用和已经决定的工具不打断，见第 04、05 篇）。然后扣一次模型额度，再去抢全进程的并发配额。
- 工具执行之前，再检查一次取消，扣一次工具额度，发"工具开始"事件（带上模型给的原始参数和同一轮所有调用的 ID，供接管重建历史用），执行，发"工具结束"事件（输出最多留 4 万字符）。除委派外的工具整体 30 秒超时。

**结束。** 模型调用追问工具或结束工具时，会话上记下结论，流被截断，循环退出。结论对象单独落一条事件——因为"工具结束"事件会随流截断丢掉，而结论如果丢了，接管方就得再花一次模型调用把同样的结论重新生成一遍。

## 三、先读后引

不做这件事的后果很直接：检索返回的是截断摘要，模型完全可以凭摘要下结论、再把摘要的编号当引用写进报告，用户点开引用发现原文根本没有这句话。这是评审最容易问、也最容易翻车的地方。

做法是把"可引用"定义成一个服务端维护的集合，模型没有任何办法往里加东西，只有真正走完一次阅读才会加。具体是四道闸：

1. **检索只产生候选。** 检索命中的每个块都会按"运行 ID + 来源身份 + 正文与位置的 hash"算出一个稳定证据 ID，连同数据库里的完整正文一起存成一份证据快照（注意存的是数据库正文，不是向量库或重排返回的摘录）。返回给模型的只是截断摘录和这个 ID，快照本身标记为"未读"。稳定 ID 还带来一个好处：同一个块重复检索到，保存是幂等的，接管后重做一次检索不会产生重复证据。
2. **有未读候选就不许再搜。** 最近一次检索返回的候选里只要还有既没读过、也没尝试读过的，再调检索就被拒绝，错误信息里列出未读的 ID。同时，同一个（查询语句，文档范围）组合最多允许两次，第三次直接拒绝并提示"换措辞不会让不存在的事实出现"。
3. **必须阅读时直接改工具选择。** 服务端在下一次模型调用里把工具选择从"任选其一"改成"只能调阅读工具"，模型没有绕开的余地。
4. **结束时逐条校验引用。** 每条发现必须有 1—12 个证据 ID，且全部落在可引用集合里；有任何一个不在，整次结束调用被拒，错误信息列出越界的 ID 和当前允许的 ID，回传给模型重来。产物生成阶段还会拿这批 ID 回证据表再查一次，确认"已读、属于本次运行、在允许的知识库与文档范围内"，不满足就直接失败，不生成。

阅读工具本身也有讲究。它按证据 ID 取回**首次保存的那份快照**，而不是重新去库里查当前内容，这样引用永远指向模型当时看到的文字；取回前先校验正文 hash 和快照记录一致。支持两种模式：只读本块，或读受限的邻接块。邻接展开会生成一份新的快照、返回一个新的证据 ID（提示词明确要求引用这个新 ID）。如果发现文档版本、名称、正文 hash 或来源位置已经变了，就标记为"来源已变化"，只返回旧快照并让模型在结论里说明这一点——不会悄悄用新内容替换。

子 Agent 还多一条限制：只能阅读自己检索返回过的证据 ID，不能凭猜测或从父 Agent 那里听来的 ID 去读别的东西。

## 四、预算：算什么、怎么算、耗尽时怎么办

没有预算的话，一次任务的成本和时长完全由模型的发挥决定；而且一旦探索阶段把额度用光，最后连"把已有发现整理成报告"的钱都没有了，等于前面全白跑。

**算什么。** 一次运行共用一份预算，主 Agent、所有子 Agent、产物生成都从这一份里扣：

- 模型调用总数 16 次，其中 2 次预留给产物生成。也就是探索阶段最多 14 次，探索阶段扣额度时会把预留量减掉再判断，扣不到就抛"模型调用额度耗尽"。
- 工具调用总数 24 次，在工具真正执行前扣。
- 单次请求输入上限 28000 token，由服务端自己估算（超了怎么压缩属于上下文布局，见第 06 篇）。
- 总活动时长 300 秒，等待用户补充条件的时间不计入。探索阶段还要再预留 min(30 秒, 总时长的 1/5)，留给收尾。
- 每次模型调用本身超时 60 秒，工具超时 30 秒，单个子任务超时 180 秒。
- 子 Agent 每个最多 6 次本地模型调用；并且子 Agent 扣全局额度时要求"扣完还剩至少 1 次"，保证主 Agent 一定还能做一次整合。

**在哪扣。** 额度在真正发出 HTTP 请求**之前**扣，不是在成功返回之后。原因是失败和超时同样消耗上游资源和时间，按成功计数就等于给失败重试开了无限额度。代价是：一次网络失败也占掉一次额度。同时每次调用在"调用台账"里留一条记录：调用 ID、模型、角色（主 / 子 / 产物生成）、任务 ID、状态、供应商返回的真实 token 用量、时延与首字时延；失败和被取消的调用也留记录，只是用量字段标成"未知"而不是填 0。台账随预算快照一起落库，既是成本核算依据，也是第 06 篇缓存命中率的数据来源。

**并发。** 进程内一个公平信号量限制同时进行的模型请求数（默认 2），主 Agent、子 Agent、产物生成共用。等待时每 100 毫秒检查一次取消，总等待超过"剩余探索时间和单次调用超时的较小值"就放弃并报配额等待超时——不会无限排队。

**耗尽时的行为。** 不是直接抛错了事，而是分三层收敛：

- **提前告知。** 每次模型调用都会附一条临时的提醒消息（只在本次请求里，不写进 Agent 的记忆，这样历史前缀保持逐字节稳定），内容包括：本次之后还剩几次探索调用、当前精确的可引用证据 ID 列表、已读文档与未读候选文档、以及"剩 2 次以内就别开新检索了，缺的事实写成缺口"。子 Agent 的提醒里还会强调只能引用自己读过的 ID；主 Agent 的提醒里带上已经通过校验的子任务压缩结果。
- **强制收尾。** 当剩余探索调用不超过 1 次时，工具选择被改成"只能调结束工具"。
- **真的用光。** 抛出带原因码的耗尽异常（模型额度 / 工具额度 / 时长 / 上下文 / 子任务数各有自己的码）。这时如果已经有可引用证据，收尾逻辑会把已有的发现打包成一个"部分完成"的结果，动用预留的那 2 次额度照常生成产物，任务记为 PARTIAL，原因码写进执行问题；如果一条证据都没读到，就直接失败并保留原因，不生成空产物——空报告会让用户以为"资料里确实没有"，而真实原因是检索不可用。

还有一个专门的退化路径：**模型不肯用原生工具结束**，而是输出一段纯文本或一段假装成工具调用的 JSON。这种情况下服务端追加一条修复指令（明确要求现在就调结束工具、只能用已读证据、不要再检索），并把后续调用的工具选择钉死在结束工具上，同一上下文里最多再给 2 次机会；仍然不行就报"必须通过原生工具结束"。这些修复调用照常扣全局额度。

检索连续失败 2 次也会触发类似的收敛：会话进入"检索受阻"状态，之后再调检索、再委派子任务都被拒绝，提醒消息里直接告诉模型"检索服务不可用不等于资料不存在，用已读证据结束，执行问题由服务端保留"；追问工具在"有执行问题且无任何可引用证据"时也被禁用，防止模型把一次检索超时包装成"请您上传资料"去问用户。上游重试、熔断本身见第 07 篇。

## 五、按需委派子 Agent

需要委派的典型场景是"对比 A 和 B 两份材料的某几个维度"：两条线互不依赖，串行做要多花一倍时间，而且两份材料的原文塞进同一个上下文很容易顶到输入上限。但子 Agent 带来的风险也很明确——额度被子任务抢光、子任务互相看到对方的中间过程污染结论、一个子任务挂了拖垮整个任务、父子在同一个线程池上互相等待死锁。

**委派的形状。** 主 Agent 一次提交 1—4 个子目标，每个要有目标、维度、期望产出，文档范围可选且**只能收窄**不能扩大（服务端校验，模型给的文档 ID 必须是简报里允许的）。深度只有一层：子 Agent 的工具集里没有委派工具。

**去重与原子分配。** 同一批里目标归一化后不能重复，跨批也不能和之前委派过的目标重复（恢复运行时会把历史上已委派的目标重新登记进去，只有"执行中断"的那些允许重派）。然后一次性申请 N 个子任务名额——要么 N 个全给，要么一个不给并抛出子任务数额度耗尽。不做逐个申请是因为部分成功最难处理：模型请求两条对比线，只批了一条，结果就是个不对称的半成品，还得再想办法补另一半。额度不够时这个错误作为普通的工具错误回传给模型，模型可以改成串行自己做，不会让整个任务失败。

**上下文隔离。** 每个子 Agent 拿到一个全新的会话：独立的消息历史、独立的已读证据集合、独立的取消控制（父的取消会级联到子，子的失败不会反向取消父）。它们共享的只有预算、证据存储和知识范围。返回给父 Agent 的也不是子 Agent 的对话历史，而是一个压缩结果：最多 8 条发现、8 条缺口、8 条冲突，总文字不超过 8000 字符，每条发现带证据 ID。父 Agent 想细看某条证据，可以自己再读一次——证据 ID 是全局稳定的。

**线程池分离。** 子任务跑在一个专用的有界线程池上（核心和最大都等于最大并发子任务数 2，队列 32，满了直接拒绝）。关键是父 Agent 不在这个池上等待：委派工具返回的是一个异步流，父 Agent 的等待发生在它自己的执行线程上。如果父子共用一个池，2 个线程被两个父 Agent 占着等子任务、子任务又排在队列里等线程，就是典型的池内互等死锁。

**并发与失败隔离。** 子任务按提交顺序并发执行、并发度 2、结果按提交顺序收集。每个子任务的超时取"配置的 180 秒"和"整次运行剩余时长"的较小值。**每个子任务的错误在自己那一条流上被吸收**：超时、执行异常、额度耗尽都会先取消这个子会话，然后转换成一个状态为失败或部分完成的结果对象返回给父 Agent，原因码写在执行问题里；如果它已经读到过证据，还会把读到的证据 ID 一并带回来（那些 ID 对父 Agent 依然可引用）。所以一个子任务挂掉，另一个照常完成，父 Agent 拿到的是"一份结果 + 一条失败说明"，可以继续往下走，只是最终结论会被标成部分完成。

**结果入账。** 子任务的每次状态变化（排队、运行中、终态）都写一次检查点到运行状态里，接管方据此知道哪些子目标已经做完、不用重做。入账严格由订阅方完成：超时或取消之后，那个还在后台跑的子任务即使迟到返回，也不会经过入账这一步。入账时父 Agent 还要再校验一次——子任务结果里引用的每个证据 ID 必须在它自己的已读集合里，否则拒绝接受。检查点落库和父端接受是同一段串行代码里的两步，但不是一个数据库事务。

## 六、产物：报告或计划

研究结束时拿到的是一组带证据 ID 的发现，还不是用户要的东西。产物生成是同一次运行里一次单独的模型调用，用预留的那 2 次额度、一个专门的生成角色模型，**不带任何工具**——它的任务是组织表达，不是继续研究，给了工具就又能去检索，预算控制就漏了。

输入是：简报、主 Agent 的结论、所有子任务结果、以及所有可引用证据的**完整正文**（前面说过，这批证据会先回证据表复核一遍归属和已读状态）。如果输入超过上限，做法是反复把当前最长的那条证据砍一半，直到装得下——而不是丢掉整条证据，因为丢了证据就没法校验引用了。

输出要求是纯 JSON。校验分几层：

- 类型互斥：报告类型不能带计划结构，计划类型不能带报告章节。
- 引用：每个章节、每条前置条件、每个步骤、每个参数都必须带非空的证据 ID，且全部在允许集合内、不重复。
- 引用编号由服务端分配：模型的正文里出现 `[1]` 这类编号或锚点会直接判非法，编号是服务端按引用出现顺序生成的，同时产出一张引用清单（证据 ID、文档名、版本、正文 hash、块 ID、原文摘录、来源位置）。这样"正文的第 3 个角标"和"引用清单第 3 条"永远对得上。
- 计划特有的：步骤序号必须从 1 连续；参数没有取值时，取值、单位、引用都必须为空，服务端自动把它转写成一条待确认项——空着比编一个数值安全得多。
- 空产物必须有解释：没有章节 / 没有步骤时，缺口或执行问题至少得有一条，否则判非法。
- 主结果和各子任务的缺口、冲突、执行问题会合并去重，追加成 Markdown 末尾的固定几节。

校验失败给**一次**修复机会：把错误原因、模型的原始输出、允许的证据 ID 列表一起追加回去再问一次。如果修复后的输入超过上限就直接停——不能为了塞下而裁掉证据，那样引用就无从校验了。两次都不过，这次运行记为失败，但研究阶段的发现保留在状态里，用户能看到"研究做完了、产物没渲染出来"，而不是全部丢失。校验通过则把产物对象、引用清单和 Markdown 一起随终态落库。

## 边界与不足

- 预算计数、已读集合、检索去重计数都活在内存里，只随事件快照落库。接管时靠重放已完成的工具调用重建，在途的那一次调用会被丢弃重做——W2 的测量里每个被接管任务重复 1 次模型调用（模拟上游，独立 JVM，租约 6 s / 轮询 1 s，118/118）。这次重复的额度会被重复计。
- 额度扣减、事件落库、实际的 HTTP 请求不在同一个事务里。扣完额度后进程崩溃，这一次额度就白扣了；反过来也存在调用已发出但记录没落库的窗口。
- 子任务的检查点落库和父端接受引用是两步，只靠同一段串行代码保证顺序，不是数据库事务；接受过程中失败会留下一个"已落库但父端未接受"的中间态。
- "先读后引"只保证被引用的证据确实在这次运行里被读过、且在允许范围内，**不保证陈述和证据的内容一致**。没有做句子级的蕴含校验，模型仍可能给一段读过的文字挂上一个它并不支持的结论。
- 委派的层数（1 层）、并发（2）、总数（4）、子 Agent 本地模型调用数（6）都是写死上限的配置，配置校验会强制并发不超过 2、总数不超过 4。需要更深的多跳研究时没有扩展余地。
- 委派本身没有做过专门的容量或质量基准。离线评测跑的是关闭委派的单 Agent 模式；多 Agent 下"已完成的子任务接管后不重跑"只由测试覆盖，没有端到端实测。

## 口述版

这个项目里研究任务是一个 Agent 跑的工具循环：检索、读原文、必要时拆子任务、最后结束。我的做法是模型只决定下一步做什么，所有硬约束放在服务端包装层。最主要的两件事，一是"先读后引"：检索只返回候选 ID 和截断摘要，同时把数据库原文存成一份带 hash 的证据快照标为未读；只有真正调阅读工具、取回那份快照，这个 ID 才进"可引用集合"。有未读候选时再调检索会被拒绝，服务端还会把下一次调用的工具选择直接改成只能调阅读；结束时逐条校验每个引用是否在集合里，不在就把错误回传让模型重来；生成报告前还会回证据表复核一次归属和已读状态。引用编号也是服务端按出现顺序分配的，模型在正文里自己写角标会被判非法，这样正文角标和引用清单永远对得上。

二是预算。一次运行共用一份额度：模型调用 16 次其中预留 2 次给产物生成，工具调用 24 次，输入 28000 token，总时长 300 秒。额度在发 HTTP 之前扣，因为失败同样花上游资源和时间；每次调用在台账里留一条记录，包含真实 token 用量和时延，失败和取消也留。耗尽不是直接抛错：每次调用会附一条临时提醒告诉模型还剩几次、当前能引用哪些 ID；剩一次时工具选择被钉死在结束工具上；真的用光时，只要读到过证据就用预留额度生成一份标记为部分完成的产物，一条证据都没有才判失败——不能用空报告掩盖检索不可用。另外模型如果输出纯文本不走原生结束工具，服务端会追加修复指令再给两次机会。

委派是按需的：主 Agent 一次提交 1 到 4 个独立子目标，名额一次性原子分配，要么全给要么不给，因为部分成功的对比任务是个半成品。子 Agent 是独立上下文、独立已读集合，只回传一个不超过 8 条、8000 字符的压缩结果，不回传历史。它们跑在专用线程池上，父 Agent 不占这个池等待，不然父子会在池里互等死锁。每个子任务的超时和异常在自己那条流上被吸收成一个失败状态的结果对象，不影响同批其它子任务，最终结论标成部分完成。不足也很清楚：先读后引只能保证证据被读过，保证不了陈述和原文一致，没做句子级蕴含校验；预算计数在内存里，接管时在途那次调用会重复计一次。
