# 04 任务生命周期：创建、状态机、事件流、取消

研究任务是分钟级的长任务：用户提交一个目标，服务端要跑十几次模型调用、几十次检索和阅读，最后产出一份带引用的报告。这一篇讲这条任务从"被创建"到"进入终态"之间，外部接口能做的四件事——创建、看状态、订阅进度、取消——各自在库里留下什么、怎么保证重复请求和断线重连不会把任务跑第二遍。

执行侧的另外一半（心跳续租、跨实例接管、epoch 写保护的由来、从事件重建上下文续跑、优雅停机、容量结论）在第 05 篇，这里只讲到"事件怎么落库、断线怎么按序号续上"为止。Agent 的工具循环与子任务委派见第 03 篇。

前置约定：任务表里有几个字段贯穿全篇——状态、修订号（每次状态变更加一，给客户端做乐观并发）、epoch（每次被某个执行者领取时加一，是 fencing token）、租约令牌与租约到期时间、事件序号计数器。写保护的口径始终是同一句话：**状态是执行中、epoch 等于我领取时拿到的那个、租约令牌是我的、租约还没过期**，四条同时成立才允许写。

## 1. 幂等创建：同一请求只建一次任务

不这么做会出什么事：创建接口背后是一次几十秒到几分钟、要花真钱调模型的执行。用户手滑双击、前端超时重试、网关重发，任何一次重复都会变成一次完整的重复计费执行，而且同一个会话里会多出一条看起来一模一样的任务。

做法是把幂等键放在数据库唯一约束上，而不是放在应用层的"先查再插"里：

- 请求体里必须带一个客户端生成的请求 ID。任务表上有 `(所有者, 客户端请求 ID)` 的唯一索引，插入语句写成"冲突就什么都不做"。并发的两次相同请求里，只有一条插进去，另一条的影响行数是 0；两条都接着按幂等键把这一行读回来，返回同一个任务。这一步不靠查询和插入之间的时间差，所以不存在"两个线程都查到不存在"的竞态。
- 幂等键不能只对 ID 负责，还要对"请求内容"负责。创建时把会话 ID 加上服务端确认后的任务说明（目标、约束、允许的知识库与文档范围）算一个指纹，存进任务状态里。回查到已有任务时比对指纹：不一致就直接报错（同一个请求 ID 不能提交不同的请求），而不是悄悄返回一个内容不同的任务。这是常见的"幂等键被复用"陷阱——只认键不认内容，客户端换了参数重试就会拿到旧结果还以为生效了。
- 插入成功的那一次，在同一个事务里还做两件事：新会话时补一条会话记录（沿用已有会话则只更新时间），以及写入第一条事件"已排队"。也就是说任务行和它的第一条事件要么都在，要么都不在。
- 权限校验只在"确实是新请求"时做：回查命中已有任务时跳过范围校验，免得源文档后来被停用导致用户连自己已经跑完的任务都打不开。注意这不是权限漏洞——每次执行者领取任务时都会按所有者当前权限重新校验一次知识库范围，撤销授权后旧任务不会继续检索（详见第 08 篇权限隔离）。

创建事务提交后，才把任务交给本机线程池（快速路径）。这一步刻意放在事务外：线程池满了抛拒绝时，只是把它从本地在执行的集合里摘掉，任务仍然以"排队中"躺在库里，等任一实例的轮询领走，**不判失败**。提交入口不会因为本机忙就拒绝用户。X6 容量基准（模拟上游，300 个积压任务 × 1/2/3 实例、每实例 2 个槽位，共 3600 个任务）里提交被拒 0 个，3 实例时 300 个中有 286—288 个是被轮询领走的，就是这条路径在积压下的表现。

"重新生成"接口走的是同一条创建路径：先确认上一条任务已进终态，再用它的任务说明加上客户端新给的请求 ID 建一条新任务。所以重新生成本身也是幂等的，而且不会覆盖上一次的结果和事件。

## 2. 状态机与条件更新

不这么做会出什么事：状态字段如果用"读出来、改一下、写回去"的方式更新，在多实例加上用户并发操作下必然出现互相覆盖——刚被接管的任务被旧执行者写成失败、已取消的任务被写成完成、等待补充条件的任务被重复提交两份不同的条件。

状态有八个：排队中、执行中、等待补充条件，以及五个终态（完成、部分完成、失败、已取消，另加一个只为读取历史保留的"中断"）。允许的迁移只有这几条：

- **排队中 → 执行中**：被某个实例领取。领取语句里同时做四件事——epoch 加一、发一个新的租约令牌、写上执行者标识、把租约到期时间设成"数据库当前时间 + 30 秒"。租约时间一律取数据库时钟，各实例的本机时钟不参与判定，避免时钟漂移把别人的健康任务判成过期。
- **执行中 → 执行中（换了执行者）**：只有在租约已过期时才允许接管，并把接管次数加一；超过 3 次判定为毒任务，直接写成失败、原因 `EXECUTOR_LOST`（执行者反复失联的终止码），不再接管。接管细节在第 05 篇。
- **执行中 → 排队中**：优雅停机时主动交还，不计接管次数。
- **执行中 → 等待补充条件 / 终态**：由执行者写入，受上面那四条写保护约束。
- **等待补充条件 → 排队中**：用户补充条件后重新入队。
- **任意非终态 → 已取消**：用户取消，见第 5 节。

两类条件更新值得单独说：

**执行者侧的条件更新**，统一收口在"写保护"那四条上。所有会改状态或追加事件的写入（追加事件、子任务快照、结束任务）都是同一个套路：开一个短事务 → 锁住任务行 → 判断写保护是否仍成立 → 不成立就返回 false，调用方当作"我已经不是当前执行者"处理。这里返回 false 而不是抛异常，是因为这种情况在设计上是正常的（被接管、被取消），不该走失败路径把任务写坏。

**用户侧的条件更新**，用修订号做乐观并发。补充条件的接口要求客户端带上它看到的修订号，服务端在事务里锁行后核对：状态必须是"等待补充条件"，修订号必须与当前一致，否则报错要求刷新。这挡住了两个人（或两个浏览器标签）同时补充条件时后写覆盖先写的情况。补充条件本身只追加到约束列表里（上限 20 条），知识库和文档范围保持创建时服务端确认的那一份，模型和用户都不能在这个入口扩大检索范围。

## 3. 事件按序号持久化

不这么做会出什么事：如果进度只在内存里广播，那么刷新页面就看不到之前的步骤，实例重启之后更无从知道任务跑到哪一步；而如果事件序号用"当前最大值加一"来算，多线程并发写事件时必然撞号，回放顺序就乱了。

- 事件表的主键是 `(任务 ID, 序号)`，序号不是自增列，而是任务行上的一个计数器。分配方式是一条 `UPDATE 任务表 SET 事件序号 = 事件序号 + 1 ... RETURNING 事件序号`：行锁天然把并发的分配串行化，一次往返既加了号又拿到了号，不需要 `MAX(序号)+1` 那种读—改—写。主键再兜一层底，撞号会直接插入失败而不是静默重复。
- 追加事件与写保护检查在**同一个短事务**里：先锁任务行、再判断"我是否仍是当前执行者"、再写 usage 快照和事件。所以一个失去租约的旧执行者不可能往事件流里插进一条迟到的进度。
- 事件本身是执行的账本，不只是给前端看的：任务开始（连同主 Agent 的首条请求原文）、每次模型调用开始与结束（带 usage）、每次工具调用开始（带模型给出的原始参数）与结束（带输出）、结论已确定、产物、终态。第 05 篇的"从事件重建上下文续跑"就是把成对的工具开始/结束还原成一轮工具往返，靠的正是这份账本。工具输出落库有 40,000 字符上限，超出部分截断。
- 模型和工具都在事务之外执行，事务只覆盖"分配序号 + 写一行"。这是刻意的：长任务里绝不能让一次模型调用把数据库连接和行锁占几十秒。代价是"工具执行完了但结束事件还没落库"这种半步状态确实存在，处理办法是重做（见第 6 节）。

推送给客户端的事件做了字段裁剪：产物、已读来源、子任务事件原样下发，其余事件只保留工具名、状态、输出类型、原因这几个白名单字段。模型的原始参数、原始请求、隐藏推理都留在库里供续跑使用，不进 SSE。

## 4. SSE：断线按序号续传，重连不重复触发执行

不这么做会出什么事：很多流式接口把"订阅"和"执行"绑在同一个请求上——连上就开始跑，断开就取消。这样一来浏览器切后台、网络抖动、反向代理超时都会杀掉一次已经花了钱的执行；用户刷新页面还会再触发一次执行。

这里把两者彻底拆开：**执行由数据库队列驱动，SSE 只是持久事件的只读视图。** 连接、重连、断线都不会调度执行，也不会取消执行。

一次订阅的流程是这样的：

1. 请求线程里先按所有者读一次任务做鉴权，并把所有者固定下来传给异步线程（不依赖线程本地变量，因为后续推送发生在另一个线程池里）。同时限制同时在线的订阅数（100 个），超了直接拒绝，避免一个任务被开无数个长连接。
2. 确定起始游标：优先取重连时浏览器自动带上的 `Last-Event-ID` 头，与查询参数里的游标取较大值；解析不出数字就报参数错误。这就是断线续传——客户端不需要自己记状态，`EventSource` 断线重连时会把最后收到的事件 ID 带回来。
3. 每 750 ms 轮询一次事件表，取"序号大于游标"的下一页（一次 100 条），逐条推送。每条 SSE 消息的 `id` 就是事件序号，客户端收到就更新自己的 `Last-Event-ID`。推完一批再推一条任务快照，让前端不用自己拿事件拼状态。
4. 任务进入终态或"等待补充条件"时，不立刻关连接，而是再把尾部事件读干净（循环读到不足一页为止），然后才结束这条流。这是为了避开一个竞态：结束事务里产物事件和终态事件是一起提交的，如果先看到终态就断开，可能漏掉同事务里那条产物事件。
5. 客户端已经断开时，容器抛出的写异常只用来关闭这条订阅，不再往已经断掉的响应里写东西，也不能让通用异常处理器往流里塞一段 JSON（那会污染事件流的格式）。

用轮询数据库而不是进程内发布订阅，是因为执行者可能根本不在接这条连接的实例上——订阅与执行完全解耦之后，任何实例都能服务任何任务的订阅，代价是最多 750 ms 的推送延迟，对分钟级任务可以接受。

## 5. 取消：一路传到 Agent、工具与 HTTP 连接

不这么做会出什么事：用户点了取消，界面上停了，后台却还在烧模型额度和检索资源；更糟的是那个还在跑的执行最后会把"完成"或"失败"写回一条已经取消的任务上，用户看到的状态自己变了回去。

取消分两段，先写库、再停本地。

**第一段（同步、写库即生效）**：取消接口在一个事务里锁住任务行，如果已经是终态就原样返回（取消一个已完成的任务不报错、不改状态）；否则把状态写成"已取消"、**epoch 加一**、清空租约令牌与到期时间、把在途子任务一并标成已取消，并追加一条取消事件。这一步之后，无论执行者在哪个实例上、正在做什么，它的写保护条件都已经不成立了。接口在这里就可以返回。

**第二段（异步、尽力而为）**：如果执行恰好在本实例上，直接触发这次执行的取消信号；如果在别的实例上，那个实例会在下一次心跳续租（默认 10 秒一次）失败时、或者执行中任意一次检查点上发现自己已经不是当前执行者，然后自行停止。也就是说跨实例取消的生效延迟最坏一个心跳周期。

本地取消信号的传播链条是这样的（取消状态是一次性的布尔量，加一个 Reactor 的单值信号，加一组注册进来的中断回调）：

- **Agent 层**：Agent 的事件流上挂了 `takeUntilOther(取消信号)`，信号一发就终止订阅；同时注册了一个中断回调，直接调用 SDK 的 Agent 中断。
- **模型调用层**：模型调用包装器在每次调用前、拿并发额度的等待循环里、真正发请求前都做检查，并且在整条响应流上同样挂了 `takeUntilOther(取消信号)`。取消让 Reactor 的订阅被 cancel，这个 cancel 一路传播到 SDK 的 HTTP future 和响应 socket，也就是说不是"等它返回再丢掉"，而是真的把连接断掉。重试条件里也显式排除了"已取消"，避免取消之后退避重试又发一次请求。调用台账在取消分支上补一条状态为已取消的记录，usage 不会假装成 0。
- **工具层**：每个工具方法入口、工具中间件在执行每个工具调用之前，都会调用会话的检查点。这个检查点做三件事：看本地取消位、看时间预算、**再问一次数据库"我是不是当前执行者"**。最后这条是关键——它让"取消"和"被接管"走同一条判定，不需要额外的通知通道。
- **检索与阅读的 HTTP**：检索走一个带截止时间的请求作用域，取消回调注册进去后，取消会直接 cancel 正在跑的任务并中断线程；作用域关闭时也会 cancel，保证不留悬挂请求。
- **子任务**：主任务的取消回调里绑了每个子任务自己的取消对象，主取消会逐个触发子任务取消（第 03 篇）。

**为什么迟到的写入一定会被拒**：因为取消把 epoch 加了一、把租约令牌清空了。旧执行者手里的领取凭证记着旧 epoch 和旧令牌，它之后任何一次写事件、写子任务快照、写终态，都会在事务里先锁行再核对这四条，核对不过就返回 false 静默丢弃。这是 fencing token 的标准用法：不依赖"能不能通知到对方"，而是让过期的持有者**在写入点**被数据库拒绝。所以即使本地取消完全没生效（线程卡死、信号丢了），任务的最终状态也不会被它污染。

唯一的例外是一条补记：本地执行真正结束时，允许往这条已取消的任务上写 usage 和一条"本地执行已结束"的事件，条件是状态确实是已取消、epoch 正好等于"我领取时的 epoch + 1"（也就是那次取消是紧接着我这次执行发生的）、并且这条补记还没写过。它只能写 usage 和回执，**写不了状态、也写不了研究结果**。这样做是为了如实记下取消前已经产生的费用。

还有一条如实标注的边界：取消事件的负载里"远端计算是否已停止"这一项明确写的是 `unknown`。我们能断开连接、能停止本地执行，但供应商那一侧是否真的停止了计算和计费，客户端拿不到确认，所以不假装知道。

## 6. 哪些步骤不在同一个事务里

这一节单独列出来，是因为面试里"你说的一致性到底保到哪一层"必问，而这些缝隙都是有意留的。

- **创建事务 与 本地调度**：任务行、会话行、首条事件同事务；提交之后才丢给线程池。线程池拒绝时任务留在库里，靠轮询兜底。
- **取消写库 与 本地停止**：两段。中间这段时间里执行可能还在跑，但它写不进去。跨实例时这段最长约一个心跳周期。
- **模型调用 与 调用台账**：调用开始事件、HTTP 调用、调用结束事件是三次独立提交。进程在 HTTP 途中被杀，这次调用的 usage 就丢了——所以预算恢复是"按已落库的 usage 近似"，不是精确。
- **工具开始事件 / 工具执行 / 工具结束事件**：三次独立提交，语义是**至少一次**。没有配对结束事件的那一步在续跑时会被丢弃重做，靠的是检索与阅读本身只读、证据按稳定 ID 幂等，重做安全（第 05 篇）。
- **产物与终态**：这两条在同一个事务里提交，所以不存在"状态已完成但没有产物"。SSE 关流前多读一次尾部，就是为了不漏掉同事务里的产物事件。
- **证据写入 与 事件**：证据表按稳定 ID 幂等写入，与事件不在同一事务，依赖幂等而不是原子性。

## 边界与不足

- 取消只保证"本地停止 + 迟到写入被拒"，不保证供应商侧的计算和计费立即停止；事件里对此如实标为 `unknown`。取消也不退还已消耗的预算。
- 跨实例取消不是即时的：依赖失去租约的执行者自己在下一次心跳（默认 10 秒）或下一个检查点上发现，最坏要等一个心跳周期。检查点之间如果卡在一次长的上游调用里，实际停止还要更晚。
- 写保护挡得住"过期执行者写库"，挡不住"执行者还活着、心跳照常、执行线程却卡住"。X2 的 20 次重复里出现过 1 次执行者在注入故障前就完全静止、原因未查明（模拟上游；临时库已删、没有线程转储）。
- SSE 是 750 ms 轮询数据库的只读视图，不是推送：进度有最多一个轮询周期的延迟；同时在线订阅上限 100 个是进程内的硬限，没有按用户或按任务分配配额。
- 模型调用的 usage 与工具结束事件都不与实际动作同事务，进程被杀时会丢最后一次的记录；工具输出落库 40,000 字符上限，超出后重建的请求前缀不再逐字节相同（只影响缓存命中，不影响正确性）。
- 本篇引用的唯一实验数字来自 X6 容量基准，基于模拟上游；幂等创建、取消、断线续传这几条路径由单元与集成测试覆盖，没有做过独立的压测。

## 口述版

这个平台的研究任务是分钟级的长任务，所以从接口进来的每一步我都按"数据库是唯一事实来源"来设计。创建是幂等的：客户端带一个请求 ID，任务表上有所有者加请求 ID 的唯一索引，插入语句写成冲突就不做，然后两边都按这个键把行读回来，所以并发重试只会建一条任务；我还把会话和任务说明算了个指纹存下来，同一个请求 ID 换了内容会直接报错，而不是悄悄返回旧任务。创建事务提交后才交给本机线程池，池满了不判失败，任务留在库里等任一实例轮询领走——容量基准里 3600 个任务提交被拒 0 个就是这条路径。

状态变更全是条件更新。执行者每次写库都要满足四条：状态是执行中、epoch 等于我领取时拿到的、租约令牌是我的、租约没过期，不满足就静默丢弃；用户侧补充条件用修订号做乐观并发，防止两个页面互相覆盖。进度不是内存广播，而是持久化的事件表，序号由任务行上的计数器用一条 update ... returning 在行锁里原子分配，不用 max 加一；追加事件和写保护检查在同一个短事务里，模型和工具都在事务外跑。

前端用 SSE 订阅，但订阅和执行是完全解耦的——连上、断开、重连都不会触发或取消执行，它只是事件表的只读视图。每条消息的 id 就是事件序号，浏览器重连时自动带 Last-Event-ID 回来，服务端从那个序号之后接着推，所以断线续传不需要客户端记状态，也不会重复跑任务。

取消分两段。第一段同步写库：状态改成已取消、epoch 加一、清空租约，这一步一落地，那个正在跑的执行者就已经写不进任何东西了。第二段是尽力而为地停掉本地执行——Agent 事件流和模型响应流上都挂了取消信号，取消会让 Reactor 的订阅被 cancel 并一路传到底层 HTTP 连接，检索走的是带截止时间的请求作用域，取消会直接断掉在跑的请求；工具入口和每次模型调用前的检查点还会再问一次数据库"我是不是当前执行者"，所以取消和被接管走的是同一条判定。关键是这两段的先后顺序：即使本地取消完全失效，迟到的写入也会因为 epoch 对不上被拒绝，这就是 fencing token 的用法——不依赖能不能通知到对方，而是让过期的持有者在写入点被数据库拦下。唯一的例外是允许补记 usage 和一条本地执行结束的回执，写不了状态和结果。至于供应商那边是不是真的停了计算，我们拿不到确认，事件里就如实写成 unknown。
