# 05 长任务的持久化执行（简历第 1 条）

研究任务是分钟级的长任务：一次任务要做若干轮检索和阅读，再写出带引用的产物，默认最长允许跑 300 秒。这种任务一旦开始，就必然会撞上发版重启、实例宕机和扩缩容。这一篇讲的是：任务怎么从"绑在某个进程的内存里"变成"存在数据库里、谁都能接着跑"。

任务的幂等创建、状态机、SSE 事件续传和取消传播由第 04 篇写；故障注入实验怎么搭（多 JVM、`kill -9`、不变量检查脚本）由第 09 篇写，本篇只写结论。

## 一、原来的三个缺陷

不改会出什么事：一次发版就能把全集群正在跑的研究任务全部作废，而且用户看到的是"失败"，不是"稍后继续"。

只读核对上游自带的实现时发现三个问题，其中第一个比"丢任务"更糟：

- **启停就清库**。实例启动和关闭时各执行一次"孤儿清理"：把**全库**所有排队中和执行中的任务标成中断，不区分这些任务归谁执行。多实例部署下，任何一个实例启动或停止，都会杀掉其他实例正在健康执行的任务。单实例时这段逻辑看起来是对的——因为单实例下"全库的任务"恰好就是"我的任务"。
- **一次性长租约，没人续、没人扫**。领取任务时把租约直接设成"最长时长 + 30 秒"，即 330 秒，之后既不续租，也没有任何一处扫描过期租约。所以租约只是一个摆设：进程死了，那一行会在"执行中"状态停留 330 秒，然后永远停在那里，没有任何人来接。
- **队列在内存里，满了就判失败**。调度只发生在收到 HTTP 请求的那个实例的内存线程池里；线程池队列满了，任务直接被写成失败（原因是"队列已满"）。也就是说高峰期的任务不是排队，而是被拒绝。

再加一条后果：重启之后任务只能整体重新发起，之前已经花掉的模型调用全部作废——对一个十几次模型调用的任务，这既是钱也是分钟级的等待。

目标因此定为三条：**不丢**（进程没了，任务还在，且有人接着跑）、**不重复出产物**（接管不能产生第二份产物或第二次写入）、**不白跑**（接管方从中断处继续，不从头开始）。

## 二、把数据库当队列

**问题**：任务要能被"任一实例"领走，就必须有一个所有实例都看得见的队列。

**为什么不另起一个消息队列**。Redis 和 RocketMQ 都在这个项目的技术栈里，本来可以直接用。不用的理由是：任务状态（状态机、预算用量、事件序列、产物）本来就必须存在 PostgreSQL 里，如果再引入一个队列，就出现两处状态，要额外解决"消息已投递但数据库事务回滚""数据库写成功但消息没发出去"这类不一致，通常又要引入事务消息或本地消息表——那本质上还是回到数据库。而这里的量级是分钟级任务、每实例只跑 2 个，根本不需要消息队列的吞吐。所以直接把**任务表当队列**，领取与状态变更放在同一个事务里，只有一处事实来源。这个做法在 Java 生态里有成熟先例（db-scheduler、Quartz 的 JDBC 集群模式）。

**领取语句**。每个实例定时轮询（默认 5 秒一次），一条语句取出可领取的任务：

- 条件是"排队中"，或者"执行中但租约已过期"——后者就是原执行者失联；
- 按更新时间、ID 排序，取的条数等于本实例当前的空闲槽位数（默认每实例 2 个槽位，用"正在执行的任务数"算空闲）；
- 加 `FOR UPDATE SKIP LOCKED`：已经被别的实例锁住的行直接跳过，不阻塞。这是多实例并发领取不互相等待的关键，没有它，三个实例轮询时会排成一队，轮询间隔越短越明显。
- 表上建了一个部分索引（只索引排队中和执行中的行，按租约到期时间和更新时间），让这条语句不去扫描全部历史任务。

领到之后在同一个事务里，对每一行做真正的"占有"（见下一节）。如果本地在把任务交给线程池时被拒（比如正在停机），就立刻把它交还队列，不会出现"领了却没人跑"。

**线程池满不再判失败**。创建接口仍然有一条本地快速路径：任务刚创建就直接扔给本机线程池执行，省掉一次轮询延迟。但这条路径失败时不再写失败——任务本来就已经落库、处于排队中状态，把它从本地登记表里摘掉就行，下一轮轮询会有实例（可能还是自己）把它领走。W7 的积压实验里 3600 个任务提交被拒 0 个，就是这条改动在压力下的表现。

## 三、执行者身份、短租约与心跳

**问题**：数据库这一行怎么知道"现在归谁跑"？以及"这个人是不是还活着"？

**执行者身份**。每个实例在启动时生成一个执行者 ID（JVM 的运行时名字加一段随机后缀），写在任务行上。它**只用于诊断**（日志里看谁在跑、被谁接管），写保护一点都不依赖它——因为同一个进程重启后名字可能一样，而且它也防不住"同一个进程里的旧线程"。真正的写保护是 epoch 和租约令牌。

**为什么是短租约 + 心跳，而不是一次给足**。一次性给满整个任务时长（原来的 330 秒），意味着进程崩溃后要等 330 秒才能被接管；给得太短又会在正常执行时被误接管。短租约加续租把这两件事解耦：租约只回答"我最近还活着吗"，与任务实际要跑多久无关。默认租约 30 秒、心跳 10 秒续一次（配置校验里强制租约至少是心跳的 2 倍，也就是允许丢 2 次心跳），所以失联后最多 30 秒就可以被接管。代价是每个在跑的任务每 10 秒多一次很轻的数据库更新。

**领取/接管这一步做了什么**（都在同一个短事务、同一把行锁里）：

1. 先按 ID 锁住这一行，再读一次当前的执行者、接管次数，以及"租约是否仍然有效"。这一步是必要的：轮询语句的可见性和行锁获取之间有时间差，如果这次是接管（行是"执行中"）但租约其实还没过期，就直接放弃，不抢。
2. epoch 加一、生成一个新的租约令牌、写上自己的执行者 ID，租约到期时间设成"数据库当前时间 + 30 秒"。**所有租约时间都取数据库时钟**，各实例本机的时钟偏差完全不参与判定——否则一个快了 1 分钟的实例会把别人正常的任务全部当成过期。
3. 如果是接管，接管次数加一；同时把在途的子任务（并行 worker）标成中断——它们随旧进程一起消失了，是否重派由主 Agent 在预算内自己决定。
4. 写一条"执行开始"事件，载荷里带上 epoch、执行者 ID、是第几次接管、上一个执行者是谁。

**心跳与自停**。一个单线程的定时任务每 10 秒给本实例所有在执行的任务续租一次。续租语句的条件和写保护完全一致：状态是执行中、epoch 相同、租约令牌相同、**且租约尚未过期**。最后一条是关键——已经过期的租约不允许自己"续"回来，否则就会和已经接管的新执行者同时认为自己持有租约。

续租返回"没有更新到任何行"意味着三种情况之一：被别人接管了、任务被取消了、任务已经结束了。三种情况下本实例都应该停：立刻触发本地取消，这个取消信号会一路传播到底层的 HTTP 请求，把正在进行的模型调用也断掉。

有一个例外：续租时抛异常（数据库暂时不可用、连接池取不到连接）**不自杀**，只记日志。理由是数据库抖一下就让所有在跑的长任务自尽代价太大；如果数据库在租约到期前恢复，续租就接上了，如果没恢复，那这个执行者反正也写不进任何东西，由 fencing 兜底。

## 四、epoch 写保护：旧执行者的迟到写入

**问题**：即使续租失败后我们会主动停，"停"也不是瞬间的——一个正在等待模型响应的线程、一个 `SIGSTOP` 之后被唤醒的进程，都可能在新执行者已经接管之后，还带着旧的上下文往库里写事件、写状态、甚至写产物。这正是 Kleppmann 讲的"进程暂停导致的双重执行"，光靠锁和租约解决不了，必须有 fencing token。

**做法**：任务行上的 epoch 就是 fencing token，每次领取严格递增；领取时同时发一个一次性的租约令牌。执行者手里握着"任务 ID + epoch + 令牌"这一组东西，**每一次写入**都在同一个短事务里先锁行、再核对这三项加上"状态仍是执行中、租约未过期"，不满足就什么都不做、返回一个布尔值 false，而不是抛异常。

被这样保护的写入包括：追加事件（同时更新用量快照）、子任务检查点、结束（写终态、产物、错误摘要）、交还队列。也就是说，旧执行者接管之后能做的**唯一**一件事，是什么都做不了。它写不进事件，也写不成失败——任务不会因为旧执行者的退场而变成失败状态。

还有一处更主动的检查：主 Agent **每次模型调用开始前**都会查一次"我是否仍然是当前持有者"。这样旧执行者不仅写不进去，也不会继续浪费上游配额——它会在下一次模型调用前直接抛出"租约已被取代"停下来。X2 的进程暂停场景里能看到这个效果：被暂停超过租约的实例恢复后，续租被拒 6 次然后自行停止（模拟上游、租约 6 秒的单次测量；重复 20 次时旧执行者每次都自行停止写入）。

一个附带的好处：取消只要写库就生效（第 04 篇）。取消时 epoch 也加一，执行在别的实例上时，对方下一次续租或写入就被拒，自己会停。不需要跨实例的通知通道。

## 五、由事件表重建上下文，从中断处续跑

**问题**：接管方如果从头开始，前面十几次模型调用的钱和时间就白花了；但如果要"续"，就得把 Agent 的对话上下文恢复出来。

**为什么不存 Agent 快照**。直接把 Agent 的内存状态序列化存库是最直观的做法，但快照是一份和代码强耦合的私有结构，改一次提示词或工具签名就得考虑版本兼容，而且它和事件流是两份状态，可能不一致。这里已经有一条现成的、为了给前端做 SSE 回放而持久化的**事件表**，它天然按序号有序、写入和状态变更在同一事务里。所以采用 Temporal 那种"由事件历史重放得到当前状态"的思路，只是简化成"重建一段对话"，而不是确定性重放整个工作流。

**重建的过程**：

1. 分页把这个任务的全部事件读出来（每页 500 条），从**最后一次用户补充条件之后**开始算——之前的那一阶段已经结束了，不该再进上下文。
2. 首条用户消息不是重新拼出来的，而是执行第一次调用时就把**原文**随"研究开始"事件持久化下来，重建时直接取出。
3. 工具调用按"开始"和"结束"两个事件成对还原：开始事件里有工具名和模型给出的参数（连同模型输出的原始参数文本一起存），结束事件里有输出和状态。同一轮里模型可能一次决定多个调用，这些调用归入同一条 assistant 消息，还原成 tool_call 加工具结果的标准形状。
4. **没有配对完成的那一步直接丢弃**，由模型重新决定要做什么。这就是"至少一次"语义的来源。
5. 除了对话，本地状态也一并恢复：已读证据、检索次数计数（用来判断是否重复检索）、候选文档、已完成的子任务结果。预算也从库里持久化的用量恢复，所以接管不会让一个任务把预算重新花一遍。
6. 如果事件里已经有"结论"事件（模型已经调用过结束工具，或者已经决定要反问用户），接管方**不再调用模型**，直接拿这个结论去生成产物。这一条修掉了一个很贵的场景：任务在"已经想明白、正在写产物"时崩溃，重来一次要把整个研究再做一遍。

**为什么"至少一次"在这里是安全的**。重做的只可能是崩溃时在途的那一步，而这一步必定是下面三类之一：检索（只读）、阅读来源（只读，证据按内容的稳定 ID 幂等保存，重复保存不会产生第二条）、或者一次模型调用（重复的代价是一次调用费，不产生副作用）。产物只有一份，因为写产物走的是带 fencing 的结束写入，同一个任务只有当前持有者能写、而且写完就是终态。X2 的不变量检查逐任务确认了这一点：恰好一个终态事件、至多一个产物、事件序号连续、已完成的同名同参数工具调用没有被执行第二次。

**重建的前缀要逐字节相同**。这一条是为了让 W1 的提示缓存在接管后仍然命中（另见第 06 篇）：首条消息用持久化的原文、工具参数用模型给出的原始文本、assistant 消息补上 SDK 会写进去的 Agent 名字。测试在三个截断点（完成一步后 / 工具在途 / 已得出结论）比对过重建请求与首次执行逐字节相同。

**身份从哪来**。接管的任务没有原始 HTTP 请求线程，也就没有登录上下文，而检索要按用户的知识库权限过滤。做法是按任务行上的所有者用户 ID 从用户表重建登录身份；用户已被删除时只保留 ID、不带角色（按最小权限处理）。另外每次领取（包括接管和续跑）都会重新校验一次所有者对目标知识库是否仍有读权限，撤权后的任务会以"权限已撤销"结束，而不是拿旧范围继续跑下去（另见第 08 篇）。

## 六、毒任务：反复接管失败怎么办

**问题**：如果一个任务每次执行都让执行者崩溃（比如触发了某个必然 OOM 的输入），无限接管会像传染病一样把整个集群逐个拖垮——这是"任务不丢"这个目标的反面代价。

**做法**：任务行上记接管次数，上限默认 3 次。第 4 次有人想接管它时，不再领取，直接把任务写成失败、错误摘要是 `EXECUTOR_LOST`（执行者失联），并写一条事件说明原因。等于一个不进死信队列的"死信"：任务终止在自己的行上，用户能看到明确的失败原因和完整事件历史。

关键区分：**只有"失联被接管"计数，停机主动交还不计**。否则一次滚动发版就可能把长任务的接管配额耗光——发版时每个实例交还一次，三个实例就是三次。

## 七、优雅停机：把任务交还，而不是等它过期

**问题**：发版是最常见的"故障"。如果停机时什么都不做，任务要等租约过期（最长 30 秒）才会被别人接管，而且崩在哪一步就得重做哪一步。发版的次数远多于宕机，值得单独处理。

**做法**（参考 Spring Boot 的优雅停机和 Kubernetes 的终止宽限期）：

1. 收到停机信号后，第一件事是**停止领取**：本地快速路径和轮询都不再接新任务。
2. 给所有在途任务打一个"请交还"的标记。这个标记**不打断**正在进行的模型调用或已经决定要执行的工具——粗暴打断等于制造一次需要重做的在途调用。
3. 主 Agent 在**下一次模型调用开始之前**检查这个标记，命中就抛一个专门的"交还"信号停下来。这就是"步边界"。
4. 服务识别出这是交还（而不是真失败），把任务写回排队中、清空租约令牌与到期时间，并写一条"已交还"事件。任务回到排队状态意味着**其他实例下一轮轮询就能领走，不用等租约过期**，接管次数也不加。
5. 宽限期默认 20 秒。到点还没走到步边界的任务，直接强制交还并取消本地执行——注意顺序：先交还再取消，而被取消的执行因为写保护已经无法把任务写成失败。

实现时踩到一个并发问题值得记住：Agent SDK 自带一个 JVM 关闭钩子，它和我们的停机逻辑并发执行，谁先到不确定。它先到时会在"模型已经决定调用工具、工具还没执行"的位置中断 Agent 并关掉模型的 HTTP 传输，这个失败曾被写成任务失败。修法是把这类异常一并识别为"进程正在停机"，同样走交还。

X2 的实测（重复 20 次）：`SIGTERM` 场景下任务恢复时间 P50 1.08 s、P95 1.11 s、最大 1.11 s，执行者退出耗时 P50 1.12 s、最大 1.22 s（另有一次单次测量为退出 0.91 s、恢复 0.95 s），远低于失联接管的约 5 秒——这正是"交还"相对"等租约过期"的差别。这些都是模拟上游、租约 6 秒 / 心跳 2 秒 / 轮询 1 秒的实验配置。

## 八、容量：加机器有没有用，瓶颈在哪（W7）

**问题**：上面这套让任务不丢了，但积压的时候加机器有用吗？数据库当队列会不会自己变成瓶颈？

实验条件（全部数字基于模拟上游，每次模型调用 0.7—0.9 秒，零接口费）：每格一个新的随机隔离运行库和新的模拟上游，实例是共享该库的独立 JVM；先空转 30 秒量空闲轮询，再一次性提交 300 个脚本化任务。参数用生产默认：每实例 2 个槽位、2 个并发模型调用、租约 30 秒、心跳 10 秒、轮询 5 秒；另跑一组轮询 1 秒作对照。实例数 1 / 2 / 3，轮询 5 秒每格重复 3 次、轮询 1 秒每格 1 次，合计 3600 个任务。

结论：

- **加机器有用，接近线性**。排空吞吐 12.2 / 24.0 / 35.8 条每分钟，加速比 1.00 / 1.98 / 2.95；轮询 1 秒时 13.3 / 26.5 / 39.7，加速比 2.98。三次重复之间相差不到 0.2%。
- **瓶颈是槽位和轮询间隔，不是数据库**。各格吞吐是"槽位上限"（实例数 × 槽位 ÷ 单任务时长）的 85%—95%，差的那部分是轮询间隔：槽位空出来之后最多要等一个间隔才被填上。把轮询从 5 秒降到 1 秒补回大半，吞吐 +9.5% / +10.1% / +10.7%，代价是空闲轮询从 0.2 次/秒/实例升到 1.0 次/秒/实例。
- **领取语句不是成本**。应用侧计时（含连接池取连接与事务）均值 4.1—5.6 ms、最大 85 ms；一次调用按空闲槽位一次领多个任务，300 个任务的一轮排空里每实例只发 52—231 次，领取耗时占排空时长不到 0.12%。镜像没启用 `pg_stat_statements`，所以只有应用侧口径。
- **积压不会在门口失败**。3600 个任务提交被拒 0 个；3 实例时 300 个里有 286—288 个是被轮询领走的，其余直接进了提交实例的空槽。
- **压力下没有从"至少一次"变成"多次"**。3600 次运行不变量 0 失败（恰好被一个执行者启动一次、恰好一个终态事件、至多一个产物、事件序号连续、状态全部完成）。
- **积压的代价在等待时延上**。300 个任务、3 实例、轮询 5 秒时排队等待 P50 242 秒、P95 470 秒；等待随实例数等比下降（1 / 0.51 / 0.34）。要压等待只能加实例或加槽位，降轮询帮助很小。

## 九、和另外两种方案的取舍

- **消息队列（RocketMQ / Kafka）**：见第二节。核心理由是避免"队列与状态两处事实"，以及这里的量级用不上消息队列的吞吐。反过来说，如果任务是毫秒级、每秒上万条，数据库轮询的写放大和锁竞争就不划算了，那时候应该换。
- **Redis 分布式锁**：锁能解决"同一时刻只有一个执行者"，但解决不了**进程暂停**——持锁者被 `SIGSTOP` 或长 GC 暂停超过锁的过期时间，锁自动释放、新执行者拿到锁，旧执行者醒来后仍然认为自己持有锁并继续写。必须在被保护的资源那一侧做 fencing 检查，而这里被保护的资源就是 PostgreSQL 里那一行。既然写保护最终要落在数据库，锁本身放在数据库里更省一个组件、也少一处"锁和数据不在同一个事务里"的缝。X2 的进程暂停场景就是专门验证这一点的。
- **工作流引擎（Temporal 这类）**：功能上完全覆盖这里的需求，而且更强（确定性重放、定时器、补偿）。不用的理由是引入一整套外部服务和编程模型，对预研原型太重；而且它的确定性重放要求业务代码写成确定性的 workflow，Agent 的执行本来就不确定，收益打折。这里借了它的思路（事件历史重建上下文）但没借它的实现。

## 边界与不足

- **租约只能发现"进程死了或被暂停"，发现不了"进程活着但卡住"**。心跳是一个独立的定时线程，执行线程死锁、卡在某个不超时的调用上时，心跳照常续租，任务不会被接管，只能等任务自己的总时长上限（默认 300 秒）兜底。W2 重复 20 次时恰好撞上过一次：某个执行者在注入故障**之前**、9 秒内发出 14 次上游请求后完全静止，驱动等了 120 秒超时；临时库已删、没有线程转储，**原因未查明**，也无法事后确认它当时是否仍在续租。
- **`SIGTERM` 下仍会重复 1 次模型调用**。理论上不该重复——交还点就在模型调用之前——但 Agent SDK 自带的关闭钩子会先在"模型已经决定调用工具、工具还没执行"的位置中断，这个决定没有落库，接手方只能再调用一次。要消除得在模型返回时就持久化它的调用决定并让 SDK 执行待处理调用，没有做。
- **W2 / W7 的数字全部基于模拟上游**（每次模型调用 0.7—0.9 秒）。这测的是队列与执行器，不是供应商：真实上游的天花板是对方的限流。实例是同一台机器上共享一个 PostgreSQL 的独立 JVM，不含网络延迟、连接池上限和数据库自身的负载；只测到 3 实例 × 2 槽位，再往上是否仍线性没测，也没找到数据库的拐点。W7 全是无故障的干净排空，故障下的行为看 W2。
- **X2 只跑了单 Agent 模式**。模拟上游的策略不读续跑提示，所以多 Agent 模式下"已完成的子任务不重跑"只由单测和集成测试覆盖，没有进程级实验；在途子任务被标为中断后是否重派由主 Agent 决定。
- **续跑只恢复主 Agent，且有一处会破坏逐字节相同**。工具输出落库有 40,000 字符上限，超出时重建的前缀不再逐字节相同（只影响缓存命中率，不影响正确性）；结束修复的计数是按事件近似恢复的；老版本事件里没有原始请求，这类历史任务接管后只能从头执行。
- **恢复时间由租约决定**。失联接管约等于"租约剩余 + 轮询间隔"，生产默认最坏约 35 秒。租约调短能更快接管，代价是续租写入更密。
- **接管身份来自用户表**，用户被删除时只保留 ID、不带角色。

## 口述版

这个项目里的研究任务是分钟级的长任务，一次要做十几次模型调用。我接手时发现的问题比"重启丢任务"还严重：原来的实现在实例启动和关闭时会把全库所有排队和执行中的任务标成中断，单实例下没事，多实例下任何一个实例发版都会杀掉别人正在跑的任务；租约是领取时一次性给满整个任务时长的，既没人续也没人扫；线程池队列满了直接判任务失败。

我的做法是把数据库当队列。没有另起 MQ，因为任务状态本来就在 PostgreSQL 里，再加一个队列就有两处状态要对齐，而这里的量级也用不上 MQ 的吞吐。每个实例每 5 秒轮询一次，用 `FOR UPDATE SKIP LOCKED` 按自己的空闲槽位领任务——默认每实例 2 个槽位，被别人锁住的行直接跳过，多实例并发领取不互相阻塞。领取的条件是"排队中"或者"执行中但租约已过期"，后者就是接管。

活性判断用短租约加心跳：租约 30 秒、每 10 秒续一次，所以失联最多 30 秒后就能被别人接管，而不是等整个任务时长。租约时间全部取数据库时钟，实例之间的时钟偏差不参与判定。续租失败说明已经被接管或者已经结束，本地立刻取消执行；但如果是续租时数据库抛异常，我不自杀，只记日志，因为数据库抖一下让所有长任务自尽代价太大。

光有租约不够，因为进程可能被暂停后又醒过来。所以每次领取 epoch 加一、发一个新的租约令牌，执行者的每一次写入——写事件、写检查点、写终态、写产物——都在同一个短事务里核对 epoch、令牌和租约是否还有效，不满足就什么都不做。这就是 fencing token，旧执行者醒来以后什么都写不进去，也写不成失败。我用 `SIGSTOP` 超过租约再 `SIGCONT` 验证过：旧执行者续租被拒了 6 次然后自己停了。

续跑不是从头跑。我没有存 Agent 快照，而是用已有的持久化事件重建上下文：工具调用的开始和结束事件成对还原成 tool_call 和工具结果，没有配对完成的那一步丢掉让模型重做。语义是至少一次，这里是安全的，因为检索和阅读都是只读的、证据按内容的稳定 ID 幂等保存、产物的写入有 fencing 保护只可能有一份。重建时我还保证请求前缀和第一次执行逐字节相同，所以接管后提示缓存还能命中。另外如果事件里已经有结论，接管方直接生成产物，不再调用模型。

另外两件事：一个是毒任务，一个任务如果每次都把执行者搞崩，无限接管会拖垮整个集群，所以接管超过 3 次就判失败、错误码是执行者失联，但停机主动交还不计这个次数，否则一次滚动发版就把配额耗光了。另一个是优雅停机，发版比宕机常见得多，所以停机时我不打断在途的模型调用，而是在下一次模型调用之前把任务交还回队列，别的实例下一轮轮询就能领走，不用等租约过期。

验证上我起了多个独立 JVM 共享一个运行库，注入 `kill -9`、`SIGTERM`、`SIGSTOP`，这三种杀法各重复 20 次，每次都用新库和新的模拟上游。结果是恢复时间 `kill -9` 和 `SIGSTOP` 的 P50 大约 5.1 秒、`SIGTERM` 大约 1.1 秒，每个被接管的任务只重复了 1 次模型调用——就是崩溃时在途的那次，已经完成的检索和阅读一次都没重做；不变量 0 失败。容量上用 300 个积压任务测 1、2、3 个实例，吞吐 12.2 / 24.0 / 35.8 条每分钟，加速比接近线性，瓶颈是槽位和轮询间隔不是数据库——领取语句均值 5 毫秒左右，占整个排空时间不到 0.12%。

最后说限制：这些数字全部是模拟上游，测的是队列和执行器不是供应商；租约只能发现进程死掉或被暂停，发现不了进程活着但执行线程卡住——20 次重复里就撞到过一次，原因我没查出来；`SIGTERM` 下理论上可以做到 0 重复，但 SDK 的关闭钩子会先在"模型已决定、工具未执行"的位置中断，所以还是会重复 1 次。
