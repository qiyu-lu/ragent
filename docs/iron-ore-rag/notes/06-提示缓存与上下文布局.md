# 06 提示缓存与上下文布局（简历第 2 条）

研究任务是一个多轮的 Agent 循环：模型决定调用哪个工具，服务端执行，把结果追加进历史，再把**整段历史连同系统提示和工具定义**重新发给模型。一个任务通常十次左右调用，越往后每次请求越长，一个任务累计的输入 token 随轮数近似平方增长。这条链路上唯一能大幅省钱的手段是提示缓存——让供应商复用上一次请求已经处理过的前缀。上线前的成本估算就卡在这里：台账显示缓存几乎没生效，一个任务的输入几乎全额计费。

这一篇讲三件事：提示缓存到底是什么；怎么用调用台账定位到"哪一段前缀被谁改坏了"；改完之后成本降下来了，答案质量有没有跟着掉。

## 一、先讲清楚提示缓存的机制

不先讲清楚机制，后面所有做法都像玄学。面试官在这一节的追问密度最高。

**前缀匹配，不是内容匹配。** 供应商缓存的是"请求的一段开头"。两次请求只有在**从第一个 token 开始逐字节相同**的那一段上才可能复用；一旦出现第一处差异，从差异点往后全部要重新计算。所以缓存的单位是前缀，不是"消息"，也不是"相似度"。这带来一条很反直觉的推论：改动越靠前，损失越大。在系统提示末尾加一行字，和把整段历史全部重写，对缓存的破坏是一样的——都是命中率归零。

一次请求的序列化顺序，通常是：系统提示 → 工具定义 → 历史消息（按顺序）→ 本轮新消息。工具定义虽然在协议里是单独字段，但对缓存而言和系统提示同属最前面那一段，工具换个顺序也会让整个请求失配。

还有一条：命中一般按固定块大小对齐（实测观察到 128 token 对齐），所以命中长度总是略小于真正相同的前缀长度，不会精确等于。

**隐式与显式是两种机制。**

- 隐式缓存：不需要在请求里做任何标记，供应商自行判断能不能复用。它免费，但**不保证命中**——文档明写不保证，我们的探针实测是"前缀完全稳定的情况下，逐步走 4 次只命中 1 次"。它适合当作白捡的收益，不能当作成本模型的基础。
- 显式缓存：在请求里给某条内容块打一个缓存断点，告诉供应商"从开头到这里这一段，请存下来"。代价是这一段第一次要按**写入价**计费，之后命中按**命中价**计费。

**计费折扣与有效期**（按供应商上下文缓存文档，也是我们台账折算计费输入时用的权重）：隐式命中按输入价的 20% 计，显式命中按 10% 计，显式写入按 125% 计。显式缓存有效期 5 分钟，且**命中即续期**。

有效期这一条决定了选型：Agent 的相邻两次模型调用之间只隔一次工具执行，远小于 5 分钟，所以一条会话内的显式缓存几乎一直是热的；只有任务与任务之间才会过期。写入多付 25%、之后每次省 90%，在一个任务十次调用的场景下第二次就已经回本。

## 二、发现问题：调用台账

**不做台账会怎样**：成本只能看月底账单，账单是聚合的，既分不清哪种角色的调用贵，也看不出"本来应该命中却没命中"。等发现贵的时候已经没有现场可查。

台账（每次模型调用一条记录的账本）在模型调用包装器里写：发请求前记一条"开始"，带上调用 ID、模型名、角色（主 Agent / worker / 最终生成）、任务 ID 和估算输入；流结束后补齐供应商返回的输入 token、输出 token、**命中 token**、缓存写入量、缓存类型、整次耗时与首包耗时。两条关键设计：

- **失败、超时、取消的调用也要落账**。记录写在流的终止回调里，四种结局（完成、失败、超时、取消）都会补齐，并标上状态。否则重试次数多的任务成本会被系统性低估。
- **缺失的值不写，不用 0 冒充**。供应商没返回就是没返回，报告里记为缺失。旧批次缺字段时报告同样记缺失，这样新旧批次可以放在一张表里比。

拿一次完整回归的台账做离线报告（折扣率是参数，不写死），结果是：单 Agent 模式 3,486 次调用、输入 3,803 万 token、命中 197 万，命中率 5.2%；多 Agent 模式输入 4,427 万 token、命中 8,448，命中率 0.02%。后者基本等于完全没有缓存。

更有意思的是 5.2% 这个数字：它不是"有时候命中"，而是**每次都恰好命中 1,280 token**。1,280 正好等于该模式下工具定义 714 + 静态提示 632 + 模板 17 按 128 取整。也就是说供应商在共享前缀上有一段未公开的行为，只在这一段生效，后面全不算。另一种模式的对应长度（926 + 1018）在三千多次调用里一次都没出现过。结论：这点收益不可解释、不可依赖，不能当作基线以为"缓存是生效的"。

定位手段是**协议级探针**，而不是读代码猜。做法是用协议测试夹具捕获 SDK 实际发出的请求字节，然后每次只改一处，重放到真实端点（共 34 次调用），看命中数变化：

| 与上一次请求的差别 | 命中 |
| --- | --- |
| 逐字节相同 | 4/4 命中（128 token 对齐） |
| 系统消息末尾加一行，工具不变，前 1,944 token 相同 | 0 |
| 工具换序；或把提醒移出系统消息 | 0 |
| 只改提醒里的数字并追加历史（旧布局的真实下一步） | 0 |
| 系统消息稳定、历史只追加（纯隐式） | 逐步 4 次命中 1 次 |
| 显式断点打在最新一条历史消息上 | 3/3 命中整段旧前缀（1949→2272→2394），写入只计增量 |
| SDK 生成的消息级缓存标记 | 被忽略：0 写入、0 命中 |

这张表把所有推测变成了事实，尤其是最后一行——SDK 的缓存开关在这个供应商上是完全无效的空操作。

## 三、两个根因

**根因一：每轮把易变提醒拼进第一条系统消息。** 服务端每次调用都要告诉模型一些随轮数变化的信息：还剩几次探索调用、当前允许引用的证据 ID 集合、阅读覆盖情况、检索是否已被熔断。原实现把这些直接拼在系统提示后面。系统提示是请求的**第一条消息**，改它等于从第 0 个 token 就不一样，整个请求必然失配。多 Agent 模式命中率 0.02%，就是这么来的。

**根因二：上下文超限时从最早往后滑动裁剪。** 输入超过上限就丢掉最早的一轮往返。丢掉最早那轮，意味着**前缀的开头变了**，之后每一轮都在变，缓存永远追不上。

探针还顺带暴露了第三个问题：首条用户消息用了不保证键序的哈希表序列化，键序随 JVM 实现变化。同一进程内不受影响，但续跑、被其他实例接管重建上下文时，拿不到和之前逐字节相同的前缀。

## 四、做法

四条改动围绕一个目标：**让一次任务里的每一次请求，前缀都是上一次请求的严格扩展。**

### 1. 稳定前缀 + 提醒后置

系统提示只保留静态内容（角色、规则、输出契约），不再包含任何随轮变化的东西；工具定义顺序固定。易变提醒改成**每次请求临时追加在消息列表最末尾的一条用户消息**，并且**不写回 Agent 记忆**。这样下一轮请求里只有一条新的提醒，上一轮的提醒不会留在历史里。

为什么不把提醒放在第二条系统消息？兼容端点对多条 system 的处理不可靠。为什么不塞进最后一条工具结果里？那样确实也能保持前缀，但等于篡改工具的真实输出，Agent 读到的证据就不再是服务端实际返回的东西。追加在末尾的临时用户消息是唯一不动历史、又能稳定传达状态的位置。

最终产物生成那次调用不加提醒，也不打缓存断点——它的输入是按证据裁剪过的，和研究循环不共享前缀。

### 2. 历史只追加，序列化确定性

Agent 记忆里只往后追加，已写入的消息不再改写。首条用户消息改用**按键排序**的序列化写法，保证跨进程、跨实例重建出同一串字节。

### 3. 阈值压缩代替滑动裁剪

不裁剪是不行的——上下文会突破模型上限。但裁剪的频率可以从"每轮"降到"很少"。做法是：估算输入没超过上限（默认 **28,000** token）就一个字不动；一旦越线，**一次性压到上限的 60%**，然后在两次越线之间保持前缀不变。

压缩顺序是先轻后重：

- 先把最早的那些轮里的工具结果换成**可恢复的存根**——保留原来的工具调用 ID 和工具名（所以工具调用与工具结果仍然成对，协议不会因为缺一半而报错）、保留这条结果里出现过的证据 ID 列表，正文换成一句说明，告诉模型可以用 `read_source`（按证据 ID 重读原文的工具）把这段内容取回来。已经读过的证据仍然可引用。短结果（600 字符及以下）原样保留，替换它不划算。
- 存根还不够就整轮移除，从最早的一轮开始。
- 最新一轮观察始终完整保留；全部压完仍超上限就直接按"上下文预算耗尽"失败，不做降级猜测。

关键在于**水位只增不减**，存了几轮、丢了几轮保存在模型调用包装器实例里，每次调用重新按同一水位生成同一份视图。所以压缩后的前缀依然是稳定的、可缓存的，只在越线的那一次请求上丢一次缓存。

为什么不用滑动窗口？因为滑动窗口每轮都改前缀，等于放弃缓存；而且每轮丢一点，模型一直在"刚刚好丢掉需要的东西"的边缘，还会反复丢。阈值压缩是"平时零成本，越线时集中付一次代价"。

### 4. 显式缓存断点

断点打在两个位置：**第一条系统消息（含工具定义）**，以及**提醒之前的最后一条历史消息**（即倒数第二条）。

为什么不用 SDK 默认的位置？SDK 默认标记最后一条消息，而我们的最后一条恰好是每次都变的提醒——标在那里，等于每次都要求供应商按 125% 重写整段历史，是最坏的选择。标在倒数第二条，缓存的边界正好落在"这次之前的全部稳定内容"上。

系统消息上那个断点的作用不一样：它让**不同任务的第一次调用**也能共享静态前缀（系统提示 + 工具定义在所有任务里是同一串字节），否则每个新任务的首次调用都要从零算。协议允许每个请求最多 4 个断点，这里只用 2 个。

最后是线路格式的适配：供应商只认**内容块里**的缓存标记，SDK 把它写成消息级字段，会被静默忽略（探针表最后一行）。不改 SDK，在 HTTP 传输层套一个装饰器，发送前把消息级标记改写进内容块；同时从流式响应的 usage 里读出 SDK 不解析的"缓存写入 token 数"，交给台账，否则写入成本会整个漏记，算出来的账是虚低的。

显式缓存由一个开关控制，关掉之后不再打标记、退回隐式，稳定前缀和阈值压缩仍然保留。换供应商时先关这个开关，再写新的适配器。

## 五、效果与质量护栏

成本改善（W1，真实上游，同一 40 题、单 Agent 与多 Agent 两种模式、全部角色用同一个 Flash 模型，改动前后各跑一次）：

- 命中率：单 Agent 模式 9.8% → 78.4%；多 Agent 模式 0.2% → 80.0%。
- 单任务计费输入：分别下降 **69%** 与 **75%**（按文档折扣折算的输入 token 当量，不是账单）。

成本降了，还要回答一个更难的问题：**答案有没有变差？**缓存是纯粹的传输层优化，理论上不该改变模型看到的内容——但提醒的位置确实变了（从系统消息末尾挪到了整段消息的最末尾），这是一个真实的提示改动。第一次 40 题对照里，多 Agent 模式的可回答题 F1 出现了明显下降，但那一格只有 6 题，样本太小，不能下结论，所以又做了两轮扩样。

最终的质量护栏（W6，MuSiQue 数据集 400 道未见过的题、其中可回答 196 道，多 Agent 模式，改动前后按 4 块交错运行）：

- 缓存收益在新题上复现：命中率 0.15% → 80.4%；单任务计费输入 77,113 → 21,436（−72%），每一块都一致。
- 配对答案 F1 **−0.034**，95% 自助法区间 **[−0.080, +0.011]**——**未见显著下降，但不能排除约 0.08 以内的下降**。EM 0.352 → 0.291。
- 与之前引出疑问的 45 题合并后是 −0.045 [−0.088, −0.002]，注意那 45 题本身就是因为偏向下降才被拿来复核的。
- 噪声标定：把同样的 80 题用**同一个后臂**重跑一次，F1 变化 +0.059。**运行间噪声与要测的效应同量级**，这是这组数字最重要的一句话——它说明单次运行的 F1 差值本身就不可靠。
- 损失的位置查清楚了：15 题从作答改为"资料中没有"（贡献 −0.056），反向有 11 题（+0.025），拒答总数 47 → 47 没变；其余多是格式差异，升降大致抵消。
- 两臂都没有触发压缩，所以这组数字里的差异与压缩存根无关。

结论的写法是："成本收益确定且可复现；质量在这个样本量下看不出显著下降，但也不能证明没有下降。"一个可能的解释是末尾提醒里的"剩余调用次数"让模型更早收手（后臂每任务主 Agent 调用确实更少），但这只在少数题上有迹象，**未验证，也未修**。下一步应该做的对照是"提醒放末尾但不含剩余次数"的变体。

## 六、取舍小结

- **为什么不是滑动窗口裁剪**：滑动窗口每轮都改前缀，与缓存根本冲突；阈值压缩把"每轮付一点"换成"很少的几次集中付"，两次越线之间前缀完全不变。代价是单次压缩更激进（一次压到 60%），以及需要额外保证工具调用与结果的配对。
- **为什么选显式而不是只靠隐式**：隐式免费但供应商明确不保证，探针实测前缀完全稳定时也只有 4 次命中 1 次，没法写进成本模型。显式写入贵 25%、命中省到 10%，有效期 5 分钟且命中续期，而 Agent 相邻调用间隔远小于 5 分钟，第二次调用就回本。代价是绑定了供应商的内容块语法，需要一个可关闭的开关和传输层适配。
- **为什么断点不放在最后一条**：最后一条是每次都变的提醒，标在那里等于每次按写入价重写整段历史。

## 边界与不足

- 质量护栏的统计力有限：W6 的配对 F1 区间是 [−0.080, +0.011]，**不能排除约 0.08 以内的真实下降**；合并旧 45 题后区间是 −0.045 [−0.088, −0.002]，而那 45 题本身偏向下降，不是独立证据。
- **同题重跑同一后臂的 F1 变化是 +0.059**，运行间噪声与要测的效应同量级。任何基于单次运行的质量结论都不成立，包括"没有下降"这一条。
- **两臂都没有触发压缩**（输入都低于 28,000 的估算上限），所以阈值压缩这条路径完全没有被真实实验覆盖，只有协议测试覆盖。压缩改写早期消息之后，如果最新断点与系统消息之间超过 20 个内容块，还需要重写一次整段前缀，这个情况没有实测过。
- 计费输入是按文档折扣折算的**输入 token 当量，不是账单**，没有核对过发票。延迟方面，首包耗时只有新台账才有，做不了前后对比；单次调用耗时没有可靠改善，每个任务的**首次调用反而慢约 0.35 秒**，怀疑与写缓存有关，未验证。
- 显式缓存依赖这一家供应商的内容块语法和它返回的缓存用量字段。换供应商需要写新的传输适配器，或者关掉开关退回隐式；稳定前缀与阈值压缩不受影响。
- 多 Agent 模式在实验里几乎不发生委派，worker 的缓存行为没有被真实实验覆盖，只有协议测试。5.2% 那种"共享前缀恰好命中固定长度"的供应商行为是未公开的，探针复现不了，不作为任何设计依据。

## 口述版

我们的研究 Agent 是多轮循环，每轮都要把整段历史连同系统提示和工具定义重发给模型，输入随轮数快速增长，所以成本几乎全在输入上。我给每次模型调用记了一份台账，包括输入、输出、缓存命中和缓存写入，失败和超时的调用也落账。拿一次完整回归的台账一算，命中率单 Agent 模式只有 5%，多 Agent 模式 0.02%，基本等于没有缓存。而且那 5% 不是有时候命中，是每次恰好命中 1,280 token，正好是工具定义加静态提示的长度按 128 取整——是供应商在共享前缀上一段没有文档的行为，不可依赖。

提示缓存是**前缀匹配**：两次请求必须从第一个 token 开始逐字节相同，出现第一处差异就从那里往后全部重算。我用协议夹具抓下 SDK 实际发出的请求字节，每次只改一处重放到真实端点，确认了两个根因：一是每轮把剩余调用次数、可引用证据 ID 这些易变提醒拼进了第一条系统消息，改第一条等于整个请求失配；二是上下文超限时从最早往后滑动裁剪，前缀开头每轮都在变。探针还发现 SDK 自带的缓存开关在这个供应商上是空操作——它写成消息级字段，而供应商只认内容块里的标记。

改法是四条。系统提示只留静态内容，易变提醒改成每次请求临时追加在末尾的一条用户消息，而且不写回 Agent 记忆，所以历史里永远只有一条最新提醒；历史只追加，首条消息改成按键排序序列化，这样续跑或被别的实例接管也能重建同一串字节。裁剪改成阈值压缩：不超上限一个字不动，越线才一次压到上限的 60%，先把最早的工具结果换成保留工具调用 ID 和证据 ID 的存根、模型可以用重读工具取回原文，不够再整轮移除，水位只增不减，所以两次越线之间前缀是稳定的。最后是显式缓存断点，打在系统消息和提醒之前的最后一条历史上——SDK 默认标最后一条，而最后一条是每次都变的提醒，标那儿等于每次按 125% 重写整段历史；系统消息上那个断点让不同任务的首次调用也能共享静态前缀。显式标记在传输层装饰器里改写进内容块，同时从流式 usage 里把 SDK 不解析的缓存写入量读回来记账，否则写入成本会漏记。选显式而不是只靠隐式，是因为隐式文档明写不保证，实测前缀完全稳定时也只有 4 次命中 1 次；显式写入贵 25%、命中只要 10%，5 分钟有效且命中续期，而我们相邻两次调用间隔远小于 5 分钟。

效果是同一 40 题真实上游前后对照，命中率从 9.8% 和 0.2% 涨到 78% 和 80%，单任务计费输入降了 69% 和 75%。我还做了质量护栏：400 道没见过的题前后交错跑，命中率 0.15% 到 80.4%、计费输入降 72% 复现了，配对 F1 是 −0.034，95% 区间 [−0.080, +0.011]，没有显著下降，但也不能排除 0.08 以内的下降。我特意用同一个后臂把同样的题重跑了一次做噪声基线，F1 变化 +0.059，跟要测的效应同一量级——所以我的结论只能说成本收益是确定的，质量在这个样本量下看不出差异，但没证明没差异。另外这两组实验都没触发压缩，压缩路径只有协议测试覆盖，这是我知道的最大的覆盖空洞。
