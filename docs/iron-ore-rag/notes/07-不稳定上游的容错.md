# 07 不稳定上游的容错（简历第 3 条）

这一篇讲研究任务在调用第三方模型与 embedding 接口时，怎么在上游超时、限流、干脆不回包的情况下，仍然给出一个诚实的结果：能做完的做完，做不完的明确说"检索服务不可用"，而不是交一份看起来完整、实际上没有任何证据的报告。

## 一、历史事故：三层同一个超时，失败被吞成空结果

上线前的一次批量跑，1200 个任务里有 72 个超时，全部卡在检索工具上，耗时清一色是 30.01 秒。原因有两层：

第一层是超时没有分层。HTTP 调用、检索通道、研究工具这三层的超时都配成了同一个 30 秒。这意味着内层永远不会先于外层结束：最里面那次 HTTP 请求要等满 30 秒，外面的通道和工具也就只能等满 30 秒，中间没有任何一层有机会说"我还剩一点时间，换个办法补救"。上游一次不回包，整条链就是 30 秒起步，而一次研究任务的总预算也只有 300 秒——十分之一的预算被一次调用吃掉，而且什么都没换回来。

第二层更麻烦：上游失败被吞成了空结果。这是检索链路的原有设计——每个检索通道自己 catch 住异常，返回一个"零条结果"的通道结果；后置处理器抛异常就跳过该处理器。对面向用户的即时问答来说这是合理的降级：一个通道挂了，另外几个通道的结果照样拼出答案。但研究任务是长链路、多轮自主决策的：模型拿到"零条结果"，得到的信息是"库里没有这方面的资料"，于是它会改写查询再搜一次、再得到空结果，最后老老实实写一份"未检索到相关资料"的报告，任务状态是成功。使用者看到的是一份成功完成、内容空洞的报告，而真实原因是 embedding 接口没回包。**失败被伪装成了"事实上不存在"**，这比直接失败更危险。

所以这一条要解决的是两件事：让每一层都在自己该结束的时候结束；让"调用失败"和"检索无命中"在整条链路上一直是两种不同的东西。

## 二、分层截止时间：一次检索工具调用从头到尾

先交代这个流程：发起者是研究 Agent 的模型，它决定调用检索工具并带来一个查询串和可选的文档范围；它想得到的是一批候选证据（证据 ID + 截断摘录）。这次调用到"把候选列表作为工具结果返回给模型"为止，不包括后续的正文阅读，也不包括把结论写成报告。

核心做法是：进入工具时一次性算出**这次调用的绝对截止时刻**，之后每一层都从这个截止时刻往回推自己能用多久，并且每一层都比上一层再收紧一点。承载这个截止时刻的是一个显式的"请求作用域"对象——它记录截止时刻、身份（运行 ID、任务 ID、工具调用 ID）、一个事件回调和一份本次运行内的 embedding 小缓存。它不随线程继承，必须显式传递或显式绑定到线程上，这样它跨线程池边界时不会被漏掉、也不会被别的请求误用。

按顺序：

1. **算这次检索的截止时间。** 任务级预算是总时长 300 秒，扣掉给收尾阶段留的时间（总时长的五分之一，最多 30 秒）得到"探索期剩余"。检索工具的截止时间取"探索期剩余"和"工具超时 30 秒减 2 秒"两者中的较小值。减掉的这 2 秒就是分层的第一刀：留给工具层自己收尾（记事件、把失败转成工具结果字符串），保证工具层的判定先于上层的工具超时生效，不会出现"上层已经判超时、下层还在跑"。

2. **进入检索服务，选出通道并逐个下发。** 研究路径只走能回查持久化块的向量通道（不走联网通道，也不走无法回溯正文的通道）。每个通道在检索线程池里执行，提交前、拿到结果后都重新检查一次剩余时间；等待结果时用的超时就是"当前剩余时间"，而不是一个固定值。如果此刻一个启用的通道都没有，不是返回空列表，而是直接抛一个不可重试的失败——全站没有可用通道是配置事故，不能静默成"没搜到"。

3. **通道内部先做 embedding。** 把查询串发给 embedding 接口，这是整条链上唯一一次真正打到第三方的调用。这里是分层的第二刀：**单次 HTTP 调用的超时取"12 秒"和"剩余时间"中的较小值**。12 秒是硬上限，所以一次不回包最多损失 12 秒，而不是把 28 秒的检索预算全部耗光——留下的余量正好够做一次重试。

4. **拿到向量后查库。** 数据库查询超时同样从剩余时间推：取"剩余时间折算的秒数"与 5 秒中的较小值，至少 1 秒。连接上还挂了取消钩子，可以把语句取消掉。

5. **回到工具层。** 候选块逐条做来源核验（索引里的来源必须和数据库里的一致、必须落在允许的范围内），写入证据表，返回候选列表。到这里工具调用结束。

为什么不用"每层各配一个固定超时"这种更简单的写法？因为固定值只能保证"最坏情况下每层不超过多少"，保证不了"内层一定先于外层结束"——链路上只要多一跳、或者上一层已经消耗了一半时间，固定值就会失效，退化成事故里那种三层同时到点。传绝对截止时刻则是无论调用栈多深、前面花了多久，每一层看到的都是同一个终点，自己再往内收紧。代价是所有中间层都得显式接收并传递这个对象，不能靠线程本地变量隐式继承——这正是它被设计成"显式携带、从不继承"的原因。

## 三、有限重试与带抖动的退避

不重试的问题很直接：上游的超时和限流大多是瞬时的，一次失败就放弃，等于把可恢复的抖动当成了永久故障。无脑重试的问题同样直接：把上游压垮，并且让本来就紧张的时间预算更紧张。

判断能不能重试，靠的是把底层异常规整成一个带"阶段 + 错误码 + 是否可重试"的统一失败类型。判定规则是按错误类型分的：

- **可重试**：网络错误（连接失败、读超时、对端断开）、被限流、上游 5xx。这些是"请求没有被正确处理完"，重发一次是安全的。
- **不可重试**：上游返回的业务错误、响应格式非法（缺 data 数组、维度不对、出现非有限数值）、以及所有候选模型都被熔断跳过的情况。这些重发一次结果一样，只是白花时间。
- **取消不算失败**：用户撤销、实例停机、租约被别人接管都属于取消，既不重试也不计入熔断。

重试预算刻意留得很小：**embedding 只重试一次（总共两次尝试），并且剩余时间不足 1.5 秒时直接不重试**。后面这条是必须的——否则会出现"重试刚发出去就撞上截止时间"，既浪费一次上游调用又救不回来。

退避用的是指数退避 + equal jitter：**基数 300 毫秒、上限 2000 毫秒**，实际等待时间等于"本次上限的一半 + 在另一半里随机取"。第一次重试的上限是 300 毫秒，所以实际等待落在 150 到 300 毫秒之间。

为什么不用固定 300 毫秒等待（这正是改之前的写法）？因为一次上游抖动往往同时打掉很多并发调用，固定等待会让它们在同一时刻一起重试，对刚要恢复的上游形成第二波冲击；语料导入那种固定指数梯度也有同样问题。为什么不用纯随机（full jitter）？因为纯随机可能抽出接近 0 的等待，重试几乎立刻发出，起不到"给上游喘口气"的作用。equal jitter 的一半固定保证不会立刻重发，另一半随机保证同批失败者彼此错开。

退避期间不是死等：等待被切成小片，每片之间都重新检查一次截止时间和取消标志，所以正在退避时任务被取消或超时，能立刻跳出来。

研究模型的流式调用走的是另一套但同样的思路：最多重试一次、基数 300 毫秒、带抖动；只对网络类、可重试的 HTTP 状态码、以及"流中途断开导致响应不完整"重试，取消和预算耗尽不重试。整次模型调用还有一个总超时——取"剩余预算"和"模型调用超时 60 秒"中的较小值，而且这个超时卡在"收齐整个流"上，不是 idle 超时；否则上游只要持续吐空包就能把一次调用无限延长。

## 四、把"调用失败"和"检索无命中"分开

这是整条里最关键、也最容易在面试里被追问的一点。检索返回零条，可能是两件完全不同的事：库里确实没有相关内容（这是有效信息，应当写成资料缺口）；或者 embedding 没回包、数据库超时（这是执行故障，跟库里有没有内容毫无关系）。上游把两者都表示成"空列表"，于是模型无法区分，最终产出一份错误的结论。

分离是在三个位置同时做的，缺一个都会漏：

1. **通道与后置处理不再吞异常。** 在研究路径（有截止时间对象时），通道里的异常被规整成统一失败类型往上抛，而不是转成空结果；后置处理器出错同样往上抛，而不是跳过。面向用户即时问答的那条路径保持原样降级——两条路径对"部分通道失效"的诉求本来就不同：问答要的是尽快给个答案，研究要的是结论可信。

2. **工具层把失败如实转述给模型。** 工具捕获到统一失败类型时，返回的不是空结果，而是一个明确的错误工具结果，里面带上出错阶段、错误码、是否可重试，并且用一句话讲清楚语义："这是一次执行失败，不是不存在相应资料的证据。" 可重试的还会补一句"允许有限重试，已读证据请保留"，不可重试的则是"不要重复同一个失败请求"。另外，参数错误也走错误工具结果这条路（模型可以自己改参数重试），但和执行失败是两类文案。

3. **落库时不让空草稿掩盖故障。** 会话里维护一个"执行问题"列表，任何一次检索失败都会往里记一条（错误码 + 阶段）。收尾时：只要有执行问题在，结果状态就是"部分完成"而不是"完成"；如果既有执行问题、又一条可引用证据都没有，任务直接判失败并保留失败原因，不生成产物。还堵了一条侧路：模型不能用"向用户提问"来掩盖检索故障——已读证据为空且存在执行问题时，提问工具直接拒绝，并说明"追问用户补资料修不好一个超时的检索服务"。

分离做到位的直接效果，是把"错误完成"这个最坏的失败形态清零——任务要么真做完，要么如实失败，不会出现"状态成功但没有证据"。

## 五、取消怎么传到底层 HTTP 调用

不做这件事的后果：用户撤销任务、实例优雅停机、租约被另一实例接管之后，底层那个 HTTP 请求还挂在上游那里，占着连接和线程，直到自己超时为止；半开探测名额也一直被它占着。

做法是给截止时间对象挂一组"取消动作"，各层在进入阻塞操作前注册、退出时注销：

- 检索线程池里的任务注册"打断执行线程"；
- HTTP 调用注册"取消这次请求"（客户端侧的取消会真正断开连接）；
- 数据库查询注册"取消这条语句"。

触发源有三个，都汇到同一个入口：任务级的控制对象（撤销、停机）在建立检索作用域时把自己的中断回调绑到作用域的取消上；截止时间到了，作用域自己先标记超时再触发取消；上层线程被中断同样触发取消。触发时逐个执行已注册的动作，并且用"先摘除再执行"的方式保证每个动作只跑一次；后注册的动作如果发现已经取消了，会立刻执行——避免"刚注册完就永远等不到取消"的竞态。

## 六、连续失败之后停止补查

即便每次失败都如实告诉了模型，模型的自然反应仍然是"换个说法再搜一次"。检索服务真的不可用时，这会把剩下的所有时间和调用额度全部烧在注定失败的重试上，最后连"把已经读到的证据整理成部分结论"的机会都没有了。

所以在会话层记一个连续失败计数：检索成功一次就清零，失败一次加一，**连续失败达到 2 次就进入"检索受阻"状态**。进入之后：

- 再调用检索工具会被直接拒绝，返回的错误里明确写着"停止搜索，用已读到的证据和执行问题收尾；改写查询修不好一个不可用的检索服务"；再派发子任务去搜同样被拒。
- 每轮模型调用前追加的提醒里会加上同样的指示，并且告诉模型"空的发现/缺口数组是合法的，因为服务端会保留执行问题"——否则模型会因为"结果不能为空"的校验而反复挣扎。
- 如果此时模型还欠一次收尾调用，会主动给它补一次"结束调用"的额度，让它有机会正常收尾。

阈值取 2 而不是更大，是因为每次失败的代价已经包含了一次 12 秒的等待加一次重试；再多试几轮，任务的时间预算就没了。

## 七、候选模型的熔断与回退

上游某个模型持续故障时，如果每次调用都老老实实等满超时再换下一个候选，那么故障期间每一次调用都要先白白付一次超时的代价。

模型路由这一层维护每个候选模型的健康状态，三态：关闭、打开、半开。**连续失败 2 次就打开熔断，打开持续 30 秒**；30 秒后第一次调用转入半开，同一时刻只放一个探测请求进去，探测成功则恢复关闭并清零计数，探测失败则重新打开 30 秒。

这里有两个专门为带截止时间的调用做的处理：

- **带截止时间的调用不做跨模型回退，但失败照样计入熔断。** 不回退的原因是 embedding 向量不可跨模型比较——用另一个模型的向量去查用原模型建的索引，出来的结果是错的，这种"降级"比失败更糟。但"不回退"不等于"不记账"：改之前的实现在这条分支上直接重抛异常，压根没走到记失败那一步，于是研究路径的 embedding 超时从来不会让任何模型进入熔断，熔断对最需要它的这条链路完全失效。修完之后，截止时间内的失败会照常记入失败计数。
- **取消只归还半开名额，不计失败。** 取消不是上游故障。更重要的是，如果取消时不把半开探测名额还回去，这个模型会永远停在"探测进行中"，之后所有调用都被拒绝——一次用户撤销就能让一个健康的模型被永久拉黑。归还时会核对探测令牌，只有自己那次探测才会被归还，避免归还掉别人正在进行的探测。

如果所有候选都因为熔断被跳过，不是再去等一次超时，而是立刻抛一个**不可重试**的"熔断打开"失败，让上层马上走执行失败那条路。

## 八、X3 实验：模拟上游下的前后对照

要拿到"多大故障率下系统表现如何"的数字，不能靠真实供应商——故障率不可控、不能复现、还要花钱。所以做了一个可脚本化的模拟上游（怎么搭在第 09 篇），实验中所有数字都来自它，不是真实供应商。

实验设计：50 个脚本化研究任务，注入的故障只有一种——**embedding 请求无响应**（被挂住 90 秒），这是最贵的一种故障；注入比例 0% / 10% / 30% / 50%；对照的是治理前后两个版本的代码，治理前那一版就是"三层同为 30 秒、不重试"。先用单个随机种子跑了一轮，之后用 4 个种子（7 / 11 / 13 / 17）各跑一整套，每个版本在每个故障率下共 200 个任务，区间用 Wilson 95%。

4 个种子合并的结果（模拟上游，50 任务 × 4 个种子 = 每格 200 任务）：

| 无响应率 | 成功率 前 [95% 区间] | 成功率 后 [95% 区间] | 浪费的模型调用 前 → 后 |
| ---: | --- | --- | --- |
| 0% | 100% [98.1, 100] | 100% [98.1, 100] | 0 → 0 |
| 10% | 87.5% [82.2, 91.4] | 100% [98.1, 100] | 51 → 0 |
| 30% | 57.5% [50.6, 64.1] | 98.5% [95.7, 99.5] | 160 → 11 |
| 50% | 36.0% [29.7, 42.9] | 86.0% [80.5, 90.1] | 218 → 121 |

简历上引用的是 30% 这一档：成功率由 57.5% 提升至 98.5%。单个种子的旧数字是 88 / 54 / 40% → 100 / 100 / 82%，其中"30% 档治理后 100%"在多种子下不成立，合并后是 98.5%——这也是补跑 4 个种子的原因。

几点要连着说的：

- **成功的判定是严格的**：任务状态为完成、有产物、并且读到了每个被要求文档的证据。"错误完成"指状态是完成但缺这些证据——1600 个任务里错误完成是 0，每版每档的 95% 上限为 1.9%。这条对应第四节的分离：两版的失败都是如实失败，旧版的形态是 30 秒处整体超时，新版是"没有证据的失败"或"部分完成"。
- **成功率换来的代价是变慢和多打上游**。单种子那轮的 30% 档，治理后 P50 从 1.1 秒升到 12.9 秒、P95 升到 37.3 秒（这两个数只有单种子那轮有，4 个种子合并的表里没有耗时分位）；但旧版在这一档把慢任务直接判成失败，它的 P50 只统计了幸存者，两者不可直接比。单种子那轮里，治理后的 embedding 请求数随故障率从 75 涨到 156，多出来的就是重试带来的额外上游负载——**这是用负载换成功率**。
- **50% 这一档救不回全部**：两次尝试都碰上无响应的概率约 25%，重试无能为力，成功率 86.0%。
- **熔断的修复不在这组数字里**。评测命令直连 embedding 客户端，不经过模型路由那一层，所以第七节讲的熔断补缺（失败计入、半开名额归还）**只由单元测试覆盖，没有进入 X3 的数字**。

回归方面，这一轮改动后 Python 41/41、Java 225/225 通过（改之前是 36/220），在中文区域设置下同样全绿。

## 九、边界与不足

1. 只注入了一种故障。限流（429）、上游 5xx、延迟分布、流中途断开、以及 chat 端点的故障，模拟上游都有旋钮，但没有跑过基准，所以"这套容错在限流下表现如何"目前没有数字。
2. 熔断与半开名额归还这两项修复没有进入 X3 的数字，只由单元测试覆盖——评测入口绕过了模型路由层。
3. 全部数字来自模拟上游，不是真实供应商。真实上游的故障形态（半开连接、慢速吐字、部分响应、跨可用区抖动）比"挂住 90 秒不回包"复杂。
4. 治理前那一版是在"三层同为 30 秒"的配置下跑的，所以对照测的是"治理前的实际行为"，不是"同样超时配置下单纯加重试能带来多少收益"，两种提升被合在了一个数字里。
5. 重试预算是固定的一次，没有做重试预算令牌桶、对冲请求、舱壁隔离。故障率高时重试会放大上游负载（50% 档最明显），目前没有任何机制在全局层面压住这种放大。
6. 模拟上游的请求日志在请求结束时才写，所以格子结束时仍被挂住的请求不会出现在它的日志里，无响应次数以 Java 侧的调用台账为准；同一种子也无法逐请求复现，因为两路并发请求的先后顺序不固定。

## 十、口述版

这条做的是上游不稳定时的容错。起因是一次批量跑，1200 个任务里 72 个超时，全都卡在检索工具上、耗时清一色 30 秒出头。查下来两个问题：一是 HTTP、检索通道、研究工具三层超时都配成了 30 秒，内层永远不会先于外层结束，一次不回包就吃掉任务总预算的十分之一；二是检索通道原本会把异常吞掉、返回空结果，这对即时问答是合理降级，但研究任务是自主多轮的，模型看到空结果就以为库里没资料，最后交出一份状态成功、内容空洞的报告——失败被伪装成了"事实上不存在"。

我的做法是三块。第一块是分层截止时间：进工具时算出一个绝对截止时刻，放在一个显式传递、不随线程继承的请求作用域里，每一层从它往回推并再收紧一点——工具层比上层少 2 秒，单次 HTTP 调用最多 12 秒，数据库查询最多 5 秒，这样一次不回包最多损失 12 秒，剩下的时间正好够做一次重试。不用各层配固定超时，是因为固定值保证不了内层先于外层结束。第二块是有限重试：把底层异常规整成带阶段、错误码和可重试标志的统一失败，只对网络错误、限流、5xx 重试，格式错误和熔断打开不重试，取消既不重试也不计熔断；embedding 只重试一次，剩余时间不足 1.5 秒就不重试；退避用指数退避加 equal jitter，基数 300 毫秒、上限 2 秒，一半固定一半随机——原来是固定等 300 毫秒，同一批失败的调用会在同一时刻一起重试，对刚恢复的上游形成二次冲击。第三块也是最重要的一块，把"调用失败"和"检索无命中"彻底分开：研究路径上通道不再吞异常，工具层把失败原样告诉模型并明确写上"这是执行失败，不是不存在资料的证据"，落库时只要有执行问题就不给完成状态，既没有证据又有执行问题就直接判失败，还堵了模型用"向用户提问"来掩盖故障的侧路。另外取消会一路传到底层，真正 cancel 掉 HTTP 调用和数据库语句；检索连续失败两次就禁止再搜，让模型拿已有证据收尾；模型路由那层有熔断，连续失败两次打开三十秒、半开只放一个探测，带截止时间的调用不跨模型回退——向量不可跨模型比较——但失败照样计入熔断。

效果上，因为真实上游的故障率不可控也不能复现，我做了一个可脚本化的模拟上游来打数字。50 个研究任务、4 个随机种子、每格 200 个任务，只注入 embedding 无响应这一种故障。30% 无响应率下成功率从 57.5% 提升到 98.5%，Wilson 95% 区间两版不重叠；1600 个任务里"状态成功但没有证据"这种错误完成是 0。代价也很清楚：成功任务变慢，单种子那轮的 30% 档 P50 从 1.1 秒涨到 12.9 秒，embedding 请求数也随故障率上升，本质是用负载换成功率；50% 那档两次尝试都撞上无响应的概率约四分之一，重试救不回来，成功率 86%。要补充两点：所有数字来自模拟上游不是真实供应商，而且熔断那部分修复因为评测入口绕过了模型路由层，没进这组数字，只由单元测试覆盖。
