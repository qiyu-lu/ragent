# 08 知识库权限隔离

这一篇讲企业资料的可见范围：谁能看到哪个知识库，这个判断在系统的哪一个地方做出，以及它必须发生在检索的哪一步之前。改造之前，知识库是全局共享的——登录之后按 ID 就能读、改、删任何一个库，问答检索的"全局范围"就是全部有效库，研究任务入口的注释直接写着"当前知识库是全局共享"。企业资料的第一条安全需求恰好就是不同的人看到不同的资料，出错就是数据泄露，所以这是整套加固里唯一一个"做错了不是慢、是错"的问题。

## 一、可见性三档与授权关系

先要有一个数据模型能表达"这份资料给谁看"。做法参考了两个成熟产品的形状：知识库层面的三档可见性，以及检索结果按身份裁剪。

每个知识库有一个**所有者**和一个**可见性**档位，三档分别是：全员可读（`PUBLIC`）、仅自己（`PRIVATE`）、指定成员（`RESTRICTED`）。另有一张**授权表**，一行表示"某个对象在某个库上有某种权限"：对象可以是一个用户，也可以是一个角色；权限分为只读和管理两级，管理蕴含只读。管理员角色对所有库都有全部权限，所有者对自己的库有管理权限。

几个判断上的约定，都是会被追问的地方：

- **授权只在"全员可读"和"指定成员"两档上生效，在"仅自己"这一档被忽略**。理由是这一档表达的是使用者的明确意图——只有我能看——不应该被一条忘记清理的历史授权打破。要放开就先改档位，是一个显式动作。
- **数据库列的默认值是"仅自己"，但存量数据迁移成"全员可读"**。这两个方向看似矛盾，其实是同一条原则的两面：存量库在改造前本来就是全员可见的，迁移不能改变既有行为，否则一上线所有人的检索都空了；而任何绕过应用层直接插入的新行，出错时应当偏向拒绝，所以列默认取最严的一档。通过接口新建的库，不指定可见性时也按"仅自己"落库。
- **迁移只做加法、可以重复执行**：加两列、建一张表、按原有的创建人用户名回填所有者。

## 二、唯一的判定入口

这一节的问题是：权限规则一旦分散，就一定会漏。知识库、文档、分块三层接口加上问答、研究、版本比较，如果每处各写一段"是不是我的库、是不是公开",总有一处写反或者漏写，而且以后加一档可见性要改十几个地方。

所以所有判定都收敛到一个**权限判定入口**上，它只做一件事：给定一个主体和一个权限级别，算出这个主体能访问哪些库。核心是一条 SQL，把"管理员 / 所有者 / 全员可读 / 授权命中"四个条件并起来，未删除的库才参与。其他所有地方都调它，不各写一套规则。它对外有两种用法：

- **按 ID 的操作**（改库、删库、上传文档、改块、看某个块）：调"要求当前用户对这个库（或这个文档所在的库）有某权限"，不满足就抛异常。这里有一个刻意的设计：**不可读和不存在返回同一条提示**，只有"能读但不能管"时才提示无权管理。否则拿一批 ID 去试，从提示的差别就能问出"这个库存在"这件事。
- **按范围的操作**（列表、文档搜索、检索）：取出可访问的库集合，作为查询条件拼进 SQL，而不是查完再过滤。

另外三条规则：

- **身份缺失一律按无权处理，绝不回退为全局可见**。没有登录用户、后台线程接管时按用户 ID 查不到人、用户已被删除，这三种情况都返回一个"什么都没有"的主体。这类地方最容易写成"拿不到身份就不加过滤"，那等于给自己留了一个越权后门。研究任务的执行线程不在请求线程里，所以判定入口另外提供了"按用户 ID 重建主体"的方法，查不到用户就是无权。
- **判定结论不缓存**，每次请求现算，靠授权表上的对象索引撑住开销。代价是多一次数据库查询，换来的是撤销授权在下一次请求立即生效，不存在缓存过期窗口——权限系统里"过一会儿才生效"本身就是缺陷。
- 少数管理型接口（后台看板、链路追踪、摄取）不按库判定，而是在路由层直接限定管理员角色。它们能绕过知识库直接读到内容或者写入任意库，按库判定不合适。

## 三、过滤必须发生在召回之前

发起方是一个普通用户提问，带来的是一句自然语言，想得到的是一段带来源的回答；这一节只看"这次检索能碰到哪些库"这一个决定。

流程是这样的：提问进来后，检索引擎为每个子问题解析一次**检索范围**，范围等于"当前启用中的知识库"与"当前用户可读的知识库"的交集。范围算完就放进这次检索的上下文里，各个检索通道只读不判。向量检索把这批库名直接拼进 SQL 的 `IN` 条件里，也就是说不可读的库的向量根本不参与排序。

**为什么不能召回之后再滤**，这是这一节唯一要记住的事：检索只取相似度最高的若干块（默认 TopK 很小），如果先按全库召回再按权限筛，那些名额会先被不可读库里的高分块占掉，筛完剩下的结果变少甚至为空——用户看到的不是"没有权限"，而是"这个系统查不到东西"，而且那些内容已经进过进程内存和日志。集成测试就是照这个场景搭的：构造一个私有库的块与查询向量完全相同（相似度 1.0），公开库的块相似度 0.6；所有者取 TopK=1 命中私有库的块，其他用户取 TopK=1 拿到的是公开库那个 0.6 的块。如果过滤在召回之后，其他用户这一个名额会被私有库的块占走，过滤完就是空结果。

顺着改的时候还发现一个陷阱：**空范围过去被当成"不限"**。当时还在的关键词通道在库列表为空时不加库过滤，直接搜整个共享索引。以前没有调用方会传空列表，所以不算 bug；但权限裁剪之后，"这个用户一个库都读不到"变成了正常情况，空范围立刻就成了全库泄露。这类"空即全部"的默认值在加权限时要专门清一遍。当前代码里检索只剩向量通道和联网通道（关键词与图谱两条一直没启用的通道随后被删掉了），向量通道遇到空范围是直接跳过检索。

## 四、研究任务的归属校验

研究任务是长跑的：创建时排队，可能几分钟后才被某个实例领走执行，中途还可能被另一个实例接管。所以权限要在两个时刻各查一次。

- **创建时**逐个校验所选的库：当前用户必须对每个库可读，且这个库确实可用；不可读和不存在给同一条提示。所选的文档必须属于所选的库之一，否则拒绝——不然可以用一个自己有权的库做外壳，夹带一个别人的文档 ID 进来。
- **每次领取时**（包括第一次执行、跨实例接管、断点续跑）按任务所有者重新算一遍权限：任务记录里存的那批库，必须全部仍在所有者当前可读的集合里，否则**不调用模型**，直接把任务置为失败并记下原因码（`KB_ACCESS_REVOKED`，表示执行期间权限被撤销）。放在领取处而不是每一步检索前，是因为领取是所有执行路径的共同入口，只有一处。
- 研究运行本身**按所有者隔离**：查运行、拉事件流、读证据和产物，都带上所有者条件，管理员也读不到别人的运行。这是既有设计，权限改造沿用了它。
- **停止流的接口**原先不校验归属，任何人拿到任务 ID 就能掐断别人的流。现在流开始时先把"任务 ID → 用户 ID"写进 Redis，再把任务 ID 随事件发给前端，保证停止请求到达时归属一定已经写入；停止只允许所有者或管理员。之所以放共享存储而不是进程内存，是因为多实例部署时停止请求可能落到任何一个实例上。归属记录带 30 分钟过期，任务结束时**不删**——删了的话用户在流结束那一瞬间点停止会被判成越权。

## 五、泄露通道清点

有了判定入口和召回前过滤，还要回答一个问题：绕开检索，还有哪些地方会把资料内容或"某份资料是否存在"这件事漏出去。逐条清点的结论：

- **Redis**：只有两份全局配置缓存、停止标记和任务归属，没有检索结果缓存，也没有答案缓存。没有缓存反而简化了这里——一旦按问题文本缓存答案，缓存键里不带身份就是跨用户泄露，带身份又基本不会命中。
- **会话记忆与历史消息**：按会话所有者读取，别人的会话读不到。但**已经生成的回答和当时的来源快照，在撤销授权后对提问者仍然可见**，没有做回收。这与"资料已经被下载过一份"是同一类情况，权限只能管住新的读取。
- **事件流**：问答的 SSE 只发给发起这次请求的那条连接；研究任务的事件流按所有者读取。
- **向量复用缓存**：按内容哈希寻址（模型标识、维度、文本哈希三段），**键里不带任何库或用户信息，返回值也不含访问结论**。所以它既不会把别人库里的向量取给你看（取到的只是你自己这段文本的向量），命中与否也不能用来推断某个库里有没有某段内容——命中只说明"系统里某处曾经嵌入过这段一模一样的文本"，而调用方手里本来就有这段文本。
- **管理型接口**（链路追踪里有别人的问题和召回片段，摄取接口能写入任意库，后台看板同理）：一律在路由层收紧为只允许管理员。这条规则覆盖的前缀里还包含当时的评测与图谱接口，它们后来随检索瘦身一起移除了，规则保留着。
- **一处没收紧**：Agent 配置、示例问题这类全局配置的写接口仍然只校验登录。它们不含资料正文，判断是风险可接受。

越权矩阵的结论（三种身份 × 三档可见性 × 二十多个按 ID 的接口，再叠加授予、按角色授予、撤销几个阶段）：**299 项全部符合预期，其中 173 项允许、126 项拒绝**；判成"拒绝"要同时满足抛出异常且底层业务服务没有被调用——只看异常不够，有些实现是先查了数据再抛错，那时内容已经读出来了。测试怎么搭在第 09 篇。

## 边界与不足

- **召回前过滤只在向量通道上成立**。当时还在的图谱通道是单实例单张图，没法按库限定召回范围，只能拿到结果后把不可读库的内容剔掉——结果不泄露，但名额已经被占，属于召回后过滤，真正的隔离要按库分实例。这条通道此后随同关键词通道一起被删除，所以当前代码里不存在这个缺口；但换成任何一种"只能全局召回"的外部检索组件时，这个问题会原样回来。
- **权限撤销对正在执行的那一次研究任务不是立即生效的**，要等到下一次领取才会被拒，最长为一次运行时限；已经保存的证据和产物不回收。
- **已生成的回答、来源快照不受后续权限变化影响**，只有新的检索受控。
- **运维遗留**：可见性这两列由一次数据库迁移添加，当前代码的检索会读可见性字段，本地库如果没有补执行这次迁移，直接跑新代码会因为缺列报 SQL 语法错误（已经出现过一次，表现为几条研究任务全部失败）。部分数据库已执行，其余本地库在运行新代码前仍需手动补上。
- **授权变更没有写进业务变更日志**，事后查不到"谁在什么时候把哪个库开给了谁"；前端也没有可见性与授权的界面，只能调接口。
- **越权矩阵在服务端方法层驱动接口，不经过 HTTP 与登录拦截器**，所以"管理员专属路由"那部分只做了规则审阅，没有端到端验证。

## 口述版

企业资料的知识库原先是全局共享的，登录之后按 ID 能读能改任何一个库，检索的全局范围就是全部库。我加了一层权限隔离：知识库有所有者和三档可见性——全员可读、仅自己、指定成员，另有一张授权表按用户或角色授予只读或管理，管理蕴含只读；授权只在全员可读和指定成员两档生效，"仅自己"这一档忽略授权，因为它表达的是明确意图，不该被一条遗留授权打破。所有判定收敛到一个入口，一条 SQL 把管理员、所有者、公开、授权四个条件并起来，其他地方一律调它，不各写规则；身份缺失一律按无权，绝不回退为全局可见；结论不缓存，撤销下一次请求就生效。

最关键的一点是过滤发生在召回之前：解析检索范围时先把有效库和当前用户可读的库求交，向量检索直接把这批库拼进 SQL 条件。如果放在召回之后，TopK 名额会先被不可读库的高分块占掉，用户看到的不是"没权限"而是"查不到"。我写了一个集成测试证明这件事：私有库里放一个和查询向量完全相同的块，公开库放一个相似度 0.6 的块，其他用户取 TopK=1 拿到的是那个 0.6 的公开块。研究任务因为是长跑的，创建时校验一次，之后每次领取——包括跨实例接管——都按任务所有者重算一次，不满足就直接失败、不调模型；停止接口原先不校验归属，改成把任务归属写进 Redis，只有所有者或管理员能停。最后我把泄露通道逐条清了一遍：缓存键、会话记忆、事件流、向量复用缓存、管理型接口，其中链路追踪、摄取这些能绕过知识库读到内容或写入任意库的后台接口收紧成只允许管理员。验证是一个越权矩阵，三种身份乘三档可见性乘二十多个按 ID 的接口，加上授权和撤销几个阶段共 299 项全部符合预期，173 允许 126 拒绝，判定拒绝要求既抛异常、底层服务又确实没被调用。不足是召回前过滤只对能按库限定范围的检索组件成立，当时的图谱通道就只能在结果侧过滤；撤销权限对正在跑的那一次任务要等下次领取才生效，已经生成的回答和证据也不回收。
