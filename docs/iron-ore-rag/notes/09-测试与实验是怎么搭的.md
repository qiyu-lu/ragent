# 09 测试与实验是怎么搭的

这个项目是预研原型，没有上线，也就没有线上流量、没有告警、没有事故复盘。七项后端加固每一项都声称"改好了什么"，而唯一能拿出来的证据只能是自己造的。这一篇讲的就是这套证据是怎么造的：每种验证解决的是"不这么做会出什么事"，为什么选了这条路而不是另一条，以及它到底证明不了什么。

证据分三层，越往下越贵、越不可重复：

- **回归**：每次改完代码跑一遍，验证的是程序行为（协议字节、状态流转、权限判定），不花接口费，几十秒出结果；
- **模拟上游上的实验**：用一个自己写的模拟上游，把故障、并发、积压这些平时碰不到的情况按需造出来，可以重复几十上百次。它测的是我写的这套机制，不是供应商；
- **真实上游上的一次性对照**：只有成本和答案质量这两件事模拟上游算不出来，必须真调模型。这类实验贵、慢、只能跑一两次，所以结论要写得最保守。

下面八项按这个顺序展开。

## 一、回归：两层，一层快一层真

**不这么做会出什么事**：提示缓存、租约接管、权限判定这几处改动都在"看不见"的地方——请求的字节、数据库的行、SQL 的条件。改坏了不会报错，只会悄悄地不命中、悄悄地多跑一遍、悄悄地多看一个库。所以每一项都必须有一条能反复跑的命令。

一条回归命令承担了全部日常验证。它由我在本地发起，不需要任何凭证和网络，跑完给出通过数，到"这次改动没有破坏已知行为"为止。命令里串了两层。

**第一层是协议层测试，模型换成脚本化的本地 HTTP 桩。** 测试进程里起一个本地 mock 服务器，按预先写死的步骤序列依次返回工具调用（检索 → 阅读 → 再检索 → 阅读 → 结束），被测代码走的是真实的模型工厂、真实的 SDK、真实的流式解析，只是终点换成了本地地址。这样能做到的事情是**逐字节断言**：把首次执行发出的五个请求体原样录下来，再让接管续跑从持久事件重建一遍对话，在三个截断点（完成一步后、工具在途、已得出结论）比较两次请求的字节是否完全相同。提示缓存那一项的所有结论——系统消息稳定、提醒每次只有末尾一条、压缩后前缀不变、显式标记打在内容块里——也都是这么断言的。

- **为什么用桩而不是 mock 掉模型对象**：缓存命中与否取决于请求体的字节，重复调用与否取决于流是否读完。把模型换成一个 Java 接口的 mock，这两件事都消失了，测试就只能验证"我调了几次某方法"。用本地 HTTP 桩，从序列化到连接、超时、取消都还在链路里。
- **它证明不了什么**：桩不会像真实供应商那样计费、限流、返回缓存命中统计。"前缀稳定"是事实，"前缀稳定就会命中"不是——那需要真实端点的探针（见第四节）。

**第二层是集成测试，连真实 PostgreSQL 与 pgvector，并且自建随机库。** 脚本在本地的 PostgreSQL 容器里新建一个随机命名的库，灌入建表脚本，把连接串通过环境变量传给测试进程，测试跑完无论成败都把库删掉。测试类本身还多加了一道锁：连接串必须匹配"本机 + 随机前缀库名"的形式，否则直接拒绝启动。

- **为什么不用内存数据库或容器化测试框架**：这一批改动里有一半的正确性就落在 PostgreSQL 的具体行为上——跳过锁定行的并发领取、行锁内分配事件序号、向量相似度排序、部分索引、同一事务里跨两张表先删后插。换成内存数据库，这些语义要么不存在要么不一样，测过了也不算数。
- **为什么每次新建随机库而不是复用一个测试库**：并发领取和接管的测试会把数据库写成各种中间状态，复用会让上一次的残留影响下一次；随机库名加上那道连接串校验，也让"误连开发库把数据删了"这种事在代码层面不可能发生。
- **它证明不了什么**：跑的是本机单实例 PostgreSQL，不含网络延迟、连接池上限、数据库本身的负载。另外越权矩阵这类测试是在服务端 Java 层直接调 Controller 方法，不经过 HTTP 与登录拦截器（见第八节）。

回归通过数本身也要留条件：W7 之后是 Python 53/53、Java 13 + 211，约 40 s。更早记录过的 13 + 260 是删测试的瘦身重构之前的数，没有逐项核对，所以不能拿两个数相减说"少了多少测试"。

## 二、模拟上游：一个可以随手拧坏的上游

**不这么做会出什么事**：故障注入、进程被杀、三百个任务排队——这些实验每跑一次都要几百上千次模型调用。用真实供应商，一是钱，二是不可重复（对方的延迟和限流每次都不一样），三是没法主动制造"接口 50% 不响应"这种情况。没有模拟上游，后面四个实验一个都做不成。

模拟上游是一个独立的 Python 进程，对外是 OpenAI 兼容接口：一个对话补全端点，一个向量化端点。实验脚本给它分配一个空闲端口，把被测的 Java 进程的供应商地址指过去，跑完把它连同临时数据库一起关掉。

它有三个关键性质。

**一，对话端点是确定性的策略，不是录播。** 它读收到的整段对话，从里面解析出任务目标提到的几个资料编号和已经发生过的工具调用，然后按固定规则算出下一步：每个编号先检索、再读第一条候选，检索空结果或读不到就重试一次，两次不成就记一条缺口，全部处理完就结束研究；当上游被要求提供委派工具且目标里有多个编号时，先派子任务，再把子任务引用过的证据汇总后结束。没有工具定义的请求被当成最终成文，返回一份引用了全部给定证据的 JSON 报告。因为它只看对话内容，**同一段对话永远得到同一个动作**——这正是接管实验需要的：换一个进程、从事件重建出同样的对话，模拟上游会给出同样的下一步。

- **为什么是独立进程而不是 Java 内的 mock**：一是被测的要是整条 HTTP 链路（连接、流式解析、分层超时、取消传递）；二是故障注入实验要同时跑"治理前"和"治理后"两个历史版本的代码，旧版本没法改，但它们都读同一批供应商地址的环境变量，指过去就能用。

**二，向量化端点是确定性向量。** 它把文本里的第一个资料编号（没有就用整段归一化文本）做哈希，用哈希当随机种子生成一个定长单位向量。于是"查询里提到某个编号"和"那份文档的标题"哈希到同一个种子，余弦相似度为 1，必然排第一；不相关的编号几乎正交。检索结果因此完全可预测，实验里任何一次"没读到该读的资料"都只能是故障或代码造成的，不是检索质量的波动。

**三，故障是一组旋钮，由一个固定种子的随机数发生器统一抽。** 每个 HTTP 请求进来抽一次：无响应（把连接挂住默认 90 秒，然后一个字节都不回地关掉）、429 或 503、流传到一半断开（只对对话端点）、再叠加一段均匀分布的延迟。旋钮按端点分开设，所以可以只坏向量化、不坏对话。每个请求都追加一行日志，另有一个统计端点。

- **为什么"无响应"要挂住连接而不是直接关闭**：直接关闭是一个立刻可见的错误，客户端会马上重试；真正贵的故障形态是对方收了请求却不回复，把调用方的超时预算耗光。历史上那次事故（1200 个任务里 72 个卡在 30.01 秒）就是这个形态，所以基准注入的就是它。
- **它证明不了什么**：模拟上游的延迟是我设的均匀分布，故障是我设的独立同分布。真实供应商的慢是相关的、成串的，限流是有配额语义的。所有基于模拟上游的数字都只说明"我这套队列、重试、租约、接管在这种输入下怎么表现"，一个都不能当作对供应商的容量或可用性承诺。另外模拟上游的请求日志是在请求结束时才写的，实验结束时仍被挂住的请求不会出现在日志里，所以无响应的次数要以 Java 侧的台账为准。

## 三、接管实验：多个 JVM 抢一个数据库，然后按下故障按钮

**不这么做会出什么事**：心跳租约、跨实例接管、断点续跑、优雅停机这四件事，单元测试能验证"函数在给定输入下返回什么"，但真正要回答的问题是"执行者进程突然没了，这个任务会怎样"。这个问题只有把进程真的杀掉才能回答。

一次实验由实验脚本发起：它建一个随机隔离的运行库和一个模拟上游，按场景启动若干个**独立的 JVM 执行器进程**（不是线程），它们共享那一个数据库，跑的是生产里同一套执行服务——同样的租约、心跳、轮询领取、续跑、停机。脚本往库里提交几个脚本化任务，等到任务确实跑起来（判据是数据库里已有两次工具结束事件，不是"进程启动了"），再注入故障，然后等所有任务进入终态，最后直接查数据库做判定。一次场景到此为止，库删掉。

六个场景：无故障基线、`kill -9` 杀掉持有任务的执行者、运行中启动一个新实例、`SIGTERM` 优雅停机、`SIGSTOP` 暂停超过租约后再 `SIGCONT` 放行、以及每个接手者都被杀的毒任务。

- **为什么要三种不同的杀法**：它们对应三种完全不同的失败语义。`kill -9` 是进程瞬间消失，续租停止，任务要靠租约过期被别人接走；`SIGTERM` 是有序退出，进程有机会在步边界主动把任务交还队列，接手方不用等租约；`SIGSTOP` 最刁钻——进程还在、TCP 连接还在、只是被冻住，解冻后它会**以为自己还持有任务**继续往下写。这一场验的就是围栏：旧执行者恢复后续租被拒、写入被拒、自己停下来，而不是和新执行者一起写同一个任务。
- **为什么要一个毒任务场景**：接管机制自己会制造新的故障模式。如果一个任务每次被接手都让接手者崩溃，无限接管会把整个集群轮流拖死。所以要验证接管次数超过阈值后任务被判为失败、执行者失联，而不是继续传染。

**判定不看日志，看数据库里的不变量。** 每个任务逐条检查：恰好一个终态事件；至多一个产物；事件序号从 1 开始连续无洞；**已完成的工具调用（同名同参数）没有被执行第二次**；状态不是"被中断"。另外还核对每个被要求的资料是否都留下了已读证据。重复的模型调用数不是直接数出来的，而是拿无故障基线那一档的干净调用数作差——超出的部分就是重做。

- **为什么用"同名同参数的工具调用只出现一次"当不变量**：续跑的语义是"至少一次"，崩溃时正在途中的那一次模型调用无论如何都要重做。真正不能容忍的是**已经完成的步骤被重做**——那意味着重复计费、重复写入。把不变量定在这里，既如实承认了至少一次，又能把"多做一步"和"从头再来"区分开。
- **"迟到写入被拒"怎么体现**：事件序号连续、终态事件恰好一个、已完成步骤不重做，这三条合起来就排除了两个执行者同时写同一个任务。暂停场景里另外数了旧执行者日志里"租约丢失"的次数，确认它自己停了。至于"过期接管后旧执行者的写入被明确拒绝"这一条，是连真实 PostgreSQL 的那层集成测试直接断言的（拿过期的那次领取去写，写入返回失败），实验只能给出间接证据。
- **恢复时间怎么测**：从注入故障那一刻（脚本记下的墙钟）到**新持有者写下第一条运行开始事件**的时间差。两个时刻用的是同一台机器的时钟，所以不涉及跨机时钟偏差。一次重复里如果有多个任务，取最慢的那个——因为关心的是"全部任务都回到活着的执行者手里"。百分位用最近秩。
- **为什么要重复 20 次而不是跑一次**（只有三个杀进程的场景重复了 20 次，基线、新实例、毒任务三个场景各跑一次）：单次的恢复时间是一个样本，说明不了分布。重复之后能看出恢复时间集中在约 5.0—5.1 秒和约 6.1 秒两档，正好差一个轮询间隔——这个结构比平均值更能解释机制。每次重复都用新的库和新的模拟上游，出错的重复如实记录并计入分母，不重试。

实验参数为了缩短时间被调小了：租约 6 秒、心跳 2 秒、轮询 1 秒（生产默认是 30 / 10 / 5 秒）。结果：`kill -9` 恢复时间 P50 / P95 / 最大 5.13 / 6.12 / 6.12 秒，暂停场景 5.12 / 6.12 / 6.12 秒，优雅停机 1.08 / 1.11 / 1.11 秒；每个被接管的任务重复 1 次模型调用（就是在途那次，118 个任务全是 1）；不变量 0 失败。

**它证明不了什么**：

- 全部基于模拟上游，模型调用固定在 0.7—0.9 秒，所以恢复时间的绝对值只在这套参数下成立；换成生产默认参数，失联接管大约是"租约剩余 + 一个轮询间隔"，最坏 35 秒左右，这是推算不是实测。
- 租约只能发现进程死亡或被暂停，**发现不了进程活着、心跳照常、执行线程却卡住**。20 次重复里恰好撞上一次：某个执行者在注入故障之前就完全静止，等到超时。临时库已删、没有线程转储，原因没查出来。这个限制正好由实验自己暴露。
- 只跑了单 Agent 模式。模拟上游的策略不读续跑提示，所以"已完成的子任务不重跑"只由单元测试和集成测试覆盖。
- 优雅停机仍然重复一次模型调用，原因是 SDK 自带的关闭钩子先在"模型已决定、工具未执行"处中断了 Agent，这个决定没落库。实验能测出这一次重复，但消除它需要改持久化，没做。

## 四、缓存实验：同一份负载，前后各跑一遍

**不这么做会出什么事**：提示缓存的收益是账单上的事，协议测试只能证明请求字节稳定、标记打在了正确的位置，证明不了供应商真的按折扣计费。而这件事又是整个改动的全部意义。

实验由一条脚本发起：它用**临时 git 工作树**把"前"臂（改动之前的那个基线标签）和"后"臂（改动所在的提交）各检出一份、各自编译，然后在同一批固定题目上分别跑一遍，最后用一个离线报表脚本读两边冻结下来的调用台账，出对照表。这次实验会真实调用模型供应商，所以到"两臂的台账都落盘、报表生成"为止，不做任何重跑。

- **为什么用临时工作树，而不是把旧代码 revert 回来跑一遍**：两臂必须是**同一个仓库里的两个真实提交**，各自带着自己的配置、模板和提示词。手工回退容易漏掉其中一部分，而且跑完还要恢复。工作树的做法是检出即编译、跑完即删，两臂的源码指纹都写进各自的运行目录，事后可核对。
- **顺序怎么排**：非分块的那次用的是前 B、后 B、后 C、前 C 这种一前一后再一后一前的次序。因为供应商的延迟和负载会随时间漂移，如果先把前臂全跑完再跑后臂，漂移就整个落在臂的差上。交错以后漂移至少被分摊到两边。
- **先跑一个小样闸门**：正式开跑之前先在后臂上跑六个固定题之外的任务，检查向量化失败率是否超过 10%、任务是否缺失或大面积失败，不过关就停下来不烧钱。这是为了避免"花了钱才发现环境不对"。

**命中率和计费输入的口径**，这是最容易被含糊过去的地方，所以写死：

- 报表只读已经冻结的批次里的调用台账、事件流和预测文件，**不调用任何接口**，可以反复重算。
- 一次调用只有在供应商真的回了用量、且输入 token 不为空时才计入"已知"；其余记为未知，单独列出，不当作 0。
- **命中率 = 所有已知调用的命中 token 之和 ÷ 输入 token 之和**，是总量口径，不是"命中的调用占比"。另外单独给出单次调用命中率的 P10 / P50 / P90，因为总量口径会被少数超长请求主导。
- **计费输入 = 未命中部分 × 1 + 命中部分 × 折扣 + 显式写入部分 × 1.25**，其中隐式命中 20%、显式命中 10%、显式写入 125%，取自供应商的上下文缓存文档，并且写成参数、在报告里记录用的是哪组权重。结果的单位是**输入 token 当量，不是钱**。
- 单任务计费输入 = 总计费输入 ÷ 不同任务数。

结果（同 40 题、两种模式、全部角色同一个小模型、真实上游）：命中率 B 模式 9.8% → 78.4%，C 模式 0.2% → 80.0%；单任务计费输入 −69% / −75%。

**它证明不了什么**：

- 计费输入是**按文档折扣折算的 token 当量，不是账单**，没有核对过发票。折扣换供应商就变。
- 每臂只跑一次。单任务的数字里还混着"后臂主 Agent 调用次数更少"这个因素，不能全归给缓存。
- 单次调用的延迟没有可靠改善，每个任务的首次调用反而慢了约 0.35 秒，怀疑与写缓存有关，没验证。
- 没有触发过阈值压缩（输入都低于估算上限），压缩只由协议测试覆盖。
- C 模式几乎没发生过委派，所以子 Agent 的缓存行为没被这次实验覆盖。

## 五、质量护栏：证明"省了钱"容易，证明"没改坏答案"难

**不这么做会出什么事**：缓存改动动了提示的结构——把易变的提醒从系统消息搬到了每次调用末尾临时追加的一条消息。这在理论上不该改变模型作答，但它确实改变了模型看到的东西。第一次对照里就出现了一个 F1 下降的信号，样本只有几题。如果就这么把"省了七成"写进简历，等于把一个可能的质量回退藏起来了。

护栏实验由我在真实上游上发起，目标只有一个：**在足够大的、模型没见过的题上，给缓存改动前后的答案质量一个带区间的配对差**。跑完出一份归因报告，到此为止——不做修复，因为修复超出这一轮范围。

**题怎么抽。** 抽样脚本只读题目文件里的两列：题目 ID 和它的原始题目 ID，**不看答案，也不看"是否可答"标签**。规则是：按"种子 + 题目 ID"的哈希升序排列；凡是在开发期回归题集里出现过的题，连同它同源的其它版本一起剔除；剩下的每个原始题目只保留第一个版本；取前 4 × 100 题，写成四个连续的块。

- **为什么必须剔除见过的题**：整个冲刺期间的调试、探针、复核都用的是回归题集。在这些题上再比一次，比的是"对这批题调过的参数"，不是泛化。
- **为什么连同源版本一起剔除**：这个数据集里同一个原始问题会有可答和不可答两个版本，只剔掉见过的那一个，另一个版本还是泄露。
- **为什么不看答案和可答标签**：抽样一旦碰到标签，就有按难易挑题的可能，哪怕无意。抽完以后评分阶段才读标签。
- **它证明不了什么**：这是一个公开的多跳问答数据集，不是企业检测资料。它能验证的是"这次改动有没有让作答变差"这个相对问题，不能用来宣称这个系统在业务语料上的绝对质量。

**前后怎么交错。** 四个块按"前 1、后 1、后 2、前 2、前 3、后 3、后 4、前 4"的次序执行，两臂交替开工、总次序前后对称。理由和上一节一样，而且更要紧：这一次跑的是四百道题、时间跨度更长，供应商的漂移更有机会混进臂的差里。交错之后还能逐块看均值——如果某一块特别异常，能看出来是漂移还是真效应。

**配对差和 bootstrap 区间。** 归因脚本把两臂按题目 ID 配对，只取两边都评过分的可答题，对每道题算**后臂 F1 减前臂 F1**，取这些差值的均值，再用百分位 bootstrap（对题目重抽样一万次，取 2.5% 与 97.5% 分位）给区间。

- **为什么用配对差而不是比两边的平均 F1**：题目之间的难度差异远大于两臂的差异。不配对的话，方差全被题目难度占掉，什么都看不出来。配对之后每道题自己和自己比，剩下的方差才是改动带来的。
- **为什么用 bootstrap 而不是 t 检验**：单题 F1 的分布是个夹在 0 和 1 之间、在两端堆积的怪分布，均值的正态近似靠不住。百分位 bootstrap 不需要对分布做假设，重抽样种子和次数都写进报告，可以原样复算。
- **归因分类是附带的，不参与统计**：脚本把每道下降的题分成"失败/改为拒答/两边都拒答/只是格式不同/确实答错"。格式类的判定是把两边的答案和参考答案都归一化后看词集合是否互相包含（"100" 与 "100th" 这类）。这些标签只用来解释损失落在哪里，EM 和 F1 本身仍然用数据集官方的定义和归一化。

**噪声基线是什么。** 同一批题、**同一个后臂版本**，再跑一次，然后用完全相同的配对差和 bootstrap 流程比较两次后臂。这条基线回答的是："什么都没改的情况下，两次运行之间的差有多大？"结果是 +0.059，区间 [−0.032, +0.158]——和被测效应同一个量级。

- **为什么必须有这条基线**：Agent 每次运行都会走不同的检索路径、不同的调用次数，本身就有随机性。没有噪声基线，一个 −0.03 的配对差既可以说成"明显变差"，也可以说成"没变化"，全凭说的人。有了基线，正确的结论只能是"效应没有超出运行间噪声"。
- **判定规则为什么必须事先写死**：这类实验的结果是一条带区间的数，区间大概率会跨过 0。如果等结果出来了再决定"看区间还是看点估计""要不要合并那 45 道旧题"，那就是拿结论去挑口径。所以事先定死：看配对差的点估计和 95% 区间，区间含 0 就只能说"未见显著下降"，同时必须把区间下界一起报出来当作"不能排除的下降幅度"。

结果（400 道未见过的题、可答 196、C 模式、前后 4 块交错）：命中率 0.15% → 80.4%，单任务计费输入 77,113 → 21,436（−72%），每块一致；配对答案 F1 −0.034，95% 区间 [−0.080, +0.011]，**未见显著下降，但不能排除 0.08 以内的下降**；EM 0.352 → 0.291。与最初引出疑问的 45 题合并后是 −0.045，区间 [−0.088, −0.002]，那 45 题本身偏向下降。损失的位置查清楚了：15 题由作答改为拒答（贡献 −0.056），反向 11 题（+0.025），拒答总数 47 → 47；两臂都没有触发压缩，所以排除了压缩存根这个解释。

**它证明不了什么**：

- 未见显著下降不等于没有下降。区间下界 −0.080 就是必须一起说出来的那句话。
- 噪声基线只跑了一次、只在 80 题上跑，它本身也是一个带宽区间的估计。
- "末尾提醒让模型更早收手"只是一个和数据相容的解释（后臂主调用更少、剩余预算更多），**没有验证，也没有修**。要验证得再做一个"提醒放末尾但不含剩余次数"的变体。
- EM 的下降比 F1 明显，说明相当一部分损失是措辞和格式，但这只是归因分类给的印象，没有单独做统计。

## 六、上游实验：多种子、Wilson 区间、错误完成

**不这么做会出什么事**：上游治理改的是超时分层、抖动退避、熔断计数。这些东西平时完全看不出来——接口不坏的时候，改与不改一模一样。唯一能说明问题的是一句"在多大的故障率下，系统还能做完多少任务"。

实验由脚本发起：它把"治理前"和"治理后"两个历史提交各建一个临时工作树、各自编译，然后对每一个（版本 × 故障率）组合建一个独立的模拟上游和一个随机隔离库，用那个版本自己编译出来的评测命令跑同一批 50 个脚本化任务。跑完写出预测、台账、trace，报告阶段离线汇总。一格到此为止；某一格的预测不完整就整格重跑，已完成的格保留。

- **只注入一种故障**：向量化接口无响应，比例 0 / 10% / 30% / 50%。挑这一种是因为它最贵——无响应会把调用方的超时预算整段吃掉，而历史事故就是这个形态。429、5xx、延迟分布、流中断这些旋钮都有，但没跑基准。
- **两版的先后在每个故障率上轮换**：同样是为了不让机器状态的漂移固定偏向某一版。
- **多种子**：最早只跑了一个种子，结果显示"治理后 30% 档 100% 成功"。换三个种子再跑，同一档就变成了 98.5%。所以最终报告是 4 个种子各跑一整套、每格合并成 200 个任务。**单种子的漂亮数字是不稳的**，这是实验自己教的。
- **为什么用 Wilson 区间**：成功率是个二项比例，而且经常贴着 100% 或很低。正态近似在两端会给出超出 [0,1] 的区间，样本小的时候尤其离谱。Wilson 区间在两端表现正常，而且能直接用来回答"两版的区间是否重叠"这个问题。
- **同一个种子也不能逐请求复现**：两路并发请求的先后顺序不固定，所以同种子重跑会有小的差别。这一点写在结论里，不当作 bug。

**"错误完成"的定义**是这组实验里最重要的一个约定。一个任务只有同时满足三条才算**成功**：状态是完成、有产物、并且**每一个被要求的资料文档都留下了已读证据**。状态是完成但缺这些证据的，叫**错误完成**——也就是上游挂了，系统却交出了一份答案。其它终态（失败、部分完成）算**如实失败**。

- **为什么要单列这一类**：可用性实验最容易自欺的地方就是把"成功率"定义成"状态是 COMPLETED 的比例"。一个把上游失败吞成空结果、然后照常成文的系统，在这个定义下成功率会很好看，而它恰恰是最危险的那种。把"错误完成"单独拎出来做一列，才算真的在测"失败是不是如实的"。
- **浪费的模型调用**：没成功的任务所消耗的模型调用数，用来说明故障的成本不只是失败本身。

结果（每格 200 个任务、向量化无响应 10 / 30 / 50%）：成功率 87.5 / 57.5 / 36.0% → 100 / 98.5 / 86.0%，Wilson 95% 区间两版不重叠（例如 50% 档 [29.7, 42.9] → [80.5, 90.1]）；**错误完成在 1600 个任务里是 0**。

**它证明不了什么**：

- 全部基于模拟上游。真实供应商的故障不是独立同分布的。
- 旧版在 30 秒处整体超时，是当时那套配置决定的。所以这里比的是"治理前的实际行为"和"治理后的实际行为"，不是"同一超时下纯重试带来的收益"。
- 评测命令直连向量化客户端，不经过模型路由层，所以熔断那处补缺**不在这些数字里**，只由单元测试覆盖。
- 收益有代价：成功任务变慢了（旧版把慢任务直接判死，它的 P50 只统计了幸存者），而且重试让向量化请求数随故障率上升——这是用负载换成功率。

## 七、容量实验：积压排空、加速比、领取语句计时

**不这么做会出什么事**：把队列放进数据库、用跳过锁定行的方式轮询领取，最容易挨的三个问题是"加机器有没有用""数据库会不会成为瓶颈""积压的时候任务会不会在门口就被拒掉"。这三个问题都得用数字答。

一格实验的流程：建一个随机隔离库和一个模拟上游，启动 1 / 2 / 3 个独立 JVM 执行器，**先让它们空转一段时间**（这段用来量空闲轮询的频率），然后由其中一个实例通过和 HTTP 接口同一条创建路径一次性提交 300 个任务。本机线程池能吃多少吃多少，剩下的留在库里，由任何一个有空槽的实例轮询领走。脚本等到库里所有任务都进入终态，再停掉实例，最后查数据库统计。一格到此为止，库删掉。

**口径全部写死**：

- **排空吞吐** = 任务数 ÷（第一条创建到最后一条终态事件），时间取**数据库时钟**，这样不受各实例的本地时钟影响。
- **槽位上限** = 实例数 × 每实例槽位 ÷ 单任务服务时长（首次运行开始事件到终态事件的均值）。这是"领取免费且瞬时"时的理论天花板，拿实测吞吐去比它，就能看出差距是被领取开销吃掉的，还是被轮询间隔吃掉的。
- **排队等待** = 创建到首次运行开始，百分位用最近秩。
- **领取语句计时**是应用侧口径，**包含从连接池取连接和整个事务**，执行器周期性打印累计的调用数、领取数、总耗时、最大耗时，报告取排空结束后的那一条。

- **为什么要算槽位上限这条参照线**：单看"3 个实例比 1 个快 2.95 倍"说明不了瓶颈在哪。有了这条线，就能说"实测是上限的 85%—95%，差的那部分是轮询间隔——槽位空出来之后最多要等一个间隔才被填上"，并且能用一组轮询 1 秒的对照直接验证这个解释（吞吐回补了大半，代价是空闲轮询从 0.2 次/秒/实例升到 1.0 次/秒/实例）。
- **为什么领取语句计时用应用侧口径而不是数据库侧**：本机的 PostgreSQL 镜像没开语句统计扩展，拿不到数据库侧的数。应用侧口径反而更保守——它把连接池和事务开销都算进去了，结论是"不是成本"就更站得住。这个限制要明说。
- **不变量也照样查**：每个任务恰好被一个执行者启动一次、没有接管也没有交还、恰好一个终态事件、至多一个产物、事件序号连续、状态是完成。这是把接管实验的那套不变量搬到压力场景下再验一次——**"至少一次"有没有在压力下变成"多次"**。

结果（300 个积压任务 × 1/2/3 实例、每实例 2 个槽位、轮询 5 秒重复 3 次加轮询 1 秒各 1 次、共 3600 个任务）：吞吐 12.2 / 24.0 / 35.8 条每分钟，加速比 1.00 / 1.98 / 2.95（轮询 1 秒为 13.3 / 26.5 / 39.7，加速比到 2.98），是槽位上限的 85%—95%；3 实例时等待 P50 242 秒、P95 470 秒；**提交被拒 0 个**，不变量 0 失败；领取语句均值 4.1—5.6 毫秒、最大 85 毫秒，占整段排空时长不到 0.12%。结论是瓶颈在槽位和轮询间隔，不是数据库。

**它证明不了什么**：

- 模拟上游的延迟是固定的，所以这测的是队列和执行器，**不是供应商**。真实上游的天花板是对方的限流。
- 实例是同一台机器上的独立 JVM，共享一个本机 PostgreSQL，不含网络延迟、连接池上限、数据库自身负载。
- 只测到 3 个实例 × 2 个槽位，再往上是否仍然线性没测；数据库在这个领取频率下还有余量，但没有找到拐点。
- 全部是无故障的干净排空。故障下的行为要看接管实验和上游实验。

## 八、越权矩阵：把"应该允许还是拒绝"算出来，再逐格对

**不这么做会出什么事**：权限是这类系统里唯一一处"错一次就是数据泄露"的地方。而权限的错法特别隐蔽——不是某个接口忘了加校验，就是某个接口的校验放在了业务逻辑之后。靠人一个接口一个接口地看，看不过来也看不住。

矩阵测试由 JUnit 发起，连真实 PostgreSQL、用真实的权限判定服务，而**下游的业务服务全部是 mock**。它自己建三个用户（所有者、另一个普通用户、管理员）、三种可见性各一个知识库和一份文档，然后遍历所有按 ID 操作的接口，逐格调用、逐格判定。跑完打印全部结果并断言总数，到此为止。

**矩阵怎么生成**：接口清单是一张显式的表，每一项写明接口名、它需要的权限（读还是管理）、以及怎么调用；一共 23 项（知识库 7、文档 10、分块 6）。行是（操作者 × 可见性）的组合，并且分四个阶段推进：先是无授权下三个操作者 × 三种可见性共 9 组；然后给普通用户在受限库上授读、在私有库上授管理（私有库必须忽略授权）；然后按角色授予管理权限；最后撤销。共 13 组 × 23 项 = 299 格。

- **期望值是另算的，不是抄实现**：测试类里有一张独立的规则表——管理员和所有者全部允许；其他用户在公开库上可读，在受限库上按授权，在私有库上一律拒绝。每一格的期望值由这张表算出来，再和实际行为比。如果期望值是从被测代码里读出来的，那这个测试永远会通过。
- **断什么言**：允许的格子必须正常返回；拒绝的格子必须**同时满足两条**——抛出客户端异常，**并且下游业务服务一次都没有被调用**。第二条是这整套测试的重点：它断言的是"鉴权发生在业务逻辑之前"。只断异常的话，一个先查库、拿到数据、再判定权限然后抛异常的实现也能通过，而那个实现已经把数据读进内存和日志了。
- **还断了几件相邻的事**：列表和文档搜索传给下游的范围集合里只有可读的库（6 项）；身份缺失、用户已删除、库已删除时可访问集合为空（4 项）——出错时偏向拒绝，而不是退回全局可见；停止接口只有任务所有者和管理员能调，拒绝时下游取消方法未被调用（4 项）。
- **召回前过滤单独证**：另一条集成测试在真实 pgvector 上构造一个"私有库里有一个与查询完全相同的块（相似度 1.0）、公开库里有一个相似度 0.6 的块"的局面，然后让另一个用户取 TopK=1。**如果过滤发生在召回之后，唯一的名额会被私有库那个块占掉，过滤后结果为空**；实际结果是他拿到了公开库那个 0.6 的块。这个构造是专门为了把"召回前"和"召回后"两种实现区分开设计的——普通的检索测试两者都能通过。

结果：299 项全部符合预期，其中 173 项允许、126 项拒绝，拒绝时业务服务未被调用。

**它证明不了什么**：

- 矩阵在服务端 Java 层直接驱动 Controller 方法，**不经过 HTTP 和登录拦截器**。管理员路由的拦截只做了编译和规则审阅，没有端到端的 HTTP 测试。
- 业务服务是 mock，所以它证明的是"鉴权在业务之前拦住了"，不是"业务服务自己也不会越权读"。
- 矩阵只覆盖按 ID 操作的接口。全局配置类的写接口仍然只校验登录，没有收紧。
- 当时的图谱通道只能在结果侧过滤，这一项没法用"召回前"的构造去证。该通道与关键词通道（两条都一直没启用）此后已被删除，当前代码里不存在这个缺口；但换成任何"只能全局召回"的外部检索组件时，它会原样回来。

## 边界与不足

- **没有一个数字来自线上**。所有实验都在本机跑：本机的 PostgreSQL 容器、本机的多个 JVM、本机的模拟上游。没有网络延迟、没有跨机时钟、没有真实并发用户、没有连接池和数据库负载的上限。所有"能扛住多少"的说法都只在这套环境里成立。
- **机制类的数字全部基于模拟上游**（接管、上游治理、容量三项）。模拟上游的延迟是均匀分布、故障是独立同分布，而真实供应商的慢和限流是成串的、有配额语义的。这些实验证明的是我写的队列、重试、租约、接管在给定输入下的行为，不是对供应商的任何承诺。
- **成本类和质量类的实验只跑了一两次**，真实上游那两次对照各臂只有一遍。计费是按文档折扣折算的 token 当量，不是账单，没有核对发票。
- **质量护栏用的是公开的多跳问答数据集，不是企业检测资料**。它能回答"这次改动有没有让作答变差"，回答不了"这个系统在业务语料上答得多好"。而且它的结论本身是"未见显著下降、不能排除 0.08 以内的下降"，不是"没有影响"。
- **有些限制是实验自己暴露出来但没有修的**：租约发现不了"进程活着、执行线程卡住"；优雅停机仍然重复一次模型调用；质量回退的最可能解释（末尾提醒让模型更早收手）没有验证也没有修。这些都停在"已知"，不是"已解决"。
- **越权矩阵不经过 HTTP 层**，管理员路由的拦截没有端到端测试。

## 口述版

我这个项目是预研原型，没有上线，所以没有线上流量可以拿来证明改动有效。我的办法是把证据分三层。最底下一层是回归：协议层的测试把模型换成本地的脚本化 HTTP 桩，这样整条链路——序列化、流式解析、超时、取消——都还在，我能对请求做逐字节断言，比如接管续跑之后重建出来的请求和第一次执行的请求是不是完全一样；集成测试连真实的 PostgreSQL 和 pgvector，每次新建一个随机命名的隔离库、跑完删掉，因为像跳过锁定行的并发领取、同一事务里跨两张表先删后插这些东西，换成内存数据库就测不出来了。

中间一层是我自己写了一个模拟上游——一个 OpenAI 兼容的独立 Python 进程，对话端点按对话内容确定性地吐出工具调用序列，向量化端点把文本哈希成确定性向量，另外有一组故障旋钮：无响应、限流比例、流中断，随机种子固定。有了它我才能做那三个机制实验：多个独立 JVM 共享一个数据库，我用 kill -9、SIGSTOP、SIGTERM 注入三种不同语义的故障，然后不看日志、直接查数据库的不变量——恰好一个终态产物、事件序号连续、已完成的步骤没有被做第二次；故障注入实验在四个种子上各跑一整套，成功率用 Wilson 区间，并且单独定义了一个叫"错误完成"的类别，就是上游挂了但系统照样交答案，这一类在一千六百个任务里是零，我觉得这比成功率本身更重要；容量实验是三百个任务的积压，我同时算出一条"只受槽位限制"的理论上限线，用来说明瓶颈是槽位和轮询间隔、不是数据库。

最上面一层是真实上游的前后对照，只能跑一两次，所以我在方法上特别小心：两臂用临时 git 工作树从两个真实提交各自编译，前后交错执行来抵消供应商的漂移；质量护栏那次是四百道模型没见过的题，抽样脚本只读题目 ID、不看答案和可答标签，前后分四块交错，用配对差加 bootstrap 区间，而且事先跑了一条噪声基线——同一个版本同一批题再跑一遍，差是正零点零五九，和被测效应同量级。所以我的结论只能写成"未见显著下降，但不能排除零点零八以内的下降"，这个下界我一定会一起说。

这套东西证明不了的部分我也写在文档里：全部在本机、机制类的数字全部基于模拟上游、成本是按文档折扣折算的 token 当量不是账单、质量用的是公开数据集不是业务语料。我的看法是，没有线上流量的时候，验证的价值不在于把数字做得好看，而在于口径事先写死、边界如实写出来——比如那次重复二十次的接管实验里有一次执行者在注入故障之前就自己卡住了，原因没查出来，我把它留在报告里，因为它恰好说明租约只能发现进程死掉，发现不了进程活着但线程卡住。
