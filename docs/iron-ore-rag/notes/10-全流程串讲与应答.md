# 10 全流程串讲与应答

这一篇不讲新机制，把 03—07 串成一条能连续讲出来的线，另外准备几段固定的应答。

## 一、3 分钟项目介绍稿

**前 30 秒说清是什么、我做了什么：**

这个项目是给检测机构做的资料问答与研究平台，基于一个开源 RAG 项目改造。它有两种用法：直接提问，几秒出一段带来源的回答；或者提一个研究任务，后台 Agent 反复检索、阅读、成文，一次跑几分钟、十几次模型调用。我负责研究任务模块以及围绕它的可靠性和成本优化。先说明一下，这是预研原型，没上线、没有真实流量，数字都是本地实验做的。

**中间 2 分钟按三条主线讲，每条"问题—做法—结果"三句：**

第一条是长任务可靠性。原来的实现在实例启动和关闭时会把全库所有排队和执行中的任务标成中断，多实例下任何一个实例发版都会杀掉别人正在跑的任务；租约是领取时一次性给满的，没人续也没人扫。我把数据库当队列，用 `FOR UPDATE SKIP LOCKED` 按空闲槽位领取，活性判断改成租约 30 秒加 10 秒心跳，每次领取 epoch 加一并发新的租约令牌，执行者每次写入都要核对 epoch 和令牌，旧执行者醒过来写不进去；续跑不存 Agent 快照，而是用已有的持久化事件重建上下文。验证上起多个独立 JVM 共享一个库，注入 `kill -9`、`SIGSTOP`、`SIGTERM`，这三种杀法各重复 20 次：恢复时间 `kill -9` 的 P50 约 5.1 秒，每个被接管任务只重复 1 次模型调用——崩溃时在途的那一次，不变量 0 失败。

第二条是模型调用成本。我加了一个调用台账记录每次模型调用的 token 和缓存命中，发现多轮调用的提示缓存几乎全部失效，命中率不到 10%。根因有两个：每轮把易变的提醒写进了第一条系统消息，前缀每轮都变；还有滑动裁剪也在改前缀。改法是稳定前缀、提醒挪到消息末尾且不写回记忆、历史只追加并用确定性序列化、裁剪改成阈值压缩、再配显式缓存断点。同负载前后对照，命中率从 9.8% 恢复到 78.4%，单任务计费输入降了 69%。之后我还补了一个质量护栏，在 400 道没见过的题上做前后交错对照，答案 F1 的配对差是 −0.034，95% 区间含 0，没见到显著下降——但也不能排除 0.08 以内的下降。

第三条是上游容错。原来三层超时都设成同样的 30 秒，内层一超时外层也就跟着废了；而且上游失败被吞成空结果，任务照样"成功"但内容是空的。我改成分层截止时间，内层必须先于外层结束；只对可重试的错误做有限重试并带抖动退避；把调用失败和检索无命中彻底分开；再加候选模型的熔断回退。用自己写的模拟上游注入 embedding 30% 请求无响应，任务成功率从 57.5% 提升到 98.5%，Wilson 区间两版不重叠。

**最后 30 秒收在边界上：**

这三项里，接管和容错的数字是在模拟上游上跑的，测的是我这套机制而不是供应商；成本和质量那两项是真调了模型，但只跑了一两次。最大的不足是没有线上流量，所有结论都是本地实验的结论。

## 二、一条研究任务的完整串讲（含中途被杀）

这是最值得练熟的一段：它把 03—07 全部串起来。建议讲的时候按时间顺序走，被打断也能从任意一步继续。

**提交。** 用户在会话里提一个研究任务，请求带会话 ID、任务说明、选中的知识库，前端还带一个客户端请求 ID。服务端先对选中的每个知识库校验权限，再插任务表——唯一约束是（所有者，客户端请求 ID），用 `ON CONFLICT DO NOTHING` 加回读来做幂等，而不是"先查再插"；同时还存一个请求指纹，防止同一个请求 ID 换了内容重复提交。任务行、会话行和第一条事件在同一个事务里写入。事务提交之后才尝试本地调度，池满不判失败，留在库里等轮询领走。接口立刻返回任务 ID，用户去订阅事件流。（04）

**领取。** 每个实例每 5 秒轮询一次，按自己的空闲槽位（默认 2 个）用 `FOR UPDATE SKIP LOCKED` 领取，条件是"排队中"或者"执行中但租约已过期"。领到之后 epoch 加一、发一个新的租约令牌、租约设为 30 秒，另有一个定时线程每 10 秒续租。这里还会按任务所有者重新校验一次知识库权限——权限是创建之后可能被撤销的，所以每次领取都要重算，不通过就直接失败，一次模型都不调。（05、08）

**执行。** Agent 进入工具循环：检索、阅读、（可选地）委派子 Agent、追问用户、结束。每次模型调用之前先在预算里扣额度再发 HTTP，默认模型调用 16 次、工具调用 24 次、输入 28000 token、总时长 300 秒，并且给收尾留出额度和时间。检索只产候选，不直接给模型当事实；有未读候选时不许再检索；结束时逐条校验每个发现引用的证据都在已读集合里——这就是"先读后引"。每一次模型调用、每一次工具开始和结束都作为事件写进事件表，序号由任务行上的计数器在行锁里用 `UPDATE ... RETURNING` 原子分配。（03、04）

**这中间的两条横向机制。** 一是提示缓存：每次请求的前缀是稳定的，易变的提醒放在消息末尾而且不写回记忆，历史只追加，超过阈值才做一次压缩而不是每轮滑动裁剪，再配两个显式缓存断点，所以十几轮调用之间前缀能一直命中。二是上游容错：这次检索的截止时间是从任务总预算一层层收紧下来的——任务 300 秒，留出收尾，工具 30 秒，单次 embedding 取 12 秒和剩余时间的较小值，数据库查询取 5 秒和剩余的较小值；只对可重试错误重试一次，带抖动退避；如果 embedding 真的挂了，返回的是"调用失败"而不是"没查到"，模型不会把它当成"资料里没有"。（06、07）

**实例被杀。** 假设这时候运维 `kill -9` 了这个实例。进程没了，心跳停了，任务行还停在"执行中"，租约还剩不到 30 秒。另一个实例的下一轮轮询（5 秒一次）会看到"执行中但租约已过期"，把它领走：epoch 再加一、换新令牌、接管次数加一。所以最坏恢复时间大约是"租约剩余 + 一个轮询间隔"，生产默认配置下约 35 秒；实验里把租约调成 6 秒、轮询 1 秒，测出来 `kill -9` 的 P50 是 5.13 秒。

如果是发版走 `SIGTERM`，不用等租约过期：停机时实例不打断在途的模型调用，而是在下一次模型调用之前把任务交还回队列，别的实例下一轮就能领走，实验里 P50 是 1.08 秒。交还不计接管次数，否则一次滚动发版就把配额耗光了。

**续跑。** 接手的实例不从头跑。它把这个任务的事件按序号读出来，把工具调用的开始和结束事件成对还原成 tool_call 和工具结果，没有配对完成的那一步丢掉、让模型重做。语义是"至少一次"，在这里是安全的：检索和阅读都是只读的，证据按内容算出的稳定 ID 幂等保存，产物的写入有 fencing 保护所以只可能有一份。重建时还保证请求前缀和第一次执行逐字节相同，所以接管之后提示缓存仍然能命中。实测每个被接管的任务只重复 1 次模型调用——就是崩溃时在途的那一次，已经完成的检索和阅读一次都没重做。（05、03、06）

**旧执行者醒过来怎么办。** 如果是 `SIGSTOP` 这种"假死"，进程后来会醒。它醒来以后想写事件、写检查点、写终态，每一次写入都在一个短事务里核对四个条件：状态是执行中、epoch 等于我领取时拿到的那个、租约令牌是我的、租约没过期。epoch 已经被接管者加过了，所以它什么都写不进去，连"把任务标成失败"都做不到。这就是 fencing token——不依赖它自己发现被接管，而是在写入点拒绝它。（05）

**收尾。** 接管方跑完剩下的步骤，生成报告：这一步不带工具，输入里带完整的证据正文，输出的 JSON 要过校验——引用必须在已读证据集合里、编号由服务端分配、步骤序号连续，不合格给一次修复机会。产物和终态在同一个事务里写入，同样受写保护。前端那边全程订阅 SSE，每条消息的 id 就是事件序号，中途断线重连时浏览器自动带 `Last-Event-ID` 回来，服务端从那个序号之后接着推——订阅和执行是完全解耦的，连上、断开、重连都不会触发或取消执行。所以用户看到的只是进度停了几秒又继续，不知道后台换了一个实例。（03、04）

**如果用户中途点了停止。** 取消是两段式的：先写库——epoch 加一、清掉租约、标记子任务、写一条取消事件；再尽力停本地。跨实例时最坏一个心跳周期之内旧执行者自己停下。取消一路传到 Agent 的事件流、模型调用、底层 HTTP 连接和数据库查询；取消之后迟到的写入被 fencing 拒绝，不会把一个已取消的任务改回执行中。（04）

## 三、"这是 demo 吗"的应答

对方问这句话时，真正想知道的是"你的经历有多少水分"。所以不要辩解，先承认，再把话题引到"你怎么在没有流量的情况下拿到证据"。

> 是预研原型，没有上线，也没有真实流量，这点我在简历里也写了。但我做的不是能跑通就算的 demo，而是把几个真会在生产里出问题的地方做出来并且验证过。
>
> 比如长任务丢失这件事，我没有用"重启一下看看"来验证，而是起了多个独立的 JVM 共享一个数据库，用 `kill -9`、`SIGSTOP`、`SIGTERM` 注入故障，这三种杀法各重复 20 次，每次都用新的数据库；每次跑完都用数据库里的记录核五条不变量——终态事件恰好一条、产物至多一份、事件序号从 1 连续、已完成的同名同参工具调用不重做、状态不是"中断"。"旧执行者的迟到写入写不进去"这一条不在实验脚本里，是连真实 PostgreSQL 的集成测试直接断言的（拿过期的那次领取去写，写入返回失败）。恢复时间是从注入时刻到新执行者接手的第一条事件之间算的，给的是 P50 和 P95 不是平均值。
>
> 成本那条也是同样的做法：我用临时工作树把改之前的版本构建出来，同一批题目前后交错各跑一遍，比的是同一道题在两个版本上的配对差，不是两组平均值；还专门跑了一次同题重跑来量运行间的噪声有多大，免得把噪声当成效果。
>
> 我能承认的是：这些实验里有三项是在我自己写的模拟上游上跑的，测的是我写的队列和容错逻辑，不是供应商的真实行为；成本和质量那两项真调了模型，但因为贵，只跑了一两次。所以我说的是"在这些条件下测到了什么"，不会说"线上提升了多少"。

## 四、已知限制的主动说法

这些话与其等对方挖出来，不如自己先说——先说是"知道边界"，被挖出来是"没想清楚"。

- **没有真实流量，也没有线上监控。** 可观测性只到调用台账和事件表的程度，没有告警、没有灰度、没有回滚演练。要上线首先缺的是这一层。
- **租约发现不了"活着但卡住"。** 心跳是独立线程，执行线程死锁或卡在某个不超时的调用上时心跳照常续租，只能等任务的总时长上限兜底。20 次重复里正好撞到过一次执行者静止，临时库已删、没有线程转储，**原因没查出来**——这个也照实说。
- **`SIGTERM` 下仍然会重复 1 次模型调用。** 交还点本来就在模型调用之前，理论上可以做到 0 重复，但 Agent SDK 自带的关闭钩子会先在"模型已经决定调用工具、工具还没执行"的位置中断，这个决定没落库，接手方只能再调一次。要消除得持久化模型的调用决定，我没做。
- **质量护栏只能说"未见显著下降"。** 配对 F1 是 −0.034，95% 区间 [−0.080, +0.011] 含 0；但合并早期那 45 道引出疑问的题之后是 −0.045 [−0.088, −0.002]，而且同题重跑的噪声是 +0.059、和效应同量级。所以不能排除 0.08 以内的下降。
- **模拟上游的数字不能外推。** 它的延迟是均匀分布、故障是独立同分布，真实供应商的慢是成串的、限流是有配额语义的；而且实例是同一台机器上的独立 JVM，不含网络延迟和数据库自身负载，只测到 3 实例 × 2 槽位。
- **容量只测到线性区间内。** 加速比 1.00 / 1.98 / 2.95，瓶颈是槽位和轮询间隔不是数据库，但没找到数据库的拐点在哪。
- **是一个人做的。** 没有代码评审，取舍都是我自己定的，有些地方（比如毒任务判定、压缩阈值）只有一个默认值，没有经过不同负载的检验。

## 口述版

一条研究任务的完整生命是这样的：用户提交，服务端按（所有者，客户端请求 ID）做幂等插入任务表，任务行和第一条事件同事务写入，提交后再尝试调度，池满就留在库里；某个实例轮询时用 `SKIP LOCKED` 领走，epoch 加一、拿新的租约令牌、租约 30 秒、10 秒续一次，并且按任务所有者重新校验知识库权限；Agent 进入工具循环，检索、阅读、成文，每次调用前先扣预算再发请求，每一步都作为事件按序号落库，请求前缀保持稳定所以提示缓存能一路命中，每一次上游调用的截止时间都是从任务总预算收紧下来的。

假如这时候实例被 `kill -9`，心跳停了，租约过期之后另一个实例的下一轮轮询把它领走，epoch 再加一。接手方不从头跑，而是把事件按序号读出来重建对话，没有配对完成的那一步丢掉让模型重做——实测每个被接管的任务只重复 1 次模型调用，就是崩溃时在途的那次。旧执行者如果后来醒过来，它的每一次写入都要核对 epoch、租约令牌和租约是否还有效，epoch 已经变了，所以它什么都写不进去，这就是 fencing。前端那边全程订阅 SSE，断线重连带 `Last-Event-ID` 从断点续传，订阅和执行是解耦的，所以用户只会看到进度停了几秒又继续。最后产物和终态在同一个事务里写入，同样受写保护，所以无论接管多少次，终态产物都只有一份。

如果对方问这是不是 demo，我会直接承认是预研原型、没上线，然后讲我是怎么在没有流量的情况下拿证据的：多 JVM 故障注入、三种杀法各重复 20 次、五条不变量、P50 和 P95 而不是平均值；成本那边用临时工作树建旧版本、同批题目前后交错、比配对差、还专门量了一次运行间噪声。同时说清楚哪几项是模拟上游、只能说明我写的机制在这种输入下怎么表现。
