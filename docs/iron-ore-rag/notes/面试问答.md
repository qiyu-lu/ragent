# 面试问答

这份是口述稿，不是知识清单。每题的「答」按 150—300 字写、先结论后理由，能直接念出来；「要点」是念不下去时的提词；「可能的追问」是对方大概率接着问的方向；「另见」指向同一件事的另一个角度（取舍题、通用题或八股题）。机制本身在同目录的 11 篇复习笔记里，这里不重复推导。

三条底线，每次开口都要守住：

- **数字连条件一起说**。真实上游还是模拟上游、多少个任务、几个种子、租约与轮询是什么配置，少一个都会被追出来。
- **预研原型、没上线、没有真实流量**，这句要主动说，不要等对方问。接管、上游容错、容量三项的数字来自自己写的模拟上游，只有成本和答案质量两项真调了模型。
- **没做的就说没做**。标了 **项目里没做** 的题，先承认，再讲理解和成熟做法，不要编经历。

全文 82 题，分六组加一组补充。答案里的事实与数字只取自 11 篇复习笔记与冲刺状态文件。

## 第 1 组　简历逐句深挖（Q1—Q27，27 题）

> 对简历三条的每个短语至少两问：是什么、为什么、怎么验证、坏了会怎样、数字怎么来的。答案里的数字一律连同条件说（真实上游 / 模拟上游、任务数、种子数、租约与轮询配置）。

### Q1 简历第一句说"分钟级任务在发版、宕机时丢失"，原来到底丢的是什么？

**答**：丢的不只是进度，是整批任务加上已经花掉的钱。我接手时只读核对了原来的实现，有三个问题。第一个比丢任务更糟：实例启动和关闭时各做一次孤儿清理，把全库所有排队中和执行中的任务标成中断，不区分归谁执行，单实例下看着是对的，多实例下任何一个实例发版都会杀掉别人正在健康执行的任务。第二个是租约形同虚设：领取时一次性设成"最长时长加 30 秒"也就是 330 秒，之后既不续租也没有任何地方扫过期，进程死了那一行会停在执行中然后永远停在那里。第三个是队列在收到请求那个实例的内存线程池里，队列满了直接把任务写成失败。再加上重启后只能整体重发，一个任务十几次模型调用全部作废。

**要点**：启停清全库、单实例下才成立、租约 330 秒无人续无人扫、内存队列满了判失败、重启后已花的调用全作废

**可能的追问**：
- 你是怎么发现这三个问题的？——只读核对上游自带的实现，不是线上故障
- 单实例下为什么看不出来？——全库的任务恰好就是我的任务
- 目标定成什么？——不丢、不重复出产物、不白跑

### Q2 领取任务那条语句是怎么写的，为什么一定要 FOR UPDATE SKIP LOCKED？

**答**：每个实例默认 5 秒轮询一次，一条语句取出可领取的任务。条件是状态为排队中，或者状态是执行中但租约已经过期——后者就是原执行者失联。按更新时间和 ID 排序，取的条数等于本实例当前的空闲槽位数，默认每实例 2 个槽位。加 SKIP LOCKED 是因为已经被别的实例锁住的行要直接跳过而不是排队等，没有它，三个实例轮询的时候会排成一队，轮询间隔越短越明显。表上还建了一个部分索引，只索引排队中和执行中的行，按租约到期时间和更新时间排，这样这条语句不会去扫全部历史任务。领到之后在同一个事务里对每一行做真正的占有。

**要点**：排队中或租约已过期、按空闲槽位数取、SKIP LOCKED 避免实例间排队、部分索引避免全表扫、领取与占有同事务

**可能的追问**：
- 领了却跑不起来怎么办？——提交给线程池被拒就立刻交还队列，不会出现领了没人跑
- 这条语句本身会不会变成瓶颈？
- 创建接口还有一条本机快速路径吗？——有，但失败时不判失败，任务留在库里等轮询

**另见**：Q66（行锁语义）

### Q3 心跳租约是什么，为什么不在领取时把租约一次给足整个任务时长？

**答**：租约只回答一件事——我最近还活着吗，它跟任务实际要跑多久没有关系。一次性给满整个任务时长，也就是原来那 330 秒，意味着进程崩溃后要等 330 秒才可能被接管；给得太短又会在正常执行时被误接管。短租约加续租把这两件事解耦了。默认租约 30 秒、心跳 10 秒续一次，配置校验里强制租约至少是心跳的两倍，也就是允许丢两次心跳，所以失联后最多 30 秒就能被别人接管。代价是每个在跑的任务每 10 秒多一次很轻的数据库更新。续租语句的条件和写保护完全一样，而且要求租约尚未过期——已经过期的租约不允许自己续回来，否则会和已经接管的新执行者同时认为自己持有租约。

**要点**：租约只表示活性与任务时长解耦、默认 30 秒 / 心跳 10 秒、强制租约至少两倍心跳、过期租约不许自己续回、代价是每 10 秒一次轻写

**可能的追问**：
- 续租失败了怎么办？——立刻本地取消，取消信号一路传到底层 HTTP，把在途的模型调用也断掉
- 续租的时候数据库抛异常也自杀吗？——不，只记日志，数据库抖一下让所有长任务自尽代价太大，后面有 fencing 兜底
- 租约调短是不是就一定更好？

**另见**：Q35（参数怎么定）

### Q4 一个实例被杀之后，任务多久能恢复？

**答**：结论是大约一个租约周期。失联接管的时间约等于租约剩余加一个轮询间隔，生产默认租约 30 秒、轮询 5 秒，最坏大概 35 秒，这个是推算不是实测。实测那组数字是把参数调小之后跑的：租约 6 秒、心跳 2 秒、轮询 1 秒，基于模拟上游，三个杀进程的场景各重复 20 次（基线、新增实例、毒任务三个场景各跑一次）。结果是 kill -9 的恢复时间 P50 5.13 秒、P95 和最大都是 6.12 秒，进程暂停场景是 5.12 / 6.12 / 6.12 秒。恢复时间的定义是从脚本记下的注入时刻，到新持有者写下第一条运行开始事件之间的时间差，两个时刻取的是同一台机器的时钟。重复 20 次之后能看到恢复时间集中在 5.0 到 5.1 秒和 6.1 秒两档，正好差一个轮询间隔。

**要点**：约等于租约剩余加一个轮询间隔、生产默认最坏约 35 秒是推算、实测用租约 6 秒 / 心跳 2 秒 / 轮询 1 秒、kill -9 的 P50 5.13 秒 P95 6.12 秒、重复 20 次、分布分两档差一个轮询间隔

**可能的追问**：
- 为什么报 P50 和 P95 不报平均值？——单次是一个样本，分布的两档结构比平均值更能解释机制
- 发版的时候也要等这么久吗？
- 为什么不直接用生产默认参数跑？——每次重复都要等一个租约周期，20 次重复乘六个场景时间太长

**另见**：Q35、Q63（实验参数）

### Q5 心跳线程自己卡住，或者进程活着但执行线程卡死了，你这套机制能发现吗？

**答**：发现不了，这是我知道的一个真实缺口。租约只能发现进程死了或者被暂停：心跳是一个独立的定时线程，如果执行线程死锁、或者卡在某个不带超时的调用上，心跳照常续租，任务就不会被接管，只能等任务自己的总时长上限兜底，默认 300 秒。而且反过来，如果是心跳线程卡住、执行线程还在跑，那租约会过期、任务被别人接管，这时候靠的是 epoch 写保护——旧执行者后面什么都写不进去，所以不会写坏，只是白跑一段。这个缺口不是我推演出来的，是实验自己撞到的：20 次重复里有一次，某个执行者在注入故障之前、9 秒内发出 14 次上游请求之后完全静止，驱动等了 120 秒超时。临时库已经删了、也没有线程转储，原因我没查出来，也没法事后确认它当时是否还在续租。

**要点**：租约只发现进程死或被暂停、执行线程卡住靠任务总时长 300 秒兜底、心跳卡住则靠 epoch 写保护不写坏、20 次重复里撞到过一次、原因未查明

**可能的追问**：
- 那要怎么补？——需要进度心跳，比如把"最近一次工具结束事件的时间"也纳入活性判定，这个我没做
- 任务总时长兜底之后任务是什么状态？
- 为什么不干脆缩短租约？——缩租约管不住这种情况，心跳照常续

### Q6 各个实例的时钟不同步，会不会把别人正常的任务判成过期？

**答**：不会，因为所有租约时间都取数据库时钟，各实例本机的时钟完全不参与判定。领取和接管的时候，租约到期时间设成"数据库当前时间加 30 秒"；判断一行是不是过期，也是在数据库里拿当前时间比。这样全集群只有一个时间基准。如果用本机时钟，一个快了一分钟的实例会把别人正在健康执行的任务全部当成过期去抢，这是多实例部署里很典型的一类事故。另外实验里测恢复时间用的是同一台机器的墙钟，注入时刻和新执行者写第一条事件的时刻取自同一个时钟，所以那组数字本身也不涉及跨机时钟偏差。

**要点**：租约时间一律取数据库时钟、本机时钟不参与判定、全集群一个时间基准、避免快钟实例抢别人的健康任务、实验测时用同一台机器墙钟

**可能的追问**：
- 数据库自己的时间跳了怎么办？
- 那这样是不是每次判活性都要访问数据库？——是，但本来写保护也在数据库的短事务里做
- 时钟不参与判定，那心跳周期是本机定时器算的吗？

### Q7 有了租约为什么还要 epoch 写保护，租约不是已经保证同一时刻只有一个执行者了吗？

**答**：因为"停"不是瞬间的。续租失败之后我们会主动停，但一个正在等模型响应的线程、一个被暂停之后又被唤醒的进程，都可能在新执行者已经接管之后，还带着旧上下文往库里写事件、写状态甚至写产物。光靠锁和租约解决不了，必须有 fencing token。做法是任务行上的 epoch 就是这个 token，每次领取严格加一，同时发一个一次性的租约令牌。执行者手里握着任务 ID、epoch 和令牌，每一次写入都在同一个短事务里先锁行，再核对这三项加上"状态仍是执行中、租约未过期"，四条同时成立才写，不成立就什么都不做、返回一个 false 而不是抛异常。所以旧执行者接管之后能做的唯一一件事，是什么都做不了——它写不进事件，也写不成失败。

**要点**：停不是瞬间的、进程暂停后醒来会双重执行、epoch 每次领取加一是 fencing token、写入点核对四条件、失败返回 false 不抛异常、旧执行者连"写成失败"都做不到

**可能的追问**：
- 哪些写入受这个保护？——追加事件、子任务检查点、写终态与产物、交还队列
- 除了写入点，还有别的地方拦吗？——每次模型调用开始前会再查一次自己是不是当前持有者，免得旧执行者继续烧上游配额
- 取消也走这条吗？——取消时 epoch 也加一，所以跨实例取消不需要额外的通知通道

**另见**：Q29（为什么不用分布式锁）、Q72（和秒杀的对照）

### Q8 断点续跑的上下文是怎么恢复的，为什么不直接把 Agent 的内存状态存成快照？

**答**：因为快照是一份和代码强耦合的私有结构，改一次提示词或者工具签名就要考虑版本兼容，而且它和事件流是两份状态，可能不一致。这里已经有一条为了给前端做断线续传而持久化的事件表，天然按序号有序、写入和状态变更在同一事务里，所以我用事件重建上下文。重建的过程是：分页把这个任务的事件读出来，从最后一次用户补充条件之后开始算；首条用户消息不是重新拼的，是第一次调用时就把原文随开始事件存下来直接取出；工具调用按开始和结束两个事件成对还原成 tool_call 加工具结果；没有配对完成的那一步直接丢弃，让模型重新决定。另外已读证据、检索计数、候选文档、子任务结果和预算用量也一并恢复。

**要点**：快照与代码强耦合且是第二份状态、事件表本来就有且按序号有序、首条消息存原文、工具开始与结束成对还原、未配对的那一步丢弃重做

**可能的追问**：
- 如果任务是在"已经想明白、正在写产物"的时候崩的呢？——事件里已有结论事件的话，接管方不再调用模型，直接拿结论生成产物
- 接管之后没有登录上下文，检索怎么按权限过滤？——按任务行上的所有者用户 ID 重建身份，每次领取还会重新校验一次知识库读权限
- 重建出来的请求和第一次是逐字节相同的吗？

**另见**：Q30（为什么不用工作流引擎）

### Q9 续跑会不会重复扣预算、重复写产物？

**答**：预算不会重复扣，产物不会有第二份。预算是从库里持久化的用量恢复的，所以接管方不会把一个任务的额度重新花一遍；不过要说清楚，恢复是"按已落库的用量近似"，不是精确——模型调用的开始事件、HTTP 调用、结束事件是三次独立提交，进程在 HTTP 途中被杀，那一次的用量就丢了。产物这边是确定的：写产物走的是带 fencing 的结束写入，只有当前持有者能写，而且产物和终态在同一个事务里提交，写完就是终态。实验的不变量逐任务确认过这一点——恰好一个终态事件、至多一个产物、事件序号从 1 开始连续无洞、已完成的同名同参数工具调用没有被执行第二次。W7 的 3600 次运行里这些不变量也是 0 失败。

**要点**：预算从库里的用量恢复、恢复是按已落库用量近似不精确、产物写入带 fencing 且与终态同事务、不变量逐任务核对、3600 次运行 0 失败

**可能的追问**：
- 那到底哪一步会被重做？
- 证据会不会重复写？——证据按内容算出的稳定 ID 幂等保存，重复保存不会产生第二条
- 已完成的子任务会不会重跑？——单 Agent 模式有进程级实验，多 Agent 模式只由单测和集成测试覆盖

**另见**：Q31（至少一次的安全性）、Q62（不变量）

### Q10 简历说"通过 kill -9、进程暂停等故障注入验证"，具体怎么验的，判定标准是什么？

**答**：实验脚本先建一个随机隔离的运行库和一个模拟上游，按场景启动若干个独立的 JVM 执行器进程——是进程不是线程，它们共享那一个数据库，跑的是同一套执行服务。脚本提交几个脚本化任务，等到数据库里确实已有两次工具结束事件才注入故障，而不是等进程启动，然后等所有任务进终态，最后直接查数据库判定。六个场景：无故障基线、kill -9、运行中加一个新实例、SIGTERM 优雅停机、SIGSTOP 暂停超过租约再放行、以及每个接手者都被杀的毒任务。三种杀法对应三种失败语义：kill -9 是进程瞬间消失要等租约过期，SIGTERM 是有序退出能主动交还，SIGSTOP 是进程还在、连接还在、只是被冻住，解冻后它会以为自己还持有任务。判定不看日志，看数据库里的五条不变量。

**要点**：独立 JVM 共享一个库、等到有两次工具结束事件才注入、六个场景三种杀法、判定看数据库不变量不看日志、每次重复都用新库新模拟上游

**可能的追问**：
- 为什么用"同名同参数的工具调用只出现一次"当不变量？——续跑语义是至少一次，在途那次必然重做，不能容忍的是已完成的步骤被重做
- 重复的模型调用数是怎么数出来的？——拿无故障基线那一档的干净调用数作差
- "旧执行者的迟到写入被拒"这条实验能直接证明吗？——不能，实验只有间接证据，直接断言是在连真实 PostgreSQL 的集成测试里做的

**另见**：Q62、Q63（实验怎么搭）

### Q11 发版重启比宕机常见得多，这种情况你是等租约过期吗？如果一个任务反复把接手者搞崩呢？

**答**：发版走的是另一条路，不等租约过期。收到停机信号后先停止领取，然后给在途任务打一个"请交还"的标记，这个标记不打断正在进行的模型调用和已经决定要执行的工具——粗暴打断等于制造一次需要重做的在途调用。主 Agent 在下一次模型调用开始之前检查这个标记，命中就停下来，服务把任务写回排队中、清空租约令牌，别的实例下一轮轮询就能领走。宽限期默认 20 秒，到点还没走到步边界的强制交还并取消本地执行，顺序是先交还再取消。实测 SIGTERM 的恢复时间 P50 1.08 秒，远低于失联接管的约 5 秒。反复搞崩接手者的那种任务，靠任务行上的接管次数，上限默认 3 次，第 4 次想接管时直接判失败、原因是执行者失联，并写一条事件说明；关键是只有失联被接管才计数，停机主动交还不计，否则一次滚动发版三个实例就把配额耗光了。

**要点**：停机先停领取再打交还标记、不打断在途调用、在下一次模型调用前的步边界交还、宽限期 20 秒先交还再取消、SIGTERM 恢复 P50 1.08 秒、接管上限 3 次交还不计数

**可能的追问**：
- SIGTERM 下模型调用一次都不会重复吗？——理论上应该是 0，实际还是会重复 1 次
- 毒任务判成失败之后用户看到什么？——明确的失败原因加完整的事件历史，相当于一个不进死信队列的死信
- 宽限期设多长合适？——只有一个默认值，没有经过不同负载检验

**另见**：Q70（优雅停机的完整流程）

### Q12 加机器有没有用？数据库当队列会不会自己先变成瓶颈？

**答**：加机器有用，接近线性，而且瓶颈是槽位和轮询间隔，不是数据库。这是 W7 的容量基准，全部基于模拟上游，每次模型调用固定 0.7 到 0.9 秒。做法是每一格用新的隔离运行库和新的模拟上游，先空转 30 秒量空闲轮询，再一次性提交 300 个积压任务，参数用生产默认：每实例 2 个槽位、租约 30 秒、心跳 10 秒、轮询 5 秒；实例数 1、2、3，轮询 5 秒每格重复 3 次，另跑一组轮询 1 秒作对照，合计 3600 个任务。排空吞吐是 12.2、24.0、35.8 条每分钟，加速比 1.00、1.98、2.95；轮询降到 1 秒是 13.3、26.5、39.7，加速比 2.98。各格吞吐是槽位上限的 85% 到 95%，差的那部分就是轮询间隔——槽位空出来最多要等一个间隔才被填上。

**要点**：模拟上游 300 个积压任务 × 1/2/3 实例、每实例 2 槽位共 3600 任务、吞吐 12.2/24.0/35.8 条每分钟、加速比 1.00/1.98/2.95、槽位上限的 85%—95%、瓶颈是槽位与轮询间隔

**可能的追问**：
- 凭什么说数据库不是瓶颈？——领取语句应用侧计时均值 4.1 到 5.6 毫秒、最大 85 毫秒，一轮排空里每实例只发 52 到 231 次，占排空时长不到 0.12%
- 积压的代价体现在哪？——等待时延，3 实例轮询 5 秒时排队等待 P50 242 秒、P95 470 秒，要压等待只能加实例或加槽位，降轮询帮助很小
- 再往上加实例还线性吗？——只测到 3 实例乘 2 槽位，没找到数据库的拐点，而且是同一台机器上的独立 JVM，不含网络延迟

**另见**：Q28（队列选型的代价）、Q73（满了为什么不拒绝）

### Q13 简历说"通过调用台账发现"，这个台账是什么，不做会怎样？

**答**：台账是每次模型调用一条记录的账本，写在模型调用包装器里。发请求之前记一条开始，带调用 ID、模型名、角色、任务 ID 和估算输入；流结束之后补齐供应商返回的输入 token、输出 token、命中 token、缓存写入量、缓存类型、整次耗时和首包耗时。有两条设计是刻意的：一是失败、超时、取消的调用也要落账，记录写在流的终止回调里，四种结局都补齐并标上状态，否则重试多的任务成本会被系统性低估；二是缺失的值不写、不用 0 冒充，供应商没返回就记成缺失，这样新旧批次能放在一张表里比。不做台账的话，成本只能看月底账单，账单是聚合的，既分不清哪种角色的调用贵，也看不出本来应该命中却没命中，等发现贵的时候现场已经没了。

**要点**：每次调用一条记录、记命中 token 与缓存写入量、失败超时取消也落账、缺失不用 0 冒充、账单是聚合的看不出该命中却没命中

**可能的追问**：
- 台账算出来的结果是什么？——单 Agent 模式 3486 次调用、输入 3803 万 token、命中 197 万、命中率 5.2%；多 Agent 模式输入 4427 万、命中 8448、命中率 0.02%
- 台账存在哪？——随任务的预算快照一起落库
- 计费输入是账单数字吗？——不是，是按文档折扣折算的输入 token 当量，没核对过发票

### Q14 提示缓存到底是怎么工作的？

**答**：关键是前缀匹配，不是内容匹配。供应商缓存的是请求的一段开头，两次请求只有在从第一个 token 开始逐字节相同的那一段上才可能复用，一旦出现第一处差异，从差异点往后全部要重新计算。所以缓存的单位是前缀，不是消息，也不是相似度。由此有一条很反直觉的推论：改动越靠前损失越大，在系统提示末尾加一行字，和把整段历史全部重写，对缓存的破坏是一样的，都是命中率归零。序列化顺序通常是系统提示、工具定义、历史消息、本轮新消息，工具定义虽然在协议里是单独字段，但对缓存而言和系统提示同属最前面那一段，工具换个顺序也会让整个请求失配。另外命中一般按固定块大小对齐，我实测观察到是 128 token 对齐，所以命中长度总是略小于真正相同的前缀长度。

**要点**：前缀匹配而非内容匹配、从第一个 token 起逐字节相同、第一处差异之后全部重算、工具定义等同于最前面那一段、实测按 128 token 对齐

**可能的追问**：
- 隐式和显式有什么区别？——隐式免费但文档明写不保证命中，显式要打断点、第一次按写入价计费
- 折扣是多少？——按供应商文档，隐式命中按输入价 20%、显式命中 10%、显式写入 125%
- 有效期多久？——显式缓存 5 分钟且命中即续期，Agent 相邻两次调用之间只隔一次工具执行，远小于 5 分钟

**另见**：Q34（显式对隐式）

### Q15 简历说"每轮改写首条系统消息破坏了缓存前缀"，这个根因你是怎么定位的？

**答**：不是读代码猜的，是用协议级探针做出来的。做法是用协议测试夹具捕获 SDK 实际发出的请求字节，然后每次只改一处，重放到真实端点，一共 34 次调用，看命中数怎么变。结果是：逐字节相同 4 次全中；系统消息末尾加一行、工具不变、前面 1944 个 token 相同，命中 0；工具换序或者把提醒移出系统消息，命中 0；只改提醒里的数字再追加历史，也就是旧布局真实的下一步，命中 0。根因于是确定了两个。一是服务端每次调用都要告诉模型一些随轮数变化的信息——还剩几次探索调用、当前允许引用的证据 ID 集合、阅读覆盖情况、检索是否已被熔断——原实现把这些直接拼在系统提示后面，而系统提示是第一条消息，改它等于从第 0 个 token 就不一样。二是上下文超限时从最早往后滑动裁剪，丢掉最早那一轮意味着前缀的开头变了，缓存永远追不上。

**要点**：协议夹具抓请求字节、每次只改一处重放真实端点共 34 次、系统消息末尾加一行即命中归零、根因一是易变提醒拼进首条系统消息、根因二是滑动裁剪改动前缀开头

**可能的追问**：
- 探针还发现了什么？——SDK 生成的消息级缓存标记在这个供应商上是空操作，0 写入 0 命中，因为供应商只认内容块里的标记
- 还有第三个问题吗？——首条用户消息用了不保证键序的哈希表序列化，同进程内没事，但续跑和跨实例接管时拿不到相同的字节
- 为什么非要重放到真实端点？——协议测试只能证明请求字节稳定，证明不了供应商真的按折扣计费

### Q16 "分离静态前缀与动态提醒"具体怎么做的？提醒不放系统消息还能放哪？

**答**：目标只有一句话——让一次任务里的每一次请求，前缀都是上一次请求的严格扩展。系统提示只保留静态内容，也就是角色、规则、输出契约，不再包含任何随轮变化的东西，工具定义顺序固定。易变提醒改成每次请求临时追加在消息列表最末尾的一条用户消息，而且不写回 Agent 的记忆，所以下一轮请求里只有一条新提醒，上一轮的不会留在历史里。为什么不放第二条系统消息？兼容端点对多条 system 的处理不可靠。为什么不塞进最后一条工具结果里？那样确实也能保持前缀，但等于篡改工具的真实输出，Agent 读到的证据就不再是服务端实际返回的东西。追加在末尾是唯一不动历史、又能稳定传达状态的位置。另外历史只追加不改写，首条用户消息改成按键排序的序列化。

**要点**：系统提示只留静态内容、工具定义顺序固定、提醒改成末尾临时用户消息、不写回记忆所以历史里只有一条、历史只追加、首条消息按键排序序列化

**可能的追问**：
- 上下文超限怎么办，不裁剪会顶到模型上限吧？——改成阈值压缩，估算输入不超过 28000 token 就一个字不动，越线才一次性压到上限的 60%，水位只增不减
- 压缩的时候前缀不还是变了吗？——只在越线那一次丢一次缓存，两次越线之间前缀完全不变，比滑动窗口每轮都改要好
- 最终产物生成那次调用也这么处理吗？——不加提醒也不打断点，它的输入是按证据裁剪过的，和研究循环不共享前缀

**另见**：Q32、Q52（阈值压缩）

### Q17 显式缓存断点打在哪两个位置，为什么不用 SDK 默认的位置？

**答**：打在两处：第一条系统消息（含工具定义），以及提醒之前的最后一条历史消息，也就是倒数第二条。不用 SDK 默认位置是因为它标记的是最后一条消息，而我们的最后一条恰好是每次都变的提醒——标在那里等于每次都要求供应商按 125% 的写入价重写整段历史，是最坏的选择。标在倒数第二条，缓存的边界正好落在这次之前的全部稳定内容上。系统消息那个断点作用不一样，它让不同任务的第一次调用也能共享静态前缀，因为系统提示加工具定义在所有任务里是同一串字节，否则每个新任务的首次调用都要从零算。协议允许每个请求最多 4 个断点，这里只用了 2 个。还有一层是线路格式适配：SDK 把缓存标记写成消息级字段会被静默忽略，所以在 HTTP 传输层套了一个装饰器，发送前把它改写进内容块。

**要点**：断点打在首条系统消息与倒数第二条历史、SDK 默认标最后一条正好是每次都变的提醒、系统消息断点让跨任务共享静态前缀、4 个断点只用 2 个、传输层装饰器把消息级标记改写进内容块

**可能的追问**：
- 为什么选显式而不是只吃隐式？——隐式文档明写不保证，探针实测前缀完全稳定时也只有 4 次命中 1 次，没法写进成本模型
- 写入贵 25% 划算吗？——之后每次省到 10%，一个任务十次调用，第二次就回本
- 缓存写入量怎么记账？——SDK 不解析这个字段，我从流式响应的 usage 里读出来交给台账，否则写入成本整个漏记、算出来的账是虚低的

**另见**：Q34（为什么要显式）

### Q18 命中率从不足 10% 到 80%，这么大的提升是怎么做到的？

**答**：说实话不是优化出了什么神迹，是基线本来就是坏的。改之前命中率单 Agent 模式 9.8%、多 Agent 模式 0.2%，等于前缀根本没有被复用过。更能说明问题的是台账里那个 5.2% 的基线：它不是有时候命中，而是每次都恰好命中 1280 个 token，1280 正好等于那个模式下工具定义 714 加静态提示 632 加模板 17 按 128 取整，也就是供应商在共享前缀上有一段没有文档的行为，只在这一段生效，后面全不算；另一种模式对应的长度在三千多次调用里一次都没出现过。所以正确的说法是，把一个被破坏的前缀修好，命中率回到这类多轮 Agent 该有的水平——78.4% 和 80.0%。按前缀匹配的机制，没命中的那部分就是这一轮新追加的内容，它本来就没有被上一次请求处理过。

**要点**：基线是坏的不是优化出来的、改前 9.8% 与 0.2%、5.2% 那档是每次恰好命中 1280 token 的未公开行为、改后 78.4% 与 80.0%、未命中的是本轮新追加的内容

**可能的追问**：
- 为什么剩下的 20% 命中不了？
- 那个 1280 的行为能当基线吗？——不能，不可解释也不可依赖，不能据此以为缓存是生效的
- 这两组数字的条件是什么？——真实上游，同一批 40 题，单 Agent 与多 Agent 两种模式，全部角色用同一个模型，改动前后各跑一次

### Q19 "单任务输入成本下降约 70%"是怎么算出来的，是账单吗？

**答**：不是账单，是按供应商文档的折扣把输入 token 折算成计费当量算出来的，我没有核对过发票，这一点我会主动说。折算的权重就是文档里的三档：隐式命中按输入价的 20% 计，显式命中按 10% 计，显式写入按 125% 计。折扣率在报告脚本里是参数、不写死，所以口径可以复算。W1 那次同负载对照的结果是单任务计费输入分别下降 69% 和 75%，简历上写的约 70% 取的是这两个里偏保守的那个口径。后来 W6 那次在 400 道没见过的题上又复现了一遍：单任务计费输入从 77113 降到 21436，也就是降了 72%，而且四个块每块都一致。

**要点**：不是账单是按文档折扣折算的输入 token 当量、隐式命中 20% / 显式命中 10% / 显式写入 125%、折扣率是脚本参数可复算、W1 是 −69% 与 −75%、W6 复现为 77113→21436 也就是 −72%

**可能的追问**：
- 延迟有没有变？——首包耗时只有新台账才有，做不了前后对比；单次调用耗时没有可靠改善，每个任务的首次调用反而慢约 0.35 秒，怀疑跟写缓存有关，没验证
- 为什么不直接拿账单比？——实验是本地跑的，账单是聚合的，分不到任务和角色
- 这个降幅在真实业务负载上还成立吗？

**另见**：Q46（评测口径）

### Q20 成本降了，答案质量有没有跟着变差？

**答**：在这个样本量下看不出显著下降，但我不能说没有下降。缓存本身是传输层优化，理论上不该改变模型看到的内容，但提醒的位置确实从系统消息末尾挪到了整段消息的最末尾，这是一个真实的提示改动，所以要单独验。最终的质量护栏是 400 道模型没见过的题、其中可答 196 道，多 Agent 模式，前后分 4 块交错运行。结果是配对答案 F1 −0.034，95% 自助法区间 [−0.080, +0.011]，EM 从 0.352 降到 0.291。区间含 0，所以只能说未见显著下降，同时必须把区间下界一起报出来——不能排除 0.08 以内的下降。这个判定规则是事先写死的，不是等结果出来再挑口径。

**要点**：配对 F1 −0.034、95% 区间 [−0.080, +0.011] 含 0、EM 0.352→0.291、未见显著下降但不能排除 0.08 以内的下降、判定规则事先写死

**可能的追问**：
- 为什么用配对差加 bootstrap 而不是比两边平均 F1？——题目之间的难度差远大于两臂差，不配对方差全被难度占掉；单题 F1 夹在 0 和 1 之间、两端堆积，正态近似靠不住
- 你怎么知道 −0.034 不是运行间噪声？——我专门跑了噪声基线，同一批 80 题用同一个后臂重跑一次，F1 变化 +0.059、区间 [−0.032, +0.158]，跟被测效应同量级，所以任何基于单次运行的质量结论都不成立
- 损失落在哪些题上？——15 题从作答改成了"资料中没有"，贡献 −0.056，反向有 11 题、+0.025，拒答总数 47 到 47 没变；一个可能的解释是末尾提醒里的剩余调用次数让模型更早收手，但这只在少数题上有迹象，未验证也未修

**另见**：Q46、Q60、Q61（配对差与噪声基线）

### Q21 如果换一家模型供应商，你这套缓存机制还成立吗？

**答**：分两部分看。稳定前缀、提醒后置、历史只追加、阈值压缩这四条是与供应商无关的，任何做前缀匹配缓存的供应商都吃这一套，换家不用改。真正绑定的是显式断点那一层：它依赖这一家供应商的内容块语法，以及它在流式响应里返回的缓存用量字段。所以我做了一个开关，关掉之后不再打标记、退回隐式，前面那四条照常生效；换供应商的动作就是先关开关、再写新的传输适配器。另外还有一个现实问题，我的台账要靠供应商返回的命中 token 和缓存写入量来做成本核算，如果新供应商不返回这些字段，我就只能记成缺失而不是填 0，命中率这个指标在那家上会直接失效。

**要点**：稳定前缀与阈值压缩与供应商无关、显式断点绑定内容块语法与用量字段、有开关可关掉退回隐式、换家的动作是先关开关再写传输适配器、对方不返回用量字段则命中率指标失效

**可能的追问**：
- 隐式缓存在别家能指望吗？——这家实测前缀完全稳定时也只有 4 次命中 1 次，别家没测过
- 传输适配器为什么不直接改 SDK？——不改 SDK，在 HTTP 传输层套一个装饰器，换家换装饰器就行
- 多模型混合路由的时候缓存怎么办？

### Q22 "分层超时"是什么意思，为什么不是每层各配一个固定超时？

**答**：起因是一次批量跑，1200 个任务里 72 个超时，耗时清一色 30.01 秒，全部卡在检索工具上。当时 HTTP 调用、检索通道、研究工具三层的超时都配成同一个 30 秒，内层永远不会先于外层结束，中间没有任何一层有机会说"我还剩一点时间，换个办法补救"。我的做法是进入工具时一次性算出这次调用的绝对截止时刻，放在一个显式传递、不随线程继承的请求作用域里，之后每一层都从这个截止时刻往回推自己能用多久，而且每一层都比上一层再收紧一点：工具层取"探索期剩余"和"工具超时 30 秒减 2 秒"的较小值，单次 HTTP 调用取 12 秒和剩余时间的较小值，数据库查询取剩余时间和 5 秒的较小值、至少 1 秒。所以一次不回包最多损失 12 秒，剩下的余量正好够做一次重试。固定值只能保证最坏情况下每层不超过多少，保证不了内层一定先于外层结束——链路上多一跳、或者上一层已经花掉一半时间，它就退化成事故里那样三层同时到点。

**要点**：事故是 1200 任务里 72 个清一色 30.01 秒、原来三层同为 30 秒、改成传绝对截止时刻、每层从截止时刻往回推并再收紧、HTTP 单次最多 12 秒留出重试余量、固定超时保证不了内层先结束

**可能的追问**：
- 这个截止时刻为什么不用线程本地变量传？——它要跨线程池边界，隐式继承会漏掉也会被别的请求误用，所以设计成显式携带、从不继承
- 减掉的那 2 秒干什么用？——留给工具层自己收尾，记事件、把失败转成工具结果字符串
- 取消能传到底层吗？——能，作用域上挂了一组取消动作，线程中断、HTTP 请求取消、数据库语句取消都注册在上面

### Q23 重试会不会把上游打得更惨？你怎么控制放大？

**答**：控制在四个地方。一是重试预算刻意留得很小，embedding 只重试一次、总共两次尝试，而且剩余时间不足 1.5 秒时直接不重试，否则会出现重试刚发出去就撞上截止时间，既浪费一次上游调用又救不回来。二是只对该重的错误重试：网络错误、被限流、上游 5xx 可以重，业务错误、响应格式非法、所有候选都被熔断跳过不重；取消不算失败，既不重试也不计熔断。三是退避用指数退避加 equal jitter，基数 300 毫秒、上限 2000 毫秒，实际等待是本次上限的一半加另一半里随机取，第一次重试落在 150 到 300 毫秒之间——原来是固定等 300 毫秒，一次抖动会同时打掉很多并发调用，它们会在同一时刻一起重试，对刚要恢复的上游形成第二波冲击。四是模型路由那层有熔断，连续失败 2 次就打开 30 秒，之后转半开、同一时刻只放一个探测进去。

**要点**：只重试一次且剩余不足 1.5 秒不重试、按错误类型区分可重试与不可重试、取消不计失败、指数退避加 equal jitter 基数 300 毫秒上限 2 秒、熔断连续失败 2 次开 30 秒半开单探测

**可能的追问**：
- 为什么不用 full jitter？——纯随机可能抽出接近 0 的等待，重试几乎立刻发出，起不到给上游喘口气的作用
- 带截止时间的调用会不会换个模型再试？——不会，embedding 向量不可跨模型比较，用另一个模型的向量去查原模型建的索引结果是错的，比失败更糟；但失败照样计入熔断
- 全局层面有没有压住放大的机制？——没有，重试预算是固定的一次，没有做重试令牌桶、对冲请求、舱壁隔离，故障率高时 50% 那一档的放大最明显

**另见**：Q47（失败与无命中分离）

### Q24 "区分调用失败与检索无命中"是什么意思，为什么重要？57.5% 到 98.5% 这组数字怎么测出来的？

**答**：检索返回零条可能是两件完全不同的事：库里确实没有相关内容，这是有效信息；或者 embedding 没回包、数据库超时，这是执行故障。原来的检索链路会把异常吞成空结果，对即时问答是合理降级，但研究任务是多轮自主决策的，模型看到空结果就以为库里没资料，换个说法再搜一次、还是空，最后交出一份状态成功、内容空洞的报告——失败被伪装成了事实上不存在。分离是在三处同时做的：研究路径上通道和后置处理不再吞异常；工具层把失败如实转述给模型，带上阶段、错误码、是否可重试，并明说这是执行失败不是不存在资料的证据；落库时只要有执行问题就不给完成状态，既没有证据又有执行问题就直接判失败、不生成产物。数字这边是拿自己写的模拟上游跑的，不是真实供应商——真实供应商的故障率不可控、不能复现还要花钱。设计是 50 个脚本化任务、4 个随机种子各跑一整套，所以每一格是 200 个任务；注入的故障只有一种，embedding 请求被挂住 90 秒不回包，比例 0、10、30、50%；对照的是治理前后两个真实提交各自编译出来的版本。30% 这一档成功率从 57.5% 到 98.5%，Wilson 95% 区间分别是 [50.6, 64.1] 和 [95.7, 99.5]，两版不重叠。

**要点**：空结果有两种含义必须分开、通道不吞异常加工具层如实转述加落库不给完成状态、模拟上游 50 任务 × 4 种子每格 200 个、只注入 embedding 挂住 90 秒、30% 档 57.5%→98.5%、Wilson 区间不重叠

**可能的追问**：
- 成功的判定标准是什么？——状态完成、有产物、并且读到了每个被要求文档的证据；"错误完成"指状态完成但缺这些证据，1600 个任务里是 0，每版每档的 95% 上限是 1.9%
- 为什么用 Wilson 区间？——成功率是二项比例而且经常贴着 100%，正态近似在两端会给出超出 [0,1] 的区间
- 为什么要跑 4 个种子？——最早单种子的结果是 30% 档治理后 100%，换种子再跑就变成 98.5%，单种子的漂亮数字是不稳的
- 代价是什么？——用负载换成功率，单种子那轮 30% 档治理后 P50 从 1.1 秒升到 12.9 秒、embedding 请求数从 75 涨到 156；50% 那一档两次尝试都撞上无响应的概率约 25%，重试救不回来，成功率 86.0%

**另见**：Q47（通用视角）、Q59（模拟上游能不能信）

### Q25 简历最后一句说"验证任务不丢失、产物不重复"，这两件事分别靠什么保证？
**答**：是两套机制，我分开说。"不丢"靠的是任务状态在数据库里、活性由短租约加心跳表示：进程没了，那一行还在，租约到期之后任何一个有空槽的实例轮询时都能把它领走，领取条件就是"排队中，或者执行中但租约已过期"。所以"不丢"的前提是"执行状态从来不只活在某个进程的内存里"。"不重复出产物"靠的是 fencing：每次领取 epoch 加一、发一个新的租约令牌，执行者每一次写入都在短事务里核对状态、epoch、令牌、租约未过期四条，旧执行者醒过来一个字都写不进去；而产物和终态是在同一个事务里提交的，所以同一个任务只可能有一份产物。两者的验证方式也不一样：不丢是用恢复时间来量的，模拟上游、租约 6 秒、重复 20 次，kill -9 的 P50 是 5.13 秒；不重复是用数据库里的不变量来判的——恰好一条终态事件、至多一份产物、事件序号连续、已完成的同名同参工具调用没被执行第二次，故障实验和 3600 个任务的容量实验里都是 0 失败。
**要点**：不丢靠状态在库里加租约到期可接管、不重复靠 epoch 与租约令牌的写入点校验、产物与终态同事务、不丢用恢复时间量、不重复用数据库不变量判
**可能的追问**：
- 那"不白跑"呢？——靠事件重建上下文续跑，已完成的步骤不重做，只有在途那一步重来
- 这两件事有没有可能同时失效？
- 为什么不变量要查"事件序号连续"？——它加上"终态恰好一条""已完成步骤不重做"合起来才排除了两个执行者同时写一个任务

### Q26 简历说"实现分层超时"，如果哪一层的超时配错了，最先表现出什么？你怎么知道分层真的生效了？
**答**：配错最先表现出来的就是那次事故的形态——一批任务的耗时高度一致地卡在某个数值上。当时是 1200 个任务里 72 个超时，耗时清一色 30.01 秒，这个"清一色"本身就是信号：正常的超时分布不会这么齐，齐说明所有层都在同一个点到期、没有任何一层有机会先收手。所以分层有没有生效，第一眼就看失败任务的耗时分布是不是贴着一个固定值。更具体地说，如果内层配得比外层大，内层就永远不会先结束，外层一到点整条链一起废，中间那层攒下的部分结果也没人用；如果外层配得太小，就会出现"上层已经判超时、下层还在跑"，留下悬挂的请求占着连接和半开探测名额。我这边是靠传一个绝对截止时刻来保证顺序的：工具层比上层少 2 秒，单次 HTTP 最多 12 秒，数据库查询最多 5 秒，每一层都是从同一个终点往回推、再自己收紧一点，所以无论调用栈多深、前面花了多久，内层一定先于外层结束。
**要点**：配错的表现是失败耗时贴着一个固定值、内层大于外层则外层一到点全废、外层过小则留下悬挂请求、绝对截止时刻保证顺序与调用深度无关、每层再收紧一点
**可能的追问**：
- 那 2 秒的收尾时间不够用会怎样？——工具层来不及把失败转成工具结果字符串，模型看到的就是一次上层超时，退回"不知道发生了什么"
- 现在有没有监控能看到这个分布？——没有，只有调用台账里的耗时字段，没有面板也没有告警
- 取消和超时是同一套机制吗？——截止时刻到了，作用域先标超时再触发取消，走的是同一组注册进来的取消动作

**另见**：Q22（分层超时的做法）、Q59（模拟上游能不能信）

### Q27 加了重试和退避之后，任务反而变慢了、打上游的请求也更多了，这算不算改坏了？
**答**：不算改坏，但这是一笔要讲清楚的交易：用负载和时延换成功率。数字我会一起说——模拟上游、只注入 embedding 无响应这一种故障，单种子那一轮的 30% 档，治理后成功任务的 P50 从 1.1 秒升到 12.9 秒、P95 升到 37.3 秒，embedding 请求数随故障率从 75 涨到 156。但这两个数不能直接比：旧版在这一档把慢任务直接判成失败了，它的 P50 只统计了幸存者，而新版是把本来会失败的任务救回来、这些任务本来就慢。所以正确的读法是"多出来的时延属于原本会失败的那批任务"。代价的边界我也知道：重试预算是固定的一次，没有做重试令牌桶、对冲请求、舱壁隔离，故障率高的时候放大是真实存在的，50% 那一档最明显——全局层面目前没有任何机制压住这种放大，这是我知道的缺口。真要上线，我会先加一个重试预算的全局比例上限，宁可让一部分请求直接失败，也不让重试把上游打得更久。
**要点**：用负载与时延换成功率、单种子 30% 档 P50 从 1.1 升到 12.9 秒、请求数 75 涨到 156、旧版 P50 只统计幸存者不可直接比、没有全局重试预算是已知缺口
**可能的追问**：
- 那怎么判断这笔交易划算？——看"错误完成"这一类：1600 个任务里状态成功但没有证据的是 0，说明慢下来的同时没有拿正确性去换
- 50% 那一档为什么救不回来？——两次尝试都撞上无响应的概率约 25%，重试无能为力，成功率 86.0%
- 全局重试预算怎么做？——限制重试占总请求的比例，桶空了直接失败不重试

**另见**：Q23（重试怎么控放大）、Q47（失败与无命中分离）

### Q28 为什么用数据库当任务队列，而不另起一个消息队列？

**答**：因为任务状态本来就必须在 PostgreSQL 里，再加一个队列就出现两处事实。研究任务的状态机、预算用量、事件序列、产物都要持久化在库里，如果领取走消息队列，就要额外解决"消息已投递但数据库事务回滚""数据库写成功但消息没发出去"，通常又得上事务消息或本地消息表，绕一圈还是回到数据库。而且这里的量级是分钟级任务、每个实例只跑 2 个槽位，用不上消息队列的吞吐。所以直接把任务表当队列，领取和状态变更在同一个事务里，只有一处事实来源，Java 生态里这个做法有成熟先例。代价有三条：轮询有延迟，槽位空出来最多等一个轮询间隔才被填上；数据库要承担轮询的读写；而且这套只在这个量级成立。容量实验里也验证过瓶颈不是数据库——模拟上游、300 个积压任务 × 1/2/3 实例共 3600 个任务，领取语句应用侧均值 4.1 到 5.6 毫秒、最大 85 毫秒，占整个排空时长不到 0.12%，真正的瓶颈是槽位数和轮询间隔。如果任务变成毫秒级、每秒上万条，这个结论就反过来了，那时候该换消息队列。

**要点**：两处状态要对齐、事务消息或本地消息表绕回数据库、量级用不上 MQ 吞吐、领取与状态变更同事务、瓶颈实测在槽位不在库

**可能的追问**：
- 轮询间隔调小不就行了？实验里轮询从 5 秒降到 1 秒，吞吐只涨 9.5% 到 10.7%，代价是空闲轮询从 0.2 次/秒/实例升到 1.0 次/秒/实例，等待时延几乎没改善。
- 数据库当队列怎么避免多实例互相阻塞？
- 什么时候你会推翻这个选择？

**另见**：Q12（容量实测）、Q29、Q30

### Q29 既然要解决"同一时刻只有一个执行者"，为什么不用 Redis 分布式锁？

**答**：因为锁解决不了进程暂停。持锁者被 SIGSTOP 或者一次长 GC 暂停超过锁的过期时间，锁自动释放、新执行者拿到锁开始跑，旧执行者醒过来仍然认为自己持有锁，继续往库里写事件、写状态、甚至写产物。要挡住它，必须在被保护的那份资源那一侧做 fencing 检查，而这里被保护的资源就是任务表里的那一行。既然写保护最终要落在数据库上，把"锁"也放在数据库里就少一个组件，也少一处"锁和数据不在同一个事务里"的缝。具体做法是每次领取 epoch 加一、同时发一个一次性的租约令牌，执行者每次写入都在同一个短事务里先锁行、再核对四条——状态是执行中、epoch 是我领取时拿到的、租约令牌是我的、租约没过期，不满足就什么都不做、返回 false。代价是每次写入都多一次行锁和条件判断，而且旧执行者不是立刻被通知停下，只是写不进去。进程暂停这个场景我专门跑过：模拟上游、租约 6 秒，被暂停超过租约的实例醒来后续租被拒 6 次然后自行停止。

**要点**：锁挡不住进程暂停、fencing 必须在资源侧、资源就是库里那一行、epoch + 租约令牌 + 四条写保护、旧执行者写不进也写不成失败

**可能的追问**：
- 为什么执行者 ID 不能当写保护的凭证？
- 租约发现不了什么故障？
- 和秒杀项目的分布式锁具体差在哪？

### Q30 Temporal 这类工作流引擎功能上完全覆盖你的需求，为什么不用？

**答**：功能上确实覆盖，而且比我做的更强——确定性重放、定时器、补偿都有。不用有两个理由。一是它要引入一整套外部服务和编程模型，对一个预研原型太重；二是它的确定性重放要求业务代码写成确定性的 workflow，而 Agent 的执行本来就不确定——模型每轮决定调哪个工具是随机的，重放拿不到同一条路径，这部分收益直接打折。所以我借了它的思路但没借它的实现：续跑不存 Agent 快照，而是用已经为前端 SSE 回放持久化的事件表重建上下文。选事件表而不是快照，是因为快照是一份和代码强耦合的私有结构，改一次提示词或工具签名就要考虑版本兼容，而且它和事件流是两份状态、可能不一致；事件表天然按序号有序，写入和状态变更在同一个事务里。代价是我只做到"重建一段对话"，不是确定性重放整个工作流：定时器、补偿、子工作流这些我都没有，重试策略也是自己写死的一次。如果以后任务编排变复杂、要有分支和补偿，自己拼这些不如直接上引擎。

**要点**：外部服务与编程模型太重、Agent 执行本身不确定使重放收益打折、借事件历史思路、快照与代码强耦合且是第二份状态、只做到重建对话不是重放工作流

**可能的追问**：
- 事件表重建具体重建了哪些东西？
- 没有配对完成的那一步怎么处理？
- 什么情况下你会改用工作流引擎？

### Q31 接管续跑是"至少一次"语义，为什么不做成"恰好一次"？

**答**：因为在这条链路上做到恰好一次要付的代价远大于收益，而至少一次在这里本来就是安全的。重做的只可能是崩溃时在途的那一步，这一步必定是三类之一：检索，只读；阅读来源，也是只读，而且证据按内容算出的稳定 ID 幂等保存，重复保存不会产生第二条；或者一次模型调用，重复的代价就是一次调用费，不产生副作用。真正有副作用的写入只有产物和终态，它们在同一个事务里提交、并且受 fencing 写保护，同一个任务只有当前持有者能写、写完就是终态，所以只可能有一份。要做成恰好一次，得把每一次工具执行和模型调用都变成"先落决定、再执行、再落结果"的两阶段，等于给每步加一次事务往返，还得处理决定已落、执行未做的中间态——换来的只是省掉一次调用费。验证上，接管实验里每个被接管任务重复的模型调用恰好是 1 次，118 个里 118 个都是；不变量 0 失败。容量实验 3600 次运行在压力下也没有从至少一次变成多次。

**要点**：重做的只是在途那一步、检索与阅读只读、证据按稳定 ID 幂等、产物受 fencing 只有一份、恰好一次要两阶段落决定不划算

**可能的追问**：
- SIGTERM 下为什么还会重复 1 次模型调用？因为 Agent SDK 自带的关闭钩子会先在"模型已决定调用工具、工具还没执行"的位置中断，这个决定没落库，接手方只能再调一次；要消除就得持久化模型的调用决定，我没做。
- 如果重做的那一步是写操作会怎样？
- 不变量具体检查了哪几条？

### Q32 上下文超限时为什么用阈值压缩，而不是常见的滑动窗口裁剪？

**答**：因为滑动窗口跟提示缓存根本冲突。提示缓存是前缀匹配——两次请求必须从第一个 token 开始逐字节相同，出现第一处差异就从那里往后全部重算。滑动窗口每轮丢掉最早的一轮往返，等于每轮都改前缀的开头，缓存永远追不上。原来的实现就是这样，多 Agent 模式下命中率只有 0.02%。改成阈值压缩之后：估算输入没超过上限——默认 28,000 token——就一个字不动；一旦越线，一次性压到上限的 60%，然后在两次越线之间保持前缀不变。压缩顺序是先轻后重，先把最早那几轮的工具结果换成可恢复的存根，保留工具调用 ID、工具名和证据 ID 列表，模型可以用按证据 ID 重读原文的工具把内容取回来；存根不够再整轮移除；最新一轮始终完整保留。水位只增不减，所以压缩后的前缀依然稳定，只在越线的那一次丢一次缓存。还有一个副作用是滑动窗口每轮丢一点，模型一直在"刚刚好丢掉需要的东西"的边缘反复丢。代价是单次压缩更激进，而且要额外保证工具调用和工具结果成对，不然协议会报错。

**要点**：缓存是前缀匹配、滑动窗口每轮改前缀、阈值压缩平时零成本越线集中付一次、存根保留工具调用 ID 与证据 ID 可重读、水位只增不减

**可能的追问**：
- 阈值压缩这条路径测过吗？没有——成本和质量两组实验里两臂输入都低于 28,000 的估算上限，压缩完全没触发过，只有协议测试覆盖，这是我知道的最大覆盖空洞。
- 压缩之后前缀还能命中吗？
- 为什么最新一轮要完整保留？

**另见**：Q52（通用视角）、Q33（为什么不做摘要）

### Q33 为什么不干脆把整段历史做一次摘要，用摘要替代原文？

**答**：先说清楚，全量摘要我没做，这是取舍层面的判断，不是实验结论。不做的理由有三条。第一条是缓存：摘要是模型生成的，每次重新摘要几乎不可能得到逐字节相同的文本，而它又在整段历史的最前面，等于每摘要一次就把整个前缀作废一次；而存根方案保留的是原来的工具调用 ID 和工具名，是确定性的。第二条是这条链路有"先读后引"的约束——结束时要逐条校验每个发现引用的证据都在已读集合里，引用编号由服务端分配。摘要会把证据 ID 揉掉，模型就没法再准确引用，而存根明确保留了这条结果里出现过的证据 ID 列表，已经读过的证据仍然可引用。第三条是可恢复性：存根是可逆的，模型觉得需要就用重读工具按证据 ID 把原文取回来；摘要一旦生成，丢掉的细节就取不回来了。代价是存根省下来的 token 比摘要少——摘要能把十几轮压成几百字，存根只是把长工具结果换成一句说明，所以极端长的历史下存根可能压不够，那时只能整轮移除。

**要点**：摘要不确定破坏前缀缓存、揉掉证据 ID 与先读后引冲突、存根可用重读工具逆回原文、摘要不可逆、存根压缩率低于摘要

**可能的追问**：
- 那压不够怎么办？先整轮移除最早的一轮，全部压完仍超上限就直接按"上下文预算耗尽"失败，不做降级猜测。
- 这条取舍有实验支撑吗？没有，压缩路径本身就没被真实实验覆盖。
- 摘要会不会反而提高答案质量？

### Q34 为什么要用显式缓存断点，不能靠供应商的隐式缓存白捡吗？

**答**：因为隐式缓存供应商文档明写不保证命中，没法写进成本模型。我用协议夹具抓下 SDK 实际发出的请求字节，每次只改一处重放到真实端点做探针，其中一行就是"系统消息稳定、历史只追加"的纯隐式场景，逐步走 4 次只命中 1 次。这种不可预测的收益可以当白捡，不能当基线。台账里那个 5.2% 的命中率更能说明问题：它不是"有时候命中"，而是每次都恰好命中 1,280 token，正好等于工具定义 714 加静态提示 632 加模板 17 按 128 取整——是供应商在共享前缀上一段没有文档的行为，另一种模式的对应长度在三千多次调用里一次都没出现过。显式缓存是在请求里给内容块打一个断点，写入按 125% 计费、命中只按 10%，有效期 5 分钟而且命中即续期；Agent 相邻两次调用之间只隔一次工具执行，远小于 5 分钟，所以一个任务十来次调用，第二次就回本。代价是绑定了这家供应商的内容块语法和它返回的缓存用量字段，所以我留了一个开关，关掉就退回隐式，稳定前缀和阈值压缩不受影响；换供应商时先关开关再写新的传输适配器。

**要点**：隐式文档明写不保证、探针实测稳定前缀也只 4 次命中 1 次、5.2% 是未公开行为不可依赖、写入 125% 命中 10% 第二次回本、绑定供应商语法所以留开关

**可能的追问**：

### Q35 租约 30 秒、心跳 10 秒、轮询 5 秒这几个参数是怎么定的？调大调小各有什么代价？
**答**：先说清楚，这几个是我定的默认值，不是压测出来的，这是它的弱点。定的时候只有两条硬约束。一条是配置校验强制租约至少是心跳的两倍，也就是允许连丢两次心跳才判失联，否则一次网络抖动就会让健康的任务被抢走。另一条是失联接管的恢复时间约等于"租约剩余加一个轮询间隔"，所以 30 秒加 5 秒，生产默认最坏大约 35 秒——这个数要能被业务接受。往下调的代价是写放大：租约越短，每个在跑的任务续租越密；轮询越短，空闲实例对数据库的空转查询越多，容量实验里轮询从 5 秒降到 1 秒，空闲轮询从每秒每实例 0.2 次升到 1.0 次，吞吐只涨 9.5% 到 10.7%，排队等待几乎没改善。往上调的代价是恢复变慢，而且租约调长之后"活着但卡住"的任务占住槽位的时间也更长。所以我的取法是：轮询间隔决定的是吞吐的边角损失，租约长度决定的是最坏恢复时间，两者要按业务能忍的恢复时间倒推，而不是各自拍一个数。
**要点**：默认值不是压测出来的、强制租约至少两倍心跳允许丢两次、恢复时间约等于租约剩余加一个轮询间隔、调小换来写放大与空转查询、按可接受的恢复时间倒推
**可能的追问**：
- 实验为什么用 6 秒 / 2 秒 / 1 秒？——为了缩短实验时间，每次重复都要等一个租约周期，20 次重复乘六个场景按生产参数跑太久
- 那实测的 5.13 秒能外推到生产吗？——不能，生产默认最坏约 35 秒是推算不是实测
- 有没有想过按任务类型给不同的租约？——没做，现在只有一套全局默认值

### Q36 权限过滤为什么必须在召回之前，召回之后再滤不是更简单吗？

**答**：因为向量检索只取相似度最高的少数几块，默认最终进模型是 10 条。如果先按全库召回再按权限筛，那些名额会先被不可读库里的高分块占掉，筛完剩下的结果变少甚至为空——用户看到的不是"你没有权限"，而是"这个系统查不到东西"，答案质量被别人的私有数据悄悄拖垮了；而且那些内容已经进过进程内存和日志，块数、耗时这些旁路信息还会泄露"存在一条更匹配的内容"。做法是检索范围解析时先求交：当前启用中的知识库，与当前用户可读的知识库，交集算完放进这次检索的上下文，向量通道直接把这批集合名拼进 SQL 条件，不可读库的向量根本不参与排序，各通道只读不判。这件事我用集成测试证明过：私有库里放一个和查询向量完全相同、相似度 1.0 的块，公开库放一个 0.6 的；所有者取 TopK=1 命中私有库那块，其他用户取 TopK=1 拿到的是公开库那个 0.6 的块。代价是这条只对"能按库限定召回范围"的检索组件成立，当时那条单实例单张图的图谱通道就只能在结果侧过滤，名额还是被占。

**要点**：TopK 名额被不可读高分块占掉、表现为查不到而不是没权限、范围求交后拼进 SQL 各通道只读不判、集成测试用 1.0 对 0.6 证明、只对能按库限范围的组件成立

**可能的追问**：
- 顺着改的时候踩到什么坑？空范围过去被当成"不限"——那条关键词通道在库列表为空时不加过滤直接搜整个共享索引。以前没有调用方传空列表所以不算 bug，加权限之后"一个库都读不到"变成正常情况，空范围立刻就是全库泄露。
- 判定结论缓存吗？

### Q37 增量更新为什么按内容哈希复用向量，而不是做文档级的差异比对？

**答**：因为按文档寻址的增量在几个真实场景下完全命不中。缓存键是（模型、维度、向量文本的 SHA-256）三段，和块 ID、文档、知识库都无关。如果改成"文档 ID + 块序号"，那么同一份资料上传新版本在我们这里是另一份独立的文档记录，就一块都命不中；回退到旧版本也命不中；原样重新入库同样要看文档 ID 对不对得上。按内容寻址的话这三种情况都能命中。实测一份 79 块的调研表，真实上游单次运行：原样重新入库和回退旧版本都是 0 次上游调用，V1.2 升到 V1.3 只有 2/79 块需要重嵌入，计费 token 从全量的 45,722 降到 1,368，占 2.99%；同样的流程在模拟上游下块数和命中数完全一致，说明复用率只由文本决定。代价是天花板卡在分块边界上：表格是按行顺序贪心累加分块的，在一张表中间插一行，插入点之后每一组都整体后移，这张表后面所有块的文本都变了、哈希全变、一个都命不中。修复方向是改成按内容滚动哈希决定切点，我没做，实测也没覆盖到这种情况——手上只有一对真实版本，改动正好落在段落里。

**要点**：键是模型加维度加向量文本哈希、新版本是另一份文档按文档寻址全不命中、回退与原样重入也能命中、79 块里 2 块重嵌入 token 降到 2.99%、表中插行会让该表后续块全失效

### Q38 你们的分块策略是怎么定的？

**答**：我们的原则是切法由文档结构唯一决定，用户只能调体量。解析出来的不是一整坨文本，是一串带类型的结构块——标题、段落、列表、代码、表格、图片，分块按这个类型分发。用户能配的只有分块预算：目标块大小默认 1024 字符，重叠默认取块大小的八分之一，表格每块行数上限 50，为保完整性允许撑到目标的 3 倍，块大小硬上限 8192 字符。几个取舍我会主动讲：块大小取 1024 而不是常见的 512，是因为防语义稀释靠按章节边界打包，不是把块压小，而且最终进模型的默认只有 10 块，块太小名额会被同一章节的碎片占满；目标大小是目标不是硬上限，切开一个完整语义单元的代价高于超出目标；重叠不只是冗余，它同时是切分时向后回退找句末标点的最大距离，中文长句配 1024 配 64 经常回退不到句号，所以重叠按块大小等比给。硬上限 8192 在构造预算时就拦，因为真正的约束是嵌入模型的输入长度，不拦的话要到向量化那一步才报错。
**要点**：结构决定切法、用户只调体量、1024 而非 512、重叠兼做回退距离、硬上限受嵌入输入长度约束
**可能的追问**：

- 那表格怎么切？
- 块大小改了以后已经入库的文档怎么办？

### Q39 表格和带章节层级的文档怎么分块？

**答**：表格是按行贪心累加：从第一行往组里加，加到超过行数上限或者再加一行会超预算就落一块，**每块都带完整表头**，不带表头的后半截检索出来就是一堆没有列名的数字。预算是按展示文本和向量文本两种渲染各自的实际长度算的。这里有个关键点：展示文本是完整的 markdown 表格，向量文本改写成"列名: 值"的形式，因为 markdown 表格靠位置对齐列名和值，嵌入模型读不懂位置。章节层级也是同一个思路——每个块存两份文本，展示文本是文档原貌，向量文本等于"正文里还没出现的那几级章节路径加上正文"。同一节被切成多块时，只有首块自带标题，续块光看正文不知道自己属于哪一章，所以要补章节路径；首块已经自带的那几级就不再重复拼，不然只是把章节名连写两遍白占向量位置。向量文本会跟展示文本一起落库，这样换嵌入模型时可以直接重新向量化，不用重新解析、重新调版面服务和视觉模型。
**要点**：表格按行贪心、每块带表头、向量文本写成"列名: 值"、块存展示与向量两份文本、章节路径只补未出现的层级
**可能的追问**：
- 表格中间插一行会怎样？（这张表后面所有块的边界整体后移，哈希全变、缓存一个都命不中——这是我们增量更新的天花板，没修。）
- 图片和扫描件怎么处理？
- 为什么向量文本要单独落库而不是用的时候现拼？

### Q40 混合检索是怎么做的？RRF 为什么要按名次融合？

**答**：**项目里没做**——我们的检索引擎是多通道结构、融合逻辑也在，但我把上游自带的关键词通道和图谱通道整块删掉了，现在只剩一条向量通道加一条默认关闭的联网通道，所以严格说线上跑的是单通道，融合在单通道时会被跳过、保持原召回顺序。融合本身的做法我清楚：去重按块身份合并多路命中、保留首次出现的实例，**不比较跨通道的原始分数**，因为余弦分和 BM25 分量纲不同，直接比是错的；然后 RRF 只看各通道各自的原始名次，按"权重 ÷ (k + 名次)"累加，我们的 k 取 20 而不是常见的 60，因为候选池通常只有几十条，60 会把名次差异抹平。通道权重让新接入或可信度低的通道话语权小一些。我的理解是，混合检索真正解决的是两类召回盲区：BM25 管精确匹配（型号、编号、条文号这类词，向量反而不敏感），向量管同义和口语化表达，两路互补。
**成熟做法**：真实业务一般双写一份倒排索引（ES/OpenSearch）和一份向量索引，检索时两路并行各取 Top50，用 RRF 融合后再送 rerank；对型号、标准号这类强字面查询额外加精确匹配通道并给高权重。
**要点**：只剩向量通道、量纲不同不能直接比分、RRF 只看名次、k 取 20 的理由、通道权重
**可能的追问**：
- 删掉关键词通道是不是丢了精确匹配能力？（是，编号类查询目前只靠向量，这是已知缺口。）
- RRF 和加权求和、归一化后相加比有什么优劣？
- 通道超时了怎么办？

**另见**：Q41（候选池预算）

### Q41 为什么要 rerank？粗排和精排的成本怎么控？

**答**：我们把检索漏斗显式拆成三段预算，一次算好，各阶段只读属于自己的那段：每通道召回额度默认 20（想大，保召回）、候选池上限默认 40（这是重排的成本天花板）、最终进模型条数默认 10（产品语义上的 TopK）。启动时校验漏斗单调收窄。融合之后先按候选池上限截到 40 条，回表富化和重排都只在这 40 条上做，所以精排成本有上界。重排看的是富化阶段单独拼的一段"文档名 + 结构化检索文本"，最终进模型的上下文仍然用原始正文——这样 PDF 的标准文件名、表格的列名键值能参与精排，又不会污染引用和前端预览。我自己加了一个候选池成本兜底：融合被关掉或者融合失败时，上面那道截断就不存在了，回表和重排会先按全量做完再截断，所以我加了一个独立的守卫处理器放在富化和重排之前，保证无论融合是否生效，候选池规模都有同一个上限。另外整条后处理链是某个处理器抛异常就跳过它、链继续走，不让一次重排失败毁掉整次召回。
**要点**：三段预算、漏斗单调收窄、候选池 40 是精排成本上界、重排看结构化文本、富化只在候选池内回表
**可能的追问**：
- 重排模型挂了怎么办？（跳过这个处理器，链继续，退化成融合后的顺序。）
- 候选池 40 和最终 10 这两个数字怎么定的？
- 交叉编码器重排的延迟怎么控？

### Q42 一个问题被拆成多个子问题，TopK 怎么分？

**答**：上游原来的做法是给每个子问题各发一份最终条数——配置写 10、问题拆成 3 个，实际进模型的就是 30 条，拆得越多上下文越长、精度越低、token 成本越高，而这三件事都不写在配置里。更隐蔽的是跨子问题重复：两个子问题召回同一块，去重后名额就凭空少一个，没人补。所以我把最终条数改成**整次请求**的总额度，在子问题之间分摊：总额度除以子问题数，余数按顺序前几题各多一条；极端情况下子问题数超过总额度，靠后的题分到 0 条，显式打警告并跳过它的检索，保证"最终 10 条"这个产品契约不被突破。相应地重排也不能在子问题内部截断了，改成模型返回的头部在前、没进头部的候选按原顺序追加在后，整池往上传。最后做一次全局去重，产出一份唯一有序的块列表。这个顺序很重要，提示词分组渲染、来源编号、离线评测的命中率都按它走，否则评测数字和线上行为对不上。
**要点**：TopK 是请求级总额度、按子问题分摊余数前置、重排不在子问题内截断、全局去重后唯一有序列表、顺序被提示词与评测共用
**可能的追问**：
- 跨子问题重复留下的空位补不补？（我实现了一个公平回填，按题轮询各补一个，但默认关闭，线上仍是取配额前缀不回填。）
- 为什么空位不按全局最高分竞争？（不同 query 下的重排分数分布不同，不可横向比较。）
- 分到 0 条的子问题用户知道吗？

### Q43 查询改写怎么做？改写失败了会不会把整次问答拖住？

**答**：分两步。先做规则归一化，把配置好的业务术语别名统一替换成标准词；再把归一化后的问题连同最近 4 条对话消息（最多两轮，只留用户和助手消息、把系统摘要过滤掉省 token）一起，调一次快速档模型，要求返回一个 JSON：改写后的问题、是否需要拆分、子问题数组。有一处判断是我改的——**以模型返回的"是否拆分"布尔位为准**，而不是看数组里有几条。上游忽略这个字段，模型明明判定不拆、数组里偶发多条，也会触发多次检索，白白瓜分后面的上下文额度。失败处理很简单而且是单层的：模型调用异常、返回不是合法 JSON、改写结果为空，一律回退成"归一化后的问题"单条，不做跨档位升级重试。理由是改写只是检索质量的优化，不值得为它把整次问答拖住。改写开关关掉时走纯规则：归一化后按标点切句。
**要点**：规则归一化在前、快速档模型返回 JSON、以布尔位判定是否拆分、失败单层回退不重试、开关关掉退回规则切句
**可能的追问**：
- 为什么不用多路改写（HyDE、多查询生成）？项目里没做，那会让检索次数和上下文额度都翻倍。
- 指代消解为什么只带最近两轮？
- 改写带来的收益你们量化过吗？（没有，这条链路上没有端到端的答案质量对照实验。）

### Q44 怎么防止模型编造引用？

**答**：这是我在研究任务里做得最重的一块，做法是把"可引用"定义成一个服务端维护的集合，模型没有任何办法往里加东西，只有真正走完一次阅读才会加。四道闸：第一，检索只产生候选，命中的每个块按"运行 ID + 来源身份 + 正文与位置的 hash"算一个稳定证据 ID，连同数据库里的完整正文存成一份证据快照标记为未读，返回给模型的只有截断摘录和这个 ID。第二，最近一次检索返回的候选里只要还有既没读过也没尝试读过的，再调检索就被拒绝；同一个"查询语句加文档范围"最多允许两次，第三次直接拒绝，提示"换措辞不会让不存在的事实出现"。第三，必须阅读时服务端在下一次模型调用里把工具选择从"任选其一"改成"只能调阅读工具"，模型没有绕开的余地。第四，结束时逐条校验，每条发现必须有 1 到 12 个证据 ID 且全部在集合里，有一个不在整次结束调用被拒、错误回传给模型重来；产物生成前还会拿这批 ID 回证据表复核一次归属和已读状态。另外引用编号是服务端按出现顺序分配的，模型自己在正文里写角标会被判非法。
**要点**：可引用集合只由服务端加、检索只给候选 ID、有未读不许再搜、工具选择强制改写、结束与产物两次校验、编号服务端分配
**可能的追问**：
- 阅读工具取的是快照还是当前库里的内容？（首次保存的快照，取回前校验正文 hash；发现文档版本或正文变了就标"来源已变化"，只返回旧快照并让模型在结论里说明。）
- 这套能保证陈述和证据内容一致吗？
- 模型就是不调结束工具、输出一段纯文本怎么办？

**另见**：Q45（引用合法但陈述不实）、Q54（工具契约当约束）

### Q45 引用都合法，但那句话其实证据里没说，怎么办？

**答**：**项目里没做**。我们的"先读后引"只能保证被引用的证据确实在这次运行里被读过、且在允许的知识库与文档范围内，**不保证陈述和证据的内容一致**——没有做句子级的蕴含校验，模型仍然可能给一段读过的文字挂上一个它并不支持的结论。普通问答那条链路更薄一些：上下文就是模型看到的全部，链路里没有"检索到的内容是否足以回答"的判定，也没有生成后的忠实度校验；空检索会短路回一句固定话术，但"检索到了但都不相关"会照样送进模型。我的理解是，这件事要做得单独加一层生成后校验：把答案按句子拆开，每句连同它引用的原文段落送给一个小模型或 NLI 模型判断蕴含关系，不成立的句子要么删掉、要么降级成"资料未明确说明"，同时把这个判定结果作为一个可观测指标长期跟踪，而不是一次性检查。
**成熟做法**：生产上常见的是"答案句 × 引用片段"逐对过一个轻量裁判模型或 NLI 模型，不通过就重写该句或整体拒答，并把忠实度得分采样落盘做长期监控。
**要点**：只保证读过不保证蕴含、问答链路无生成后校验、无"上下文是否足够"判定、需要句级 NLI 与拒答降级、应作为持续指标
**可能的追问**：
- 为什么没做？（成本与延迟：每句多一次模型调用，而研究任务的预算是一次运行 16 次模型调用。）
- 如果要做，放在产物生成之前还是之后？
- 拒答率会不会因此失控？

**另见**：Q44

### Q46 RAG 系统你们怎么评测？用了哪些指标？

**答**：我们做的是端到端的前后对照，不是检索侧的指标体系。具体是：在一个公开的多跳问答数据集上抽 400 道模型没见过的题（抽样脚本只读题目 ID 和原始题目 ID，不看答案也不看可答标签，凡是在开发期回归题集里出现过的题连同同源版本一起剔除），改动前后分 4 块交错运行，用数据集官方定义的 EM 和 F1，按题目 ID 配对算"后臂 F1 减前臂 F1"的均值，再用百分位 bootstrap 给 95% 区间。结果是配对 F1 −0.034、区间 [−0.080, +0.011]，结论只能写成"未见显著下降，但不能排除 0.08 以内的下降"。最重要的一条是我事先跑了噪声基线：同一批题、同一个版本再跑一次，F1 变化 +0.059，**运行间噪声与要测的效应同量级**——没有这条基线，一个 −0.03 既可以说成明显变差也可以说成没变化，全凭说的人。检索侧的指标（命中率、MRR、上下文精度召回、忠实度）我们没有搭，这是缺口。要说清楚的边界是：这是公开数据集不是企业检测资料，它能回答"这次改动有没有让作答变差"，回答不了"这个系统在业务语料上答得多好"。
**要点**：端到端 EM/F1、配对差加 bootstrap、噪声基线同量级、抽样不看答案与标签、无检索侧指标、公开数据集非业务语料
**可能的追问**：
- 为什么用配对差而不是比两边平均 F1？（题目难度差异远大于两臂差异，不配对方差全被难度占掉。）
- 为什么用 bootstrap 不用 t 检验？（单题 F1 夹在 0 和 1 之间、两端堆积，均值的正态近似靠不住。）
- 判定规则是什么时候定的？（事先写死，区间含 0 就只能说未见显著下降，并且必须把下界一起报出来。）

**另见**：Q60、Q61（统计方法）、Q58（三层证据）

### Q47 检索返回零条，你怎么知道是库里没有还是接口挂了？

**答**：这是我们踩过的最贵的一个坑。上线前一次批量跑，1200 个任务里 72 个超时，全部卡在检索工具上、耗时清一色 30.01 秒。原因之一是检索通道原本会 catch 住异常返回"零条结果"——这对面向用户的即时问答是合理降级，但研究任务是长链路多轮自主决策的，模型拿到零条就以为库里没资料，改写查询再搜一次、再得到空结果，最后交出一份状态成功、内容空洞的报告。**失败被伪装成了"事实上不存在"**，这比直接失败更危险。分离是在三个位置同时做的：通道和后置处理在研究路径上不再吞异常，规整成带"阶段 + 错误码 + 是否可重试"的统一失败往上抛；工具层把失败如实转述给模型，错误结果里明确写"这是一次执行失败，不是不存在相应资料的证据"；落库时会话维护一个执行问题列表，只要有执行问题结果状态就是"部分完成"，既有执行问题又一条可引用证据都没有就直接判失败、不生成产物。还堵了一条侧路——模型不能用"向用户提问"来掩盖检索故障。
**要点**：空结果不等于无资料、三处同时分离、统一失败类型带可重试标志、执行问题决定终态、禁止用追问掩盖故障
**可能的追问**：
- 效果有数字吗？（模拟上游、每格 200 任务、注入 embedding 无响应：30% 档成功率 57.5% → 98.5%，Wilson 95% 区间两版不重叠；1600 个任务里"状态成功但没有证据"这种错误完成是 0。）
- 模型反复换措辞重试怎么办？（连续失败 2 次进入"检索受阻"，再调检索直接拒绝，让它用已读证据收尾。）
- 为什么即时问答那条路径保留降级？

**另见**：Q24（简历口径）、Q55（连续失败即停）

### Q48 文档改版了，知识库怎么增量更新？

**答**：原来是一份几十页的调研表改一行数字，重新入库时每个块都重新送去向量化，按 token 重复付费。我在唯一那个向量化入口上加了一层缓存，键是**（模型、维度、向量文本的 SHA-256）**，和块 ID、文档、知识库都无关。按内容寻址而不是按文档寻址是关键分岔：如果按"文档 ID + 块序号"做增量，上传新版本成了另一份文档就完全命不中、回退旧版本也命不中；按内容寻址的话，原样重新入库、新版本里没变的段落、回退旧版本，三种情况都能命中。模型那一段用解析后的"供应商:模型名"而不是配置里的别名，因为别名改指向之后旧向量还会被当成有效命中返回，而不同模型的向量不在同一个空间里。维度也在键里，取回来之后还会再核一遍向量长度。实测一份 79 块的调研表，真实上游单次运行：V1.2 升到 V1.3 只有 2 块需要重嵌入，计费 token 从 45,722 降到 1,368，占 2.99%；原样重入和回退旧版本都是 0 次上游调用。落库那边关系库块表和向量表在同一个事务里先删后插，集成测试证明过版本切换对检索方是原子的。
**要点**：内容寻址不按文档寻址、键含模型与维度、模型用解析后标识不用别名、缓存不参与正确性可降级、先删后插同事务
**可能的追问**：
- 缓存写入为什么不和块写入同事务？（缓存只省钱不参与正确性，放进去的话块写入失败会把已经付过费的向量一起回滚，正好和目的相反。）
- 复用率的天花板在哪？（表格按行贪心累加，表中间插一行会让这张表后面所有块的边界整体后移、全部失效，没修。）
- 事务覆盖到哪？（只覆盖 PostgreSQL 这两张表；启用 ES、图谱或 Milvus 时它们的先删后插在事务之外。）

**另见**：Q37（取舍）、Q67（事务边界）

### Q49 embedding 模型怎么选？换模型要付出什么代价？

**答**：**项目里没做**选型评测——嵌入模型是上游选定的，我没有做过多个模型在业务语料上的召回对照实验。我做的是把"换模型"这件事的代价显式化。代价有两块：一是全量重算，每个块都要重新调一次嵌入接口付一次 token；我们把向量文本单独落库正是为了这一步——换模型可以直接重新向量化，不必重新解析、重新调版面服务和视觉模型。二是不能混用，同一个库里的向量必须来自同一个模型和维度，向量落点由知识库配置和部署配置合成、不允许为空也不允许回落到系统默认模型，因为嵌入模型选错是一个静默错误，要到检索质量变差才发现。同一条规则在两个地方复用过：向量复用缓存的键里含模型和维度，带截止时间的调用不做跨模型回退（用另一个模型的向量去查原模型建的索引，结果是错的，这种降级比失败更糟）。我的理解是，选型至少要在自己的语料上比中文表现、维度与存储成本、最大输入长度这三项，而不是看公开榜单。
**成熟做法**：真实业务会先用几百条人工标注的"查询—正确片段"对，在候选模型上跑召回率 @k 与 MRR 做离线对比，再看维度带来的存储与检索开销；换模型走双写双索引灰度，验收通过再切流。
**要点**：项目未做选型对照、向量文本落库换模型可免重解析、模型与维度不可混用、不跨模型降级、选型应看自有语料召回
**可能的追问**：
- 换模型期间新旧向量怎么共存？项目里没做双索引，只能整库重建。
- 为什么维度也要进缓存键？（同一模型截成不同维度的向量互不通用。）
- 多语言或专业术语场景怎么办？

### Q50 向量库怎么选？为什么用 pgvector？

**答**：**项目里没做**选型对比实验，我不能说 pgvector 比别的快。能说的是为什么这个场景下它够用，以及我们怎么把选型的影响面缩到最小。够用的理由：我们的任务状态、块表、证据表本来就在 PostgreSQL 里，向量放在同一个库意味着关系库块表和向量表的先删后插可以在同一个事务里扇出，版本切换对检索方是原子的——这一点我用集成测试证明过：第三个落点在两张表都已经删旧插新、尚未提交时停住，另一个连接读到的仍然是旧版本的 3 个块，放行提交后才整体切到新版本的 2 个块。换成外部向量库，这个事务就没了。另外权限过滤也受益，我们能在一条 SQL 里把"可读知识库集合"当过滤条件跟向量检索一起下推，做到召回前过滤而不是召回后过滤。代价也明确：检索引擎本身是多通道可插拔的，落库是扇出到多个落点，加一个索引后端就是加一个落点实现；但一旦启用 ES、图谱或 Milvus，它们的先删后插就在事务之外了，失败时可能半新半旧。还有一个细节：带过滤条件的向量检索会有召回悬崖，我们靠会话级放宽索引参数来填满 LIMIT，并且拿回结果先按分数排序再截断，不信任数据库返回序。
**成熟做法**：数据量在千万级以内、且要和业务数据做联合过滤时，多数团队直接用 pgvector 或同库方案；上亿向量、要求毫秒级和独立扩缩容时才拆出专用向量库，并接受索引与业务库最终一致。
**要点**：未做选型对比、同库换来跨表事务、权限过滤可下推做到召回前、落点可插拔但事务只覆盖同库、过滤式检索的召回悬崖与排序不可信任
**可能的追问**：
- HNSW 的参数你们调过吗？（只在带过滤时会话级放宽扫描参数，没有做过召回率与延迟的系统调参。）
- 数据量涨到什么程度你会换？
- 多知识库是分表还是分集合？（共享表，按集合名 IN 在一条 SQL 里查完整个范围。）

### Q51 多轮对话的记忆是怎么管的？

**答**：问答链路上是"最近若干轮原文加一条摘要"。历史和摘要并行从库里读：一边读最近 8 轮原始消息，一边读该会话最新的一条摘要，超过 9 轮开始压缩、摘要限 400 字，摘要以一条系统消息的形式插在历史最前面。两边都有兜底——摘要读失败就不带摘要，历史读失败就当空历史，都不让一次问答挂掉。然后把用户这句话追加进消息表，追加动作内部会顺带触发会话创建、标题生成，以及达到阈值时的历史压缩。要注意落库和后面的检索、生成不在同一个事务里，也不可能在，因为后面要跑几秒到几十秒的模型流；所以中途失败时用户消息已经存在、助手消息缺失，这是有意的，前端刷新后仍能看见自己问了什么。还有一个细节：送去做查询改写的历史只取最近 4 条消息，而且只留用户与助手消息、把系统摘要过滤掉，因为改写只需要解指代，带上摘要是白花 token。研究任务那条链路的记忆完全不同，是 Agent 自己的消息历史，只追加不改写。
**要点**：最近 8 轮加 400 字摘要、并行读且各自兜底、摘要作为首条系统消息、落库与生成不同事务、改写只取 4 条且过滤摘要
**可能的追问**：
- 摘要是什么时候生成的？（追加消息时达到阈值触发，不阻塞当前这轮回答的主路径。）
- 摘要丢信息怎么办？
- 研究 Agent 的记忆为什么只能追加？

### Q52 上下文快超限了怎么办？为什么不用滑动窗口？

**答**：我们用的是阈值压缩而不是滑动窗口。做法是：估算输入没超过上限（默认 28,000 token）就一个字不动；一旦越线，一次性压到上限的 60%，然后在两次越线之间保持前缀不变。压缩顺序先轻后重——先把最早那些轮的工具结果换成可恢复的存根，保留原来的工具调用 ID 和工具名（所以工具调用与工具结果仍然成对，协议不会因为缺一半报错）、保留这条结果里出现过的证据 ID 列表，正文换成一句说明告诉模型可以用重读工具把原文取回来；600 字符及以下的短结果原样保留，替换它不划算；存根还不够就从最早的一轮开始整轮移除；最新一轮观察始终完整保留；全部压完仍超上限就按"上下文预算耗尽"失败，不做降级猜测。关键在于水位只增不减，每次调用按同一水位重新生成同一份视图，所以压缩后的前缀依然稳定、可缓存，只在越线那一次请求上丢一次缓存。不用滑动窗口的原因是它每轮都改前缀，等于放弃提示缓存，而且每轮丢一点，模型一直在"刚刚好丢掉需要的东西"的边缘。诚实地说，这条路径在我的两组真实上游实验里都没被触发，只有协议测试覆盖。
**要点**：阈值触发一次压到 60%、存根保留工具调用 ID 与证据 ID、短结果不替换、水位只增不减、最新一轮完整保留、压缩路径缺真实实验覆盖
**可能的追问**：
- 为什么不直接换成长上下文模型？（输入越长单次越贵，而且这是多轮循环，每轮都重发整段历史。）
- 存根之后模型还能引用那些证据吗？（能，已经读过的证据仍在可引用集合里，原文可以用重读工具取回。）
- 一次压到 60% 是不是太激进？

**另见**：Q32（取舍）

### Q53 这种多轮 Agent 的成本怎么降？

**答**：先说清楚钱花在哪：研究任务是多轮循环，每轮都要把整段历史连同系统提示和工具定义重新发给模型，一个任务十次左右调用，累计输入随轮数近似平方增长，成本几乎全在输入上。所以主要手段是提示缓存。我先给每次模型调用记了一份台账——调用 ID、模型、角色、任务 ID、供应商返回的真实 token 用量、命中 token、缓存写入量、时延与首字时延，失败超时取消的调用也落账，缺失的值记为缺失不用 0 冒充。拿一次完整回归的台账一算，单 Agent 模式命中率 5.2%、多 Agent 模式 0.02%，基本等于没有缓存。定位靠协议级探针：用协议测试夹具捕获 SDK 实际发出的请求字节，每次只改一处重放到真实端点，共 34 次调用，确认了两个根因——每轮把易变提醒拼进第一条系统消息，以及上下文超限时从最早往后滑动裁剪，两者都让前缀从头就不一样。改完之后真实上游同一 40 题前后对照，命中率 9.8%→78.4%、0.2%→80.0%，单任务计费输入分别降 69% 和 75%。要说明计费输入是按供应商文档折扣折算的**输入 token 当量，不是账单**，没有核对过发票。另外入库侧按内容哈希复用向量也是成本项，实测一份 79 块的表改版只需重嵌 2 块。
**要点**：输入随轮数近似平方增长、台账定位而不是看账单、协议探针单变量重放、命中率升到八成左右、计费输入是 token 当量非账单
**可能的追问**：
- 提示缓存具体怎么改的？
- 降了成本质量有没有掉？（做了 400 题的护栏，配对 F1 −0.034、区间 [−0.080, +0.011]，未见显著下降但不能排除 0.08 以内的下降；同一版本重跑的噪声是 +0.059，同量级。）
- 有没有考虑小模型分流、蒸馏或语义缓存？项目里没做。

**另见**：Q13、Q18、Q19（台账与成本数字）

### Q54 原生 function calling 和 ReAct 文本解析怎么选？模型不肯调工具怎么办？

**答**：我们走的是原生工具调用，循环形状还是 ReAct——模型输出一次工具调用、服务端执行、结果回灌、再调模型。我的看法是这两者不是对立的，ReAct 是循环的组织方式，原生 function calling 是这一步的传输格式；能用原生就别自己解析文本，因为自己解析要处理模型把 JSON 写在代码块里、多调用怎么分割、参数类型怎么还原这些事，而原生格式由供应商保证结构，出错的是参数值不是格式。更重要的是工具契约本身可以当约束用：主 Agent 注册四个工具加一个委派工具，子 Agent 只注册三个——追问和再委派在工具契约层就不存在，模型看不见，也就不可能调用。服务端还会动态改工具选择，比如有未读候选时把选择从"任选其一"改成"只能调阅读工具"，剩余调用不超过 1 次时钉死在结束工具上。模型不肯用原生工具结束、输出一段纯文本或一段假装成工具调用的 JSON，这种退化路径我们专门处理：服务端追加一条修复指令（现在就调结束工具、只能用已读证据、不要再检索），并把后续调用的工具选择钉死在结束工具上，同一上下文最多再给 2 次机会，仍然不行就报"必须通过原生工具结束"。这些修复调用照常扣全局额度。
**要点**：ReAct 是循环形状、原生调用是传输格式、工具契约当权限边界、动态改工具选择、退化路径给 2 次修复机会且照常扣额度
**可能的追问**：
- 工具参数校验放哪？（服务端，模型给的文档范围只能收窄不能扩大，超出简报允许范围直接拒绝。）
- MCP 呢？（上游自带的 MCP 工具我删掉了，项目里没用。）
- 工具定义顺序有讲究吗？（有，工具定义对提示缓存而言和系统提示同属最前面那一段，换个顺序整个请求就失配。）

### Q55 Agent 不收敛、一直在那儿转怎么办？

**答**：靠一份共享预算加三层收敛，不依赖提示词的自觉。预算是一次运行共用的，主 Agent、所有子 Agent、产物生成都从这一份扣：模型调用总数 16 次其中 2 次预留给产物生成，工具调用 24 次，单次请求输入上限 28,000 token，总活动时长 300 秒（等待用户补充条件不计入），探索阶段还要再预留 min(30 秒, 总时长的 1/5) 留给收尾；单次模型调用超时 60 秒、工具 30 秒、子任务 180 秒。额度在真正发出 HTTP 请求**之前**扣，不是成功返回之后，因为失败和超时同样消耗上游资源和时间，按成功计数等于给失败重试开了无限额度，代价是一次网络失败也占掉一次额度。耗尽不是直接抛错，分三层：每次调用附一条临时提醒（只在本次请求里、不写进记忆），告诉模型还剩几次、当前能引用哪些证据 ID、剩 2 次以内就别开新检索了；剩余探索调用不超过 1 次时工具选择被改成只能调结束工具；真的用光时，只要读到过证据就用预留的 2 次额度生成一份标记为"部分完成"的产物，一条证据都没有才判失败——不能用一份空报告掩盖检索不可用，那会让用户以为资料里确实没有。
**要点**：一份共享预算、发请求前扣额度、临时提醒不写回记忆、剩一次钉死结束工具、有证据就出部分完成、无证据不出空产物
**可能的追问**：
- 重复检索怎么挡？（同一个"查询语句加文档范围"最多两次，第三次拒绝；有未读候选时禁止再搜。）
- 进程崩了预算怎么算？（预算计数在内存里、只随事件快照落库，接管时在途那次调用会被丢弃重做，这次的额度会被重复计。）
- 并发怎么控？（进程内一个公平信号量限制同时进行的模型请求数，默认 2，等待时每 100 毫秒检查一次取消，超过阈值报配额等待超时，不无限排队。）

**另见**：Q63（预算耗尽的行为）

### Q56 什么时候该上多 Agent？代价是什么？

**答**：我们是按需委派，不是默认多 Agent。典型场景是"对比 A 和 B 两份材料的某几个维度"：两条线互不依赖，串行做要多花一倍时间，而且两份材料的原文塞进同一个上下文很容易顶到输入上限。代价我踩过四条：额度被子任务抢光、子任务互相看到对方的中间过程污染结论、一个子任务挂了拖垮整个任务、父子在同一个线程池上互相等待死锁。对应的做法是：深度只有一层，子 Agent 的工具集里没有委派工具；一次提交 1 到 4 个子目标，名额**一次性原子分配**，要么全给要么一个不给，因为部分成功最难处理——模型请求两条对比线只批了一条，结果是个不对称的半成品；每个子 Agent 拿到全新的会话，独立消息历史、独立已读证据集合、独立取消控制（父的取消级联到子，子的失败不反向取消父），回传的不是对话历史而是一个压缩结果，最多 8 条发现、8 条缺口、8 条冲突、总共不超过 8000 字符，每条带证据 ID；子任务跑在专用有界线程池上，父 Agent 的等待发生在它自己的执行线程上，否则就是典型的池内互等死锁。要说清楚的边界是：委派本身没有做过专门的容量或质量基准，离线评测跑的是关闭委派的单 Agent 模式。
**要点**：只在互不依赖时委派、一层深度、名额原子分配、上下文隔离只回传压缩结果、线程池分离防互等死锁、无端到端基准
**可能的追问**：
- 子任务挂了怎么办？（在它自己那条流上被吸收成一个失败或部分完成的结果对象返回给父 Agent，原因码写在执行问题里，同批其它子任务照常完成，最终结论标成部分完成。）
- 子任务的结果父 Agent 会无条件接受吗？（不会，入账时再校验一次，子任务引用的每个证据 ID 必须在父自己的已读集合里。）
- 接管之后已完成的子任务会重跑吗？（子任务每次状态变化都写检查点，接管方据此知道哪些做完了；不过这条只由测试覆盖，没有端到端实测。）

**另见**：Q68（线程池分离）

### Q57 流式输出怎么做？连接断了这一轮就没了吗？

**答**：两条链路做法不一样。问答链路是一条 SSE 长连接：先回元信息（会话 ID、任务 ID），再按类型分别推思考片段和正文片段（按码点切成小块发，按码点是为了不把代理对劈开），最后推完成事件（带消息 ID、来源列表、消息状态）和一个结束标记再关连接。正文在内存里累积，**完成时才一次性落库**；落库失败只记日志但仍然发完成事件，因为前端已经看完整段回答了，此时报错只会让用户以为答案没生成，代价是这条回答不进历史。连接只关一次靠 CAS 保证，关闭后再发事件静默丢弃、不抛给全局异常处理器，因为响应体已经开始写了，再走异常处理器会把响应写坏。连接有 5 分钟全局超时。**问答链路的 SSE 不支持断线续传**——没有事件 ID、不认 Last-Event-ID，连接一断这一轮只能重问，而且任务的本地注册表是进程内的，实例重启后在途任务无法恢复，只能靠 5 分钟超时兜底。带断点的续传只做在研究任务那条链路上：那边的事件按序号持久化在事件表里，序号在行锁内分配、连续无洞，前端带上已收到的序号重连就能续上。
**要点**：元信息先行、按码点切片、完成时一次性落库、关闭用 CAS 且关后静默丢弃、问答链路无续传、研究链路按事件序号续传
**可能的追问**：
- 用户点停止怎么处理？（独立的 HTTP 请求，先校验任务归属再写取消标记、广播给所有实例，各实例 CAS 置位后收尾追踪状态、取消模型流、把半截回答按"被中断"落库。）
- 为什么不用 WebSocket？

### Q58 没有线上流量，你怎么证明这些改造真的有效？

**答**：我先承认前提：这是预研原型，没上线，没有真实流量，所以我拿不出线上对比。我的办法是把证据分成三层，每层能证明什么、不能证明什么都写死。最底下一层是回归，每次改完跑一遍，几十秒出通过数，验证的是程序行为——请求字节、状态流转、权限判定，不花接口费。中间一层是我自己写的模拟上游，一个 OpenAI 兼容的独立进程，故障、并发、积压都能按需造出来，可以重复几十上百次；接管、上游容错、容量这三项实验都在它上面跑，测的是我写的队列、重试、租约、接管这套机制，不是供应商。最上面一层是真实上游上的一次性前后对照，只有成本和答案质量这两件事模拟上游算不出来，必须真调模型，所以贵、慢、只跑一两次，结论也写得最保守。没有流量的时候，验证的价值不在于数字好看，而在于口径事先定死、边界如实写出来。

**要点**：预研原型无流量、三层证据、回归几十秒、模拟上游可重复、真实上游只做成本与质量

**可能的追问**：
- 模拟上游测出来的数字和真实上游差在哪？
- 三层里哪一层你觉得最能说服人？我认为是接管实验，因为它是拿数据库里的不变量判定，不是看日志。
- 为什么不干脆找几个真实用户跑一跑？那只能说明跑得通，造不出 kill -9、上游 50% 不响应这种情况。

### Q59 模拟上游测出来的数字能不能信？和真实上游差在哪？

**答**：能信，但只能信它该信的那部分。模拟上游是我写的一个独立进程，对话端点按对话内容确定性地算出下一步工具调用，向量化端点把文本哈希成确定性向量，所以同一段对话永远得到同一个动作——这正是接管实验需要的，换个进程从事件重建出同样的对话，它给出同样的下一步。故障是一组旋钮，由固定种子统一抽：无响应、429 或 503、流传一半断开，再叠一段延迟。差别在于我设的延迟是均匀分布、故障是独立同分布，而真实供应商的慢是相关的、成串的，限流是有配额语义的。所以基于它的数字——接管恢复时间、故障注入下的成功率、排空吞吐——只说明我这套机制在这种输入下怎么表现，一个都不能当成对供应商的容量或可用性承诺。另外它的请求日志是请求结束时才写的，实验结束时还被挂住的请求不会进日志，所以无响应次数要以服务端自己的台账为准。

**要点**：确定性对话与向量、固定种子的故障旋钮、均匀分布 vs 成串故障、只证机制不证供应商、挂住的请求不进日志

**可能的追问**：
- 为什么模拟上游要做成独立进程，不在 Java 里 mock 掉模型对象？因为要测的是整条 HTTP 链路，而且故障注入实验要同时跑改动前后两个历史版本的代码，旧版本改不了，但都读同一批地址环境变量。
- 为什么"无响应"要把连接挂住而不是直接关掉？直接关是立刻可见的错误，客户端马上重试；真正贵的是对方收了请求不回复，把调用方的超时预算整段吃光。
- 成本和质量为什么不能也用模拟上游？

### Q60 为什么用配对差和置信区间，不直接看两边的平均分？

**答**：因为题目之间的难度差异远大于两个版本之间的差异。如果比两边的平均 F1，方差全被题目难度占掉，真正想看的那点差别淹没了。配对差是把两臂按题目 ID 对上，只取两边都评过分的可答题，逐题算后臂减前臂，再取这些差值的均值，每道题自己和自己比，剩下的方差才是改动带来的。区间我用的是百分位 bootstrap——对题目重抽样一万次取 2.5% 和 97.5% 分位，因为单题 F1 是个夹在 0 和 1 之间、两端堆积的分布，均值的正态近似靠不住，bootstrap 不需要对分布做假设，重抽样种子和次数都写进报告可以原样复算。结果是配对 F1 差 −0.034，95% 区间 [−0.080, +0.011]，含 0，所以我只能说"未见显著下降"，同时必须把下界 −0.080 一起报出来，当作不能排除的下降幅度。判定规则是事先写死的，不然等结果出来再挑口径，就是拿结论去选方法。

**要点**：题目难度方差远大于版本差、逐题配对、百分位 bootstrap 一万次、区间含 0 只能说未见显著下降、下界一起报、判定事先写死

**可能的追问**：
- 为什么不用 t 检验？
- 区间含 0，你凭什么说这个改动可以上简历？我说的是省了七成输入，同时说明质量上不能排除 0.08 以内的下降。
- 成功率那组为什么换成了 Wilson 区间？因为那是个二项比例，而且经常贴着 100%，正态近似在两端会给出超出 [0,1] 的区间。

### Q61 噪声基线是什么？为什么非要测它？

**答**：噪声基线就是同一批题、同一个版本，再跑一遍，然后用完全相同的配对差和 bootstrap 流程比较这两次运行。它回答的是"什么都没改的情况下，两次运行之间的差有多大"。必须测，是因为 Agent 每次运行都会走不同的检索路径、不同的调用次数，本身就有随机性。没有这条基线，一个 −0.03 的配对差既可以说成明显变差，也可以说成没变化，全凭说的人。我测出来的噪声是 +0.059，区间 [−0.032, +0.158]，和被测效应 −0.034 同一个量级，所以正确的结论只能是"效应没有超出运行间噪声"。我也会说清楚这条基线本身的弱点：它只跑了一次、只在 80 题上跑，它自己也是一个带宽区间的估计，不是一把精确的尺子。

**要点**：同版本同题重跑、量运行间随机性、噪声 +0.059 与效应同量级、没有基线就无法判定、基线本身只跑一次 80 题

**可能的追问**：
- 噪声这么大，你怎么才能测出真实的效应？要么加大样本，要么每臂多跑几次取平均，我两样都受预算限制。
- Agent 的随机性具体来自哪里？检索路径、模型调用次数、以及模型自身的采样。
- 那你后来修了那个下降吗？没有，最可能的解释我也只是提出来，没验证也没修。

### Q62 你说的"不变量检查"具体是哪几条？为什么用这几条？

**答**：故障实验的判定不看日志，看数据库里的不变量，每个任务逐条查五条：恰好一条终态事件、至多一份产物、事件序号从 1 开始连续无洞、已完成的同名同参数的工具调用没有被执行第二次、状态不是"被中断"。另外还核对每个被要求的资料是否都留下了已读证据。选这几条是因为续跑的语义本来就是"至少一次"——崩溃时在途的那次模型调用无论如何都要重做，这点我不打算掩饰。真正不能容忍的是已经完成的步骤被重做，那意味着重复计费、重复写入，所以不变量定在"已完成步骤不重做"这个位置上，既如实承认了至少一次，又能把"多做一步"和"从头再来"区分开。至于迟到写入被拒，事件序号连续、终态恰好一条、已完成步骤不重做这三条合起来就排除了两个执行者同时写一个任务；但"过期的那次领取去写会被明确拒绝"这一条是连真实数据库的集成测试直接断言的，实验只能给出间接证据。三个杀进程的场景各重复 20 次，不变量 0 失败；容量实验里把同一套不变量搬到 3600 个任务的压力场景下又验了一次，同样 0 失败。

**要点**：查库不看日志、五条不变量、至少一次是承认的、已完成步骤不重做是底线、迟到写入被拒由集成测试直接断言、压力场景下复验

**可能的追问**：
- 重复的模型调用数你怎么数出来的？不是直接数，是拿无故障基线那一档的干净调用数作差，超出的部分就是重做。
- 为什么"恰好一份产物"能成立？产物和终态在同一个事务里写，写入点有 fencing 保护。
- 这些不变量能不能自动跑在 CI 里？现在是实验脚本跑完直接查库，没有接进日常回归。

**另见**：Q10（简历口径）

### Q63 故障注入具体怎么做的？

**答**：一次实验由脚本发起：建一个随机命名的隔离运行库和一个模拟上游，按场景启动若干个独立的 JVM 执行器进程——是进程不是线程，它们共享那一个数据库，跑的是同一套执行服务。脚本提交几个脚本化任务，等到任务确实跑起来才注入故障，判据是数据库里已经有两次工具结束事件，不是"进程启动了"；然后等所有任务进终态，直接查库判定，跑完把库删掉。六个场景：无故障基线、`kill -9` 杀掉持有任务的执行者、运行中加一个新实例、优雅停机信号、暂停信号冻住超过租约再放行、以及每个接手者都被杀的毒任务。三种杀法对应三种完全不同的失败语义：瞬间消失要靠租约过期被别人接走；有序退出时进程能在步边界主动把任务交还队列，接手方不用等租约；暂停最刁钻——进程还在、连接还在、只是被冻住，解冻后它以为自己还持有任务继续往下写，这一场验的就是 fencing。结果是恢复时间 P50/P95/最大，`kill -9` 5.13/6.12/6.12 秒、暂停 5.12/6.12/6.12 秒、优雅停机 1.08/1.11/1.11 秒，每个被接管任务重复 1 次模型调用，118 个全是 1。

**要点**：随机隔离库加模拟上游、多个独立 JVM 共享一个库、按事件判定已跑起来、三种杀法三种语义、暂停场景验 fencing、毒任务防无限接管

**可能的追问**：
- 实验参数和生产一样吗？不一样，为缩短时间调小成租约 6 秒、心跳 2 秒、轮询 1 秒，生产默认是 30/10/5 秒，所以绝对值只在这套参数下成立。
- 为什么三个杀进程的场景要各重复 20 次？
- 毒任务那一场在验什么？验接管次数超过阈值后任务被判失败、执行者失联，而不是轮流把整个集群拖死。

**另见**：Q10、Q35（实验参数）

### Q64 回归测试怎么搭的？为什么这么搭？

**答**：一条命令串了两层，本地发起，不需要凭证和网络，跑完给出通过数，约 40 秒。第一层是协议层测试，模型换成一个脚本化的本地 HTTP 桩，测试进程里起一个 mock 服务器按写死的步骤序列返回工具调用，被测代码走的是真实的模型工厂、真实的 SDK、真实的流式解析，只是终点换成本地地址。这样能做逐字节断言——把首次执行发出的五个请求体原样录下来，再让接管续跑从持久事件重建一遍对话，在三个截断点比较两次请求的字节是否完全相同。不用 mock 掉模型对象，是因为缓存命中与否取决于请求体的字节、重复调用与否取决于流有没有读完，mock 成接口这两件事就消失了。第二层是集成测试，连真实的 PostgreSQL 和向量扩展，脚本每次新建一个随机命名的库、灌建表脚本、跑完删掉，测试类还多加一道锁：连接串必须匹配本机加随机前缀的形式，否则拒绝启动。不用内存数据库是因为这批改动有一半的正确性就落在数据库的具体行为上——跳过锁定行的并发领取、行锁内分配事件序号、向量相似度排序、同一事务里跨两张表先删后插，换成内存库这些语义要么不存在要么不一样。

**要点**：一条命令两层约 40 秒、脚本化 HTTP 桩保留整条链路、逐字节断言重建请求、真实数据库加向量扩展、随机隔离库加连接串校验、内存库测不出这些语义

**可能的追问**：
- 通过数是多少？Python 53/53、Java 13 + 211；更早记录过的 13 + 260 是一次删测试的瘦身重构之前的数，没有逐项核对，不能两个数相减。
- 协议测试证明不了什么？桩不会像真实供应商那样计费、限流、返回缓存统计，"前缀稳定"是事实，"前缀稳定就会命中"要靠真实端点验。

## 第 5 组　后端基础的项目化提问（Q66—Q73，8 题）

### Q66 领取任务那条语句里的 FOR UPDATE SKIP LOCKED，和普通行锁是什么关系？

**答**：FOR UPDATE 就是行级排他锁，SKIP LOCKED 只是改变了"遇到已被别人锁住的行怎么办"这一个行为——默认是阻塞等待，加上之后是直接跳过、去看下一行。放在多实例抢任务这个场景里，差别是决定性的：没有它，三个实例同时轮询会在同一批候选行上排成一队，一个等一个，轮询间隔越短越明显，等前面那个事务提交之后还很可能发现这行已经不满足条件了，白等一场。加上之后每个实例各拿各的，互不阻塞。配套的两件事也要说：一是领取条件是"排队中"或者"执行中但租约已过期"，按更新时间和 ID 排序，取的条数等于本实例当前的空闲槽位数；二是表上建了一个只索引排队中和执行中的行的部分索引，让这条语句不去扫描全部历史任务。代价是取到的不是全局严格有序的那几条——跳过被锁的行意味着放弃严格的 FIFO，换来的是无阻塞。容量实验里这条语句应用侧均值 4.1 到 5.6 毫秒、最大 85 毫秒，占排空时长不到 0.12%。

**要点**：FOR UPDATE 是行级排他锁、SKIP LOCKED 只改遇锁行为从阻塞变跳过、按空闲槽位数取条数、部分索引避免扫全表、代价是放弃严格 FIFO

**可能的追问**：
- 领到之后还要再判一次吗？要——轮询语句的可见性和行锁获取之间有时间差，所以领取时会先按 ID 锁住这一行，再读一次当前执行者和租约是否仍然有效；如果这次是接管但租约其实还没过期，就直接放弃不抢。
- 为什么不用 Redis 的 list 或者 stream？
- 三个实例的吞吐是线性的吗？

**另见**：Q2（领取语句怎么写）

### Q67 重新入库是"先删后插"，删和插之间检索会读到什么？事务隔离在这里起什么作用？

**答**：读到的是完整的旧版本，不会读到半新半旧。落库这一步是写入器开一个事务，然后扇出给所有落点——关系库的块表最先执行，向量库最后执行——每个落点内部都是先删这份文档的全部块再插新块。关键在于这两个落点确实在同一个事务里：应用只有一个数据源，一个走 MyBatis、一个走 JdbcTemplate，两者都加入外层开启的那个事务。在默认的读已提交隔离级别下，另一个连接看不到未提交的删除和插入，所以它读到的要么全是旧版本、要么全是新版本，版本切换对检索方是原子的。这件事是用集成测试验证的，不是读代码推断的：测试让第三个落点在两张表都已经删旧插新、尚未提交时停住，另一个连接这时读到的仍然是旧版本的 3 个块，放行提交后读到新版本的 2 个块，如果第三个落点抛异常，两张表一起回滚到旧版本。不这么做的后果很具体——检索会拿到一半旧版本的数字加一半新版本的，而且看不出哪块是哪版，对检测数据问答就是直接的事实错误。必须说清的边界是这个事务只覆盖 PostgreSQL，启用别的检索后端时它们的先删后插在事务之外，失败时可能半新半旧，这是上游原有的行为。

**要点**：两个落点加入同一个外层事务、读已提交下另一个连接只能看到旧版本、集成测试在未提交处停住验证、要么全旧要么全新、事务只覆盖 PostgreSQL

**可能的追问**：
- 为什么向量复用缓存不放进这个事务？因为缓存只省钱、不参与正确性，放进去的话块写入失败会把已经付过费的向量一起回滚掉，重试再付一次钱，正好和这件事的目的相反。
- 块表是物理删除吗？
- 换成两个数据源怎么办？

**另见**：Q48（增量更新）

### Q68 子任务为什么要用单独的线程池？父子共用一个池会出什么事？

**答**：会出典型的池内互等死锁。研究任务里主 Agent 可以委派子 Agent 并行做独立子目标，并发度是 2。如果父子共用一个线程池，池里 2 个线程被两个父 Agent 占着等子任务的结果，而子任务提交上来之后排在队列里等线程——线程在等队列，队列在等线程，谁都不会先释放，整个池就锁死了。所以子任务跑在一个专用的有界线程池上，核心和最大都等于最大并发子任务数 2，队列 32，满了直接拒绝。更关键的一句是：父 Agent 根本不在这个池上等待，委派工具返回的是一个异步流，父 Agent 的等待发生在它自己的执行线程上。这样即使子池全满，父也不占子池的资源。配套还有两件事：每个子任务的超时取"配置的 180 秒"和整次运行剩余时长中的较小值；每个子任务的错误在自己那条流上被吸收，超时、执行异常、额度耗尽都会先取消这个子会话，再转换成一个失败或部分完成的结果对象返回给父，所以一个子任务挂掉不影响同批其他子任务，父拿到的是一份结果加一条失败说明，最终结论标成部分完成。

**要点**：线程等队列队列等线程即池内互等死锁、子任务专用有界池核心与最大都是 2、父不在子池上等待而是等异步流、子超时取配置与剩余时长较小值、子任务错误在自己流上被吸收

**可能的追问**：
- 子任务之间怎么隔离？每个子 Agent 拿一个全新的会话，独立的消息历史、独立的已读证据集合、独立的取消控制，父的取消级联到子、子的失败不反向取消父；共享的只有预算、证据存储和知识范围。
- 返回给父的是什么？
- 委派名额怎么分配？

**另见**：Q56（多 Agent 的代价）

### Q69 研究任务的进度推送为什么用 SSE 而不是 WebSocket？

**答**：因为这条链路的需求是单向的服务端推进度，而 SSE 恰好自带我最需要的那个能力——断线续传。SSE 的重连是浏览器内建的，断开时会自动把最后收到的事件 ID 通过 Last-Event-ID 头带回来，服务端从那个序号之后接着推，客户端不需要自己记状态。我把每条 SSE 消息的 id 就设成事件序号，起始游标取 Last-Event-ID 和查询参数里的游标的较大值。WebSocket 是双向的全双工连接，但我这里没有客户端往上推的需求——取消是一个独立的 HTTP 请求，不走这条连接；而且 WebSocket 的重连和消息补发要自己实现一遍，还多一层协议升级和代理配置。更重要的一点是订阅和执行彻底解耦：执行由数据库队列驱动，SSE 只是持久事件表的只读视图，连接、重连、断线都不会调度执行也不会取消执行——很多流式接口把订阅和执行绑在一个请求上，浏览器切后台或者代理超时就杀掉一次已经花了钱的执行。代价是实现上它是每 750 毫秒轮询一次事件表，不是真推送，所以进度最多有一个轮询周期的延迟；另外同时在线订阅上限 100 个是进程内硬限，没有按用户或按任务分配配额。

**要点**：只需单向推送、Last-Event-ID 断线续传是浏览器内建的、取消走独立 HTTP 不需要双向、订阅与执行解耦连接不驱动执行、代价是 750 毫秒轮询有延迟

**可能的追问**：
- 为什么用轮询数据库而不是进程内发布订阅？因为执行者可能根本不在接这条连接的实例上，解耦之后任何实例都能服务任何任务的订阅。
- 任务结束时怎么保证不漏最后一条事件？不立刻关连接，而是循环把尾部事件读干净再结束——产物事件和终态事件是同一个事务提交的，先看到终态就断开会漏掉产物。
- 普通问答那条链路也支持续传吗？不支持，没有事件 ID、不认 Last-Event-ID，连接一断只能重问。

**另见**：Q57（流式输出）

### Q70 发版重启的时候在跑的长任务怎么办？你的优雅停机做了什么？

**答**：发版比宕机常见得多，所以单独处理。如果停机时什么都不做，任务要等租约过期才会被别人接管，生产默认最长 30 秒，而且崩在哪一步就得重做哪一步。我的流程是四步。第一，收到停机信号后第一件事是停止领取，本地快速路径和轮询都不再接新任务。第二，给所有在途任务打一个"请交还"的标记，这个标记不打断正在进行的模型调用，也不打断已经决定要执行的工具——粗暴打断等于自己制造一次需要重做的在途调用。第三，主 Agent 在下一次模型调用开始之前检查这个标记，命中就抛一个专门的交还信号停下来，这就是步边界。第四，服务识别出这是交还而不是真失败，把任务写回排队中、清空租约令牌和到期时间，写一条已交还事件，其他实例下一轮轮询就能领走，不用等租约过期。宽限期默认 20 秒，到点还没走到步边界的直接强制交还再取消本地执行，顺序是先交还再取消，被取消的执行因为写保护已经无法把任务写成失败。还有一条：交还不计接管次数，失联被接管才计——否则一次三实例的滚动发版就把 3 次的接管配额耗光了。实测 SIGTERM 场景恢复时间 P50 1.08 秒、P95 1.11 秒，远低于失联接管的约 5 秒，条件是模拟上游、租约 6 秒、心跳 2 秒、轮询 1 秒、重复 20 次。

**要点**：先停领取再打交还标记、不打断在途调用只在模型调用前的步边界停、写回排队中让别人立刻领走、宽限期 20 秒后先交还再取消、交还不计接管次数

**可能的追问**：
- 实现时踩到什么坑？Agent SDK 自带一个 JVM 关闭钩子，和我的停机逻辑并发执行谁先到不确定，它先到时会在"模型已决定调用工具、工具还没执行"的位置中断并关掉模型的 HTTP 传输，这个失败曾被写成任务失败；修法是把这类异常一并识别为"进程正在停机"，同样走交还。
- 那 SIGTERM 下还会重复调用吗？
- 毒任务怎么办？

**另见**：Q11（简历口径）

### Q71 这个项目里幂等有哪几种做法，分别用在什么地方？

**答**：三种，各管各的场景。第一种是幂等键加唯一索引：创建任务时客户端必须带一个请求 ID，任务表上有（所有者，客户端请求 ID）的唯一索引，插入语句写成冲突就什么都不做，两边都按这个键把行读回来，所以并发的重复请求只会建一条任务。关键是它不靠"先查再插"，不存在两个线程都查到不存在的竞态。这里还有一个常被忽略的坑：幂等键不能只对 ID 负责，还要对请求内容负责——我把会话 ID 加上服务端确认后的任务说明算了个指纹存进去，回查到已有任务时比对指纹，不一致直接报错，而不是悄悄返回一个内容不同的任务。第二种是条件更新：触发分块时那条更新带"状态不等于运行中"的条件，更新行数为 0 就说明已经有人在跑；用户侧补充条件用修订号做乐观并发，锁行后核对修订号，对不上就要求刷新。第三种是版本号加 fencing：执行者侧所有写入都核对四条——状态、epoch、租约令牌、租约未过期，epoch 每次领取严格递增，旧执行者醒来写不进去。另外事件序号是用一条 UPDATE ... RETURNING 在行锁里原子分配的，主键 (任务 ID, 序号) 再兜一层底。

**要点**：唯一索引加冲突不做再回读、幂等键要连内容指纹一起比、条件更新看影响行数、修订号做用户侧乐观并发、epoch 加租约令牌做 fencing

**可能的追问**：
- 唯一索引和 fencing 挡的是同一类问题吗？不是——唯一索引挡的是"同一个请求被提交两次"，fencing 挡的是"过期的持有者在写入点写脏数据"，后者靠唯一索引挡不住。
- 秒杀项目里你用的是哪一种？
- 事件序号为什么不用 MAX+1？

**另见**：Q7（fencing）

### Q72 你在秒杀项目里用分布式锁保证库存只扣一次，这里为什么是租约加 fencing？两套说法矛盾吗？

**答**：不矛盾，问的是同一批问题，只是被保护的资源不一样。秒杀那边保护的是库存这个共享数值，同一时刻只允许一个人改，锁的语义本身就够用；这里保护的是任务表里的一行以及它后续的所有写入，执行时长是分钟级，锁的持有期比秒杀长两三个数量级，所以"持有者猝死要等过期"和"持有者假死后醒来"这两件事的概率完全不同。具体差别我会主动讲：分布式锁靠持有者主动释放，持有者猝死就要等过期，更麻烦的是进程暂停——被 SIGSTOP 或者长 GC 暂停超过过期时间，锁自动释放、新执行者拿到锁，旧执行者醒来还以为自己持有。所以这里除了过期还加了 fencing token：每次领取 epoch 加一、发一个新租约令牌，每次写入都在短事务里核对，旧持有者醒过来也写不进去，这是锁本身给不了的。另一个差别是活性判断：秒杀的锁一般给一个固定过期时间，这里是短租约加心跳——租约 30 秒、心跳 10 秒续一次，租约只回答"我最近还活着吗"，和任务实际要跑多久解耦，所以失联最多 30 秒就能被接管，而不是等整个任务时长。

**要点**：被保护资源不同一个是数值一个是行与后续写入、持有期差两三个数量级、锁挡不住进程暂停所以加 fencing、短租约加心跳把活性与任务时长解耦、租约时间取数据库时钟

**可能的追问**：
- 为什么租约时间要取数据库时钟？因为各实例本机时钟有漂移，一个快了 1 分钟的实例会把别人正常的任务全部当成过期。
- 续租失败你就自杀吗？续租返回没更新到行就立刻本地取消，但续租时抛异常不自杀只记日志——数据库抖一下让所有长任务自尽代价太大，而且它反正也写不进去，由 fencing 兜底。
- 租约发现不了什么？

**另见**：Q7、Q29

### Q73 同样是限流，秒杀是入口削峰，你这个项目的限流是怎么做的？

**答**：这个项目里有两处，形态不一样。第一处是普通问答链路的公平排队，这是上游自带的：一次基于 Redis 的分布式排队，默认最多 10 路并发、排队最长等 15 秒、令牌带 30 秒租约、200 毫秒轮询；等不到不报错，而是把用户的问题和一条"系统繁忙"的助手消息落库、状态标成被拒，再在同一条 SSE 上正常收尾，前端不用为被限流单写一条错误路径。这一处和秒杀是同一个思路——拒绝要比拖垮好，因为模型调用是长连接、贵、占线程，并发上来所有人一起卡在上游，整站表现为"都很慢"而不是"少数被拒"。第二处是研究任务的槽位，默认每实例 2 个，这一处和秒杀恰好相反：队列满了不拒绝。创建接口仍然有一条本地快速路径，任务刚创建就直接扔给本机线程池，但线程池拒绝时不判失败，只是把它从本地在执行的集合里摘掉——任务本来就已经落库、处于排队中，下一轮轮询会有实例领走。差别在于一次提问用户在等一个几秒的回答，拒绝是可接受的；一个研究任务要跑几分钟，在门口拒绝毫无意义，让它排队才对。容量实验里 3600 个任务提交被拒 0 个就是这条路径在积压下的表现，代价是等待时延——300 个任务、3 实例、轮询 5 秒时排队等待 P50 242 秒、P95 470 秒。

**要点**：问答侧 10 路并发等 15 秒拒绝要比拖垮好、被拒也落库并在同一条流上正常收尾、研究任务槽位满不拒绝留在库里等轮询、短请求可拒长任务该排队、代价是等待时延 P50 242 秒

**可能的追问**：
- 要压等待时延怎么办？只能加实例或加槽位，降轮询帮助很小——轮询从 5 秒降到 1 秒吞吐只涨 10% 左右，等待几乎没改善。
- 问答那道按用户的防重锁真的生效吗？上游留了一个测评模式开关，打开时这道锁整个被跳过，而随程序发布的配置里它默认是打开的，所以当前默认配置下真正挡住并发的是那道全局闸门。
- 这些限流参数是压测出来的吗？不是，都是默认值，没上线也没有真实流量，只有模拟上游的容量基准。

**另见**：Q12（等待时延）

### Q74 这个项目最大的不足是什么？

**答**：最大的不足是没上线、没有真实流量，所有结论都是本地实验的结论——本机的数据库、本机的多个 JVM、本机的模拟上游，没有网络延迟、没有跨机时钟、没有真实并发用户、没有连接池和数据库负载的上限。往下具体说有几处。一是机制类的数字全部基于模拟上游，接管、上游容错、容量三项都是，真实供应商的慢是成串的、限流是有配额语义的，我这套是均匀分布加独立同分布。二是租约只能发现进程死掉或被冻住，发现不了进程活着、心跳照常、执行线程却卡住；20 次重复里正好撞到一次执行者在注入故障之前就静止了，临时库已删、没有线程转储，原因到现在没查出来，我把它留在报告里。三是优雅停机下仍然会重复 1 次模型调用，交还点本来在模型调用之前，理论上可以做到 0 重复，但框架自带的关闭钩子会先在"模型已决定、工具未执行"的位置中断，这个决定没落库，接手方只能再调一次；要消除得持久化这个决定，我没做。四是质量护栏只能说"未见显著下降"，不能排除 0.08 以内的下降。

**要点**：没上线没流量、机制数字全基于模拟上游、租约发现不了活着但卡住、优雅停机仍重复 1 次调用、质量下降不能排除 0.08

**可能的追问**：
- 那次执行者静止你打算怎么查？下次复现时保留临时库、加线程转储，现在只是设想。
- "活着但卡住"有什么通用的办法？让执行线程自己上报进度、心跳只在有进度时才续，我没做。
- 增量更新那块有没有类似的问题？有，表格是按行累加分组的，表中插一行会让该表后续的块全部失效；另外部分检索组件的先删后插不在同一个事务里。

**另见**：Q5、Q65

### Q75 如果要上线，还差什么？

**答**：首先差可观测性和发布流程这一层。现在能看的只有调用台账和事件表，没有告警、没有灰度、没有回滚演练，也没有面板把任务积压、接管次数、上游失败率这些数摆出来——出了事只能事后翻表。其次差真实供应商上的容错验证，现在的容错数字全在模拟上游上，真实的限流是有配额语义的、慢是成串的，上线前至少要在真实端点上做一轮带配额语义的压测。第三差几处已知的正确性缺口：增量更新里部分检索组件的先删后插不在同一个事务里，中途失败会留下不一致；表格按行累加分组导致表中插一行会让该表后续块的向量全部失效，这在经常改表格的场景下会白花很多钱。第四是权限那块的越权矩阵在服务端 Java 层直接驱动，没经过 HTTP 和登录拦截器，管理员路由的拦截只做了编译和规则审阅，上线前必须补端到端的测试。最后是容量，只测到 3 实例 × 2 槽位，数据库的拐点没找到，真实机器上要重新标一遍。

**要点**：告警灰度回滚与面板、真实端点上的容错压测、先删后插跨组件不在一个事务、表格分组导致整表后续块失效、越权矩阵不过 HTTP 层、容量拐点未标

**可能的追问**：
- 这几件里你会先做哪一件？先做可观测性，因为其它几件都要靠它才能知道有没有解决。
- 没有真实流量，灰度怎么做？只能先做开关和回滚路径，流量来了再说，这点我没办法绕过。
- 表格那个问题怎么修？改成按表结构分组或者给表格块做更细的内容寻址，我只想到方向，没实现。

**另见**：Q76（两周计划）

### Q76 再给你两周，你会做什么？

**答**：我会按"能不能减少已知风险"排，不追加新功能。第一周做两件：一是把那个已经写在报告里但没解决的质量下降查清楚——现在最可能的解释是把提醒挪到消息末尾让模型更早收手，因为后臂主调用更少、剩余预算更多，但这只是一个和数据相容的说法，要验得再做一个"提醒放末尾但不含剩余次数"的变体，跑同一批题再比一次配对差。二是把优雅停机那 1 次重复的模型调用消掉，做法是把模型已经决定的工具调用先落库再执行，接手方读到就不用重调；这件事影响的是发版时的重复计费，值得做。第二周做两件：一是"活着但卡住"的检测，让执行线程自己上报进度、心跳只在有进度时才续租，并且把那次静止的场景想办法复现出来、这次保留库和线程转储；二是把增量更新里跨组件的先删后插收进一个事务或者加补偿，再把表格的分组方式改掉。如果还有余力，就补越权矩阵的 HTTP 端到端测试。

**要点**：不加新功能只降已知风险、验证质量下降的解释、持久化工具调用决定消掉重复、进度式心跳查活着但卡住、先删后插与表格分组、补 HTTP 层越权测试

**可能的追问**：
- 为什么不先做监控？因为监控在没有流量的时候做不出真正有用的东西，这几件是现在就能验证的。
- 持久化工具调用决定会带来什么新问题？多一次写入，而且要保证决定和执行之间的幂等，我还没设计完。
- 两周做得完吗？质量那条要真调模型、排期不完全在我手里，我会先把它排在前面。

### Q77 哪部分是开源项目自带的，哪部分是你写的？

**要点**：上游给骨架 SSE 模型适配与基础问答链路、研究任务模块整体是我写的、七项改造是我写的、问答链路只动四处、删掉四个模块、解析质量属更早期工作

**可能的追问**：

## 补充　面经高频但项目未涉及（Q79—Q82，4 题）

> 近一年面经里高频、而这个项目确实没做的方向。四题一律先说没做，再给理解与成熟做法。

### Q79 MCP 你们用了吗？它解决的是什么问题？
**答**：**项目里没用**。上游自带过一套 MCP 工具接入，我在瘦身的时候整块删掉了，因为这个项目里的工具是自己实现的四五个固定工具——检索、阅读、追问、结束、委派，全都要在服务端做硬约束（参数只能收窄不能扩大、有未读候选就不许再搜、结束时逐条校验引用），接一层通用协议反而会把这些约束推到我控制不到的地方。我的理解是，MCP 解决的是"工具的供给侧"问题：让工具的定义和实现从应用里剥出来，变成可以被任意模型客户端发现和调用的独立服务，这样一套工具能被多个应用复用，也不用每接一个新模型就重写一遍适配。它不改变模型这一端的调用形状——模型看到的还是一批工具定义，还是原生 function calling 那一套。所以选不选它，看的是工具会不会被多个应用复用、以及工具是不是由别的团队提供。
**成熟做法**：工具由多个团队提供、或者同一批工具要被多个 Agent 应用复用时，用 MCP 把工具做成独立服务并统一鉴权与审计；单应用的几个私有工具直接在服务端实现更可控，不必为了赶协议而加一层。
**要点**：项目里删掉了没用、工具需要服务端硬约束、MCP 解决工具供给侧的复用与解耦、不改变模型端的调用形状、按是否跨应用复用来选
**可能的追问**：
- 那工具定义的顺序和内容对你有什么影响？——对提示缓存而言工具定义和系统提示同属最前面那一段，换个顺序整个请求就失配
- 通用协议接进来最大的风险是什么？
- 你的工具契约是怎么当权限边界用的？

### Q80 有没有考虑过 GraphRAG 或者知识图谱增强检索？
**答**：**项目里没做**，而且是反向的——上游自带一条图谱通道，我把它删掉了。删的理由有两条：一是它一直没有启用，留着只是维护成本；二是它当时是单实例单张图，没法按知识库限定召回范围，只能先全局召回再把不可读库的内容剔掉，这在我们加了权限隔离之后就是一条实打实的缺口——结果不泄露，但 TopK 的名额已经被别人的私有内容占走了，表现出来是"这个系统查不到东西"。我的理解是，图谱真正能解决的是向量检索的一个结构性短板：多跳关系型的问题，比如"哪些检测项同时受这两份标准约束"，这种问题的答案不在任何单个块里，向量检索按相似度取块永远拼不出来。代价是构图本身要额外的抽取成本，实体对齐做不好噪声很大，而且图谱的更新链路和文档入库是两套。
**成熟做法**：不把图谱当成替代方案，而是当成一条并行通道——实体与关系抽取后单独建图，只对识别为多跳、聚合类的查询走图路径，结果和向量通道一起做 RRF 融合；并且图必须能按知识库或租户分区，否则权限过滤只能在召回后做。
**要点**：项目里删掉了图谱通道、删因是未启用且只能召回后过滤、图谱解决的是多跳与聚合型问题、代价是抽取成本与实体对齐噪声、必须能按库分区否则是权限缺口
**可能的追问**：
- 多跳问题现在怎么处理？——靠 Agent 的多轮检索，模型自己决定下一步搜什么，这是用模型调用换图结构
- 图谱不能按库分区为什么就是权限缺口？
- 质量护栏那个数据集就是多跳问答，成绩说明什么？——它只能说明改动前后没有显著差异，不能说明这个系统多跳能力强

**另见**：Q36（召回前过滤为什么重要）

### Q81 Self-RAG、CRAG 这类"检索完自己判一下质量、不行就重来"的做法，你怎么看？
**答**：**项目里没做**这类质量判定。我做的是硬收敛，方向正好相反：同一个"查询语句加文档范围"最多允许两次，第三次直接拒绝，提示里写的是"换措辞不会让不存在的事实出现"；检索连续失败 2 次就进入检索受阻状态，之后再调检索直接拒绝，让模型拿已读证据收尾。之所以是这个方向，是因为我这条链路的主要风险不是"检索质量不够好"，而是"任务不收敛"和"把执行故障当成资料不存在"——一个分钟级、十几次模型调用的任务，每多一轮自我怀疑就是一次实打实的钱和时间。我的理解是，这类自纠错方案本质上是在检索后加一个评判者，判"这批材料够不够答"，不够就改写查询、扩大范围或者转向拒答；它解决的是幻觉和无效检索，代价是每轮多一次模型调用，而且评判者本身也会错。真正要上这套，前提是先有一个能衡量它有没有用的评测——不然只是多花了钱。
**成熟做法**：用一个轻量模型或重排分数的绝对值做"材料是否足够"的闸门，不够时最多改写一次查询，仍不够就直接拒答并说明已检索的范围；改写次数写死上限，并把"闸门触发率"和"拒答率"一起做成监控指标。
**要点**：项目做的是硬收敛不是质量判定、同一查询最多两次、连续失败两次禁止再搜、主要风险是不收敛与故障伪装成无资料、自纠错的代价是每轮多一次调用且评判者也会错
**可能的追问**：
- 那你怎么知道检索质量够不够？——不知道，检索侧的指标我没搭，这是缺口
- 硬收敛会不会把本来能答对的题答砸？——有可能，质量护栏里 15 题从作答改成了拒答，这是我能看到的最接近的证据
- 如果要加闸门，放在哪一步？

**另见**：Q55（硬收敛）

### Q82 检索回来的文档里如果藏了一句"忽略之前的指令"，会怎么样？
**答**：**项目里没做**针对提示注入的防护，这是我的一个明确缺口。能减轻一点后果的是几条本来为别的目的做的约束：工具集是服务端注册的，模型看不见没注册的工具，子 Agent 的工具集里根本没有委派和追问；工具参数由服务端校验，模型给的文档范围只能收窄不能扩大，超出创建时确认的范围直接拒绝；检索范围是按用户权限在召回之前求交算出来的，模型无论被怎么指挥都扩不大它能看到的库；引用编号由服务端分配，模型自己在正文里写角标会被判非法。所以最坏情况是这次任务的结论被污染，不会变成越权读别人的资料或者调用不该调的工具。但"结论被污染"本身已经够严重了——一份带引用、看起来很规范的报告，结论是被资料里的一句话操纵的。
**成熟做法**：把检索到的内容当成不可信输入处理：在提示里用明确的分隔结构把资料和指令分开并声明资料内的指令一律不执行；入库时对已知的注入模式做扫描和标记；输出侧再加一道校验，检查结论是否只由证据支持（和忠实度校验同一道工序）。权限和工具边界必须在服务端兜底，不能指望提示词。
**要点**：项目未做注入防护、工具集与参数由服务端约束、检索范围按权限召回前求交扩不大、引用编号服务端分配、最坏是结论被污染而非越权
**可能的追问**：
- 为什么说权限这条能兜住？——范围是按任务所有者当前权限每次领取时重算的，不经过模型
- 入库侧能做什么？
- 多 Agent 下污染会扩散吗？——子 Agent 回传的是压缩结果，父端入账时还会校验证据 ID 是否在自己已读集合里，但内容本身不校验

**另见**：Q36、Q54

## 附录 A　项目没有实现的部分，成熟业务会怎么处理

这一节是给自己看的，不是背诵稿。面试里被问到"这个东西你没做，那该怎么做"时，能顺着往下说；被问到"你觉得还差什么"时，可以从这里挑两三条讲。左边一律如实写"没做"，右边写一个真实生产系统的常规解法——不是最先进的方案，是一般团队会落到的那种。

### A.1 可观测性与运维

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| 没有线上监控与告警。可观测性只到调用台账（每次模型调用一条记录）和事件表，要看情况得自己去查库。 | 三件事分开：指标进时序库（任务排队长度、各状态任务数、领取语句耗时、租约过期数、每分钟模型调用数与失败率），链路进分布式追踪（一个任务 ID 串起十几次模型调用和检索），日志结构化后集中检索。告警定在**症状**上而不是资源上：排队积压超过 N 分钟、接管率突增、错误完成数 > 0、单任务成本超过分位阈值。 |
| 没有灰度、没有回滚演练。改动是整体发布的。 | 新旧执行逻辑按任务比例分流（任务行上记一个变体标记），先放 1%，看接管率与成本分位；提示词和模型版本同样走开关，能在不发版的情况下切回。回滚要定期演练，不然真出事时没人敢按。 |
| 没有成本归因与预算闸门。台账能算出一个任务花了多少 token 当量，但没有按用户、部门、知识库聚合，也没有超额拦截。 | 台账的每条记录打上租户 / 部门 / 场景标签，日结进一张成本表；给每个租户配月度预算和速率上限，接近阈值时先降级（换小模型、减少探索轮数），超了直接拒绝新任务而不是让账单继续涨。这是 LLM 应用后端和普通后端最不一样的一处运维职责。 |
| 没有对过账单。计费输入是按供应商文档折扣折算的 token 当量。 | 每月拿供应商账单和自己的台账对一次，差额超过百分之几就查（漏记的重试、没落账的取消、缓存写入没算）。没对过账的成本数字只能内部参考，不能对外承诺。 |

### A.2 长任务与队列

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| 租约发现不了"进程活着、心跳照常、执行线程卡住"。只能等任务 300 秒总时长兜底。20 次接管实验里正好撞上过一次，原因没查出来。 | 心跳不由独立线程无条件发，而是**由执行线程的进展来驱动**：执行者每完成一步才推进一次进度水位，续租时带上这个水位，超过一定时间没有进展就主动放弃租约。再加一层：每步设自己的超时，步内卡死由步超时兜底，不依赖任务总时长。线上还要有线程转储的自动采集（卡住时自动 dump 一次），否则事后无从查起。 |
| 优雅停机仍会重复 1 次模型调用。模型已经决定要调用哪个工具、工具还没执行时被框架的关闭钩子中断，这个决定没落库。 | 把"模型的决定"当成一个需要持久化的状态：模型返回工具调用后先落库，再执行工具。接管方读到"有决定、无结果"时直接执行那个工具，不重新问模型。代价是每轮多一次写库，换来的是真正的断点续跑。 |
| 毒任务只是就地判失败（接管 3 次后），没有死信队列，也没有人工重放入口。 | 终止的任务进一张死信表，带上最后一次的事件快照和失败原因；运维有一个重放接口，可以改参数后重新入队，并记录是谁在什么时候重放的。没有重放入口的话，一个可恢复的故障也只能让用户自己重新提交。 |
| 队列没有优先级、没有公平调度，按更新时间先进先出。一个用户批量提交能把队列占满。 | 领取语句按（优先级、租户配额、入队时间）排序，每个租户有在跑任务数上限，超了就跳过它的任务去领别人的。这就是加权公平排队，做法和秒杀那边的令牌桶不同：不是拒绝，而是让出位置。 |
| 没有自动扩缩容。容量实验只测到 3 实例 × 2 槽位，加速比 2.95，没找到数据库的拐点。 | 按队列积压长度和等待分位做水平扩缩（K8s 的 HPA 接自定义指标），并事先压出数据库的拐点：领取频率 = 实例数 ÷ 轮询间隔，这个值和连接池上限一起决定什么时候数据库变成瓶颈。到了拐点就改成长轮询或通知触发，而不是继续缩短轮询间隔。 |

### A.3 上游容错

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| 重试没有全局抑制。每次调用最多重一次，但故障率高时全局重试量仍然会放大上游负载（50% 无响应那一档最明显）。 | 重试预算令牌桶：全局限制"重试占总请求的比例不超过 10%"，桶空了就直接失败不重试。再加舱壁隔离，不同场景（问答 / 研究 / 入库）用各自的连接池和配额，一个场景把上游打满不会拖垮其他场景。延迟敏感的路径可以用对冲请求（等到 P95 还没回就并发发第二个），但要和重试预算一起算。 |
| 只注入过一种故障（向量化接口无响应）。限流、5xx、流中途断开、延迟分布都有旋钮但没跑过基准。 | 把故障注入做成常态化的演练：每类故障各有一条基准线，每次改容错逻辑都重跑一遍，结果进回归门禁。成熟一点的做法是在预发环境按比例注入真实故障（chaos 工程），而不是只在实验脚本里跑。 |
| 熔断的修复没有进入实验数字，因为评测入口绕过了模型路由层。 | 实验入口必须和生产走**同一条链路**。做不到的话，至少要在文档里写明这一段没有被覆盖——这正是该项目的做法，但正确的解法是把评测入口改成走完整链路。 |
| 没有多供应商的主备与自动切换。有候选模型的熔断回退，但向量化这条路不跨模型回退（向量不可跨模型比较），供应商整体不可用时就是不可用。 | 向量这条路的正确解法不是切模型，而是**双写索引**：同一批文本在两个模型下各建一套索引，主模型不可用时整体切到备用索引查询。代价是存储和入库成本翻倍，所以通常只给核心库做。对话模型这边则是标准的主备加权路由 + 健康检查。 |

### A.4 RAG 与答案质量

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| "先读后引"只保证被引用的证据确实被读过、在允许范围内，**不保证陈述和证据的内容一致**，没有句子级蕴含校验。 | 生成后加一道忠实度校验：把每条断言和它引用的原文送给一个小模型（或 NLI 模型）判是否被支持，不支持的断言要么删掉要么标灰。线上按比例抽样校验（全量太贵），不通过率进监控指标。 |
| 没有线上答案质量的持续评测。质量护栏只在改动前后各跑了一次，用的是公开多跳问答数据集，不是业务语料。 | 两套并行：一套是固定的回归题集，每次改提示词或换模型都跑，作为发布门禁；一套是线上采样 + 人工或模型标注，形成随时间变化的质量曲线。业务语料的题集要业务方一起标，这是成本最大也最不能省的一步。加上用户侧的隐式信号（复制、追问、点踩）做早期预警。 |
| 没有"检索到的内容是否足以回答"的判定。空检索会短路成一句固定话术，但"检索到了但都不相关"会照样送进模型。 | 在检索后加一道相关性闸门：用重排分数的绝对值（不是名次）设阈值，或者让小模型判一次"这些材料能不能回答这个问题"，不够就直接回"资料不足"并给出已检索到的范围。宁可拒答也不要让模型在不相关材料上编。 |
| 混合检索只剩向量一条通道，关键词与图谱通道已被删除。融合框架还在，但实际是单路。 | 向量 + 关键词（BM25）是默认配置，因为两者的失败模式互补：向量搜不到精确的型号、编号、条文号，关键词搜不到同义改写。用 RRF 按名次融合，不比较原始分数。这个项目删掉关键词通道是范围取舍，不是说它不该有。 |
| 表格分块按行顺序累加，表中插一行会让该表后续所有块的向量全部失效。 | 换成内容定义的切点（对内容做滚动哈希，切点由内容决定），插入一行只影响局部。这是备份和同步系统里的老办法（rsync、dedup 存储），用在分块上是同一个道理。 |
| 问答链路的 SSE 不支持断线续传，连接一断这一轮就得重问；断点续传只做在研究任务那条链路上。 | 两条链路用同一套：事件按序号落库，SSE 的 id 就是序号，重连带 `Last-Event-ID` 续推。代价是即时问答也要为每个片段写库，通常折中成"只持久化阶段性事件，不持久化每个 token"。 |

### A.5 数据与权限

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| 越权矩阵在服务端方法层驱动接口，不经过 HTTP 与登录拦截器；管理员专属路由只做了规则审阅。 | 关键的鉴权断言要有一层端到端的 HTTP 测试（带真实的登录态和拦截器），哪怕只覆盖几条代表性路由。方法层的矩阵负责广度，HTTP 层负责证明"拦截器真的挂上了"。 |
| 授权变更没有审计日志，事后查不到谁在什么时候把哪个库开给了谁。 | 权限变更走独立的审计表，只追加不修改，记录操作者、对象、前后值、时间、来源 IP，保留期按合规要求定。企业资料场景里这通常是硬性要求，不是加分项。 |
| 已生成的回答和来源快照在撤销授权后对提问者仍然可见，没有回收。 | 分两种口径：一般做法是承认"已读即已泄露"，只管住新的读取；高敏场景则把回答里的引用做成**动态解引用**——每次打开历史消息时按当前权限重新校验引用可见性，不可见的折叠起来。后者要付出每次读历史都查权限的代价。 |
| 块表和向量表仍然整份删掉重插，块 ID 每次重新生成，逻辑删除的旧行不断累积。 | 按内容哈希做真正的差分写入：只删改动的块、只插新增的块，块 ID 用内容哈希保持稳定（这样引用也不会因为重新入库而失效）。旧行定期归档或分区淘汰。 |
| 外部索引组件（ES、图谱、Milvus）的先删后插不在同一个事务里，失败时可能半新半旧。 | 事务只能覆盖一个数据库，跨组件要靠别的办法：本地消息表 + 重试做最终一致，或者写成幂等的版本化索引——新版本写到一个新的别名下，全部成功后原子切换别名。后者是搜索引擎里换索引的常规做法。 |

### A.6 工程流程

| 项目里没做 | 成熟业务怎么处理 |
| --- | --- |
| 一个人做的，没有代码评审。毒任务上限、压缩阈值、轮询间隔这些默认值只有一个取值，没有在不同负载下检验过。 | 这类"拍出来的常数"要么做成可热更新的配置并在监控里观察其后果，要么用一次容量实验定出取值区间再写死。评审的价值恰恰在这里——一个人看不出自己默认值的盲区。 |
| 事件表是续跑的唯一依据，但事件格式没有版本化。老版本事件里没有原始请求，这类历史任务接管后只能从头执行。 | 事件带 schema 版本号，重建时按版本分支解析；下线旧版本前先跑一次迁移把老事件补齐或标记为不可续跑。凡是"靠回放恢复状态"的系统都必须先解决事件演进，否则每次改格式都会留下一批不可恢复的历史数据。 |

## 附录 B　可以反问面试官的问题

最后一轮"你有什么想问我的"不要浪费。这几条既是真问题，也顺带说明我关心什么。

- 团队的大模型应用在线上是怎么保证长任务不丢的？是把状态放在数据库里，还是靠消息队列加重试？遇到过发版打断正在跑的任务这类问题吗？
- 模型调用的成本现在是怎么归因到具体功能、具体用户甚至具体一次请求的？有没有类似调用台账的东西，还是只能看供应商账单的总数？
- 提示缓存在你们线上的实际命中率大概什么水平？有没有因为提示结构变化导致命中率掉下去、事后才发现的情况？
- 团队有没有一套固定的评测集和判定规则？改了提示或者换了模型之后，怎么判断答案质量没有变差——是看均值，还是有配对比较和运行间噪声的概念？
- 上游供应商不稳定的时候，你们的超时、重试和降级是怎么设的？有没有区分"调用失败"和"确实没检索到"这两种情况？
- 我这个项目最大的短板是没有线上流量。如果我进来，团队里有没有能让我尽快接触到真实流量和线上问题的位置？
