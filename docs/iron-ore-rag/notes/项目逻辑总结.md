## 面试自我介绍（项目段）

> 第二个项目是一个工业检测文档的 RAG 问答和研究 Agent 平台，基于开源 Ragent 二次开发，资料来自校企合作课题的检测标准。我的工作主要在两头。一头是资料入库质量：我发现 PDF 经 MinerU 解析后，检测标准里最关键的"数字 + 单位"会成片丢失，而全部文档都开 OCR 又慢又贵，所以我在入库时加了一道解析质量闸门，用 PDFBox 读文字层，审计数字保留率和空槽，不合格的文档才改走 OCR 重新解析并择优，数值事实覆盖率从七成提到了九成以上；在这个基础上，我还做了 Excel 调研表的版面切分，以及标准号、代替关系和术语表的知识治理。另一头是研究型长任务的后端问题。在真实供应商上做批量回归时，我遇到过一批任务集体卡死在超时上，原因是几层超时配成了同一个值，而且检索失败被吞成了空结果，看起来就像"资料不存在"。所以我做了分层截止时间和带抖动的有限重试，把执行失败和查无结果分开处理；同时用心跳租约和 epoch 写保护，让任务在进程被 `kill -9` 后几秒内由别的实例接管续跑。成本上，我给每次模型调用记台账，定位到提示缓存几乎不命中，根因是易变内容写进了首条系统消息，修复后命中率到了 80% 左右，计费输入降了约七成。这些改动我都是先定好评测门槛再写代码，像混合检索这种没过门槛的方案，就保持默认关闭。

正常语速约一分半。要压到一分钟左右，删掉"在这个基础上……知识治理"一句和超时事故那几句。

## 一、普通问答

### 1. 入口：防重、排队与并发许可

- **请求**：`GET /rag/v3/chat`，带问题文本、会话 ID（可空，空表示新会话）和深度思考开关；用户身份取自登录态（Sa-Token）。
- **防重复提交**（不是限流）：控制器上的 `@IdempotentSubmit` 切面用 Redisson `RLock`，键是 `idempotent-submit:key:{userId}`。`tryLock()` 不等待，抢不到就返回"当前会话处理中"。
  - 锁在控制器方法返回时就释放，此时 SSE 已建好、请求已入队。所以它只挡几乎同时的重复点击，挡不住一个用户同时挂多条流。
  - **默认配置下这把锁不生效**：`ragent.eval.enabled: true`（上游的"测评模式"）会让切面直接放行。
- **拿许可之前**（在控制器线程里同步完成）：
  1. 创建 SSE 连接，超时 5 分钟。
  2. 会话 ID 为空就用雪花算法生成一个。会话记录要等写用户消息时才建。
  3. 生成任务 ID，并把归属写进 Redis：`ragent:stream:owner:{taskId}` = userId，30 分钟过期。
  4. 构造事件处理器：立刻发 `meta` 事件（会话 ID、任务 ID），在本地任务表注册，并回查一次 Redis 里的取消标记。前端在排队前就拿到了任务 ID，所以排队时也能点停止。
  5. 进入全局公平排队。
- **全局公平排队**（Redis 实现，所有实例共享）：
  - **入队**：生成一个排队用的 requestId（雪花 ID，不是任务 ID）。先写存活标记 `rag:global:chat:entry:{requestId}`（过期时间 = 最长等待 + 5 s），再 `ZADD` 进有序集合 `rag:global:chat:queue`。score 是全局自增序号，所以严格先进先出。
  - **轮询与唤醒**：入队后立刻试抢一次，抢不到就每 200 ms 轮询一次。有许可释放或有人重新入队时，通过 Redis 发布订阅通知各实例提前唤醒。
  - **Lua 脚本**（整个脚本是原子的）：
    - 取队列前"可用许可数 + 16"个条目，顺手删掉存活标记已过期的僵尸条目（实例崩溃留下的）；
    - 算出本请求在存活条目里的名次，名次小于可用许可数时，把自己移出队列并返回原 score；
    - 可用许可为 0 时不调脚本。
    - 所以它判断的是"是否落在队头前 N 名的窗口里"，不是严格的"是否队头"。
  - **抢许可**：用 Redisson 的可过期信号量 `RPermitExpirableSemaphore`（`rag:global:chat:semaphore`，许可数 10，所有实例共享）。`tryAcquire(0, 30 s)` 不等待：有空闲就返回许可 ID，没有就返回 null。返回 null 时用原 score 重新 `ZADD`、补写存活标记，按原顺序重新排队。
  - **状态机**：每个排队请求是一个 Ticket。PENDING 只能经一次 CAS 变成 GRANTED、TIMED_OUT 或 CANCELLED 之一，回调至多执行一次。排队期间 SSE 完成、超时或出错，就出队。
  - **等待上限 15 s**：超时后把用户问题和一条"系统繁忙，请稍后再试"（状态 REJECTED）落库，再在同一条 SSE 上依次发 `meta`、`reject`、`finish`、`[DONE]`。被限流也按正常流程收尾，前端不用单写错误分支。
- **拿到许可**：提交到入口线程池执行。线程池核心数 = 最大数 = 10，用 `SynchronousQueue` + `AbortPolicy`，并用 TTL 包装传递用户上下文。
- **许可释放**：在包装任务的 `finally` 里释放，也就是入口任务的同步部分结束时。
  - 正常是首包到达后释放；出错、空检索、开头就发现已取消而提前返回的，也在这里释放。
  - 入口线程池拒绝提交、拿到许可时请求已取消或已超时，都会立即释放。
  - 30 s 租期兜底，防止进程崩溃后许可一直占着。
  - **所以"10 路"限制的是"拿到许可 → 首包"这一段。** 首包之后，每条流占一个模型流线程直到结束（核心 max(2, CPU/2)，最大 max(4, CPU)，队列 200），整段生成的并发由这个池约束。
- **入口线程做的事**（细节见下一节）：建 trace → 读写会话记忆 → 改写 → 检索 → 装来源、组装提示词 → 启动模型流，阻塞等首包。
  - **首包**：第一段正文或思考。首包预算标准档 30 s，深度思考档 120 s。
  - **首包前失败**（启动异常、出错、超时、没内容就结束）：记一次熔断失败（连续 2 次打开，持续 30 s），取消这条流并丢掉它缓冲的输出，换下一个候选模型；全部失败才报错。首包之后出错不再切换。
  - **输出交接**：首包前的输出先缓冲，首包到达时由入口线程回放，之后由模型流线程直接推送。入口任务随即返回，释放许可。

### 2. 主链路（拿到许可后，在入口线程里按顺序执行）

- **trace**：
  - 先插一条 `t_rag_trace_run`，记 traceId、会话 ID、任务 ID、用户 ID、问题和开始时间，状态 RUNNING；插完回查一次取消。run 是拿到许可后才插的，所以排队时间不计入。
  - 各阶段由 `@RagTraceNode` 切面写进 `t_rag_trace_node`：改写拆分、检索引擎、每个子问题的多通道检索、标题生成、模型路由、首包。另外记一个"用户首包"节点，是从开始到正文第一个字的时间。
  - 结束时做条件更新，只允许 RUNNING → SUCCESS / ERROR / CANCELLED，先写的终态生效；同时记耗时和错误信息（截到 1000 字）。
- **会话记忆**：
  - **读**：在线程池里并行读两样东西。
    - 最近 8 轮原文（16 条），去掉回答里的引用角标；
    - 最新一条摘要，包成系统消息放在历史最前。
    - 任一边失败就退化成不带摘要或空历史，不让问答失败。先读历史，再写本问。
  - **写**：把用户问题落库，拿到消息 ID。新会话在这一步同步调快速模型生成标题，并建会话记录。
  - **摘要**（异步）：
    - **触发**：每条助手消息落库后检查一次，被中断、被拒绝、"未检索到"这几种助手消息也算；用户消息落库不触发。用 Redisson `tryLock`（用户 + 会话）防并发，抢不到就跳过。
    - **条件**：该会话的用户消息数 ≥ 9。取最近 8 条用户消息，最早那条是原文窗口的起点。如果上一版摘要记的 `lastMessageId` ≥ 起点，说明摘要和原文窗口还连得上，不压缩。
    - **压缩**：把 `lastMessageId` 之后到倒数第 4 条用户消息为止的原文，连同上一版摘要，交给快速模型合并成一行（400 字上限只写在提示词里，代码不截断）。结果插成一条新摘要记录，并更新 `lastMessageId`。
    - **效果**：摘要和原文窗口重叠约一半，大约每 4 轮重做一次。
- **改写与拆分**：
  1. 先按术语映射表做规则归一化，把业务别名换成标准词。
  2. 把改写提示词、最近 4 条 user / assistant 消息（过滤掉摘要）和归一化后的问题交给快速模型，返回 JSON：`rewrite`、`should_split`、`sub_questions`。
  3. 以 `should_split` 为准：要拆就用子问题并去重，不拆就只用 `rewrite`。
  - 调用异常、返回的不是合法 JSON、`rewrite` 为空，都回退成归一化后的问题这一条。
  - 改写开关关掉时，只做归一化，再按标点切句。
- **检索范围**（权限，在召回之前）：
  - 用登录态的 userId 和角色跑一条 SQL，求出可读的知识库：
    - admin 全部可读；
    - 所有者可读自己的库；
    - PUBLIC 库所有登录用户可读；
    - PUBLIC / RESTRICTED 库上授权给本人或其角色的可读；PRIVATE 库忽略授权；
    - 以上都要求库未删除。
  - 结果再和"全部未删除知识库的 collection"求交，得到本次的检索范围。
  - 每个子问题算一次，挂在检索上下文里，各通道只读不判。范围为空就不检索，直接走空检索短路。
  - 放在召回之前，是为了不让无权的高分块先占掉 TopK 名额、过滤后结果变少。
- **检索预算三段**（启动时校验逐段收窄）：
  - 每通道召回 20 条；
  - 候选池 40 条，是重排的成本上限；
  - 最终进模型 10 条。这是整次请求的总额度，在子问题之间均分，余数给前面的题；分到 0 条的子问题跳过检索。
- **多通道召回**：子问题之间并行，子问题内各通道也并行。单通道超时 15 s，超时或异常都按空结果降级，其他通道照常。
  - **向量通道**（默认开）：
    - 查询向量实时调 embedding，并归一化；
    - 先 `SET hnsw.ef_search = 200` 和 `iterative_scan = relaxed_order`，避免带过滤条件时召回不够；
    - 一条 SQL：`collection_name IN (范围) ORDER BY 余弦距离 LIMIT 20`；
    - 结果在应用侧先按分数排序，再截断。
  - **中文全文通道**【10 月新增】【默认关】：
    - 用 jieba 加术语表分词，标准号、化学式、带单位的数值整体切出，同义写法补成规范写法；
    - 在 `content_tsv` 上做 `@@` 查询（GIN 索引）；
    - 应用侧按库预存的词项统计算 BM25（k1 = 1.2，b = 0.75），取前 20 条回表拿正文。
  - **联网通道**【默认关】。
- **后处理链**（按顺序执行；某个处理器抛异常就跳过它，链继续）：
  1. **去重**：按 chunkId。
  2. **RRF 融合**：只看各通道里的名次，按 权重 / (k + 名次) 累加，k = 20。启用的通道多于一条才融合，融合后截到候选池 40 条。
  3. **候选池守卫**：融合关闭或失败时，同样截到 40 条。
  4. **元数据富化**：回表补文档名、版本、块序号、sheet、单元格等；另拼一段"文档名 + 向量文本"专给重排看，进模型的仍是原文。
  5. **重排**：qwen3-rerank。模型返回的头部排前面，没进头部的候选按原顺序追加，整池继续往下传，最终取几条留到请求级再定。
  6. 【10 月新增】【默认关】元数据加权、分数融合、重排分阈值。三个都要求重排开着。
- **请求级选择**：每个子问题取自己额度内的前几条（公平回填开关【默认关】），再全局去重，得到一份唯一、有序的块列表。提示词、来源编号、证据片段和离线评测都用这一份。
  - 一条都没选出来时短路：直接推"未检索到与问题相关的文档内容。"，这句话也作为助手消息落库，不调生成模型。
- **装来源 → 注入引用编号 → 组装提示词**（来源要先装好，编号才统一）：
  - **来源**：把最终块按文档归并，每篇取最高分的块，按分数降序从 1 编号。回表补来源类型、外链、版本、摘录、标准号、"已被代替"标记和解析复核结论。
    - "已被代替"是读取时由文档元数据算出来的【10 月新增】。
    - 来源随完成事件下发，并随助手消息落库。
  - **引用编号**：上下文里先只写内部文档 ID 作锚点。引用开关开着时，换成编号并追加引用规则；关着也要把内部 ID 抹掉，免得漏进模型可见的文本。
  - **消息序列**：
    - 系统提示词：智能体配置里的问答模板；
    - 对话历史：摘要在最前；
    - 一条用户消息：证据加改写后的问题。多个子问题时，按子问题分段编号列出。
  - **上下文渲染**：按文档聚合，文档之间按"最佳块名次"排序，文档内按块序号还原原文顺序；刻意不写文档标题。温度 0。深度思考档会发 `enable_thinking`，并解析思考内容。

### 3. 流式输出与落库

- **事件类型**：
  - `meta`：排队前就已发出；
  - `message`：分思考和正文两类，按码点切块（不劈开代理对）；
  - `finish`：带消息 ID、新会话的标题、来源和消息状态；
  - `[DONE]`；
  - 另有 `cancel` 和 `reject`。
- **完成**：
  - 正文在内存里累积。完成时一次性把助手消息落库：正文、思考、思考耗时、来源、证据片段，以及它回复的用户消息 ID。
  - 然后依次发 `finish`、发 `[DONE]`、注销任务、关闭连接。
  - 落库失败只记日志，仍然发 `finish`（消息 ID 为空），代价是这条回答不进历史。
- **出错**：注销任务，并以异常关闭连接，不发 `finish` 和 `[DONE]`。半截内容不落库，只有取消时才按"被中断"落库。
- **推荐追问**：不在这条流里。前端点击后另调一个接口，用落库的证据片段生成。

### 4. 用户取消

- 取消是一条独立的 HTTP 请求，带任务 ID。
- **校验归属**：读 Redis 的 `ragent:stream:owner:{taskId}`，只有所有者或 admin 能停。
  - 任务不存在和不属于自己，返回同一句"任务不存在或无权操作"，不泄露任务是否存在。
  - 任务正常结束时不删归属键，只清本地任务表和取消标记。否则用户在结束那一瞬间点停止，会被误判成越权。
- **先打标记、再广播**：
  1. 写取消标记 `ragent:stream:cancel:{taskId}`（30 分钟过期）。标记是给"还没在本地注册"的任务看的。
  2. 按任务 ID 把 trace 收尾成 CANCELLED。
  3. 发布到 `ragent:stream:cancel` 频道，所有实例（包括自己）都在监听器里处理。
- **各实例本地处理**：
  1. 查本地任务表，命中才处理。
  2. 用 CAS 把 `cancelled` 从 false 置成 true，保证只处理一次。本地只有这一个布尔位，没有"运行中 / 已取消"状态；"RUNNING → CANCELLED"指的是 trace 表上的条件更新。
  3. 收尾 trace。
  4. 模型流句柄已绑定的，就取消它：先置标志，再调 OkHttp 的 `call.cancel()` 断开连接。
  5. 用另一个 CAS 保证收尾只做一次：先把半截回答落库（正文非空才落，状态"被中断"），再发 `cancel`（带消息 ID）和 `[DONE]`，然后关闭连接。
- **三个竞态窗口**：
  - 取消早于本地注册：注册时回查 Redis 标记。
  - 取消早于模型句柄绑定：绑定时发现已取消，就立刻取消。
  - 取消早于 trace 插入：插入后回查。
  - 取消置位之后，所有流式回调先检查取消位，直接返回。
- **只有显式停止才会取消模型流**：SSE 断开或超时只出队、关闭发送器；模型会继续生成，结果照常落库。

## 二、文档入库

### 1. 上传登记（同步，只登记不干活）

- **入口**：`POST /knowledge-base/{kb-id}/docs/upload`，要求对该库有管理权限。请求带一个文件或一个可下载的 URL，外加摄取配置（解析档位、分块预算）。
- **上传限流**：最外层过滤器在解析 multipart 之前就拦截，免得先落临时文件。它抢 Redisson 可过期信号量 `rag:document:upload`：最多 10 个并发，等 5 s，租期 300 s，抢不到返回 429。
- **处理顺序**：
  1. 纯校验放在第一个副作用之前：来源类型、定时刷新配置、摄取配置。反过来的话，存了对象再抛错，就会留下孤儿文件。
  2. 存原文件到对象存储：S3 兼容的 RustFS / MinIO，或阿里云 OSS。
     - 文件来源按字节加文件名探测 MIME。
     - URL 来源先 `HEAD` 查大小，不超过 50 MB 才流式下载后再存。
  3. 用分块阶段同一张解析器路由表预检。没有解析器认领这个类型，就删掉刚存的对象并拒绝，避免"上传成功、分块必失败"。
  4. 从文件名解析出文档键和版本号（如 `V1.2`）。
  5. 插一条 pending 文档记录就返回。上传本身不触发摄取。
- **大文件客户端直传**【未实现】：
  - 给客户端短期受限的上传凭证（预签名 URL / STS）、分片上传、断点续传、合并对象、上传完成后回调登记，代码里都没有。面试只能当"要支持大文件我会这样做"来讲。
  - 现状是服务端 multipart 上传，单文件 50 MB，单次请求 100 MB。
  - 代码里有预签名 URL，但那是服务端自己往对象存储流式写入用的，不发给客户端。

### 2. 触发分块

- **手动触发**：管理员点"开始分块"，发一条 RocketMQ 事务消息。
  - 本地事务是一条条件更新：`status → RUNNING WHERE status <> RUNNING`。更新 0 行说明已经有人在跑，抛"正在进行中"，半消息回滚。防重复触发靠的是数据库条件更新，不是应用层判断。
  - 回查器只看状态是不是 RUNNING。
  - 本地事务成功，消息才会投递，消费者收到后执行摄取。
- **URL 定时刷新**：不走 MQ，检测到内容变化后直接在线程池里分块。
- **兜底**：定时任务每 60 s 扫一遍，把停在 RUNNING 超过 30 分钟的文档置为失败。这防的是进程崩溃后文档永远卡住、连重试入口都点不动。

### 3. 摄取内核（手动、定时、离线导入都走这一条序列）

#### 类型识别

- 按字节再探测一次 MIME，识别不出直接失败；结果回填到文档记录。

#### 解析

- 按"MIME × 解析档位"四级查找解析器，全部不命中就显式报错，不兜底到通用解析器。
- PDF、Word、PPT 走 MinerU；Excel 快速档走 POI，保真档走 MinerU。
- 调 MinerU 前要先抢分布式许可 `rag:mineru:parse`，最多 5 个并发。
- 产出 7 类带类型的结构块：标题、段落、列表、代码、表格、HTML 表格、图片。后面分块按类型分发。
- **Excel 版面切分与表头识别**【10 月新增】（默认开）：
  - **问题**：原来每个 sheet 当一张表、第 1 行当表头。调研表一个 sheet 里有好几张表，标题行冒充表头，标题和说明也被当成数据行。
  - **做法**：
    - poi读出表格，逐个读取非隐藏的sheet，将单元格变为二维文字网络；
    - 找到独立区域：将有内容的格子，以及有值的合并单元格覆盖的格子（看左上角是否有值，并且当前单元格是否落在合并单元格范围内），按照上下左右和斜角相邻关系连接起来，隔着整行或者整列空白的内容会变为不同的区域，因此一个sheet可以识别出多块表格或者文字；
    - 在区域内区分表题、说明和表格，在一块表格数据开始之前，代码找连续的单格行，一行只有一个普通单元格或者合并单元格有内容的，将其最后一行作为表题（文字不超过30字），更前面的作为说明；表头则是去掉上面的看表格的第一行，如果，这一行的单元格都不超过40字，且不到一半的有内容单元格看起来是数字就将它作为列名；
    快速档（POI）里只看单元格、合并和位置，按空行、空列把 sheet 切成多个区域。区域开头的单格行当表题或说明，结尾的当段落；中间横跨一半以上宽度的当分段，从这里拆表。每张表第一行当表头，像数据就按无表头处理。
  - **进分块**：表题挂在表格上，随每一块进入两份文本；每个区域单独分节，几个区域不会被装进同一块。
  - 开关 `rag.ingestion.excel-layout.enabled`；关掉就回到整张 sheet 一张表。

#### 解析质量闸门【10 月新增】

只作用于 MinerU 解析的 PDF，默认开。

- **起因**：国标 PDF 经 MinerU 解析后数字成片丢失，切片变成"温度控制在 ,放置 。"。
  - 定位实验的结论：关掉公式识别、换 VLM 都救不回，强开 OCR 能补回，但扫描件强开 OCR 反而更差。
  - 所以按文档判定，不一刀切。
- **做法**：
  1. **预判**：PDFBox 抽文字层,抽取文字只是为了进行预判，判断是扫描件、坏字体，还是文字层可用。坏字体的文档首次解析就开 OCR。
  2. **分步解析**：MinerU 拆成 
      - fetch：上传pdf给mineru，下载返回结果zip压缩包 → 
      - preview:服务端从zip中展开正文和结构块，用来检查数字是否大量丢失，统计数字个数、非空白字符数、疑似数字缺失的空槽，这个通过正则匹配判断，规则有：在字后跟着逗号或者句号、括号里只剩下见、式后是空括号、的字后是空格加个字等规则，然后pdfbox层如果判断文字层可用，会比较数字保留率，来进行打分判断 → 
      - complete：将选中的那份zip完整展开，处理图片进行文件存储。候选结果只展开正文做审计，选中的那次（上面打分合格的）才上传图片、调视觉模型。
  3. **审计两个指标**：
     - 严格空槽：每千字超过 0.3 处，且至少 3 处；
     - 数字保留率：切片里的数字数 ÷ 文字层的数字数，低于 0.85 不合格。只在文字层可用时看。
  4. **重解析**：不合格就把 OCR 开关取反，再解析一次，两次里择优。
  5. **兜底**：重解析失败，或两次都不合格，也不拒收，只标 NEEDS_REVIEW，等人工复核。

#### 入库正文规范化【10 月新增】（默认开）

- 按出现频次去掉页眉、页脚、水印。
- 只做不改变意思的换写：
  - 全角数字字母和部分符号转半角；
  - 单位字符展开；
  - 拼回被空格断开的小数；
  - 数值型行内公式去壳。
- 中文标点和上下标原样保留。整体 NFKC 只用在全文分词、元数据抽取和比对上，不改写入库正文。

#### 文档元数据与术语表【10 月新增】

- **抽取**：
  - 从一份pdf中抽取文档元数据，主要从pdfbox中可用的文字层中查找，用正则识别比如 GB/T 开头的相关版本，年号等，找不到再看mineru解析结果开头，先作为草稿；规则从文字层抽标准号、发布年和被代替的旧标准；再用术语表（59 条，含同义写法）匹配检测对象、组分和方法。
  - 抽取出来的
- **写入**：摄取成功后写进 `doc_metadata`，同一列还写入解析质量检测结果。人工确认过的值，重新入库时不覆盖。
- **复用**：管理员维护一份术语表，术语表用处：
  - 元数据抽取：：将文件名和解析结果中最先出现的三个标题块，与术语表中的规范词及同义写法匹配；按术语表预设的类别，把命中的规范词分别写入检测对象、组分、方法字段；
  - 查询识别：在检索重排后，进行的一次排序调整，根据术语表识别问题中的术语、读取候选块所属文档的元数据，计算匹配度；然后给重排后分加权重新排序；识别问题提到的对象和组分，供可选的元数据加权使用；
  - 中文全文分词：
    - 前期解析时会将文字进行归一化、例如处理半角和空白，使用正则将标准号、化学式、带单位的数值整体取出；
    - 其余文本交给jieba（一个中文分词工具，英文句子有空格，而中文没有，如果要做关键词检索，就需要决定哪些字符组成一个词），使用Search模式，为了得到适合搜索的词项，再过滤无用词，写入全文索引，术语表中的中文写法会提前加入到jieba 用户词典，防止专业词被拆开；
    - 过滤和补词：去掉停用词、标点等，若命中术语表中的同义写法，在同一位置补上规范词；
    - 后续入库和查询使用一个分词器；PostgreSQL的hnsw是用于近似向量搜索的分层图索引，而这里是PostgreSQL的gin词项索引，是对于一个分块，一路进行向量化，将（向量-分块）存储到数据库中，后续用于向量检索，一路是对于这个分块进行文字归一化、中文交给jieba进行分词，然后过滤和补词，将剩下的词语 （词语1-分块， 词语2-分块...）存储到数据库中；

#### 分块

切法由文档结构决定，用户只能调体量。

- **默认预算**：
  - 目标 1024 字符；
  - 重叠 128（块大小的 1/8）；
  - 表格每块最多 50 行；
  - 为保语义完整，最多可撑到目标的 3 倍（3072）；
  - 硬上限 8192。
- **段落与标题**：按章节边界打包，节与节之间不重叠。
  - 只有单个段落超过 3072、被硬切时才有重叠。
  - 这时重叠同时是往回找句末标点的最大距离。
- **表格（Excel / CSV）**：
  - 按行贪心累加，长度同时按 markdown 和"列名: 值"两种渲染算。超过 50 行，或者加下一行会超预算，就先落一块。
  - 每块都带表头。
  - 一行加上整张表头就超预算时，按非空列拆成几段窄表，列名和值不拆开。
  - MinerU 解析出的 HTML 表格按 `<tr>` 切。
- **每块两份文本**：
  - 展示文本：文档原貌，给模型和前端看。
  - 向量文本：补上正文里还没出现的章节路径，表格写成"列名: 值"，送去向量化。
  - 向量文本也落库，换嵌入模型时直接重算向量，不用重新解析。
- **表格按内容定界**【10 月新增】【默认关】：
  - **问题**：原来按行累加、到预算就切，块边界由"从表头往下累计多长"决定，和行的内容无关。表中间插一行，后面的块整体移位，文本全变，缓存全部失效。
  - **规则**：对每一行的"列名: 值"渲染算 SHA-256，取前 7 字节换成 u ∈ [0, 1)。u < 行长 / (2 × 块大小) 时，就在这一行之后切，平均约每 2 × 块大小出一个切点。
  - **为什么局部**：切不切只看这一行自己的内容，和它是第几行无关，所以改动只影响到下一个切点为止。
  - **保留与取舍**：预算和 50 行上限这两个强制切点仍保留；故意不设最小块长，否则又会依赖位置。
  - 这是逐行哈希，不是滚动哈希。
  - **为什么没开**：叠加在版面切分上，调参集按写定门槛判为退化，见四.10。

#### 向量化（按内容哈希复用）

- **模型与维度**：来自知识库配置，不允许为空或回落到默认模型。否则入库和查询的向量不在同一个空间。
- **执行步骤**：
  1. **算哈希**：对每块的向量文本（不是向量）算 SHA-256。模型这一段用解析后的"供应商:模型名"，不用配置里的别名，因为别名改指向后，旧向量就不该再命中。
  2. **批量查**：一条 `UPDATE … RETURNING` 按（模型、维度、哈希集合）查缓存，同时刷新 `last_used`。
  3. **补算**：未命中的按首次出现顺序去重，批量送 embedding，逐条校验维度。
  4. **回写**：主键冲突时保留先写的向量，只刷新 `last_used`。
  5. **组装**：按原顺序拼成"块 + 向量"，日志记块数、命中数、上送条数。
- **缓存只省钱，不参与正确性**：
  - 读写出错一律降级走上游，入库不失败；
  - 缓存写入不进落库事务，否则块写入失败会把已经付过费的向量一起回滚；
  - 缓存表存 `REAL[]`，超过 10 万条按 `last_used` 淘汰。

#### 落库

同一个 PostgreSQL，同一个事务，每个落点内部先删后插，按顺序执行：

1. **`t_knowledge_chunk`**（展示文本、向量文本、元数据、`content_tsv`）：逻辑删除旧块，批量插入新块，块 ID 每次重新生成。
2. **全文索引**【默认关】：同一事务里写 `content_tsv`（文档名 + 向量文本），提交后重算 BM25 统计。
3. **`t_knowledge_vector`**（`vector(1536)` + HNSW 索引）：先 `DELETE` 旧向量，再 `INSERT` 新向量。

集成测试验证过这个事务边界：

- 提交前，另一个连接读到的仍是旧版本的全部块；
- 提交后整体切到新版本；
- 中途失败，两张表一起回滚。

所以检索方看不到半新半旧的内容。

#### 收尾

- **成功**：写回块数、各阶段耗时、缓存命中数和成功状态。
- **失败**：任何一步异常就置为失败并记下原因，不自动重试，由人看到后手动重跑。

### 4. 版本与重新入库

- **版本号**：文件名里的 `V1.2` 被识别成版本号，去掉版本后的部分是文档键。
- **每次上传都是新记录**：V1.2 和 V1.3 是两个 doc_id，两版都能被检索到。
- **替换旧块**：只发生在同一个 doc_id 重新分块时，比如手动重跑，或 URL 刷新拉到新内容。每次都整篇先删后插，不逐块比对。
- **新版本怎么省钱**：靠内容寻址缓存跨 doc_id 命中，不是靠替换。
- **新旧标准**：由文档元数据在读取时判定，来源面板上标"已被代替"。

## 三、研究任务（Agent）

### 1. 创建（幂等）

- **入参**：
  - 研究目标、产物类型（报告或计划）、约束；
  - 允许的知识库（必填）和文档；
  - 会话 ID（可空，空则新建会话）；
  - 客户端生成的请求 ID（幂等键）。
- **唯一索引**：`ux_research_request (owner_user_id, client_request_id)`。
  - 插入写成 `INSERT … ON CONFLICT DO NOTHING`，然后在同一个事务里按这两列回读。
  - 并发重试只会建出一条任务，不存在"两个线程都查到不存在"的竞态。
- **指纹**：`SHA-256(会话 ID + 规范化后的任务简报 JSON)`，存进 `state.requestHash`。
  - 简报包括目标、产物类型、约束，以及去重后的知识库和文档范围。
  - 回读到已有任务时比对指纹：一样是同一请求的重试，返回已有任务；不一样说明同一个请求 ID 换了内容，直接报错。
- **权限**：只对真正的新请求校验。每个库都要可读、可用，所选文档必须属于所选的库。
- **同一事务里做三件事**：
  - 插任务行，状态 QUEUED；
  - 新会话插会话记录，沿用已有会话就更新它的最近使用时间；
  - 写第一条"已排队"事件，序号用 `UPDATE … SET event_sequence = event_sequence + 1 RETURNING` 分配。
- **快速路径**：事务提交后才交给本机线程池。线程池满被拒也不判失败，任务仍是 QUEUED，等任一实例轮询领走。
- **重新生成**：原任务必须已经结束，用原简报加一个新的请求 ID 再走一遍创建，不覆盖上一次的结果和事件。

### 2. 追问用户与补充条件

- **追问**：主 Agent 调 `ask_user` 后，追问作为结论落库，任务进入 WAITING_INPUT。本次执行到此结束、租约清掉；等待期间不占线程，也不计入活动时长。
- **补充接口**：
  - 请求必须带上自己看到的修订号（乐观并发），任务状态必须是 WAITING_INPUT；
  - 回答追加进简报的约束列表，最多 20 条；知识库和文档范围保持创建时服务端确认的那一份；
  - 状态改回 QUEUED，修订号加 1，写 `INPUT_RECEIVED` 事件，重新入队。
- **指纹不随补充更新**：`requestHash` 只用来判断创建请求是否重复。

### 3. 领取、租约与写保护

- **两个领取入口**（每个实例默认 2 个执行槽位）：
  - **快速路径**：创建后在本机单行 `FOR UPDATE` 领取。
  - **轮询**：每 5 s 一次，语句是 `WHERE status = 'QUEUED' OR (status = 'RUNNING' AND 租约已过期) ORDER BY update_time, id LIMIT 空闲槽位数 FOR UPDATE SKIP LOCKED`。
    - 别的实例已锁住的行直接跳过，多实例并发领取互不等待。
    - 部分索引只覆盖 QUEUED / RUNNING 行，不扫历史任务。
- **占有**（同一个短事务、同一把行锁）：
  1. 如果是接管，再确认一次租约确实已过期，防止轮询和加锁之间的时间差。
  2. epoch 加 1，发一个新的租约令牌，写上执行者 ID。租约到期时间 = 数据库当前时间 + 30 s；一律用数据库时钟，各实例本机时钟不参与。
  3. 如果是接管，接管次数加 1，在途子任务标 INTERRUPTED。超过 3 次判 FAILED（`EXECUTOR_LOST`），也就是"毒任务"，不再接管。
  4. 写 `RUN_STARTED` 事件。
- **心跳**：每 10 s 续租一次，条件和写保护相同，其中包括"租约未过期"，已过期的租约不能自己续回来。
  - 续租更新到 0 行，说明任务被接管、被取消或已结束，立刻取消本地执行。
  - 续租抛异常（数据库抖动）不自杀，只记日志，交给写保护兜底。
- **写保护（fencing）**：执行期间不持行锁。每次写入（追加事件、子任务快照、结束、交还）各开一个短事务，锁行后核对四条：
  - status = RUNNING；
  - epoch 相等；
  - 租约令牌相等；
  - 租约未过期。

  不满足就返回 false、静默丢弃，不抛异常，因为被接管、被取消在设计上都是正常情况。
- **优雅停机**：
  1. 停止领取新任务。
  2. 给在途任务打"请交还"标记，不打断进行中的模型调用和已决定的工具。
  3. 主 Agent 在下一次模型调用前停下。
  4. 任务写回 QUEUED，清掉租约，写 `RUN_RELEASED`，不计接管次数。
  5. 宽限 20 s；到点还没交还的，先强制交还，再取消本地执行。

### 4. 执行：一次运行的主线

- **复核权限**：所有者当前可读的库必须包含任务的全部知识库，否则直接 FAILED（`KB_ACCESS_REVOKED`），不调模型。不是"筛掉无权的库再继续跑"。
  - 轮询领到的任务没有请求线程，按所有者 ID 从用户表重建身份；查不到用户就按无权处理。
- **预算**：从任务行上保存的用量接着算，接管、补充条件之后都不重新计。
- **续跑**：从事件表重建对话。
  - 只取最后一次补充条件之后的事件。
  - 首条请求原文取自 `RESEARCH_STARTED` 事件。
  - 成对的工具开始 / 结束事件还原成 tool_call 加工具结果；没有配对完成的那一步丢弃重做，所以语义是"至少一次"。
  - 同时恢复已读证据、检索计数和已接受的子任务结果。
  - 已经有结论事件的，不再调模型，直接生成产物。
- **工具**：
  - 主 Agent：`search_knowledge`、`read_source`、`ask_user`、`finish_research`，外加委派用的 `conduct_research`。
  - 子 Agent：只有检索、阅读、结束三个，追问和再委派在工具层就不存在。
- **ReAct 循环**：模型通过原生 function calling 决定一步，服务端执行一步，结果回灌。
  - **每次模型调用前**：
    1. 检查取消和时长，确认租约还是自己的，看要不要交还；
    2. 抢进程级的模型并发信号量（默认 2）；
    3. 扣一次模型额度；
    4. 在消息末尾附一条临时提醒。
  - **每次工具执行前**：
    1. 过检查点：看本地取消位、看时间预算、查库确认自己仍是当前执行者；
    2. 扣工具额度；
    3. 写 `TOOL_STARTED`，带上模型给的原始参数；
    4. 执行，外层超时 30 s；
    5. 写 `TOOL_ENDED`，输出最多存 40000 字符。
- **结论**：
  - `finish_research` 或 `ask_user` 校验通过后，结论记到会话上，并单独落一条 `RESEARCH_CONCLUDED` 事件，事件流在这个工具结果处截断。
  - 流结束后如果还没有结论，就进入"原生结束修复"：追加修复指令，把工具钉死为结束工具，最多 2 次；还不行就报 `NATIVE_FINISH_REQUIRED`。

### 5. 先读后引

- **检索只产生候选**：
  - 每个命中块算一个证据 ID：`"ev-" + SHA-256(runId, kbId, docId, 文档版本, chunkId, 正文 hash, 位置 hash)`。
  - 数据库里的完整正文存成证据快照，以第一次写入为准，重复保存是幂等的。
  - 返回给模型的只有证据 ID、文档名，以及正文前 1024 字符的摘录。
- **有未读就不许再搜**：
  - 最近一批结果里只要还有没读过的候选，再调检索就被拒，下一次调用的 tool_choice 也被强制成 `read_source`。
  - 任意一次阅读成功后解除。
  - 同一个"查询 + 范围"组合最多检索 2 次。
- **阅读**：`read_source` 按证据 ID 取回快照原文，最多 16000 字符。
  - 先校验 hash。原块已变化就标 CHANGED，但仍返回快照，所以引用永远指向模型当时读到的文字。
  - 邻接模式会多读前后各 1 块，并生成新的证据 ID。
  - 子 Agent 只能读自己检索出来的 ID。
- **结束校验**（在 `finish_research` 工具里当场做）：
  - 每条发现带 1–12 个证据 ID，而且全部在可引用集合内。可引用集合 = 自己读过的 + 已接受的子任务读过的。
  - 发现、缺口、冲突三个数组各不超过 30 条，不能三者全空、又没有执行问题。
  - 不通过就作为工具错误回给模型，让它重来。

### 6. 委派子 Agent（`conduct_research`）

- **输入**：1–4 个子目标，每个带目标、维度、期望产出，以及可选的文档范围。文档范围只能在任务已保存的范围内收窄。
- **去重**：先去掉首尾空白、合并连续空白、转成小写（不去标点）再比较。
  - 同一批内和跨批次的重复都拒绝。
  - 恢复运行时，会把历史上委派过的目标重新登记；只有被标为 INTERRUPTED 的目标可以重新委派。
- **名额**：一次性原子分配，要么 N 个全给，要么一个不给。整次运行最多 4 个子 Agent；额度不够时作为普通工具错误回给模型。
- **执行**：
  - 跑在实例级的专用线程池上（2 线程、队列 32）。父 Agent 不在这个池上等待，避免池内互等死锁。
  - 单次委派最多 2 个并发。
  - 单个子任务超时 = min(剩余时长, 180 s)。
- **隔离**：
  - 每个子 Agent 有独立的消息历史、已读集合和取消控制。
  - 父取消会级联到子；子失败不会反向取消父。
  - 共享的只有预算、证据存储和知识范围。
- **子 Agent 的预算**：
  - 每个最多 6 次本地模型调用。
  - 扣全局额度时要求"扣完至少还剩 1 次"，保证主 Agent 一定还能做一次整合。
- **结果**：
  - 子任务的超时、异常、额度耗尽都在它自己那条流上被吸收，变成一个"失败"或"部分完成"的结果对象，并带回已经读到的证据 ID。
  - 返回的是压缩结果：发现、缺口、冲突每类最多 8 条，合计最多 8000 字。
  - 父 Agent 先确认其中引用的 ID 都是该子任务读过的，才接受。
- **快照**：子任务每次状态变化（排队、运行中、终态）都写进任务行的 `state.subtasks.<worker-N>`，并在同一事务里写 `SUBTASK_*` 事件。

### 7. 预算与收敛

- **一份预算**：主 Agent、所有子 Agent、产物生成都从同一份里扣。
  - 模型调用 16 次，其中 2 次留给产物生成，探索阶段最多 14 次。
  - 工具调用 24 次，在执行前扣，参数错误也算。
  - 单次请求输入上限 28000 token，由服务端按"消息 + 工具定义"的 JSON 估算。
  - 总活动时长 300 s，等待用户补充的时间不计入。探索阶段另外留 min(30 s, 总时长的 1/5) 给收尾。
  - 单次模型调用超时取 min(60 s, 剩余时间)，限的是收齐整个流的总时间，不是空闲超时。
  - 工具超时 30 s；单个子任务超时 180 s。
- **扣额度的时机**：在发出 HTTP 之前，不是成功返回之后。失败和超时同样消耗上游资源，只按成功计数，等于给重试开了无限额度。
  - 可重试的传输错误最多重试 1 次；重试也重新扣额度，台账里单独记一条。
  - SDK 内部的重试关掉了。
- **进程级公平信号量**：默认 2 个许可，本实例所有任务的主 Agent、子 Agent、产物生成共用。
  - 等待时每 100 ms 试一次，同时检查取消、时长和租约。
  - 最多等 min(剩余探索时间, 60 s)，超时报 `MODEL_QUOTA_TIMEOUT`。
- **收敛分几层**：
  - **临时提醒**：每次模型调用的末尾附一条，写明：
    - 本次之后还剩几次；
    - 当前可引用的证据 ID；
    - 阅读覆盖情况；
    - "剩 2 次以内就别开新检索，缺的写成缺口"（只是提示，代码不强制）。
  - **强制收尾**：扣完本次后剩余探索调用 ≤ 1 次时，tool_choice 钉死为 `finish_research`。这样还留出 1 次，给结束校验失败后重来。
  - **检索受阻**：检索连续失败 2 次后，再检索、再委派都被拒；没有证据时禁止 `ask_user`；并主动进入结束修复。
  - **真的耗尽**：抛带原因码的异常，共 11 种，覆盖模型额度、工具额度、时长、上下文、子任务数等。
    - 已经有可引用证据（或已接受的子任务证据）：记 PARTIAL，用预留额度照常生成产物。
    - 否则判 FAILED，不生成空产物。空报告会让人以为"资料里确实没有"。

### 8. 结束与产物

- **外层收尾的三种分支**：
  - 结论是追问：转 WAITING_INPUT；
  - 没有可引用证据、又有执行问题：判 FAILED，不生成产物；
  - 其余情况：生成产物。
- **产物生成**：
  - 一次单独的模型调用，用专门的生成角色。不带工具（否则又能去检索），不加提醒，不打缓存断点。
  - 输入：简报、结论、子任务结果，以及证据全文。证据要先回证据表复核：已读、属于本次运行、在允许范围内。
  - 输入超长时，反复把当前最长的那条证据砍掉一半，而不是整条丢掉；整条丢了，引用就没法校验。
- **输出 JSON 的校验**：
  - 报告和计划的结构互斥；
  - 每一节、每一步都必须带合法的证据 ID；
  - 正文里不许自己写 `[1]` 这类编号。引用编号由服务端按出现顺序分配，同时生成引用清单；
  - 计划步骤的序号必须连续；没有取值的参数，自动转成"待确认项"；
  - 产物为空时必须有解释。
- **修复**：校验失败修复 1 次；修复后的输入超限就直接停。两次都不过判 FAILED，研究结论仍保留在任务状态里。
- **落库**：产物、终态、用量在同一个短事务里写入，并追加 `ARTIFACT` 和终态事件，所以不会出现"已完成但没有产物"。

### 9. 状态机与事件

- **状态迁移**：代码里没有集中的状态机类，靠每个写入点的条件更新保证迁移合法。
  - 创建 → QUEUED → RUNNING（被领取）；
  - RUNNING 租约过期 → 被别的实例接管，超过 3 次判 FAILED；
  - RUNNING → QUEUED（优雅停机交还）；
  - RUNNING → WAITING_INPUT / COMPLETED / PARTIAL / FAILED；
  - WAITING_INPUT → QUEUED（用户补充条件）；
  - 任意非终态 → CANCELLED。
  - INTERRUPTED 只为读取旧记录保留，现在的代码不会再写入。
- **事件表**：主键是（任务 ID，序号）。
  - 每写一条事件，不论类型，序号都加 1；一次工具调用至少产生两条。
  - 序号在行锁里用 `UPDATE … RETURNING` 分配，不用 `MAX + 1`。
  - 追加事件和写保护检查在同一个短事务里。
- **常见事件**：
  - 运行：`RUN_STARTED`、`RUN_RELEASED`、`RESEARCH_STARTED`（带首条请求原文）；
  - 模型：`MODEL_STARTED`、`MODEL_ENDED`（模型、状态、tool_choice、工具定义指纹）；
  - 工具与来源：`TOOL_STARTED`、`TOOL_ENDED`、`TOOL_FAILED`、`SOURCE_READ`；
  - 子任务与结论：`SUBTASK_*`、`RESEARCH_CONCLUDED`；
  - 产物与终态：`ARTIFACT`、终态事件；
  - 用户操作：`CANCEL_REQUESTED`、`INPUT_RECEIVED`。
- **token 用量不在事件里**：每写一条事件，就在同一事务里把整份预算快照（含调用台账）覆盖写到任务行的 `usage` 列。
- **事务边界**：模型调用和工具执行都在事务之外，事务只覆盖"分配序号 + 写一行"，避免一次模型调用占住连接和行锁几十秒。

### 10. 用户取消

- **第一段：同步写库，写完就生效**。在一个事务里锁住任务行：
  - 已经是终态：原样返回，不报错。
  - 未结束（QUEUED / RUNNING / WAITING_INPUT）：
    - 状态改为 CANCELLED，epoch 加 1，清空租约令牌和到期时间，修订号加 1；
    - 在途子任务一并标为已取消；
    - 写 `CANCEL_REQUESTED` 事件，其中"远端计算是否已停止"如实写成 `unknown`。
  - 从这一刻起，旧执行者的任何写入都会因为 epoch 和令牌对不上而被拒。
- **第二段：异步、尽力而为**。
  - 执行恰好在本实例上：直接触发这次执行的取消信号。
  - 执行在别的实例上：那个实例在下一次续租失败时（最多一个心跳周期），或在下一个检查点，发现自己已不是执行者，自行停止。
- **取消信号的传播**：
  - **Agent 层**：事件流上挂 `takeUntilOther(取消信号)`，再注册一个回调调 SDK 的 Agent 中断。
  - **模型层**：调用前、等待并发额度时、发请求前都会检查；响应流上也挂了取消信号，取消会一路传到底层 HTTP 连接。重试条件排除了"已取消"。
  - **工具层**：工具入口和每个工具执行前的检查点。
  - **检索 HTTP 和数据库语句**：走带截止时间的请求作用域，取消时调 OkHttp 和 JDBC 的 cancel。
  - **子任务**：每个子任务的取消绑在父任务的取消信号上。
- **唯一例外**：本地执行结束时，允许往已取消的任务上补写用量和一条"本地执行已结束"事件。
  - 条件：状态是 CANCELLED，且 epoch 恰好等于"领取时 + 1"。
  - 它写不了状态和研究结果，只为如实记下取消前已经花掉的费用。

### 11. SSE 断线续传

- **鉴权**：在请求线程里按任务表的 `owner_user_id` 读一次任务。查的是数据库，不是 Redis（Redis 里的归属键是普通问答停止接口用的）。
  - 所有者 ID 用闭包变量固定后传给推送线程，不依赖线程本地变量。
  - 同时在线的订阅最多 100 个。
- **起始游标**：取查询参数里的游标和请求头 `Last-Event-ID` 中较大的那个。浏览器的 `EventSource` 断线重连时会自动带上最后收到的事件 ID。
- **推送**：
  - 每 750 ms 轮询一次事件表，取序号大于游标的下一页（100 条），逐条推送，每条消息的 `id` 就是事件序号。
  - 每推完一批，再推一条任务快照，每批都推，和有没有报告无关。
  - 推送时会裁剪字段：产物、已读来源、子任务事件原样下发；其余事件只保留工具名、状态、输出类型和原因。模型的原始参数和原始请求留在库里供续跑用，不进 SSE。
  - 推完继续轮询。
- **关闭**：
  - 只有任务进入终态或 WAITING_INPUT 时才收尾。收尾前先把尾部事件读干净，因为产物事件和终态事件在同一事务里提交，先断开可能漏掉产物。
  - 连接本身 2 分钟超时，之后浏览器带着 `Last-Event-ID` 自动重连续上。
  - 客户端断开时，只撤掉这条订阅。
- **订阅和执行完全解耦**：连接、断开、重连都不会触发或取消执行。前端只接收序号大于本地游标的事件，避免重复展示。

### 12. 提示缓存与上下文

- **提示缓存是前缀匹配**：两次请求必须从第一个 token 起逐字节相同，第一处差异之后全部重算。所以目标是让每次请求都是上一次请求的严格扩展。
- **稳定前缀**：
  - 系统消息只放稳定内容（角色、规则、输出契约）。工具定义集合固定，每次 `MODEL_STARTED` 事件都带上工具定义的指纹。
  - 首条用户消息（简报 + 已保存的状态）按键排序序列化，原文随 `RESEARCH_STARTED` 事件落库。原来用 `Map.of`，键序不确定，接管后重建不出同样的字节。
  - 随轮次变化的提醒（剩余次数、可引用 ID、阅读覆盖、检索受阻说明）放进每次请求末尾临时追加的一条用户消息，不写回 Agent 记忆，所以历史里永远只有当次这一条。
- **显式缓存断点**：
  - **位置**：打在两处。
    - 第一条系统消息，工具定义也算在这一段；
    - 倒数第二条，也就是提醒前最新的一条历史。断点随历史往后移，之后每次只为新增的那一段付写入价。
  - **不打在最后一条**：最后一条是每次都变的提醒，打在那里，等于每次都按写入价重写整段。
  - **计费**：写入按 125%，显式命中按 10%（隐式命中 20%）；有效期 5 分钟，命中即续期。
  - **传输层改写**：SDK 自带的缓存开关写的是消息级 `cache_control`，百炼会静默忽略。所以在 HTTP 传输层加了一个装饰器，发送前把标记改写进内容块，同时从流式 usage 里读出 SDK 不解析的缓存写入量。
  - **开关**：`research.explicit-prompt-cache`，yaml 里已打开。
  - 产物生成那次调用不加提醒，也不打断点。
- **阈值压缩代替滑动裁剪**：
  - **何时压**：估算输入不超过 28000 token 时一个字不动；超过就一次性压到上限的 60%。
  - **先轻后重**：
    - 先把最早几轮里超过 600 字符的工具结果换成存根。存根保留 tool_call_id 和工具名，调用和结果仍然成对；也保留结果里出现过的证据 ID，并提示模型可以用 `read_source` 重读。服务端不会按 ID 自动恢复，靠模型自己重读。
    - 存根还不够，再从最早一轮开始整轮移除。
  - **不动的部分**：最新一轮始终完整保留，系统消息和首条用户消息也不动。压完仍超，报 `MODEL_CONTEXT_BUDGET`。
  - **水位只增不减**：压了几轮、丢了几轮记在本 Agent 的模型包装器实例里。所以两次越线之间前缀保持稳定，只在越线那一次丢一次缓存。
  - 真实实验里没触发过压缩，这条路径只有协议测试覆盖。

## 四、测试、实验与日志

### 1. 回归

一条命令跑两层：

- **协议层**：用本地脚本化 HTTP 桩代替模型，走真实的 SDK 和流式解析，可以逐字节断言请求体。例如断言接管后重建的请求，和首次执行时完全相同。
- **集成层**：连真实的 PostgreSQL / pgvector，每次新建一个随机命名的库，跑完删掉。`SKIP LOCKED`、行锁里分配序号、同一事务里先删后插这些语义，换成内存数据库测不出来。

### 2. 模拟上游

- **形态**：Python 写的 OpenAI 兼容服务（`stub_upstream.py`），有对话和 embedding 两个端点。实验脚本把被测 Java 进程的供应商地址指向它。
- **对话端点**：确定性策略，不是录播。
  - 读对话里提到的资料编号，以及已经发生过的工具调用；
  - 每个编号先检索，再读第一条候选；失败就重试一次，两次都不成，记一条缺口；全部编号处理完就结束；
  - 给了委派工具、目标里又有多个编号时，先委派；
  - 没带工具定义的请求当作最终成文，返回一份引用全部证据的 JSON。
  - 同一段对话永远得到同一个动作，所以接管重建之后，下一步也一样。
- **embedding 端点**：用文本里第一个资料编号（没有就用整段文本）做哈希种子，生成单位向量。查询里提到某个编号，就和那份文档相似度为 1，检索结果完全可预测。
- **故障旋钮**：
  - 所有请求共用一个固定种子的随机数发生器，每个请求进来抽一次；
  - 可注入无响应（挂住连接 90 s 后一个字节都不回就关掉）、429 / 503、流中途断开，以及均匀分布的延迟；
  - 按端点分别设置。

### 3. 调用台账与缓存实验（W1 / W6）

#### 台账

- **记录粒度**：模型包装器给每一次实际发出的 HTTP 请求记一条，重试也单独记一条。
  - 发请求前记：调用 ID、模型、角色（main / worker / finalization）、任务 ID（main 或 worker-N）、估算输入。
  - 结束后补：状态（完成 / 失败 / 超时 / 取消）、requestId、输入 / 输出 / 命中 / 缓存写入 token、缓存类型、整次耗时、首包耗时。
- **失败也落账**：完成、出错、取消三个回调共用一个只执行一次的收尾，所以失败、超时、取消的调用也会记下。
- **缺失值不写**：供应商没返回的值直接不写这个键，`usageStatus` 保持 unknown，不用 0 冒充。
- **存储**：台账随预算快照写进任务行的 `usage` 列。

#### 定位过程

1. 用台账做离线报表：单 Agent 模式命中率 5.2%（每次恰好命中 1280 token，是供应商一段未公开的行为，不可依赖）；多 Agent 模式只有 0.02%。
2. 读百炼的缓存文档。
3. 用协议测试夹具抓下 SDK 实际发出的请求字节，每次只改一处，重放到百炼真实端点（共 34 次），看命中 token 和缓存写入量。

探针的结论：

- 系统消息末尾加一行，命中 0；工具换个顺序，命中 0；
- 系统消息稳定、历史只追加时，隐式缓存逐步 4 次只命中 1 次；
- 显式断点打在最新一条历史上，3 次全部命中整段旧前缀；
- SDK 的消息级缓存标记被供应商忽略。

根因有两个：

- 易变提醒拼在第一条系统消息里，这是实测的主因；
- 从最早一轮往后滑动裁剪，设计上也会破坏前缀，但那批实验的输入都没超过上限，实际没起作用。

#### 报表口径

- 只统计供应商返回了用量的调用。
- 命中率 = Σ命中 ÷ Σ输入。
- 计费输入 = 未命中部分 + 命中 × 折扣（显式 0.1，隐式 0.2）+ 写入 × 1.25。单位是输入 token 当量，不是账单。

#### 结果

- **W1**（真实上游，同一批 40 题，改前改后各跑一次）：
  - 命中率：单 Agent 9.8% → 78.4%，多 Agent 0.2% → 80.0%；
  - 单任务计费输入：分别 −69%、−75%。
- **W6 质量护栏**（真实上游，MuSiQue 400 道没见过的题，多 Agent 模式，改前改后按 4 块交错跑）：
  - 命中率 0.15% → 80.4%，计费输入 −72%；
  - 配对答案 F1 −0.034，95% 区间 [−0.080, +0.011]；同一版本重跑一次的噪声是 +0.059；
  - 结论只能说"未见显著下降，但不能排除 0.08 以内的下降"。

### 4. 批量回归 P7 与超时事故

- **题目**：QASPER 1005 题、MuSiQue 4834 行，各按 SHA-256（种子，题目 ID）升序取前 200，共 400 题。MuSiQue 这 200 题里可答的有 105 题。
- **上游**：真实供应商，百炼的 flash 模型加 SiliconFlow 的 embedding。
- **三种模式**：
  - A：用题目原文检索一次，取前 10 条，读全部命中块，再生成产物；
  - B：单 Agent，不注册委派工具；
  - C：允许委派（400 次里实际只委派了 2 次）。
- **执行**：按 A → B → C 分三批先后跑，每批用一个随机隔离库，并发 2，共 1200 个任务。
- **原始记录**：
  - 每题一行：题目 ID、模式、终态、错误码、耗时、产物、实际读到的证据、用量；
  - 每个事件一行的 trace；
  - 每次模型调用、每次 embedding 调用的用量。
- **离线评分**（不用裁判模型）：
  - 归一化和 SQuAD 官方脚本一致：转小写、去标点、去冠词 a / an / the、合并空白，再按空白切词。
  - EM：归一化后完全相同得 1，否则得 0。
  - F1：按词的多重集求交集。精确率 = 重合词数 ÷ 预测词数，召回率 = 重合词数 ÷ 标准词数，F1 = 2PR ÷ (P + R)。
  - 有多个参考答案时取最大值。
  - 失败、超时、格式错误按空答案计 0 分，并留在分母里。
  - 汇总里还有证据 F1、可答性、含失败任务的 P50 / P95 耗时和 token 用量。
- **超时事故**：
  - 121 个任务停在检索工具的 30 s 超时上，耗时 30.007–30.013 s。其中没读到证据、判 FAILED 的 72 个，另外 49 个以 PARTIAL 收尾。
  - 同批的 embedding 失败也正好 121 次，全部在 30.000 s 超时。HTTP、通道、工具三层都配成 30 s，几乎同时到点，外层已经没有剩余时间补救。
  - 另一个问题：A 模式有 6 次 embedding 超时被吞成空结果，同时正好有 6 个 A 任务以"完成"结束却一条证据都没有。这就是"失败被伪装成资料不存在"。两组记录没法逐条对应，只能说数量吻合。

### 5. 上游容错（W3）：分层截止时间、有限重试、失败与无命中分离

#### 分层截止时间

每一层的截止都取 min(本层上限, 剩余时间)，越往里越紧：

- **任务**：总时长 300 s，探索阶段留出 min(30 s, 总时长的 1/5) 给收尾。
- **检索工具**：进入时算一次截止 = min(探索期剩余, 30 s − 2 s)。少掉的 2 s 留给工具层自己收尾；外层 Reactor 超时是 30 s。
- **等通道结果**：用剩余时间。
- **单次 embedding HTTP**：min(12 s, 剩余)。一次不回包最多损失 12 s，剩下的时间够做一次重试。
- **数据库语句**：min(5 s, 剩余)，至少 1 s，并挂了 `statement.cancel`。
- **模型调用**：min(60 s, 剩余)，限的是收齐整个流的时间。

承载截止时间的是一个显式的请求作用域对象 `RequestOperation`。它用普通 ThreadLocal 显式绑定、不随线程继承，跨线程池时必须显式传递。

"研究检索最多 20 s"在代码里不存在。代码里的 20 是召回条数，或者停机宽限的 20 s。

#### 有限重试 + 抖动退避

- **可重试**：网络错误（含超时）、429、5xx。
- **不可重试**：401 / 403 和其他 4xx、响应格式非法、供应商业务错误、熔断打开、没有可用通道。
- **取消不算失败**：既不重试，也不计入熔断。
- **embedding**：
  - 最多尝试 2 次；剩余时间不足 1.5 s 就不重试，免得重试刚发出去就撞上截止时间。
  - 退避用指数退避加 equal jitter：基数 300 ms，上限 2000 ms，等待时间 = 一半固定 + 另一半随机，所以第一次重试等 150–300 ms。原来是固定等 300 ms，同一批失败的调用会一起重试，再次冲击刚恢复的上游。
  - 等待被切成不超过 50 ms 的小片，每片之间检查截止时间和取消。
- **研究模型的流式调用**：最多重试 1 次，基数 300 ms、抖动 0.2；只对 IO 错误、超时、流不完整和可重试的状态码重试。

#### 失败与无命中分离

- **研究路径**（带截止时间）：通道和后处理器的异常不再吞掉，而是往上抛；没有可用通道时，抛不可重试的失败。普通问答路径保持原来的降级。
- **工具层**：返回明确的错误结果，带出错阶段、错误码、是否可重试，并写明"这是执行失败，不是资料不存在的证据"。
- **会话层**：记录"执行问题"。
  - 有执行问题时，结论是 PARTIAL；
  - 没有可引用证据、又有执行问题时，直接 FAILED，不生成产物；
  - 这时 `ask_user` 被拒，防止把检索超时包装成"请您补充资料"；
  - 检索连续失败 2 次，禁止再检索和委派。

#### 熔断（模型路由层）

- 连续失败 2 次就打开，持续 30 s；半开时只放一个探测请求。
- 带截止时间的调用不跨模型回退（向量不能跨模型比较），但失败照样计数。
- 取消只按令牌归还半开名额，不计失败。
- 所有候选都被熔断时，立即抛不可重试的失败。

### 6. 故障注入实验 X3（模拟上游）

- **语料**：60 份合成文档（SRC-001 到 SRC-060），每份一句"recorded value"，经真实的 Java 导入链路入库。
- **任务**：50 个研究任务，前 25 个问 1 个编号，后 25 个比较 2 个编号；只跑单 Agent 模式。
- **对比的两个版本**：用临时 git worktree 分别检出并编译治理前、治理后的提交。后一版还包含这期间的其他改动（如提示缓存），不只是重试和分层超时。
- **故障**：只注入 embedding 无响应，比例 0 / 10% / 30% / 50%。
- **重复**：4 个种子（7 / 11 / 13 / 17），每格 200 个任务，区间用 Wilson 95%。
- **成功判定**：状态为完成、有产物，并且读到了题目要求的每一份文档的证据。状态是完成但缺证据的，单独记为"错误完成"。
- **结果**：
  - 成功率：10% 档 87.5% → 100%；30% 档 57.5% → 98.5%（区间 [50.6, 64.1] → [95.7, 99.5]）；50% 档 36.0% → 86.0%。
  - 浪费的模型调用：10% / 30% / 50% 三档分别 51 → 0、160 → 11、218 → 121。
  - 1600 个任务里，两版的错误完成都是 0。所以 X3 证明不了"失败与无命中分离"带来的收益。
  - 代价：成功任务变慢，单种子那轮 30% 档 P50 从 1.1 s 升到 12.9 s；embedding 请求数也随故障率上升，等于用负载换成功率。
  - 评测命令直连 embedding 客户端，不经过模型路由层，所以熔断只有单元测试覆盖。

### 7. 接管实验 X2 与容量实验 X6（模拟上游）

#### X2 接管实验

- **执行器**：独立的 JVM 进程，命令是 `java -cp … ResearchExecutorCommand serve --lease-seconds 6 --heartbeat-seconds 2 --poll-seconds 1 --max-concurrent-runs 4 --shutdown-grace-seconds 20`。
  - 任务用 `submit` 子命令写进库里；执行器走生产用的那套执行服务。
  - 每个场景都用新库和新的模拟上游，上游本身不注入故障。
- **六个场景**：无故障基线、`kill -9` 持有者、中途加入新实例、`SIGTERM`、`SIGSTOP` → `SIGCONT`、毒任务（每个接手者都被杀，第 4 次判 `EXECUTOR_LOST`）。
- **注入时机**：两个任务都处于 RUNNING，且各自已有至少 2 个工具结束事件。
- **判定**：不看日志，直接查数据库：
  - 恰好一个终态事件；
  - 至多一个产物；
  - 事件序号连续；
  - 已完成的工具调用（同名同参数）没有再做一遍；
  - 没有 INTERRUPTED。
- **三种杀法**：
  - `kill -9`：进程瞬间消失，等租约过期后被别人接管。
  - `SIGTERM`：优雅停机。在下一次模型调用前把任务交还队列（`RUN_RELEASED`，不计接管），别的实例下一轮轮询就领走。
  - `SIGSTOP`：不是退出，而是把进程冻住 12 s（超过 6 s 租约），再用 `SIGCONT` 放行。验证的是围栏：旧执行者醒来后续租被拒，打出 lease lost 日志并停掉本地执行；它迟到的写入被 epoch 和令牌拒掉；进程本身一直活着。
- **结果**：
  - 恢复时间从注入故障算到新持有者写下第一条 `RUN_STARTED`，每次重复取最慢的那个任务。P50 / P95 / 最大：
    - `kill -9`：5.13 / 6.12 / 6.12 s；
    - `SIGSTOP`：5.12 / 6.12 / 6.12 s；
    - `SIGTERM`：1.08 / 1.11 / 1.11 s。
  - 每个被接管的任务都只多花 1 次模型调用（118 / 118），不变量 0 失败。
  - 基线、`kill -9`、`SIGTERM`、`SIGSTOP` 各重复 20 次；新实例加入、毒任务各跑 1 次。`kill -9` 有 1 次，执行者在注入故障前就卡住了，原因未查明。

#### X6 容量实验

- 300 个积压任务，分别用 1 / 2 / 3 个实例跑，每实例 2 个槽位。
- 吞吐 12.2 / 24.0 / 35.8 条每分钟，接近线性。
- 提交被拒 0 个；领取语句平均约 5 ms，占排空时间不到 0.12%。
- 瓶颈是槽位和轮询间隔，不是数据库。

## 五、核对中发现的代码问题（只列出，没有改）

1. **防重锁默认不生效**：`ragent.eval.enabled: true` 让 `@IdempotentSubmit` 直接放行。这个开关同时管评测端点的注册，yaml 里"评测端点已删除"的注释也已经过时。
2. **问答许可可能提前过期**：租期 30 s，而首包预算标准档就是 30 s、深度思考档 120 s，代码里也没有续租。入口阶段超过 30 s，许可就在 Redis 里过期，实际并发可能超过 10。
3. **拒绝回调可能被丢**：排队超时后的拒绝回调提交到同一个入口线程池，满载时可能被拒、只留一条日志，前端要等 5 分钟 SSE 超时。这一条是从代码推断的，没有实测。
4. **取消打断不了入口阶段**：改写、检索照样跑完，等到绑定模型句柄时才取消，这期间一直占着许可。
5. **trace 不是完全旁路**：run 插入、节点开始和切面里的结束没有 try/catch，trace 表写失败会打断主链路。
6. **`ef_search` 可能没生效**：向量检索前的两条 `SET` 和查询是三次独立的 JdbcTemplate 调用，不保证落在同一个连接上。
7. **摘要失败会丢原文**：摘要模型失败时返回旧摘要，但仍会推进 `lastMessageId`，那一段原文以后不会再进摘要。
8. **改写历史少一条**：取最近 4 条历史时按过滤摘要之前的条数截取，有摘要时实际只剩 3 条。
9. **重复触发分块时接口照样成功**："开始分块"重复触发时，"正在进行中"的异常被事务监听器吞成回滚，接口照样返回成功。
10. **阈值默认值和验证值不一致**：重排分阈值默认 0.2，评测验证过的是 0.3。

## 附：相对原稿的主要更正

- **防重与排队**：
  - 防重是 `@IdempotentSubmit` 的 Redisson 锁，默认配置下被跳过，而且只覆盖控制器的同步段，不是"同一用户限流"。
  - Lua 判断的是"前 N 个存活条目的窗口"，不是严格的队头。
  - "10 路"只管到首包，不是整段生成。
- **摘要**：阈值数的是用户消息条数（≥ 9），窗口比较的是消息 ID（`lastMessageId`），不是"会话数""会话 ID"。
- **改写与权限**：
  - 改写取的是最近 4 条消息，不是 2 轮。
  - 权限过滤的对象是知识库，并且在召回之前和全部未删除库求交，不是"按角色查表"。
- **分块**：
  - 重叠只在超长段落被硬切时出现，节与节之间不重叠。
  - "两份分块"应为"每块两份文本"。
  - 内容定界是逐行哈希，不是滚动哈希；评测判为退化，默认关闭。
- **向量化与落库**：
  - 缓存哈希的是向量文本，不是向量。
  - "另一个库"其实是同一个 PostgreSQL 里的两张表。
  - 新版本是新的 doc_id，不会替换旧版本的块；替换只发生在同一文档重新分块时。
- **大文件客户端直传**：未实现。
- **研究任务**：
  - 补充条件不更新指纹。
  - 执行期间不持行锁，靠每次写入时的四条写保护。
  - 权限复核不通过时整个任务判失败，不是筛选知识库。
  - 事件序号是每条事件都加 1；用量写在任务行的 `usage` 列，不在事件里。
  - 研究任务 SSE 的归属查的是数据库，不是 Redis。快照每批都推，推完不退出，只在终态或等待补充时收尾。
  - 委派去重除了转小写，还会去掉首尾空白、合并连续空白；子任务快照在任务行的 `state.subtasks` 里，同时写事件。
- **预算**：模型调用 16 次（不是 20），工具调用 24 次（不是 20），单个子任务超时 180 s（不是 120 s），输入上限 28000 token。
- **压缩**：只把最早几轮里的长工具结果换成存根，保留 ID 由模型自己重读；服务端没有自动恢复。
- **缓存定位**：靠协议夹具抓字节、逐处改动后重放到真实端点做探针，不是"把请求发给 SDK"。
- **超时事故**：72 是判 FAILED 的那部分，超时一共 121 个；任务是在 30 s 处被判超时，不是"超过 30 s"。
- **时间预算**：没有"研究检索最多 20 s"。实际的分层是：工具 28 s，embedding HTTP 12 s，数据库 5 s，模型 60 s。
- **X3**：故障由固定种子的随机数发生器逐请求抽取；对比的后一版还含其他改动；错误完成两版都是 0。
- **X2**：SIGSTOP 是冻结进程而不是退出，验证的是旧执行者醒来后写不进去、自行停下。
