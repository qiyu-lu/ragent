# 第二部分：通用流程写作提示词

前面已给出本会话负责的流程和输出路径。请直接阅读当前项目并编写对应笔记，目标是让我后续复习时只阅读笔记，就能理解整个流程及其所在的系统框架，顺着输入、判断、数据变化和执行者交接走完整条业务，再逐渐换成自己的语言复述。源码用于写作时核实事实，复习所需的执行逻辑应已写入笔记；源码链接只是可选反查入口。

以完整、连续的总流程为正文主体：普通步骤及方法内部在调用位置讲清；少数复杂异常或重点复杂方法可以在总流程中先讲清处理过程，再到后面详解。短例子就地说明，长例子和占较大篇幅的表格另列。后置内容应帮助深入理解，读者不应为了知道“这一步怎么继续”而反复往返。

## 阅读依据与工作范围

先完整阅读本项目的 [10-my.md](../10-my.md)（项目内路径 `docs/iron-ore-rag/10-my.md`），把它作为主要表达样本：先说要完成什么，再按输入参数、内部处理、返回结果的顺序，用 Markdown 无序列表和缩进解释。它是我临时读代码写的片段，正常流程也没有写全；模仿叙述形式和思路，不把其篇幅当成详细程度的上限，也不照搬其中未经核实的说法。

如需进一步体会同样的写法，可参考 `/home/sd101t/IdeaProjects/hm-dianping/docs/learning/10-seckill.md`。不必每个会话重复阅读另一个项目，更不要把其中的 Redis Lua、库存、事务补偿等机制套到 RAG。

先确认当前 Git 分支、工作树改动和适用的仓库说明；只读 08/09 中分配给本主题的章节，再沿当前调用入口查必要的 Service、模型请求、Prompt 模板、SQL、异步执行者和配置。测试用于理解已有分支，历史改动记录用于核对设计原因与结果。不要为一个流程遍历整个仓库，也不能只把旧笔记改写一遍。

本任务只编写分配的流程文件，可以新建父目录。目标已存在时保留有用的人工表述与已核实内容，纠正错误并补齐缺失步骤。保留其他工作树改动，不修改共享 README、旧 08/09、表达样本 10、其他流程文件或业务代码；不提交、不推送，不启动服务、迁移、业务测试或真实模型评测，不另拆子 Agent、生成规划或审计报告。完成后简要报告文件及影响理解的重要修正即可。

旧笔记和注释只是定位线索。关键条件、调用顺序、默认值、异常传播和返回处理以当前实现为准；方法存在不等于当前调用，算出了某个中间结果不等于最终使用它。查不到的事实就在对应位置说明缺少什么依据，不用“系统会自动处理”填空。

## 按发生顺序讲，在当前步骤展开内部过程

每条独立流程标题下先简要说明“谁要做什么，位于整个系统的哪一段，接收上一步什么，完成后交给谁”，随后开始步骤。新建会话、已有会话、后台任务等入口有差异时，在实际分支交代。默认关闭的分支先说明启用条件，不先堆项目背景、技术栈、术语表或面试开场白。

框架职责也随调用解释：Controller 在这里接收或返回什么，Service 组织什么业务，存储层怎样查写，模型适配器把什么交给外部服务，消息或回调怎样接续执行。讲清本条链实际经过的职责和交接，不强行让每条链经过所有层，也不用一张类名关系图代替执行过程。

沿用这样的叙述方式：

“用户带着……发起请求，当前用户从……取得。程序先读取……，根据……判断能不能继续。通过后把……变成……，保存在……。接着调用……，传进去的是……；它内部先……，然后……。结果返回后，外层用……决定……。到这里本次请求返回，后面的……由另一个请求/消费者/回调继续。”

- 一级 `-` 表示一个能够独立复述的业务步骤，按实际发生顺序排列。先说这一步要做什么，再展开它内部怎样得到结果。
- 二级及必要的更深条目表示该步骤内部的读取、判断、计算、写入、调用和返回。方法内部又调用其他方法时，默认在当前位置继续展开，讲完再明确回到外层怎样使用结果；仅对后文规定的少数重点复杂方法，采用“总流程说明处理过程，后面再详解”的方式。
- 层级随逻辑需要，不硬限两级；很长的连续子流程可在当前位置用小标题组织。不要因为有第三层、SQL 或模型请求就把正常执行搬到文末。
- 合并简单赋值、重复日志和机械校验，不把不同业务动作塞成一个长段落，也不把每个字段机械分成一条。每个条目仍用连贯中文，保留“接着”“通过后”“如果……就……”的联系。

重点保留中间连接：数据原来在哪里，这一步增加、删除或改变了什么，后面谁拿这些信息做判断。例如“向量化后入库”没有说明送给模型的是哪份文本、返回数组怎样对应原 chunk，以及关系记录和向量如何共享 ID，这些都需要展开。

本会话负责的每个关键步骤，应让读者在当前位置回答下面的问题。这是检查遗漏的依据，不要求机械地加六个小标题：

- 输入具体包含什么，来自请求、登录上下文、配置、数据库还是前一步结果？哪些是 ID，哪些是实际内容？
- 内部先读什么，字段、集合、缓存或索引中的数据是什么结构，为什么下一步需要它？
- 实际按什么顺序过滤、比较、计算和分支？不满足时返回什么、是否抛异常、外层如何接着处理？
- 满足后改变哪些数据，建立什么关联，在哪个事务或条件更新内完成？如果没有原子保护，也要如实说明。
- 返回的是文本、JSON、分数、向量、状态、future 还是取消句柄？调用方怎样使用这个结果？
- 到这里已完成到哪一步，用户能看到什么，下一步由当前线程继续还是交给另一执行者？

普通 Java 方法、查询 SQL、Prompt 装配、解析器、选择器和回调都按这一深度解释。不要只对 Lua/MQ 写细节，遇到 AI 就缩成“调用大模型完成理解”“重排提升相关性”。完整的正常流程不仅包括输入到调用，还包括调用后的结果处理、落库、返回及外层继续；不能像草稿一样写到“调用大模型”就结束。不逐行翻译 import、getter 或框架样板，完整程度以能否解释关键结果怎样得到为准。

跨会话边界是有意保留的例外：只在分工指定的交接点，简述被调用流程收到什么、主要做什么、返回什么，再继续本篇自己的执行。完整内部逻辑由负责它的流程文件展开，不能每篇递归写完所有模块，也不能只留一句“详见其他文件”。例如 F 调 E 时，仍要解释子问题换回选中块和知识上下文，空结果如何影响回答；E 内部的每个排序步骤不在 F 重写。

## 少数复杂方法怎样后置详解

普通方法直接在总流程的对应步骤中展开，不采用“总流程列方法名，后面按方法逐个解释”的布局。方法有独立名字、参数多、出现 SQL/模型调用或列表层级较深，都不是单独抽出的理由。

只有本身是重点、内部逻辑又确实复杂，完整嵌入会明显打断外层主线的方法，才可以另设详解；复杂异常恢复则按后面的异常规则处理。例如多轮候选分配、复杂的表格规范化或多个取消回调竞态，确有必要时可这样组织，但不要预先规定它们一律后置。

- 总流程在实际调用位置仍按顺序说明：传入什么、内部先后做哪些处理、关键条件怎样影响分支、数据如何变化、最后返回什么，以及调用方拿结果继续哪一步。这里应是一段可复述的子流程，不能缩成“调用选择器得到最终结果”。
- 详解补上更细的循环、边界判断、推导或交错过程，不把主流程理解下一步必需的信息全部留到后面，也不再原样复制一遍主流程。详解仍用步骤及内部缩进的写法，不变成抽象术语说明。
- 总流程调用处链接到具体详解小节；详解开头明确“对应哪条流程、在哪个动作之后调用、结果交给哪个后续动作”，并提供返回该调用步骤的链接。需要时为调用步骤加稳定锚点，不让读者凭方法名重新搜索其执行位置。

判断标准：暂时跳过详解，仍能从输入走到输出，知道关键结果怎样得出；读完详解，则能进一步推演复杂内部逻辑。若跳过后连返回值从哪里来、为什么走下一步都不清楚，就应把相应内容移回总流程。后置应是少数确有必要的例外，不以压缩主流程篇幅为目标。

## RAG 中的数据转换与模型调用怎样描述

把模型看成输入输出明确的一步调用。每次出现模型时，都在调用位置说明实际发送和接收的内容：

- 改写/分类/任务草案：实际消息用了哪些角色，指令要求完成什么，问题或证据放在哪里，是否带历史、候选节点或 schema；用必要字段或最小示例说明预期返回格式。随后讲 JSON 清理、解析、字段检查和实际使用，不把模型写出的字段直接当成程序事实，也不假设所有调用都拆成 system 与 user 两条消息。
- Embedding：说明文档侧和 query 侧分别输入什么字符串，指定或选用了什么模型、维度，返回的向量数组怎样与原数据对齐。模型不返回问答答案，也不是把原文存进“1536 个关键字”。
- Rerank：说明 query 与候选文本怎样一起送入，返回的 index/score 如何映射回原 chunk；模型排序文本与最终给回答模型看的文本可能不同。没有进候选的证据不能由重排补回来。
- 最终生成：把规则、历史、证据与本次问题的消息顺序示意出来；模型返回的是增量文本，程序怎样累计、存储并发送事件。来源字段、证据 ID 和数据库状态分别由谁生成，要讲清楚。

多个模型调用要区分职责。改写模型通常没有看到整份知识库，分类模型看到候选节点不等于看到了原文，回答模型只看到本次构造的上下文，也不是自动浏览 PGVector。知识入库不会自动修改聊天模型参数。

选择、预算、格式、白名单和状态通常由程序处理，但“程序做的”不等于天然正确；例如作用域选错、过早截断、按错误键去重，会稳定地产生错误结果。每个判断都应说明项目实际采用的依据。

字符数、token 数、向量维度、候选条数是不同单位，写参数时明确限制的对象与层级。主配置、profile、数据库设置、请求参数和 Java 缺省值也要区分；默认值不一定是实际部署值。不要用历史评测的 intent=off 或 TopK 参数倒推普通聊天每次怎样执行。

中文先说业务含义，再给必要代码名。例如“为了模型检索而组织的文本（embedding_text）”“这次允许查询的集合（scope）”“回答随消息保存的证据块快照（grounding）”。不预设我已经懂这些概念，也不先插一段完整的技术教程。

## 短例子放在流程内，长例子单独解释

涉及非直观转换时，选一个贯穿的教学例子，数据标为假设，不需要复制真实资料。可以沿用“设备 C1、传感器 S7、某份台账 V3、某份规程 V1.2”的背景，但只取本流程需要的部分；数字、分数、模型输出与 ID 不作为运行证据。

- 一两句可以说清的值变化、少量字段、简短参数或计算，直接放在对应步骤下面，帮助理解当前判断。
- 需要较长输入输出、完整 JSON、较大表格、多轮计算或跨多个步骤演示的例子，可以在总流程之后另设“示例：……”小节。大表格和大段格式化内容不要塞进主流程的深层缩进，避免打断连续阅读；很小的对照仍可就地放置。
- 后置示例开头说明对应哪条流程、哪些步骤和哪次转换，按输入 → 中间变化 → 输出讲完。主流程在相关位置给出短提示与链接，示例提供返回相关步骤的链接；跨多个步骤时沿用相同的步骤称呼，读者不必反查它们在哪里执行。

是否后置取决于例子的篇幅和展示形式，不取决于这一步是否重要。主流程仍要写清实际算法和判断；不能把真正的执行规则藏进示例，导致不看例子就不知道系统怎么运行。也不要因为允许后置，把所有短例子一并移到文末。

各主题可演示这些前后变化，再按上述规则决定位置：

- 表格篇展示单元格 → headers/rows → Markdown 与键值文本 → metadata；不能只画“文件→向量”箭头。
- 改写篇展示带指代的原句、相关前文、一份假设 JSON，以及程序解析后真正保留的子问题。
- 检索篇展示少量候选的 ID、通道名次、重复关系，实际算一遍融合或请求总额度。理论预算和本次实际候选数分开。
- 回答篇展示 messages 的角色顺序及 sources/grounding 的差别；停止篇用两个执行者的交错时序。
- 任务篇展示合法与白名单外 evidenceIds；评测篇展示一题的 gold、候选、最终结果和评分分母。

## 按我的标题草稿补全一段正常流程

下面以 `10-my.md` 为表达起点，结合当前 `JdbcConversationMemoryStore.append`、`ConversationServiceImpl.createOrUpdate`、`ConversationTitleGenerator.generate` 和模板加载逻辑，示范怎样把调用前后接完整。这里只示范会话标题这一段，不要求其他主题都写它。

- 用户消息写入消息表后，会话存储层继续维护会话记录，把会话 ID、用户 ID、本次问题和当前时间传给会话服务。
  - 会话服务先检查用户 ID 是否为空，为空就抛错；不为空，再按会话 ID、用户 ID 和未删除条件查会话记录。
  - 如果已有记录，只把最后活动时间改成本次时间，更新后返回，不重新生成标题。查不到记录时，才拿本次问题生成新会话的标题。
- 生成标题的方法先读取配置中的最大长度；如果为 0 或负数，就按 30 处理。接着根据问题组装 Prompt。
  - 先准备两个键值映射：`title_max_chars` 对应转成字符串的最大长度，`question` 对应传入的问题。比如假设问题是“C1 的正常浓度是多少？”，第二个值就是这句原文。
  - 把 `prompt/conversation-title.st` 和这组映射传给模板渲染方法。
    - 模板加载器先按路径查进程内缓存；命中就直接取得模板原文，未命中才从 classpath 资源读取 UTF-8 文本并缓存。缓存的是尚未填本次问题的模板，不是上一个用户填好的 Prompt。
    - 接着逐个取映射中的键和值，把模板里的 `{title_max_chars}`、`{question}` 替换成实际内容，再把连续三个及以上的换行压成两个，并去掉整段文本首尾空白，返回填好的 Prompt。
    - 模板不存在或读取失败时会抛异常；这一步发生在后面模型调用的 try/catch 之前，所以不能说模板错误也会返回“新对话”。
  - 模板要求模型只给一个简短标题，并限制长度、保留问题主题。这里填进去的是问题和长度约束，没有再次检索知识库，也没有拿整段回答生成标题。
- Prompt 返回后，标题生成器构造聊天请求，再同步调用模型服务。
  - messages 里只有一条 user 消息，内容是刚才完整的 Prompt；这里没有另拆一条 system 消息。请求设置 temperature 为 0.7、topP 为 0.3、thinking 为 false。
  - 聊天方法传两个参数：请求对象和 `Tier.FAST`。后者让模型服务选择快速档候选，具体候选路由由模型调用流程负责；此处等待它返回标题字符串。
  - 请求构造或模型调用在这段 try/catch 中抛异常时，记录警告并返回“新对话”。正常返回时直接使用模型给出的文本，这里没有额外截断或去引号处理，因此 Prompt 的长度要求不等于程序已经强制校验标题长度。
- 标题回到会话服务后，服务把会话 ID、用户 ID、标题和最后活动时间一起构造成会话记录，插入数据库，然后返回会话存储层。标题生成器自身不负责这次插入。
- 会话存储层返回此前保存用户消息时取得的消息 ID；外层记忆服务随后检查是否需要压缩摘要，再返回该消息 ID，聊天流程继续使用它关联本轮回复。

这段保留了草稿的“参数 → 模板 → 模型调用”形式，同时补齐了触发条件、模板缓存与替换、请求内容、结果处理、落库和返回。它属于可以在调用位置讲清的普通方法，不需要再拆出一篇“标题方法详解”；长 Prompt 全文或多组输入输出对照如有必要，则按长例子规则后置。

## 独立请求、异常与原理补充怎样安排

不能把管理准备、用户请求、消息消费、定时刷新、模型回调和评测拼成一条固定流水线。同步入口在哪里返回就在哪里收束；下一条由谁触发、携带什么接着做，另起流程说明。并行子问题或通道只写真实的启动与汇合关系，不假设固定完成顺序。

同一入口中的直接分支应在原位置说完，例如参数缺失、没有证据、低置信回退、模型 JSON 解析失败、状态不允许、重复提交。事务范围、提交点、SQL 条件、影响行数和返回值处理也属于执行过程，不能统一挪到“核心机制”章节。

异常处理本身较复杂，例如跨多个执行者、多轮重试或较长的交错过程时，可以另设补充小节。原步骤先交代“断在哪里、已经完成什么、当前怎样处理、由谁接手”，再指向那段完整推演；不能只写“异常详见后文”。例如停止早于句柄绑定可以单独推演，但 bindHandle 当场检查什么仍要先讲。补充小节同样注明对应的主流程调用位置和返回去向；重点复杂方法的后置条件见前面的专节。

写异常时沿调用链追到最终结果：异常在哪里抛出，哪里捕获，捕获后是返回、转空、标失败还是重新抛出。摄取内部捕获异常后返回，不能自动推导 MQ 一定重投；future 超时也不能自动推导底层 HTTP/SQL 已取消。网络失败不直接等于远端没有执行。

复杂场景按时间说明：之前哪些修改已提交，下一次请求/任务读到什么，如何决定重试、回退、拒绝或保留失败；没有恢复入口就说明当前留下的结果。不为每条流程补一套不存在的补偿机制，不把数据库事务写成模型、对象存储、Redis 和索引一起回滚。

AI 流程还要区分“调用失败”和“结果质量不好”：模型返回了合法 JSON 但改错设备名、召回有结果但没拿到正确版本、证据 ID 合法但动作不受支持，都可能正常返回。选与本流程最相关的一两种放在对应位置，说明当前是否能识别，以及应看什么信息定位；完整评测方法归 I。

技术原理首先服务当前步骤：表头为什么跟随数据行、Embedding 与重排分别怎么比较文本、SSE 为何有单独停止请求，都要随流程说明。较长的数学推演、并发时序和替代方案比较可以后置；复杂方法和长例子按各自规则安排。无论放在哪里，补充都不能成为主流程缺步骤的补丁。

方案比较围绕一个具体问题，说明现在为何这样处理、另一种做法改变哪个步骤、增加什么成本或限制。源码只能支持机制时，用“这会……”解释影响，不虚构“当时线上发生事故，所以我们……”的设计经历。未接入能力清楚用将来或条件表述，不另起大规模改造方案。

## 成稿形式与自检

一份文件通常由“完整的各条实际流程 → 少数必要的复杂方法/异常详解、长例子与取舍 → 少量源码反查”构成，没有后置需求的部分就不设置。小标题数量随独立流程决定，不按每个方法拆标题。不要重复生成 30 秒版、2 分钟版、面试题库、术语总表、改写报告或一份技术名词摘要。

文字像我在给自己解释项目，可以自然出现“我这里先看……”，不必句句第一人称。多写明确的主语和动作，少用“通过……实现了……保障了……”；不把所有已有实现写成我个人完成的贡献。

结尾保留少量关键源码的相对链接，并写出方法/SQL/模板负责哪个判断。不要猜行号。旧笔记若有影响流程理解的错误，用几句话说明修正与依据，新正文直接采用核实后的说法；不用做整份迁移表。分工中其他目标文件尚未存在时，可以先写文件名导航，避免假装已完成。

源码存在、当前配置启用、测试覆盖、历史运行、这次实际验证是不同结论。引用历史评测必须说明数据与指标口径；块更少、纯度更高、测试通过都不能换成回答准确率提升。只做文档静态核对就如实交代，不汇总成“业务全链路通过”。

写完按以下问题检查并直接修正，不额外输出自检报告：

- 只看某一步及子条目，能否说清它收到什么、内部怎么处理、结果为什么如此、外层下一步做什么？是否仍有“调用某服务”后缺少必要内部过程的跳跃？
- 是否像 `10-my.md` 一样按动作顺序和内部缩进描述，同时补齐草稿没有写出的调用前后？有没有退回“总流程列名词，后面逐个讲方法”的形式？
- 暂时跳过后置详解和长例子，只读本篇总流程，能否说清正常业务、直接分支和前后交接？再读相关流程文件及必要详解，是否能理解整个流程与框架，而无需打开代码？
- 后置方法是否确实既重点又复杂，其输入、关键处理顺序、结果和后续动作是否已在总流程说明？每段详解能否直接找到对应调用步骤及接续位置？
- 文件、结构块、chunk、检索文本、向量、候选、最终上下文、来源、证据快照、任务对象之间，是否有不明来源或突然出现的字段？
- 每次模型调用是否解释输入/输出和程序后处理？实际发送的历史、文本和字段是否与源码一致？短例子是否就地，长例子和较大表格是否合理后置、注明对应步骤并标明假设？
- 同步返回、异步执行、并行汇合和独立请求是否清楚？异常捕获到最后是否确有重试/取消/恢复，是否把可能性说成保证？
- 主路径、可选分支、实验代码和未实现设计是否混淆？同一字段与前后流程的契约是否对得上？
- 是否保留关键原理与独有细节、删掉重复和机械条目，并只修改分配的文件？检查本次新建 Markdown 的链接、代码围栏和空白问题，未跟踪文件也要覆盖。

完成标准是“我能拿一个具体输入，顺着笔记推到输出，并解释中途每个关键决定”，不是篇幅更短或出现了更多技术名词。
