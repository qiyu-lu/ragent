# 阶段 2：工业知识闭环 Demo

## 阶段状态

- 状态：第一版工程实现已收尾，待本地页面运行时端到端验收。
- 目标：优先打通一条可展示、可写入简历的完整链路，再基于实际失败点细化。
- 主流程：中心化验室浓度检测的取样、湿重、烘干、冷却和称重流程。
- 明确不做：设备报警排查（没有可信报警资料）、真实设备控制、通用 Office 解析平台和复杂审批系统。

## 最小闭环

```text
V1.2 XLSX
  -> POI 解析全部 12 个可见工作表 + 白名单工作表的 2 张图片走现有 VLM
  -> 按表格行分块，并保存版本 / Sheet / 单元格范围 / 块类型
  -> PGVector 检索 + 严格知识库意图路由
  -> 带明确来源的回答
  -> 从本次真实检索片段生成候选任务草案
  -> 人工批准
  -> 确定性模拟执行（不连接真实设备）

V1.2 + V1.3-demo -> POI 逐单元格比较 -> 模型只解释确定性差异结果
```

这条链路复用原项目的“闲聊 / 知识库检索 / MCP 工具”分流。候选任务草案不是新的第四种全局意图：它是一次有来源检索回答后的受控动作；版本比较和批准后模拟执行属于工具调用。

## 实现边界

| 能力 | Demo 行为 |
| --- | --- |
| 文档解析 | 原生 Apache POI；全部可见工作表进入文本解析，不要求人工转 Markdown |
| 图片 | 仅“浓度检测（双场景）”白名单；当前文件实际为 2 张图；逐图调用既有 VLM |
| 图片证据 | 只描述可见设备、容器、文字和状态，不能单独证明步骤、参数或安全规则 |
| 分块来源 | 关系库与检索结果保留 `documentVersion`、`sheetName`、`cellRange`、`blockType` |
| 检索污染 | `iron-ore-demo` Profile 在无有效铁矿 KB 意图时返回空检索范围，不回退到全部知识库 |
| 候选任务 | 状态固定为 `DRAFT -> APPROVED -> SIMULATED`；每项事实必须引用本次检索的真实 chunk ID |
| 模拟执行 | 只按已批准步骤产生事件记录；不调用机器人、PLC、仪器或其他真实设备 |
| 版本差异 | 同一 `documentKey` 下两个明确版本逐单元格比较；LLM 不负责发现差异 |
| 报警排查 | 延后；取得最小设备手册、型号和报警码后再增加，不制造演示“事实” |

## 首次部署

以下操作针对阶段 0 的本地开发环境。不要通过 `down -v` 重建数据库。

### 1. 升级已有数据库

先确认目标是 `ragent-iron-ore-dev` 的本地 PostgreSQL，再执行：

```bash
docker compose -f resources/docker/dev/ragent-dev.compose.yaml exec -T postgres \
  psql -U postgres -d ragent -v ON_ERROR_STOP=1 \
  < resources/database/upgrades/v1.1.0/260812_iron_ore_demo.sql
```

空数据库首次初始化会直接使用已更新的 `resources/database/schema_pg.sql`，不再额外执行升级脚本。

当前这台本地环境已于 2026-08-12 应用并复核该迁移：4 份现有文档（含逻辑删除记录）完成 `document_key` 回填，新列和两张任务表均存在；没有删除原数据。

### 2. 使用 Demo Profile 启动后端

在现有 IDEA Run Configuration 的 active profiles 中加入：

```text
iron-ore-demo
```

等价环境变量是 `SPRING_PROFILES_ACTIVE=iron-ore-demo`。该 Profile 会开启精确来源和行内引用，只处理指定工作表的内嵌图片，并启用空作用域回退。模型、Embedding 和 VLM 密钥继续沿用本机配置，不写入仓库。

### 3. 创建知识库并摄取 V1.2

1. 在管理界面创建名称完全等于 `铁矿检测演示库` 的知识库。
2. 上传 `local-data/source/铁矿石人工检测流程调研V1.2.xlsx`。
3. 选择快速解析，使用 `maxChars=1024`、`overlapChars=128`、`rowsPerChunk=1`、`toleranceFactor=3`。
4. 启动分块，等待状态变为 `success`。
5. 抽查分块元数据：应包含 12 个工作表的文本；只有“浓度检测（双场景）”产生 2 个图片块。

`rowsPerChunk=1` 是本 Demo 为精确单元格来源采取的简单设置，不是通用表格最佳参数。

### 4. 上传受控演示版本

演示版本已由下列脚本生成；需要重建时执行：

```bash
python3 scripts/iron-ore-rag/create_v1_3_demo.py --force
```

上传 `local-data/source/铁矿石人工检测流程调研V1.3-demo.xlsx`，但不要启动分块。版本工具只需从对象存储读取它。文件名会自动得到与 V1.2 相同的 `documentKey`，版本为 `V1.3-demo`，并标记为演示数据。

脚本只修改“浓度检测（双场景）”的三格：

| 单元格 | 演示变化 |
| --- | --- |
| `F17` | 增加采样桶编号、样品编号、采样时间和操作人记录要求 |
| `F19` | 将演示温度判据从 `105±5℃` 改为 `105±3℃` |
| `F20` | 增加坩埚钳、冷却与异常停止上报文字 |

三处都带 `V1.3-demo 演示变更` 标识；它们不是经业务批准的新规程。

### 5. 导入 Demo 意图并清缓存

知识库创建后执行：

```bash
docker compose -f resources/docker/dev/ragent-dev.compose.yaml exec -T postgres \
  psql -U postgres -d ragent -v ON_ERROR_STOP=1 \
  < resources/database/examples/iron_ore_demo_intents.sql

docker compose -f resources/docker/dev/ragent-dev.compose.yaml exec -T redis \
  sh -lc 'REDISCLI_AUTH="$RAGENT_REDIS_PASSWORD" redis-cli DEL ragent:intent:tree'
```

脚本是幂等的，并拒绝在找不到唯一“铁矿检测演示库”时继续。它增加闲聊、铁矿规程检索、版本比较和任务模拟四个叶子意图，不自动删除现有教程意图。

## 固定演示流程

每轮用新会话，按以下顺序录屏或验收：

1. 问：`中心化验室采用烘干称重法检测浓度时，前置条件、操作步骤、参数、质量判据、异常处理和安全约束分别是什么？只依据 V1.2。`
2. 检查回答只引用铁矿工作簿，并在来源面板显示 `V1.2`、工作表和单元格范围；材料没有提供的类别必须明确说未提供。
3. 点击“生成候选任务”，检查卡片标记为“待人工批准”，每项内容具有证据位置。
4. 点击“人工批准”，状态变为 `APPROVED`；再点击“模拟执行”，显示逐步事件及“未连接真实设备”。
5. 新开会话问：`比较铁矿石人工检测流程调研 V1.2 与 V1.3-demo，列出精确变化，并解释这些变化可能影响哪些记录、质量控制和操作环节。`
6. 检查工具结果恰好为 `F17`、`F19`、`F20` 三处；“可能影响”属于基于差异的辅助解释，不能写成已批准结论。
7. 再问：`文档规定的浓度检测允许误差具体是多少？` 应明确资料没有具体数值，不能补造。

## 验收线

- V1.2 摄取成功，12 个可见工作表均有文本分块。
- 白名单工作表恰好处理 2 张图片；其他 109 个图片摆放不调用 VLM。
- 固定规程问题的来源只来自“铁矿检测演示库”，并显示版本、Sheet 和单元格。
- 候选任务不能绕过人工批准直接模拟；模拟执行不触发外部设备。
- 版本比较只返回受控三格变化。
- 无答案问题不编造。

如果上述任一项失败，先记录失败发生在解析、元数据、意图、检索、任务生成还是工具调用；不要为录屏反复改问题掩盖链路缺口。
